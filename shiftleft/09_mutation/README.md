# 09 · 变异测试体检：覆盖率之外的测试有效性

> 覆盖率 100% 的测试也可能是假测试——`assert is not None` 什么都保证不了。
> 本实验给满减定价模块制造 7 个变异体做体检：弱测试全绿却只杀死 2 个
> （score 28.6%，5 个存活 = 5 条断言缺口）；补上精确断言后 score 升到
> 85.7%（+57.1 个百分点）；唯一幸存者是等价变异——变异测试的理论边界。

## Background

之前的做法：覆盖率是测试的唯一体检指标，「行数跑过」被当成「行为查过」，
覆盖率报表好看就敢说测试齐全。

痛点的核心是**覆盖率测「跑过」，不测「查过」**：`assert payable(...) is not None`
这类稀薄断言让测试全绿，但把代码里的减号改成加号它们照样全绿——测试对
行为改变完全无感，覆盖了等于没查。

变异测试（mutation testing）反其道而行：自动往代码里注入微小行为改变
（变异体），跑测试看能不能杀死——杀不死的变异体就是一条显式的断言缺口。

## What

变异测试通过向被测代码注入微小行为改变并运行测试套件，用杀死率
（mutation score = 杀死数 ÷ 变异体总数）度量测试的**有效性**而非存在性。

可以把变异体想成疫苗试验里的减毒病原：注入之后，免疫系统（测试套件）
必须识别并清除它；清除不掉就说明免疫有洞。但和疫苗试验不同的是，有个别
「病原」与本体行为完全相同（等价变异），任何免疫系统都识别不了——这是
score 的理论上限，不是免疫的错。

工具探活实测：mutmut 3.8.0 在 Python 3.13 直接可用（3.x 的配置键叫
`source_paths`，旧版教程里的 `paths_to_mutate` 已弃用）。

本实验引擎用自研 AST（抽象语法树——Python 把源码解析成的树结构，可用标准
库 `ast` 读写）变异器（纯标准库）——双套件两轮、JSON 可复算完全可控，
mutmut 作对照（`probe_mutmut/`）。

## When to Use

- 核心域测试套件的断言强度体检：定价、账务这类「错一分钱就出事」的代码。
- 评审测试 PR：变异 score 比覆盖率诚实，存活清单就是改进清单。
- 何时不用：全仓库跑（变异体数量 × 套件时长，成本爆炸）；胶水与配置代码。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 行覆盖率 | 测「跑过」，稀薄断言照样 100% | 最低门槛的存在的证明 |
| mutation score（本实验） | 测「查过」，存活即缺口 | 核心域测试体检 |
| mutmut 等现成工具 | 生态成熟，报告形态固定 | 常态化接入 CI（持续集成：合入代码自动跑测试的流水线） |

## Quick Start

前置：仓库根 `.venv`（pytest），自研引擎纯标准库；对照步骤还需 venv 里装了
mutmut（没有就 `pip install mutmut`，否则脚本会在第③步报 No module named
mutmut 并中断）。一条命令跑完整动线：

```bash
./mutation.sh   # apply → observe（两轮体检+mutmut 对照）→ clean
```

注意 `clean` 会删掉 `reports/` 的两份 JSON 留档；想先看留档就分步跑
`./mutation.sh apply` → `./mutation.sh observe`，看完再 `./mutation.sh clean`。

第一轮，弱测试（五个测试全绿、四条分支都踩到，但断言稀薄）：

```text
  🫥 存活  # 0  数值字符串 "20.00" → "20.001"（L8）
  ✅ 杀死  # 1  数值字符串 "100.00" → "100.001"（L9）
  🫥 存活  # 2  数值字符串 "0.01" → "0.011"（L10）
  ✅ 杀死  # 3  比较符 Lt → LtE（L14）
  🫥 存活  # 4  异常类型 ValueError → TypeError（L15）
  🫥 存活  # 5  布尔 True → False（L22）
  🫥 存活  # 6  算术符 Sub → Add（L26）

===== 变异报告（第 1 轮 · 弱测试）=====
变异体 7 个：杀死 2 / 存活 5  →  mutation score 28.6%
```

第二轮，强测试（每个变异点都有精确断言盯着）：

```text
变异体 7 个：杀死 6 / 存活 1  →  mutation score 85.7%
（基线全绿 + 上述逐一体实测；被测模块已还原）
两轮对比：28.6% → 85.7%（提升 57.1 个百分点，✓ ≥20pp 达标）
```

诚实预期：幸存者 `#0 "20.00"→"20.001"` 两轮都活——券额多 1 厘在按分四舍五入
（`_to_cents` 调 `Decimal.quantize`，舍入到两位小数）时被吸收，对分精度的金额
行为完全不变。这是**等价变异**：score 的理论边界，最终认定需人工确认。

## How It Works

**两遍式 AST 是引擎骨架**：第一遍按确定性遍历顺序给变异点编号，第二遍
深拷贝语法树、把第 i 号节点换成孪生操作符后 `ast.unparse` 回源码。

编号与生成必须**同一遍历顺序**——`ast.walk`（广度优先）与 NodeTransformer
（深度优先）顺序不同，混用会让报告张冠李戴（本实验真踩过，见 Pitfalls）。

**判定引擎逐体实测**：写变异体 → 跑指定套件 → 非零退出即「杀死」→ 还原。
基线先跑一遍（红则拒绝变异——红套件测出的 score 无意义）。核心四类变异：

| 类型 | 例子 | 模拟的缺陷 |
|:--|:--|:--|
| 比较符翻转 | `<` → `<=` | 门槛边界 |
| 算术符翻转 | `-` → `+` | 金额计算 |
| 数值字面量 | `"20.00"` → `"20.001"` | 券额/精度 |
| 布尔/异常互换 | `True→False`、`ValueError→TypeError` | 默认行为与容错 |

**字节码缓存会让结果撒谎**：连续写入的变异体若「同秒 + 同大小」，pytest
复用旧 `__pycache__`，测的其实是上一个变异体。

本实验实测出现过两种不同结果（同一变异体一次杀一次活），解法：每轮清缓存
加 `PYTHONDONTWRITEBYTECODE=1`。

## Pitfalls & Q&A

常见故障与解法：

- **存活数每次运行不一样**：`__pycache__` 串味（同秒同大小时复用旧字节码）。
  每次跑测试前清缓存并禁写字节码，结果才确定。
- **变异报告张冠李戴**：描述遍历与生成遍历顺序不一致（见上）。两遍共用
  同一个 visitor 类，编号天然同源。
- **`raise ValueError(...)` 的 exc 是 Call 节点**：要换异常类型得改
  `node.exc.func.id`，`node.exc` 本身不是 Name。

Q&A：

- **mutmut 不是现成的吗，为什么自研？** mutmut 3.8.0 实测可用（探活样例在
  `probe_mutmut/`）；自研是为「双套件 × 两轮 + JSON 可复算」完全可控，且
  变异器本身就是最好的变异测试教材。
- **等价变异怎么办？** 识别它需要人工确认（本实验 #0 被 quantize 吸收），
  报告里显式标注；score 的真实上限是 (总数−等价数) ÷ 总数。
- **score 多少算及格？** 核心域 80%+ 常被引用；比及格线更重要的是逐个看
  存活变异——每一个都是一条写得出来的断言缺口。

# 08 · TDD 红绿重构：让提交历史为纪律作证

> 「先写测试」人人会背，难的是让节奏可查证——多数仓库的实现和测试混在
> 一个提交里，历史无法分辨谁先谁后。本实验在独立 git 仓库回放 5 轮
> 「红→绿」加 1 次重构的完整 TDD 操练：每个实现提交之前都有失败测试提交，
> 重构提交后测试保持绿，五条断言全部由脚本机械核验。

## Background

之前的做法：「先写测试」靠自觉，code review 看不出先后；实现和测试一起
提交，历史读起来永远「同步完成」。

痛点的核心是**没有节奏证据，TDD 会退化成事后补测试**——补的测试写出来
永远是绿的，它验证了实现，却没有驱动过任何设计决策。

本实验把纪律做进提交历史：测试提交标 🔴（此刻必须红）、实现提交标 🟢
（此刻必须绿）、整理提交标 🔵（必须保持绿），每次提交都实测红绿并写进
runs.log——账本齐全，脚本可审计。

## What

TDD 操练是以固定节拍驱动的开发循环：先写失败测试（红）、用最小实现让它
通过（绿）、在测试保护下重构；本实验把每个节拍落成一次提交。

可以把 runs.log 想成健身房的训练日志：每组几次、重量多少，写了才算练过。
但和训练日志不同的是，它只能证明「节奏发生了」，不能证明测试写得好——
断言质量仍然靠人审。

最小实现原则：GREEN 阶段只写让当前红测试变绿的代码（哪怕丑），美化留给
重构轮——提前预留「以后会用」的参数是节奏杀手（见 Pitfalls）。

## When to Use

- 规则类新功能：定价、折扣、校验这类逻辑密集的需求（本实验的满减五轮）。
- 修 bug：先写复现测试（红）再修（绿），这条测试留在套件里，复发当场被测出。
- 何时不用：探索性原型（设计未定，测试跟着翻）；纯样式或文案调整。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 实现+测试同提交 | 历史无法分辨先后 | 赶工的常规提交 |
| 本实验（节奏进历史） | 红绿可审计、可回放 | 规则类功能与修 bug |
| 事后补测试 | 永远绿，无驱动价值 | 遗留代码救火后的补课 |

## Quick Start

前置：git 与仓库根 `.venv`（pytest；若还没有：在仓库根 `python3 -m venv .venv`
后 `.venv/bin/pip install pytest`）。操练仓库建在 `./repo`（每次重跑自动重建），
labs/11（本系列 11 号订单实验）零接触。一条命令跑完整动线：

```bash
./tdd_kata.sh   # apply → observe（回放+核验）→ clean
```

注意 `clean` 会删掉 `./repo` 与 `reports/`——而提交历史正是本实验值得亲眼看的东西。
想自己翻历史就分步跑：`./tdd_kata.sh apply && ./tdd_kata.sh observe`（不清场），
看完再 `./tdd_kata.sh clean`。

第一段，操练回放——每轮先红后绿，全部实测：

```text
[C1] RED：先写测试并提交（此刻它必须是红的）
    测试运行：FAIL
[C1] GREEN：最小实现让它变绿
    测试运行：PASS
……（C2 门槛拒绝 / C3 券额可配置 / C4 精确到分 / C5 拒绝信息带门槛，同构）
[REFACTOR] 只动实现不动测试（提取常量与守卫），绿必须保持
    测试运行：PASS
终局全量测试：✅ 全绿
```

第二段，五条断言机械核验：

```text
✅ 断言1 红 5 轮 / 绿 5 轮（≥5）
✅ 断言2 先红后绿：每个实现提交之前都有对应的失败测试提交
✅ 断言3 节奏留档：11 条运行记录与提交一一对应（RED 全 FAIL、GREEN/REFACTOR 全 PASS）
✅ 断言4 重构保绿：REFACTOR 在全部 5 个 GREEN 之后，提交后测试运行 PASS
✅ 断言5 终局全绿：当场重跑全量测试通过
```

提交序列（时间线节选）：

```text
🔴 RED C4: 金额精确到分：19.99 + 80.10 用 20 元券，应付必须是 80.09（字符串级精确）。
🟢 GREEN C4: 实现满减规则
🔵 REFACTOR 提取常量与门槛守卫，行为不变
```

诚实预期：C4 的红来自 float 精度（`80.08999999999999`）——GREEN 轮换
Decimal 才转绿，这条正是项目 1 那个金额缺陷在 TDD 视角下的重生。

## How It Works

**驱动器只做三步节拍**：写测试 → 提交 → 跑测试期待非零（红）；写最小实现
→ 提交 → 跑测试期待零（绿）；每步的退出码写进 runs.log，节奏想作假都难：

```python
def commit(phase: str, subject: str) -> None:
    git(["add", "-A"])
    git(["-c", "user.name=tdd-kata", ..., "commit", "-m", f"{phase} {subject}"])
    code = run_pytest()
    verdict = "PASS" if code == 0 else "FAIL"
    LOG.append(f"{phase}|{subject}|{verdict}")
```

**五轮演进各有指向**：C1 基础满减（最小实现丑到用字面量 20.0）、C2 门槛
拒绝、C3 券额可配置（最考验「最小」的一轮：若 C1 提前预留了参数，这轮 RED
会直接变绿——本实验没预留，如实失败）、C4 精确到分（float 换 Decimal）、
C5 拒绝信息带门槛值。

最后的重构轮把字面量提为命名常量，并把「未满门槛就拒绝」的检查提取成独立
函数（守卫：guard，写在函数入口、条件不满足立即抛错的检查）——测试一行
不动，绿保持。

**核验是时间线配对**：`git log --reverse` 按时间正序遍历提交，🔴 计数、
🟢 消费计数，任何时刻消费超过存量即配对错乱；runs.log 与提交逐条对应，
RED 必 FAIL、GREEN/REFACTOR 必 PASS；最后当场重跑全量测试。

## Pitfalls & Q&A

常见故障与解法：

- **最小实现提前预留参数**：C1 若顺手写上 `coupon_value=20.0`，C3 的 RED
  直接变绿，节奏假死。「最小」的定义就是只让当前红变绿，多一行都算抢跑。
- **RED 提交信息带三引号残渣**：从测试片段提取 docstring 做提交标题时，
  正则取内容（`"""(.+?)"""`）而不是按行 strip——strip 去不掉行首缩进与引号。
- **嵌套三引号写脚本改源码**：用行级替换定位 `commit("🔴 RED"` 前缀，避开
  字符串字面量里的三引号冲突。

Q&A：

- **RED 阶段测试直接绿了，正常吗？** 偶尔正常（接口恰好已预留），但要警觉：
  常态化说明实现跑在了测试前面，TDD 已名存实亡。对应的警示写在 Pitfalls
  第一条。
- **重构轮动了实现，凭什么行为不变？** 凭重构之前 5 轮积累的测试保护——
  绿即不变。这正是「测试先行」的复利：重构的胆量是前面红绿买来的。
- **runs.log 自己伪造怎么办？** 核验脚本交叉比对 log 与提交（数量必须都是
  11、判定与阶段必须匹配）并当场重跑测试；单改 log 过不了数量关。

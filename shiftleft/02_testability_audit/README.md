# 02 · 需求可测性审计器：给每条用户故事打一个「能不能测」的分

> 需求评审会上「这条验收条件能不能测」的争论靠直觉，打回票也说不清差在哪。
> 本实验把可测性拆成五类可检测规则加两个结构性封顶，对用户故事量化打分并逐条给
> 改写建议：内置 10 条样例（5 好 5 坏），好故事全部 ≥80 分、坏故事全部 ≤60 分且
> 每条至少 1 条可执行修改建议，39 条单测全绿。

## Background

之前的做法是评审会上人吵：测试说「快速响应没法测」，产品说「你给个标准」，
结论依赖在场最资深那个人的耳朵，打回的需求没有量化口径。

痛点的核心是**坏需求的代价后置**：含糊验收条件流到开发，测试只能事后扯皮。
项目 1 的成本漏斗（同一缺陷发现越晚修复越贵）里，需求关拦截只要 5 分钟、
流到生产要 480 分钟——这道最便宜的关此前只能靠人肉把守。本实验把「能不能测」
拆成可检测规则：五类词表匹配加两个结构性封顶，规则即配置，输出分数与建议。

## What

需求可测性审计是在需求进入开发前，用确定性规则引擎对每个用户故事（一段独立的
用户需求，如「未满门槛用券被拒绝」）做「能不能写成自动化测试」的量化检查：
输出分数（0-100）、档位与逐条改写建议。

故事下面拆的具体检查点叫验收条件（acceptance criteria，AC，即输出表的 AC 列），
如「调用 POST /api/orders/coupon 返回 422」就是一条。

可以把审计想成机场行李托运前的尺寸称重：超规的箱子当场贴条，告诉你超在哪、
怎么打包，而不是到了登机口（开发后期）被拒载。但和称重不同的是，它评的是
「能否被测试」，不评「需求值不值得做」——业务优先级是另一码事。

| 检测规则 | 判据 | 扣分 |
|:--|:--|--:|
| 歧义词 | 「快速/友好/稳定/优化」等无法写成断言的词，每处 | 15 |
| 无可观察预期 | 验收条件不含任何数字（预期值缺失），每条 | 10 |
| 无可自动化线索 | 不提接口/字段/输入输出，测试无从驱动，每条 | 10 |
| 依赖词 | 成立与否取决于别的故事（之后/完成后），每处 | 10 |
| 连接词 | 一条验收条件塞多个行为（同时/并且），每处 | 5 |
| 结构封顶 | 0 条验收条件 → 扣 60 后封顶 40；超 7 条 → 扣 20 后封顶 55 | 60/20 |

## When to Use

典型场景：

- 迭代评审会前扫 backlog（待办需求池），不可测的带建议打回；或把词表纳入需求写作规范。
- 与项目 1 的漏斗串联：本工具就是「需求评审关」的自动化实现，堵最便宜的口。

何时不用：需求已模板化且指标全量化的团队收益有限；词表必须先与团队对齐，直接套用别人的会成批误伤。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 评审会人评 | 依赖资深个人，口径漂移 | 团队很小且需求稀疏 |
| 本工具（确定性规则） | 规则透明可配置，零 API 成本 | 例行迭代门禁（进迭代前自动跑的拦截检查） |

## Quick Start

前置：仓库根 `.venv`（含 pyyaml / pytest），无外部服务。一条命令跑完整动线，核心一步是全量审计：

```bash
./testability_audit.sh   # apply（依赖自检）→ observe（审计+单测+门禁）→ clean
```

```text
ID      标题                       AC   分数  档位
US-G1   未满门槛用券被拒绝        1  100  良好
US-G2   券抵扣金额精确            1  100  良好
US-G3   下单扣减库存              1  100  良好
US-G4   幂等防重放                1  100  良好
US-G5   订单分页查询              1  100  良好
US-B1   体验优化                  3    5  不可测
US-B2   查询提速                  1   50  不可测
US-B3   优惠券全家桶（故事过大）   9    0  不可测
US-B4   金额库存联动验证          1   50  不可测
US-B5   消息通知（有想法没验收）   0   40  不可测

……（此处接 5 条不可测故事的逐条违规明细，均带改写建议，略）

汇总：良好 5 / 需修订 0 / 不可测 5（共 10 条）
评分口径：score = 100 − Σ扣分；无 AC 封顶 40，AC>7 封顶 55；档位线 80/60
```

单条深看一条坏故事（违规明细 + 每条带改写建议）：

```bash
../../.venv/bin/python audit.py --story US-B4 --no-save
```

```text
US-B4   金额库存联动验证          1   50  不可测

⛔ US-B4 金额库存联动验证（50 分，不可测）
  ⛔ [AC1] 歧义词「正确」（−15）
     ↳ 改写建议：把「正确」换成可断言的量化指标，例如：p95 ≤ 500ms、错误率 < 0.1%
  ⛔ [AC1] 无可观察预期值（不含任何数字）（−10）
     ↳ 改写建议：补一个可观察的预期值：具体数字、状态码或终态（如返回 200、列表为空）
……（其余 3 条：无可自动化线索、依赖词「完成后」、连接词「同时」，同样附建议）
```

规则引擎自身的单测与门禁模式：

```bash
../../.venv/bin/python -m pytest tests/ -q      # 39 passed——每条规则坏查得出、好零误报
../../.venv/bin/python audit.py --gate          # 存在不可测故事 → 退出码 1
```

诚实预期：改 configs/rules.yaml 任何权重或词表重跑，分数与档位立即变化——口径对齐就是改这个文件。

## How It Works

**评分模型一行可复算**：`score = 100 − Σ扣分（下限 0）`，两个结构性封顶叠加——
验收条件为 0 条封顶 40（无可断言即不可测），超过 7 条封顶 55（先拆分再谈测试）。
分档线 80/60 也是配置。US-B3 原始扣分 160 触底 0 分：封顶是托底，不是上限。

**检测器是逐条验收条件跑一遍词表匹配**——核心十几行，刻意保持可读：

```python
for w in self.r["vague_words"]:
    if w in text:                       # 「快速」出现在 AC 里 → 无法写成断言
        findings.append(self._finding("vague_word", i, f"歧义词「{w}」", word=w))
if not any(ch.isdigit() for ch in text):
    findings.append(self._finding("no_observable", i, "无可观察预期值（不含任何数字）"))
```

**改写建议与分数同等重要**：每类违规在 SUGGESTIONS 里绑定一条具体改法
（「快速」→「p95 ≤ 500ms」）——只报不合格不给改法的审计，在会上推不动修改。

**39 条单测锁定检测器本身**：每条规则坏样本命中、好样本零误报——检测器自己先被测试。

## Pitfalls & Q&A

常见故障与解法：

- **故事 ID 引用骗过数字启发式**：US-B4 初版写「在 US-B2 完成后…」，"B2" 里的
  数字被当成预期值漏检，已改写；启发式保持简单，误判样例靠单测锁住。
- **词表误伤**：「正确」进词表后「库存正确更新」也扣分——特性非缺陷：正确无法断言；词表变更走 rules.yaml 评审。
- **单条深看（--story）本来就不落盘**：不会冲掉全量报告，命令里的 `--no-save` 只是显式声明。

Q&A：

- **80/60 的档位线有依据吗？** 约定值不是定理：调 rules.yaml 重跑即生效，团队
  按「多少分的需求愿意进迭代」定线，工具不替你拍板。
- **和 LLM（大语言模型）评审需求是什么关系？** 互补：LLM 生成或改写需求后，用本
  工具做零成本兜底审计（生成侧见 architect 线实验 25「LLM 用例生成与质量评测」）。

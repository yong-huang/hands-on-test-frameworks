# 18 · 性能预算左移：预算即测试，超支即红

> 性能问题通常在压测阶段（右移最远端）才暴露。本实验把性能预算写成可执行
> 断言——对 labs/11（labs 主线的 FastAPI 订单应用）三个接口做 10 并发取样，p95 与错误率逐一对预算比对：
> 正常 SUT 全绿 <60s，追加 1.5s 延迟端点后 p95 1533ms 超预算 200ms 即红
> （实测值 vs 预算值），报告逐接口列取样数与 p95——预算集中在 YAML，
> 改预算重跑红绿立即变化。

## Background

之前的做法：性能靠「上线后压一轮」——发现了再优化，优化完再压，来回
几轮，发版日期一推再推。

痛点的核心是**性能回归发现太晚**：一个本来 30ms 的接口被某次重构拖到
200ms，覆盖率报表看不出来、功能测试也绿——只有用户开始投诉才被注意到。

本实验把性能预算（performance budget：给接口延迟和错误率设上限）写成
可执行断言——超预算即红，让性能回归在 CI（持续集成，每次提交自动跑测试的机制）就被拦下（左移到编码阶段，
而非压测阶段）。

## What

性能预算是给每个接口的 p95（把该接口所有取样延迟排序取第 95 百分位的值，
即 95% 的请求比它快）延迟和错误率设的数值上限；「预算即测试」是
把这些上限写成可执行断言：并发取样 → 统计 p95/错误率 → 对预算断言，
超支即红。预算集中在 YAML，改预算重跑红绿立即变化。

可以把预算想成高速公路的限速牌：每条车道（接口）有自己的限速（p95
上限），超速即拍（测试变红）。但和限速不同的是，这里的「拍」是即时的——
不用等下个月账单，每次 CI 都即时告知哪条路超速。

与 performance.md 的分工：那边做 k6（开源压测工具）全链路压测工程（容量建模、瓶颈分析、
回归门禁）；本实验只做「预算即断言进 CI」的左移视角——小样本冒烟，
不替代压测。

| 接口 | p95 预算 | 错误率预算 | 实测 p95 | 结果 |
|:--|--:|--:|--:|:--:|
| /api/health | 200ms | 0% | ~30ms | ✅ |
| /api/orders | 200ms | 0% | ~39ms | ✅ |
| /api/slow-config（延迟注入） | 200ms | 0% | ~1533ms | ❌ |

## When to Use

- CI 快层末尾加一段预算检查：防重构拖慢关键接口（p95 回归秒级暴露）。
- 性能 SLA（Service Level Agreement，对用户承诺的性能指标）的日常守护：SLA 数字写进 budget.yaml，机器盯而不是人盯。
- 何时不用：需要全链路压测或容量建模的场景（那是 performance.md 的
  领域）；小样本冒烟不能替代压力测试。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| k6 全链路压测 | 高并发、多场景、有报告平台 | 上线前容量评估（performance.md） |
| 本实验（预算即测试） | 轻量 CI 冒烟，秒级反馈 | 例行 CI 中防性能回归 |
| APM（Application Performance Monitoring，应用性能监控）线上监控 | 真实流量，事后告警 | 生产环境（右移，不在本线） |

## Quick Start

前置：仓库根 `.venv`（httpx + pyyaml）。labs/11（labs 主线的 FastAPI 订单应用，即被测系统 SUT）由 perf_budget.py
自动启动
和清理（端口 8940，不影响 labs/11 默认 8899）。一条命令跑完整动线：

```bash
./perf_budget.sh   # apply → observe（全绿/红路径/pytest）→ clean
```

正常路径全绿 + 延迟注入变红（示例输出，p95 数值每次运行浮动）：

```text
接口                        取样   p95(ms)      预算     错误率      预算  结果
/api/health               20      30.3     200   0.0%     0%  ✅
/api/orders               20      38.6     200   0.0%     0%  ✅
/api/admin/stats          20      41.2     200   0.0%   100%  ✅
✅ 全部达标
```

延迟注入（追加 /api/slow-config，内建 1.5s 延迟）：

```text
/api/slow-config [延迟注入]   20    1532.6     200   0.0%     0%  ❌
  ⛔ p95 1532ms 超预算 200ms（实测值 vs 预算值）
>>> 已按预期退出 1（非零即红）：预算 200ms vs 实测 ~1500ms——这就是「预算即测试」
```

pytest 包装（CI 可直接用退出码当门禁）：

```text
1 passed in 0.77s
```

诚实预期：本地 SQLite + 单进程 uvicorn 的 p95 与生产环境不可比——
本实验验证的是「预算机制本身能拦住回归」，不是「这些数字代表生产性能」。

## How It Works

**并发取样的三种结果**：每条线程向目标接口发一个请求，记录延迟和状态码。
取样完毕后统计 p95（排序后取第 95 百分位：20 个取样即第 19 小的值）和错误率（5xx 占比），
逐接口对预算断言。

**预算集中在 YAML**：`configs/budget.yaml` 定义每接口的 p95 上限与错误率
上限，加 `concurrent` 和 `requests_per_endpoint` 两个全局参数——改预算
重跑，红绿立即变化。这是「预算即测试」的操作语义：预算变更走 diff 评审，
不是口头约定。

**延迟注入利用 SUT 的既有行为**：labs/11 的 `/api/slow-config` 内建
1.5s sleep——把它的 p95 预算设为 200ms 必红。这不修改 SUT，是「用真实
行为演示红路径」的最诚实做法。

## Pitfalls & Q&A

常见故障与解法：

- **SUT 未启动就连不上**：perf_budget.py 自含 SUT 生命周期（种子 + 启动
  + 清理），独立可跑——不需要先手动启动 labs/11。
- **预算太紧导致全红**：SQLite 单进程的 p95 受机器负载影响，多次实测在 30~75ms 间波动，预算
  200ms 余量充足。如果改成 20ms 会偶发红——预算应留合理余量，不是越紧越好。
- **并发取样数太少导致 p95 抖动**：20 个取样中 1 个异常就占 5%，
  p95 恰好取到它。如果抖动严重，增大 requests_per_endpoint。

Q&A：

- **和 k6 压测什么关系？** k6 做全链路高并发压测（容量建模、瓶颈定位），
  本实验做 CI 内秒级预算冒烟——两个粒度互补，不互替。
- **为什么 p95 不用 p99？** 按本实现的取整方式，20 个取样时 p95 和 p99
  都取到最大值——样本太少，任何分位数都不可靠；想区分更极端的尾延迟，
  先增大取样数再升级 p99。
- **admin/stats 的错误率预算为什么是 100%？** 该端点无令牌返回 403，
  本实验只要求不超时（5xx 才算错误），403 属于预期行为——预算语义是
  「不超时」而非「必须 200」。

# 17 · 多环境配置矩阵与漂移检测：先声明合法差异，剩下的才叫漂移

> 「staging（预发布环境，代码已进但还没对真实用户的最后一级环境）测出来没问题，
> 上了生产炸了」——一半的锅是配置漂移：有人手改了 staging 的重试次数、忘了同步。本实验把配置一致性做成机器判定：
> schema 校验（缺字段点名）+ 逐字段漂移分类（预期差异 vs 疑似漂移）。
> 实测：基线 7 处差异全部合法；变异（staging 删必填字段 + prod-like 改
> invariant）被点名拦截。

## Background

环境不一致导致漏测是高频事故，而**发现不一致**本身就是测试能力的一部分——
测出来的结论能不能迁移到生产，取决于两个环境到底差在哪。

差异治理的两难：差异不是越多越好也不是越少越好。dev 用 sqlite、
生产用 Postgres，这是天生的合法差异；重试次数 staging 3 次、生产 9 次，
这会让"同一个变更在两个环境表现不同"——测试结论不可迁移。
关键是**每处差异都被声明过、被解释过**。

「staging 悄悄被人改了」需要的不是开会强调纪律，而是配置的版本控制 +
漂移告警——让每处未声明的差异自动现形。

## What

多环境配置漂移检测是一套配置一致性判定系统，核心是 **schema 两张清单**：

- **expected_diff**（预期差异白名单）：db 地址、日志级别——天生该不同的字段。
- **invariant**（不变量）：超时、重试、退避（backoff，失败后按递增间隔重试的策略）——三环境必须一字不差的字段。

逐字段扁平化对比（嵌套 yaml 展平成 `database.url` 这样的点路径）后，
凡是不在白名单里的差异就是疑似漂移。

可以把两张清单想成租约的条款：租金按市场浮动（expected_diff——每层楼
本来就不同），但消防通道宽度写死一条（invariant——哪层都不能打折）。
但和租约不同的是，这里的对比是机器做的：三个环境的全部字段摊在一张
矩阵里，每个差异格子标注「合法」或「疑似漂移」。

校验错误与漂移是两类失败：校验错误（缺字段/类型错/越界）= 配置坏了，
立即拦；漂移 = 配置存疑，标注 + 审查——分级响应才推得动。

## When to Use

典型场景：

- 发布前配置审计：三环境矩阵全绿才放行，invariant 漂移当场点名。
- 「staging 测过的为什么生产炸」的复盘：矩阵报告直接回答差在哪。
- 定期巡检：漂移默认警告、`--strict` 加严为拦截——按团队成熟度选档。

何时不用：只有单一环境（本地开发）时无差异可对比；
配置已全部由 IaC（基础设施即代码）单一来源生成且无手工变更通道时，
漂移的源头已消失，检测退化为冗余保险。

实测输出（节选）：

```
① 基线：共 7 处差异：预期差异 7 处（schema 声明合法），疑似漂移 0 处
② 变异后：
   ❌ Schema 校验失败
   - [staging] 缺少必填字段 database.url
   | retry.max_attempts | 3 | 9 | 3 | ⚠️ 疑似漂移 |
   >>> 变异后退出码 1（1 = 校验拦截）
```

## Quick Start

前置条件：纯离线；变异只写 reports/ 副本，原始配置全程未动。

```bash
cd architect/17_config_drift
./config_drift.sh apply     # 基线：三环境 dev/staging/prod-like 对 schema 全合规
./config_drift.sh observe   # 基线矩阵 → 变异（删必填+改 invariant）→ 拦截与标注
./config_drift.sh clean     # 变异只写 reports/ 副本，原始配置全程未动
```

诚实预期：基线应 0 疑似漂移（7 处差异全部在 expected_diff 白名单内）；
变异后应同时出现两类拦截——schema 校验失败（缺必填字段，点名）与
invariant 漂移标注（`retry.max_attempts` 9 vs 3），退出码 1。

关键设计（这段在做什么：审计工具的自保与规则分级）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 变异写 reports/ 副本 | 原始配置是「被审计对象」，工具不能污染它 | 图省事直接改原配置，clean 就成了说谎 |
| invariant 独立于 required | 字段可以「都存在且合法」但「值不一致」 | 只查存在性查不出漂移 |
| min/max 含义随类型 | 字符串没有 min | 校验规则类型化，别用一把锤子敲所有字段 |
| 漂移白名单进 schema 评审 | 谁能改白名单=谁能定义「合法」 | 白名单散落在脚本里等于没有白名单 |

## How It Works

**schema 两张清单是配置治理的宪法**。

expected_diff 承认现实（dev 的 db 就是 sqlite、日志就是 DEBUG）；invariant 守住底线（重试策略三环境不一致，同一个变更在 staging 重试 3 次、在生产重试 9 次，测试结论不可迁移）。

**没有这两张清单，任何对比工具只会产出噪音**。


**扁平化对比**。嵌套 yaml 展平成 `database.url` 这样的点路径再对比——
报错能精确点名（`[staging] 缺少必填字段 database.url`），矩阵能逐字段
呈现。嵌套 diff 直接输出对人极不友好。

**invariant 清单的本质**。它是测试对环境的契约——先声明哪些字段必须
一致，再验证是否一致（项目 15 的契约思想在配置域的复用）。
schema 由配置的 owner（研发+运维共同）定义，invariant 清单由测试团队定义。

## Pitfalls & Q&A

踩坑清单：

- **只查存在性不查值**。现象：三环境都有 `retry.max_attempts` 但值不同，
  检测全绿。解法：invariant 清单独立于 required，逐字段比值。
- **白名单散落在脚本里**。现象：谁能改白名单没人说得清。
  解法：白名单进 schema 文件、进代码评审。
- **校验规则不类型化**。现象：字符串字段被要求 min/max。
  解法：规则随字段类型分派。
- **变异直接改原配置**。现象：审计工具污染被审计对象，clean 说谎。
  解法：变异只写 reports/ 副本。

深入问答：

- **Q：配置管理和漂移检测什么关系？**
  配置进 git + Code Review 是第一道关；漂移检测是第二道：它对比的是
  **运行时真实配置**与**git 声明**——真正的漂移往往是「线上被人热改了」
  而不是「仓库里的文件改了」。本实验对比的是文件级，生产化后数据源换
  配置中心。
- **Q：feature 开关算漂移吗？**
  本实验把 features.* 放进 expected_diff（灰度发布——新功能先对部分环境/部分
  用户逐步放开——分环境放开是正常操作）。
  但开关矩阵要有自己的治理（谁开的、何时关），漂移工具只负责把它从
  「隐蔽差异」变成「显式差异」——显式即可讨论。
- **Q：为什么「测试环境和生产不一致」必然发生？**
  因为两者的变更节奏不同：生产配置由发布管、staging 由开发随手改——
  没有同步机制，漂移只是时间问题。治本是环境配置单一来源（IaC），
  治标是本实验的定期检测 + 告警。
- **Q：和项目 16 环境工厂怎么衔接？**
  ephemeral 环境的配置来自模板+PR 覆盖，天然由代码生成、无手工漂移——
  环境工厂消灭了「实例级漂移」，本实验守住「环境级差异」的合法性。
  两层合起来才是完整的配置一致性。

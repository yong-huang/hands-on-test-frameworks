# 17 · 多环境配置矩阵与漂移检测：先声明合法差异，剩下的才叫漂移

> 「staging 测出来没问题，上了生产炸了」——一半的锅是配置漂移：有人手改了 staging
> 的重试次数、忘了同步。本实验把配置一致性做成机器判定：schema 校验（缺字段点名）
> + 逐字段漂移分类（预期差异 vs 疑似漂移）。实测：基线 7 处差异全部合法；变异
> （staging 删必填字段 + prod-like 改 invariant）被点名拦截。清单第 17/28 项。

## 1. 为什么需要它

- 环境不一致导致漏测是高频事故：**发现不一致**本身就是测试能力的一部分；
- 差异不是越多越好也不是越少越好：关键是**每处差异都被声明过、被解释过**；
- 「staging 悄悄被人改了」需要的是配置的版本控制 + 漂移告警，不是开会强调纪律。

心智模型一句话：**schema 两张清单**——expected_diff（db 地址/日志级别，天生该不同）
与 invariant（超时/重试/退避，三环境必须一字不差）；逐字段对比后，凡是不在白名单的
差异就是疑似漂移。

## 3. 快速开始

```bash
cd architect/17_config_drift
./config_drift.sh apply     # 基线：三环境 dev/staging/prod-like 对 schema 全合规
./config_drift.sh observe   # 基线矩阵 → 变异（删必填+改 invariant）→ 拦截与标注
./config_drift.sh clean     # 变异只写 reports/ 副本，原始配置全程未动
```

实测输出（节选）：

```
① 基线：共 7 处差异：预期差异 7 处（schema 声明合法），疑似漂移 0 处
② 变异后：
   ❌ Schema 校验失败
   - [staging] 缺少必填字段 database.url
   | retry.max_attempts | 3 | 9 | 3 | ⚠️ 疑似漂移 |
   >>> 变异后退出码 1（1 = 校验拦截）
```

## 4. 核心概念

### 4.1 两张清单是配置治理的宪法
expected_diff 承认现实（dev 的 db 就是 sqlite、日志就是 DEBUG）；invariant 守住底线
（重试策略三环境不一致 = 同一个变更在 staging 重试 3 次、在生产重试 9 次，测试结论
不可迁移）。**没有这两张清单，任何对比工具只会产出噪音**。

### 4.2 校验错误与漂移是两类失败
校验错误（缺字段/类型错/越界）= 配置坏了，立即拦；漂移 = 配置存疑，标注+审查。
退出码策略：错误必拦；漂移默认警告、`--strict` 加严——分级响应才推得动。

### 4.3 扁平化对比
嵌套 yaml 展平成 `database.url` 这样的点路径再对比——报错能精确点名，矩阵能逐字段
呈现。嵌套 diff 直接输出对人极不友好。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 变异写 reports/ 副本 | 原始配置是「被审计对象」，工具不能污染它 | 图省事直接改原配置，clean 就成了说谎 |
| invariant 独立于 required | 字段可以「都存在且合法」但「值不一致」 | 只查存在性查不出漂移 |
| min/max 含义随类型 | 字符串没有 min | 校验规则类型化，别用一把锤子敲所有字段 |
| 漂移白名单进 schema 评审 | 谁能改白名单=谁能定义「合法」 | 白名单散落在脚本里等于没有白名单 |

## 7. 深入要点

**Q1：配置管理和漂移检测什么关系？** 配置进 git + Code Review 是第一道关；漂移检测
是第二道：它对比的是**运行时真实配置**与**git 声明**——真正的漂移往往是「线上被人
热改了」而不是「仓库里的文件改了」。本实验对比的是文件级，生产化后数据源换配置中心。

**Q2：feature 开关算漂移吗？** 本实验把 features.* 放进 expected_diff（灰度分环境
放开是正常操作）。但开关矩阵要有自己的治理（谁开的、何时关），漂移工具只负责把它
从「隐蔽差异」变成「显式差异」——显式即可讨论。

**Q3：为什么「测试环境和生产不一致」必然发生？** 因为两者的变更节奏不同：生产配置
由发布管、staging 由开发随手改——没有同步机制，漂移只是时间问题。治本是环境配置
单一来源（IaC），治标是本实验的定期检测 + 告警。

**Q4：和项目 16 环境工厂怎么衔接？** ephemeral 环境的配置来自模板+PR 覆盖，天然由
代码生成、无手工漂移——环境工厂消灭了「实例级漂移」，本实验守住「环境级差异」的
合法性。两层合起来才是完整的配置一致性。

**Q5：schema 该谁维护？** 配置的 owner（研发+运维共同）定义 schema，测试团队定义
「哪些字段是测试相关的 invariant」——漂移检测的 invariant 清单本质是测试对环境
的契约（又见项目 15 的契约思想：先声明，再验证）。

## 8. 总结

7 处差异全部合法、1 处 invariant 漂移被当场标注、缺字段被点名拦截——配置一致性
从「感觉不对劲」变成一份可评审的矩阵报告。环境（16）+ 配置（17）齐了，下一篇是
清单项目 18「灰度发布质量评估器」：发布出去之后的质量，怎么用数据判定放量还是回滚。

# 20 · 从业务流量到压测模型：容量结论要有实测依据

> 「给你一个业务怎么定压测目标」是压测方法论的第一题。标准链路四步：
> **流量估算 → 模型设计 → 场景选择 → 容量结论**——本实验把整条链做成代码：
> 业务参数（DAU——日活跃用户数/人均请求/峰值系数）推导目标 TPS（每秒处理的
> 事务数，推导过程写进生成的 k6（开源压测工具）脚本注释），三档恒定速率实测，
> 输出有实测依据的容量结论。
> 实测：目标 93 TPS，三档 46/92/185 全部 P95≤50ms，容量 185、推荐水位 111
> （压测实操的手艺见 performance 线，本实验补方案方法论）。

## Background

「压测到 5000 QPS（每秒查询数）通过」没有意义——5000 是拍的还是算的？没有业务推导的
压测，结论无法评审也无法复现：数字从哪来、假设是什么、换一个 DAU
结论怎么变，全都说不清。

压测报告的天花板是**容量结论**：最大承载 X、推荐水位 Y、依据是什么，
三样缺一不可。只报「压了 5000 没挂」既回答不了「能承载多少」，
也回答不了「日常能跑多少」。

推导写进场景注释是方法论的关键一环：评审压测方案时吵的应该是业务假设
（峰值系数合理吗），而不是脚本细节——假设摆上台面，结论才有公信力。

## What

压测模型生成器是一套「业务参数 → 实测容量」的推导系统：
**均值→峰值→目标三步推导（全部乘法有出处），多档恒定速率实测
（P95——95 分位延迟——预算内最大吞吐 = 容量），容量 × 水位系数 = 推荐水位**。

可以把这套推导想成餐厅备货的计算：从客流（DAU）算每分钟订单（均值），按饭点集中度放大（峰值系数——二八原则：80% 流量挤 20% 时间 → ×4），再留翻台余量（安全系数 ×2）定采购目标。

但和备货不同的是，压测的"厨房产能"要实测：多档恒定速率打过去，P95 预算内能吃下的最大速率就是容量。


**水位不是容量**。容量是极限，水位是日常运行的安全边界（本实验取 60%）：
留出流量波动、实例退化、依赖变慢的余量。容量达标 ≠ 可以按容量运行。

## When to Use

典型场景：

- 新业务上线前的容量评估：DAU/人均请求/峰值系数进配置，推导 + 实测出结论。
- 大促前置压测：按活动等级加码安全系数，容量结论对照业务预期。
- 压测方案评审：推导注释即方案，吵假设不吵脚本。

何时不用：无业务参数可估（全新试水产品）时，先用小流量探边界；
只关心功能不关心容量的内部工具，压测本身都可省。

实测输出（节选）：

```
# 📈 流量推导：均值 11.6 → 峰值 46.3 → 压测目标 93 TPS（P95 预算 50ms）
probe：恒定 46 TPS × 12s → 实际 46.1，P95 2.3ms ✅
probe：恒定 92 TPS × 12s → 实际 92.1，P95 2.0ms ✅
probe：恒定 185 TPS × 12s → 实际 185.1，P95 1.7ms ✅
# 🏁 容量结论：最大可承载 185 TPS（实测依据），推荐水位 111 TPS（60%）
对照压测目标 93 TPS：容量达标，可承接目标流量
```

| 设计 | 为什么 | 坑 |

## How It Works

**推导链的三个乘法**。均值 = DAU×人均÷86400；峰值 = 均值×峰值系数
（二八原则：80% 流量挤 20% 时间 → ×4）；目标 = 峰值×安全系数（大促余量
×2）。**每个系数都是业务假设**，方案评审就是对假设的评审——
这正是「推导写进注释」的价值。

**恒定到达率而非恒定 VU**。

`constant-arrival-rate` 直接控制每秒请求数；恒定 VU（Virtual User，虚拟用户——压测工具里并发发请求的模拟用户）数的吞吐随响应时间漂移（「500 个 VU」不等于「500 TPS」）。

容量探测要控制的是速率这个自变量——labs/27 的 spike 场景同理。


**水位计算**。容量 × 60% = 推荐水位 111 TPS——水位是给日常流量的
安全边界，不是性能极限。容量结论最后对照压测目标（93 TPS）给出
「可承接」的判定。

## Pitfalls & Q&A

踩坑清单：

- **k6 升级后摘要导出静默变空**。现象：`--summary-export` 导出空 values，
  容量结论归零。解法：`handleSummary` 自定义导出（本次实测踩坑）。
- **preAllocatedVUs 给太少**。现象：到达率上不去，实测值低于目标。
  原因：VU 池排队。解法：VU 数按 rate × 预估响应时间估算。
- **单点探测下结论**。现象：「500 TPS 通过」就报容量 500。
  解法：多档倍率（0.5×/1×/2×）找拐点，精细容量二分逼近。
- **容量结论外推**。现象：读路径空库单实例的结论被当成写路径集群结论。
  解法：结论强制带「测了什么」前缀。

深入问答：

- **Q：压测达标就安全了吗？**
  不安全的三种情况：单场景达标（混合场景互相争抢）、空库达标（数据量
  上去索引失效）、单实例达标（生产是集群+依赖链）。容量结论必须带
  「测了什么」的前缀。
- **Q：峰值系数怎么定才不拍脑袋？**
  数据说话的三层：埋点历史峰值/均值比（最准）、二八原则估计（没有埋点时
  的行业近似）、业务方大促预期（前瞻性）。三者不一致时取大，并在方案里
  写明出处——「系数从哪来」比「系数是多少」更能体现功力。
- **Q：为什么压测目标要比峰值再放大？**
  生产环境的容量要吃掉三重波动：流量突增（热点事件）、容量退化
  （内存泄漏/连接堆积的慢性损耗）、多实例不均（长尾实例）。
  安全系数 ×2 是通用起点，大促前置压测按活动等级加码。
- **Q：压测环境的数据量重要吗？**
  决定性重要：空库 sqlite 和百万行 sqlite 的查询计划完全不同。
  生产化做法：脱敏快照铺底（项目 7 的数据治理）+ 按数据增长曲线推演
  「半年后的容量」。本实验空库是已知简化，结论不可直接外推。
- **Q：和 performance 线怎么分工？**
  performance 线练「压→观→剖→调」的手艺（火焰图、慢 SQL、缓存），
  本实验练「方案与结论」的方法论（流量→模型→容量→水位）。
  两者是压测工程师的两只手。

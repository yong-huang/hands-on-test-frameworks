# 20 · 从业务流量到压测模型：容量结论要有实测依据

> 「给你一个业务怎么定压测目标」是压测面试的第一题。标准链路四步：**流量估算 →
> 模型设计 → 场景选择 → 容量结论**——本实验把整条链做成代码：业务参数（DAU/人均
> 请求/峰值系数）推导目标 TPS（推导过程写进生成的 k6 脚本注释），三档恒定速率实测，
> 输出有实测依据的容量结论。实测：目标 93 TPS，三档 46/92/185 全部 P95≤50ms，
> 容量 185、推荐水位 111。清单第 20/28 项（压测实操在 performance 线已练，这里补
> 方案方法论）。

## 1. 为什么需要它

- 「压测到 5000 QPS 通过」没有意义——5000 是拍的还是算的？
- 压测报告的天花板是容量结论：**最大承载 X、推荐水位 Y、依据是什么**，三样缺一不可；
- 推导写进场景注释：评审压测方案时吵的是业务假设（峰值系数合理吗），不是脚本细节。

```bash

./load_model.sh apply     # k6 自检 + 起 SUT
./load_model.sh observe   # 推导 → 生成 k6 场景 → 三档实测 → 容量结论
./load_model.sh clean
```


## 4. 核心概念

### 4.1 推导链的三个乘法
均值 = DAU×人均÷86400；峰值 = 均值×峰值系数（二八原则：80% 流量挤 20% 时间→×4）；
目标 = 峰值×安全系数（大促余量 ×2）。**每个系数都是业务假设**，方案评审就是对假设
的评审——这正是「推导写进注释」的价值。

### 4.2 恒定到达率而非恒定 VU
`constant-arrival-rate` 直接控制每秒请求数；恒定 VU 数的吞吐随响应时间漂移
（「500 个 VU」不等于「500 TPS」）。容量探测要控制的是速率这个自变量。

### 4.3 水位不是容量
容量是极限，水位是日常运行的安全边界（本实验取 60%）：留出流量波动、实例退化、
依赖变慢的余量。容量达标 ≠ 可以按容量运行——「压测达标就安全吗」的答案就在这里。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| handleSummary 自定义导出 | k6 v2 的 --summary-export 已废弃（导出空 values） | 升级 k6 后摘要解析静默变空，容量结论瞬间归零 |
| 恒定到达率 executor | 控制自变量是速率 | preAllocatedVUs 要按 rate 估算，太小会排队失真 |
| 多档倍率探测 | 单点通过只证明「这点能扛」 | 0.5×/1×/2× 是下限，精细容量要二分逼近 |
| 读路径压测 | sqlite 单写者，写并发会锁库（labs/13 教学点） | 报告要写明压的是哪条路径，容量结论不可外推 |

## 7. 深入要点

**Q1：压测达标就安全了吗？** 不安全的三种情况：单场景达标（混合场景互相争抢）、
空库达标（数据量上去索引失效）、单实例达标（生产是集群+依赖链）。容量结论必须带
「测了什么」的前缀——本实验诚实写明「GET 读路径、空库、单实例」。

**Q2：峰值系数怎么定才不拍脑袋？** 数据说话的三层：埋点历史峰值/均值比（最准）、
二八原则估计（没有埋点时的行业近似）、业务方大促预期（前瞻性）。三者不一致时取大，
并在方案里写明出处——「系数从哪来」比「系数是多少」更能体现功力。

**Q3：为什么压测目标要比峰值再放大？** 生产环境的容量要吃掉三重波动：流量突增
（热点事件）、容量退化（内存泄漏/连接堆积的慢性损耗）、多实例不均（长尾实例）。
安全系数 ×2 是通用起点，大促前置压测按活动等级加码。

**Q4：和 performance.md 线怎么分工？** performance 线练「压→观→剖→调」的手艺
（火焰图、慢 SQL、缓存），本实验练「方案与结论」的方法论（流量→模型→容量→水位）。
前者是压测工程师的手艺，后者是架构师的话术——面试两者都要。

**Q5：压测环境的数据量重要吗？** 决定性重要：空库 sqlite 和百万行 sqlite 的查询
计划完全不同。生产化做法：脱敏快照铺底（项目 7 Q1 的数据治理）+ 按数据增长曲线
推演「半年后的容量」。本实验空库是已知简化，结论不可直接外推。

## 8. 总结

三步推导有出处、三档实测有数字、容量水位有依据——压测方案从「跑个分」升级为
一份可评审、可复现的工程文档。非功能篇刚开篇：下一篇是清单项目 21「故障注入与
降级验证」——性能之外，稳定性怎么验证。

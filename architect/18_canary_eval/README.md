# 18 · 灰度发布质量评估器：放量还是回滚，数据说了算

> 测试左移做得再好，发布后的质量仍要有人兜底——右移的核心动作是灰度期间的
> **自动化质量判定**。本实验对 baseline 与 canary 打同样的流量（读多写少的生产形状），
> 用「绝对红线 + 相对比率」双判定给出放量/回滚。实测：健康 canary 判放量；
> 注入 20% 错误率 + 300ms 延迟的劣化实例被打穿三项判定、自动回滚。清单第 18/28 项。

## 1. 为什么需要它

- 「灰度了没人看指标」= 灰度只是慢速发布，不是质量手段；
- 只看绝对阈值：灰度环境差一档（机器更小）就永远触发回滚——误杀；
- 只看相对比率：baseline 自己已经烂透时，canary「相对健康」毫无意义——漏杀；
- 判定必须**有据可查**：每一项 ✅/❌ 都带数值与阈值，回滚理由不用吵架。

## 3. 快速开始

```bash
cd architect/18_canary_eval
./canary_eval.sh apply     # 起 baseline(:8899) + 健康 canary(:8903)
./canary_eval.sh observe   # 健康判定放量 → 切劣化实例 → 判定回滚 → 验收断言
./canary_eval.sh clean
```

实测输出（节选）：

```
① 健康 canary：错误率 0.0% vs 0.0%，P95 1.6ms vs 1.9ms
   判定：✅ 放量（promote）——四项判定全过
② 劣化 canary（20% 错误 + 300ms 延迟）：
   canary: 错误率 21.7%，P95 612.2ms
   判定：⛔ 回滚（rollback）
   ❌ 错误率绝对红线：21.7% ≤ 2%
   ❌ 错误率相对比率：21.7% vs baseline 0.0%×3.0
   ❌ P95 相对比率：612.2ms vs baseline 1.5ms×1.5
```

## 4. 核心概念

### 4.1 同形状采样
判定器对两侧发**完全相同的流量形状**（50% 健康/30% 列表/20% 下单）——对比才有意义。
POST 会顺手删掉自己创建的单：评估器不能污染被评估的对象。

### 4.2 双判定缺一不可
绝对红线（canary 错误率 ≤2%、P95 ≤800ms）+ 相对比率（错误率 ≤baseline×3+0.5% 松弛、
P95 ≤baseline×1.5）。松弛量（slack）是小样本防抖：baseline 0% 错误时 ×3 仍是 0，
必须有绝对量兜底。

### 4.3 判定依据即审计记录
verdict JSON 里每项检查带实测值与阈值——回滚复盘时能回答「当时哪个指标先打穿的」。
灰度评估不是黑盒按钮，是可审计的决策链。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 采样 60 次/侧 | 小样本上 P95 抖动大，60 是判定稳定与耗时的折中 | 样本量进配置，别硬编码 |
| 劣化进程外注入 | 被测的是判定器，不是改 SUT | 改 SUT 源码造劣化=验收脚本污染被测对象 |
| POST 自清理 | 流量采样不该变成数据污染（项目 7 的纪律） | 忘了清理的评估器跑一晚，库就是垃圾场 |
| 阈值进 yaml | 阈值是业务决策不是代码决策 | 阈值改动要有评审，跟门禁规则同权 |

## 7. 深入要点

**Q1：错误率/延迟之外还要看什么？** 业务指标（下单成功率、支付转化）与资源指标
（CPU/内存/连接数）。通用兜底三件套：错误率、P95、饱和度（黄金信号）；业务指标
因产品而异，但必须进判定——技术全绿业务转化腰斩的灰度并不罕见。

**Q2：样本量 60 够吗？** 对 20% 这种大错误率足够（±10% 置信区间）；对 0.5% 级的
细微劣化完全不够——需要千万级真实流量的统计检验（假设检验/序贯分析）。本实验的
工程化版本是「探针粗筛 + 真实流量精判」两级。

**Q3：自动回滚不怕误杀吗？** 怕——所以分级响应：判定回滚先缩流量（50%→25%）观察
一个窗口，连续两个窗口仍差才回滚到底。全自动的胆子来自判定依据的置信度，置信度
来自样本量——三者是一条链。

**Q4：baseline 自己在抖怎么办？** 相对比率的 slack 就是干这个的；更彻底的做法是
双 baseline（上一版本与新版本互为参照）或者用历史同期分布做基线。灰度判定的
天花板是「基线的质量」。

**Q5：和项目 19 合成监控怎么分工？** 灰度期（分钟-小时级）用本实验的重采样判定；
上线后（天级）由合成探针持续巡检（项目 19）。前者回答「这版能不能上」，后者回答
「上线之后还活着吗」——右移的两段时间线。

## 8. 总结

健康放量、劣化回滚、四项判定三项打穿且条条有数——灰度质量从「盯着大盘人肉判断」
变成一段可审计的自动判定。环境（16）配置（17）灰度（18）三件套齐了，发布质量的
最后一块拼图是上线后的持续巡检——下一篇是清单项目 19「合成监控探针」。

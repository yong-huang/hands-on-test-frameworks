# 18 · 灰度发布质量评估器：放量还是回滚，数据说了算

> 测试左移（把测试提前到开发阶段）做得再好，发布后的质量仍要有人兜底——右移
> （对已发布系统持续验证）的核心动作是灰度期间（新版本小流量试运行期间）的
> **自动化质量判定**。本实验对 baseline（当前线上版本，作对照基准）与 canary
> （灰度新版本，只放给一小部分流量的候选版本）打同样的流量
> （读多写少的生产形状），用「绝对红线 + 相对比率」双判定给出放量/回滚。
> 实测：健康 canary 判放量；注入 20% 错误率 + 300ms 延迟的劣化实例被打穿
> 三项判定、自动回滚。

## Background

「灰度了没人看指标」= 灰度只是慢速发布，不是质量手段——放量/回滚的
判定靠人盯大盘，既慢又主观。

单一判定口径各有死穴：只看绝对阈值，灰度环境差一档（机器更小）就永远
触发回滚——误杀；只看相对比率，baseline 自己已经烂透时，canary
「相对健康」毫无意义——漏杀。

双判定的解法：绝对红线 + 相对比率同时成立才放量，任一打穿即回滚。
判定必须**有据可查**：每一项 ✅/❌ 都带数值与阈值，回滚理由不用吵架。

## What

灰度质量评估器是一套自动判定系统：**同形状采样 → 双指标（错误率/P95——95 分位延迟，即 95% 的请求都快于这个耗时）× 双判定（绝对/相对）→ 任一打穿即回滚**。

可以把评估器想成双秤验金：一杆秤称绝对重量（纯度不能低于法定下限——绝对红线），另一杆秤对比标准样品（与 baseline 的偏差不能超倍数——相对比率），两杆秤都说合格才出厂。

但和验金不同的是，评估器对两侧打的是**完全相同的流量形状**（50% 健康/30% 列表/20% 下单）——对比才有意义；且 POST 会顺手删掉自己创建的单：评估器不能污染被评估的对象。


双判定的参数：绝对红线（canary 错误率 ≤2%、P95 ≤800ms）+ 相对比率
（错误率 ≤ baseline×3+0.5% 松弛、P95 ≤ baseline×1.5）。松弛量（slack）
是小样本防抖：baseline 0% 错误时 ×3 仍是 0，必须有绝对量兜底。

## When to Use

典型场景：

- 灰度期的自动放量/回滚判定：分钟-小时级的重采样决策。
- 回滚复盘：verdict JSON 里每项检查带实测值与阈值——能回答
  「当时哪个指标先打穿的」。
- 发布质量制度建设：阈值进 yaml 进评审，判定依据即审计记录
  ——灰度评估不是黑盒按钮，是可审计的决策链。

何时不用：全量发布（无灰度对照组）时无从对比；流量太小
（每天几十个请求）时样本量撑不起判定——探针粗筛都难以为继。

实测输出（节选）：

```
① 健康 canary：错误率 0.0% vs 0.0%，P95 1.6ms vs 1.9ms
   判定：✅ 放量（promote）——四项判定全过
② 劣化 canary（20% 错误 + 300ms 延迟）：
   canary: 错误率 21.7%，P95 612.2ms
   判定：⛔ 回滚（rollback）
   ❌ 错误率绝对红线：21.7% ≤ 2%
   ❌ 错误率相对比率：21.7% vs baseline 0.0%×3.0
   ❌ P95 相对比率：612.2ms vs baseline 1.5ms×1.5
```

## Quick Start

前置条件：labs/00 体检通过；脚本自动起 baseline(:8899) 与
canary(:8903，健康/劣化两态切换)。

```bash
cd architect/18_canary_eval
./canary_eval.sh apply     # 起 baseline(:8899) + 健康 canary(:8903)
./canary_eval.sh observe   # 健康判定放量 → 切劣化实例 → 判定回滚 → 验收断言
./canary_eval.sh clean
```

诚实预期：健康 canary 应四项判定全过、判放量；劣化实例（进程外注入
20% 错误 + 300ms 延迟）应打穿至少三项判定、判回滚——被测的是判定器本身，
不是改 SUT 源码造劣化。

关键设计（这段在做什么：判定可信度的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 采样 60 次/侧 | 小样本上 P95 抖动大，60 是判定稳定与耗时的折中 | 样本量进配置，别硬编码 |
| 劣化进程外注入 | 被测的是判定器，不是改 SUT | 改 SUT 源码造劣化=验收脚本污染被测对象 |
| POST 自清理 | 流量采样不该变成数据污染（项目 7 的纪律） | 忘了清理的评估器跑一晚，库就是垃圾场 |
| 阈值进 yaml | 阈值是业务决策不是代码决策 | 阈值改动要有评审，跟门禁规则同权 |

## How It Works

**同形状采样**。判定器对 baseline 与 canary 发完全相同的流量形状
（50% 健康/30% 列表/20% 下单，读多写少的生产形状）——形状不同，
任何对比都失去意义。

**双判定缺一不可**。绝对红线防「baseline 烂透时 canary 相对健康」的漏杀；
相对比率防「灰度环境硬件差一档就误杀」。松弛量（slack）是小样本防抖：
baseline 0% 错误时 ×3 仍是 0，必须叠加绝对量（+0.5%）兜底。

**判定依据即审计记录**。verdict JSON 里每项检查带实测值与阈值——
你在上面输出里看到的每一行 ❌ 都同时有「21.7%」与「≤2%」两个数，
回滚复盘时能精确回答「当时哪个指标先打穿的」。

## Pitfalls & Q&A

踩坑清单：

- **评估器污染被评估对象**。现象：评估跑一晚，库里多了上万条测试订单。
  解法：POST 自清理（创建后即删）。
- **只看相对比率**。现象：baseline 崩了，canary「相对健康」照样放量。
  解法：绝对红线兜底，双判定缺一不可。
- **阈值硬编码**。现象：调阈值要改代码发版。解法：阈值进 yaml、进评审。
- **样本量撑不起细微判定**。现象：0.5% 级劣化判不出来（60 样本的置信
  区间±10%）。解法：探针粗筛 + 真实流量统计检验两级。

深入问答：

- **Q：错误率/延迟之外还要看什么？**
  业务指标（下单成功率、支付转化）与资源指标（CPU/内存/连接数）。
  通用兜底三件套：错误率、P95、饱和度（黄金信号）；业务指标因产品而异，
  但必须进判定——技术全绿业务转化腰斩的灰度并不罕见。
- **Q：自动回滚不怕误杀吗？**
  怕——所以分级响应：判定回滚先缩流量（50%→25%）观察一个窗口，
  连续两个窗口仍差才回滚到底。全自动的胆子来自判定依据的置信度，
  置信度来自样本量——三者是一条链。
- **Q：baseline 自己在抖怎么办？**
  相对比率的 slack 就是干这个的；更彻底的做法是双 baseline（上一版本与
  新版本互为参照）或者用历史同期分布做基线。灰度判定的天花板是
  「基线的质量」。
- **Q：和项目 19 合成监控怎么分工？**
  灰度期（分钟-小时级）用本实验的重采样判定；上线后（天级）由合成探针
  持续巡检（项目 19）。前者回答「这版能不能上」，后者回答
  「上线之后还活着吗」——右移的两段时间线。

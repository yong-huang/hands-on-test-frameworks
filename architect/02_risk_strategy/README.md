# 02 · 风险驱动的测试策略生成器：把「测多少」变成一道算术题

> 「测试不可能穷尽，你按什么决定测多少？」——背答案是「风险驱动」四个字，
> 做出来是一台可重跑的机器：功能清单进去，带风险分级、测试层级、准出标准的
> 策略文档出来。读完本篇你能复现这台机器，并理解「策略能随输入重算」
> 与 Word 版策略的本质区别。

## Background

策略文档的默认形态是 Word/PDF：写的时候热闹，改需求后没人更新，
三个月后没人说得清「文档第 3 页那句还作数吗」。策略拍脑袋的典型句式
是「重点功能多测测」——它不可执行：多测多少？测哪层？怎么验收？

架构师的回答是把策略变成**推导**：功能清单 × 风险输入 → 打分 → 等级 →
层级与准出标准。输入全部是团队里拿得到的字段（监控频率、业务定级、
缺陷库、git churn——代码变更频率，从 git 历史统计），推导规则全部在配置里——策略因此可以像代码一样
重跑、diff、评审。

本实验的 10 个功能来自真实的 SUT（订单应用，lab 11）存量 + 迭代新增；
分层口径与 [01 分层审计](../01_pyramid_audit/README.md) 同源。

## What

风险驱动的测试策略生成器是一台策略推导机器：每个功能按
**风险 = 重要性（失败影响）× 失效概率（频率 + 缺陷史，变更放大）**
打分，落入 P0-P3 等级带，等级带映射测试层级、用例类型与准出标准，
最后对照现有资产找缺口。

可以把这台机器想成保险定价：保额（影响）和出险率（概率）分开评估，
再合成保费等级——「高频但无关紧要」（健康检查）和「低频但一挂就死」
（删除订单）不会被糊成同一个数。但和保险不同的是，这里算的是测试预算的
分配：等级越高，投入的层级越多、准出门槛越高。

两个因子分开打分再相乘，是模型的核心设计（见 How It Works）。

## When to Use

典型场景：

- 新业务接手：需求分析完先跑一遍策略，回答「测多少」而不是「都测」。
- 迭代排期：churn（代码变更频率）每迭代刷新，策略每 sprint 重跑，
  测试投入跟着风险走。
- 跨团队评审：吵的应是「这个功能 impact 该不该是 critical」，
  而不是「文档那句还作数吗」。

何时不用：功能少到一眼能看完（三五条 API 的小服务）时，机器的固定成本
不划算；风险输入拿不到（无监控、无缺陷库、业务方不参与定级）时，
先补输入机制再上模型——垃圾进垃圾出。

同类方式对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 拍脑袋分层 | 快，不可复算不可评审 | 一个人两天的小项目 |
| 等价类/边界全铺 | 不看风险，成本失控 | 算法内核等极小高险模块 |
| 风险驱动策略 | 输入可查、推导可重跑、缺口可对照 | 中大型团队的默认解 |

## Quick Start

前置条件：labs/ 资产已就位（缺口分析要对照它）；纯离线，不依赖 SUT。

```bash
cd architect/02_risk_strategy
./risk_strategy.sh apply     # 自检 + 生成基线策略（纯离线，不依赖 SUT）
./risk_strategy.sh observe   # ① 基线表 ② 变异演示：改「数据导出」风险输入重跑 ③ 缺口分析
./risk_strategy.sh clean     # 删报告与变异副本（configs/ 原始输入全程不动）
```

基线策略核心表（2026-09-19 实测，10 个功能自然铺开成 4 个等级）：

```
| 功能 | 重要性 | 失效概率 | 风险分 | 等级 | 测试层级 | 优先级 |
|:---|---:|---:|---:|:---:|:---|:---|
| 创建订单 | 5 | 5 | 25 | P0 | 单元层 + 接口/集成层 + UI E2E 层 | P0（阻塞发布） |
| 登录鉴权 | 5 | 5 | 25 | P0 | 单元层 + 接口/集成层 + UI E2E 层 | P0（阻塞发布） |
| 订单状态流转 | 5 | 5 | 25 | P0 | 单元层 + 接口/集成层 + UI E2E 层 | P0（阻塞发布） |
| 删除订单 | 5 | 4.2 | 21 | P0 | 单元层 + 接口/集成层 + UI E2E 层 | P0（阻塞发布） |
| 订单列表查询 | 3 | 5 | 15 | P1 | 单元层 + 接口/集成层 | P1 |
| 金额计算 | 3 | 5 | 15 | P1 | 单元层 + 接口/集成层 | P1 |
| Admin 后台页 | 3 | 2.0 | 6 | P2 | 单元层 | P2 |
| 健康检查端点 | 1 | 5.0 | 5 | P2 | 单元层 | P2 |
| 慢加载演示页 | 1 | 1.0 | 1 | P3 | 不设门禁，探针兜底 | P3（按需抽查） |
| 订单数据导出 | 1 | 1.2 | 1 | P3 | 不设门禁，探针兜底 | P3（按需抽查） |
```

验收核心——变异演示（observe 步真实执行）：假设「订单数据导出」转正为
客户合约功能（freq low→high、impact minor→critical），重跑后该功能一行对比：

```
--- 基线 vs 变异（仅「订单数据导出」行）---
1c1,2
< | 订单数据导出 | 1 | 1.2 | 1 | P3 | 不设门禁，探针兜底 | P3（按需抽查） |
---
> | 订单数据导出 | 5 | 5 | 25 | P0 | 单元层 + 接口/集成层 + UI E2E 层 | P0（阻塞发布） |
> | 订单数据导出 | P0 | 单元层 + 接口/集成层 + UI E2E 层 | 单元层、接口/集成层、UI E2E 层 |
```

诚实预期：第二行是缺口表的新增行——升 P0 的同时，「三层全无现有用例」的缺口也立刻被照出来。

本次实测 8 个功能有缺口，最扎眼的两个：**登录鉴权是P0 但三层全无测试**（SUT 的 /login.html 裸奔中），**创建订单是 P0 但单元层为空**——接口和 E2E 都测它，业务规则却没有任何进程内测试兜底。


## How It Works

**两个因子分开打分**。重要性 = impact 定级（critical 5 / major 3 /minor 1）；失效概率 = (基础频率 + 历史缺陷加成) × 变更放大，封顶 5。

缺陷加成设 0.5/个、封顶 2：**历史缺陷提高再犯概率，但不能让三年前的老黄历一票定终身**。健康检查（影响 1 × 概率 5 = 5 分）和删除订单（5 × 4.2 = 21 分）就是两个因子分工的活例子。


**等级带即策略，准出标准即门禁**。P0≥16 / P1≥9 / P2≥4 / P3 其余。

等级不是标签而是策略包：P0 三层全覆盖 + 行覆盖 ≥90% + 阻塞发布；P3 不投入用例、靠生产探针（部署在生产环境、定时发请求验证服务存活的监控程序）兜底（对应项目 19 的右移——把验证从开发阶段移到生产监控阶段）。

准出标准全是**门禁语言**——可以直接翻译成项目 3 门禁引擎的规则。


**缺口 = 目标层级 − 现有资产**。`covered_by` 指向 labs/ 现有用例
（如创建订单 → labs/12/16/21），按 01 号实验同一套分层口径归类后与
目标层级相减。

**策略是推导出来的，不是抄来的**。打分权重、等级带、每级的用例类型与
准出标准全部在 `configs/risk_matrix.yaml`。换个团队迁移这套方法，
改的是配置不是代码。

YAML 关键字段（这段在做什么：风险输入与模型参数的分工）：

| 文件 | 字段 | 为什么 | 坑 |
|:---|:---|:---|:---|
| features.yaml | `freq/impact/churn` | 打分三输入，监控/业务方/git 都拿得到 | 定级要业务方签字，测试单方面定 impact 没有公信力 |
| features.yaml | `defects_90d` | 历史缺陷是失效概率的实证输入 | 用 90 天窗口而非累计，避免老系统被历史拖死 |
| features.yaml | `covered_by` | 现有资产指针，缺口分析的数据源 | 迭代新增功能留空数组即可，别造假填 |
| risk_matrix.yaml | `probability.defect_boost_cap` | 历史不能定终身 | 不封顶的话 12 个缺陷的功能概率直接打满 |
| risk_matrix.yaml | `bands` | 分数→等级的唯一映射 | 改带宽会整批改变策略，评审时重点盯 |
| risk_matrix.yaml | `band_policy.exit_criteria` | 策略落到门禁语言 | 写「充分测试」等于没写，要写「行覆盖 ≥90%」 |

## Pitfalls & Q&A

踩坑清单：

- **impact 由测试单方面定**。后果：定级没有公信力，策略评审变成拉扯。
  解法：业务方签字 + 故障复盘数据背书。
- **`covered_by` 造假填**。后果：缺口分析失真，缺口被隐藏。
  解法：迭代新增功能留空数组，如实标注「无现有用例」。
- **改 `bands` 带宽不做影响评估**。后果：整批功能策略翻转。
  解法：带宽变更单独评审，重跑后 diff 全表。

深入问答：

- **Q：拿到一个新业务怎么制定测试策略？**
  方法论五步链：需求分析（功能 + 四项风险输入）→ 范围/目标 → 风险识别
  （重要性 × 失效概率）→ 分层设计（等级带 → 层级/用例类型）→ 退出标准
  （门禁语言）。本实验的 `strategy.md` 章节顺序就是这条链——
  它已经被做成了可重跑的工具。
- **Q：为什么用乘法（重要性×概率）而不是加权求和？**
  乘法体现「一票否决结构」：impact=1 的功能无论多高频都进不了 P0
  （1×5=5），impact=5 但没人用的功能也够不着最高带（5×1=5）。求和会让
  「中频+中影响」和「高危+没人用」同分，恰恰淹没了最需要讨论的边角。
  25 分制还能自然切成 4 个等级带。
- **Q：P3「不测」会不会太激进？**
  P3 的完整语义是「不投用例、但右移兜底」——准出标准写的是靠生产探针兜底
  （项目 19）。测或不测从来不是二选一，测试左移和监控右移是一套预算的两端：
  健康检查这种高频低影响功能，探针比用例便宜一个量级。
- **Q：缺口分析里「创建订单缺单元层」说明了什么？**
  说明团队自动化从中间层起步（API 好写），业务规则反而没有最快的反馈层。
  这不是本仓库独有——是「从接口自动化切入」团队的通病。修复路径就是
  项目 24 的增量覆盖率卡点：新代码必须带单元测试，存量按风险排序补。
- **Q：这套模型什么时候会失灵？**
  三个已知边界：① 输入造假（业务方把自家功能全标 critical）——解法是定级
  要有 SLA 和故障复盘数据背书；② 探索性/安全/性能测试不吃这套分层——
  它们是塔外资产（见 [01 实验](../01_pyramid_audit/README.md)）。

  ③ 风险是动态的——churn 字段每迭代刷新，策略文档每 sprint 重跑一次，
  否则又会烂在网盘里。

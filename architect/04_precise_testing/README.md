# 04 · 精准测试原型：回归跑多少，由变更影响说了算

> 全量回归越来越慢（01 号实验实测过 E2E 的成本），但「少跑」必须回答「凭什么敢少跑」。
> 本实验实现工业界精准测试的**运行时路线**：`--cov-context=test` 记录「哪条用例碰过哪行」，
> git diff 取变更行，交集即最小回归集。实测：改 store.py 一行，10 条套件只推荐 2 条（省 80%），
> 且每条推荐都能说清「因为它覆盖过变更行」。清单第 4/28 项。

## 1. 为什么需要它

- 回归成本是测试体系的最大经常性开支；「全量回归」等于把 CI 时长变成代码量的线性函数。
- 少跑的安全边界来自数据：变更行从未被任何用例覆盖时，工具必须提示**漏测风险**并降级，
  而不是给出虚假的安全感。

心智模型一句话：**全量跑一次是投资（建立行级覆盖档案），之后每次变更只付推荐计算的利息**。
git diff 的变更行进「行级上下文」反查出用例集合；档案缺失时降级保护直接改判全量——宁全量、不瞎推。

## 3. 快速开始

```bash
cd architect/04_precise_testing
./precise_testing.sh apply     # 建/刷新覆盖档案（labs/13 全量跑一次 --cov-context=test）
./precise_testing.sh observe   # 造一行真实变更 → 推荐 → 验收断言 → 还原 → 降级演示
./precise_testing.sh clean     # trap 保证 store.py 永远被还原
```

实测输出（对 store.py 的 list_orders 造一行变更后）：

```
- **最小回归集（2 条）**：
  - `tests/test_isolation.py::test_truncate_isolation_fresh`
  - `tests/test_isolation.py::test_truncate_isolation_truncate`
- **回归集压缩比**：全量 10 → 2（省 80%）
- **风险提示**：变更行均有覆盖档案
验收断言通过 ✅（推荐 ≤ 全量 50% 且 ≥1 条）
```

降级演示：删掉 `.coverage` 后，工具退出码 2 并提示「降级为全量回归，宁全量、不瞎推」。

## 4. 核心概念

### 4.1 覆盖上下文（coverage context）
普通覆盖率只回答「这段代码被测过没有」；`--cov-context=test` 额外回答「**被谁**测过」。
这是精准测试的核心数据结构：行号 → 用例集合的倒排索引。

### 4.2 变更行提取
`git diff -U0` 解析 hunk 头 `@@ +start,count @@` 得到新文件行号。工作区还原由脚本
`cp 备份 + trap EXIT` 双保险——审计工具绝不能污染被审计对象。

### 4.3 两条路线（面试标准答案）
运行时路线（本实验，精确到行但依赖档案新鲜度）vs 静态路线（AST 依赖图，不需跑测试但
粒度粗，见清单项目 12）。工业界（百度/京东/有赞）两者混用：静态做初筛、运行时做精推荐。

## 5. 关键参数

| 参数 | 为什么 | 坑 |
|:---|:---|:---|
| `--cov-context=test` | 建立行→用例倒排的唯一开关 | 忘记加则档案只有总量，反查全空 |
| 上下文 `|run` 后缀 | coverage 记录的相位标记 | 不剥掉会污染 pytest node id，复现命令跑不起来 |
| 模块加载期空上下文 `''` | import 时执行的行不属于任何用例 | 不过滤会把「文件头」行算给所有用例 |
| 退出码 2 | 无数据 ≠ 无风险 | 必须与「推荐为空」区分：前者降级全量，后者变更行零覆盖 |

## 7. 深入要点

**Q1：档案过期了怎么办（档案建完代码又改了）？** 行号会漂移——这是运行时路线的头号工程
问题。生产做法：每次 CI 全量跑时自动刷新档案（本实验 apply 步即此语义），档案永远反映
「上一次全量」的世界。diff 行号与档案行号错位时按「无覆盖」保守处理，落入漏测风险提示。

**Q2：为什么推荐集断言「≤ 全量 50%」？** 压缩比是精准测试的 ROI 指标：推荐集接近全量
说明变更命中了核心路径（或档案太稀），此时收益不足以覆盖「漏推风险」，不如全量。
阈值本身应进配置并随数据校准。

**Q3：新增的行（不只是修改）没有历史覆盖，推荐什么？** 新增行必然无上下文 → 落入
「漏测风险」清单。正确输出是两条：受影响存量用例 + 「新增行需补测」清单——本工具的
`uncovered_lines` 字段就是后者，这也是精准测试反向驱动补测的入口。

**Q4：和项目 3 门禁怎么协同？** 门禁回答「必须测什么」（coverage_total ≥90%），
精准测试回答「这次最少测什么」。两者共用 labs/13 套件与 store 口径：PR 上跑推荐集 +
增量覆盖率卡点（项目 24），夜间全量刷新档案。

**Q5：测试顺序依赖会不会让档案失真？** 会——档案记录的是「那次全量」里的执行顺序。
labs/13 的教训（database is locked）说明顺序敏感套件的档案要按固定顺序（如 xdist 分发序）
采集，否则推荐集会漏掉「只有排在后面才触发的路径」。

## 8. 总结

一行变更，10 条用例，2 条推荐，80% 压缩，每条推荐可解释、可复现；无数据时宁可全量。
精准测试不是「少跑测试」的技巧，而是把回归预算重新分配到真实影响面上的架构能力。

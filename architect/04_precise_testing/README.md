# 04 · 精准测试原型：回归跑多少，由变更影响说了算

> 全量回归越来越慢（[01 审计](../01_pyramid_audit/README.md) 实测过 E2E 的成本），
> 但「少跑」必须回答「凭什么敢少跑」。本实验实现工业界精准测试的运行时路线：
> `--cov-context=test` 记录「哪条用例碰过哪行」，git diff 取变更行，交集即最小回归集。
> 实测：改 store.py 一行，10 条套件只推荐 2 条（省 80%），且每条推荐都能说清
> 「因为它覆盖过变更行」。

## Background

回归成本是测试体系的最大经常性开支。「全量回归」等于把 CI 时长变成代码量的
线性函数：仓库越大，每次提交等得越久，最后团队开始跳过回归——测试资产的
价值在执行环节流失。

 naive 的「少跑」有两种失败形态：按目录猜（改了 store.py 就跑 store 的测试——
调用方全漏）；按时长砍（慢的少跑——恰恰把高成本的 E2E 保护网砍掉）。
两者都不敢对「漏掉的用例会不会放走 bug」负责。

精准测试把问题变成数据题：**变更行 × 行级覆盖档案 = 受影响用例集合**。
少跑的安全边界来自数据：变更行从未被任何用例覆盖时，工具必须提示
**漏测风险**并降级，而不是给出虚假的安全感。

## What

精准测试（precise testing）是一种「按变更影响圈选回归范围」的技术：
用覆盖上下文建立「行号 → 用例集合」的倒排索引，用 git diff 取变更行，
两者交集就是本次变更的最小回归集。

可以把这套机制想成图书馆的索引卡：全量跑一次是**投资**（把每本书被谁
借过记上卡），之后每次变更只付**推荐计算的利息**（查几张卡就能圈出读者）。
但和索引卡不同的是，档案有时效——代码改了行号会漂移，档案永远反映
「上一次全量」的世界，错位时按无覆盖保守处理。

两条技术路线：**运行时路线**（本实验，精确到行但依赖档案新鲜度）vs
**静态路线**（AST 依赖图，不需跑测试但粒度粗，见项目 12）。工业界
（百度/京东/有赞）两者混用：静态做初筛、运行时做精推荐。

## When to Use

典型场景：

- 大仓库的 PR 验证：跑推荐集 + 增量覆盖率卡点（项目 24），分钟级反馈。
- 夜间全量的档案刷新：CI 全量跑时顺手重建档案（本实验 apply 步即此语义）。
- 变更风险沟通：推荐集 + 未覆盖变更行清单，让 reviewer 知道这次改动的
  测试盲区在哪。

何时不用：仓库很小（全量只要十几秒）时，圈选的收益盖过档案维护成本；
测试与被测代码关系松散（大量集成测试靠环境状态而非代码路径触发）时，
行级档案说明不了太多——精准测试的前提是「用例执行路径与代码行强相关」。

同类方式对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 全量回归 | 最安全，成本线性增长 | 夜间 / 发版前 |
| 按目录猜 | 快，调用方全漏 | 几乎不用 |
| 运行时精准测试 | 精确到行、可解释 | PR 快反馈 |
| 静态依赖图 | 不用跑测试，粒度粗 | 初筛、冷启动 |

## Quick Start

前置条件：labs/13 套件就位（档案的采集对象）；git 仓库可用（diff 数据源）。

```bash
cd architect/04_precise_testing
./precise_testing.sh apply     # 建/刷新覆盖档案（labs/13 全量跑一次 --cov-context=test）
./precise_testing.sh observe   # 造一行真实变更 → 推荐 → 验收断言 → 还原 → 降级演示
./precise_testing.sh clean     # trap 保证 store.py 永远被还原
```

实测输出（对 store.py 的 list_orders 造一行变更后）：

```
- **最小回归集（2 条）**：
  - `tests/test_isolation.py::test_truncate_isolation_fresh`
  - `tests/test_isolation.py::test_truncate_isolation_truncate`
- **回归集压缩比**：全量 10 → 2（省 80%）
- **风险提示**：变更行均有覆盖档案
验收断言通过 ✅（推荐 ≤ 全量 50% 且 ≥1 条）
```

诚实预期：降级演示里删掉 `.coverage` 档案后，工具退出码 2 并提示
「降级为全量回归，宁全量、不瞎推」——**无数据 ≠ 无风险**。脚本对 store.py
的修改由备份 + `trap EXIT` 双保险还原，实验后工作区应与实验前一致。

关键参数（这段在做什么：覆盖上下文的四个关键开关与语义）：

| 参数 | 为什么 | 坑 |
|:---|:---|:---|
| `--cov-context=test` | 建立行→用例倒排的唯一开关 | 忘记加则档案只有总量，反查全空 |
| 上下文 `|run` 后缀 | coverage 记录的相位标记 | 不剥掉会污染 pytest node id，复现命令跑不起来 |
| 模块加载期空上下文 `''` | import 时执行的行不属于任何用例 | 不过滤会把「文件头」行算给所有用例 |
| 退出码 2 | 无数据 ≠ 无风险 | 必须与「推荐为空」区分：前者降级全量，后者变更行零覆盖 |

## How It Works

**覆盖上下文（coverage context）**。普通覆盖率只回答「这段代码被测过没有」；
`--cov-context=test` 额外回答「**被谁**测过」。这是精准测试的核心数据结构：
行号 → 用例集合的倒排索引——apply 步跑一次全量（10 条用例，秒级），
档案就记录了每一行被哪些用例执行过。

**变更行提取**。`git diff -U0` 解析 hunk 头 `@@ +start,count @@` 得到新文件
行号。工作区还原由脚本 `cp 备份 + trap EXIT` 双保险——审计工具绝不能
污染被审计对象。

**推荐与降级的裁决**。变更行进倒排索引反查 → 命中的用例集合即推荐集；任何一步档案缺失（无 `.coverage`、无上下文数据）都改判全量。

两条退出码语义严格区分：退出码 2 = 无数据（降级全量），「推荐为空」= 变更行零覆盖（漏测风险清单）——后者不是错误，是反向驱动补测的入口（`uncovered_lines` 字段）。


**验收断言**。推荐 ≤ 全量 50% 且 ≥1 条——压缩比是精准测试的 ROI 指标，
推荐集接近全量时收益不足以覆盖「漏推风险」，不如全量（阈值进配置随数据校准）。

## Pitfalls & Q&A

踩坑清单：

- **忘了加 `--cov-context=test`**。现象：档案有总量、反查全空，推荐恒为空。
  解法：apply 步骤固定带参数，自检里校验上下文存在。
- **上下文 `|run` 后缀没剥**。现象：推荐集的 node id 带杂质，复现命令跑不起来。
  解法：解析时剥离相位标记。
- **import 期执行的行算给所有用例**。现象：文件头常量行的「覆盖者」是全量
  用例集合。解法：过滤模块加载期空上下文 `''`。
- **把「无数据」当「无风险」**。现象：档案缺失时推荐空集，流水线直通。
  解法：退出码 2 + 降级全量，宁全量、不瞎推。

深入问答：

- **Q：档案过期了怎么办（档案建完代码又改了）？**
  行号会漂移——这是运行时路线的头号工程问题。生产做法：每次 CI 全量跑时
  自动刷新档案，档案永远反映「上一次全量」的世界。diff 行号与档案行号错位时
  按「无覆盖」保守处理，落入漏测风险提示。
- **Q：新增的行（不只是修改）没有历史覆盖，推荐什么？**
  新增行必然无上下文 → 落入「漏测风险」清单。正确输出是两条：受影响存量
  用例 + 「新增行需补测」清单——这也是精准测试反向驱动补测的入口。
- **Q：和项目 3 门禁怎么协同？**
  门禁回答「必须测什么」（coverage_total ≥90%），精准测试回答「这次最少测
  什么」。两者共用 labs/13 套件与 store 口径：PR 上跑推荐集 + 增量覆盖率
  卡点（项目 24），夜间全量刷新档案。
- **Q：测试顺序依赖会不会让档案失真？**
  会——档案记录的是「那次全量」里的执行顺序。labs/13 的教训
  （database is locked）说明顺序敏感套件的档案要按固定顺序
  （如 xdist 分发序）采集，否则推荐集会漏掉「只有排在后面才触发的路径」。

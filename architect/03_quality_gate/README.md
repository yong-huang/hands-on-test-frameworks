# 03 · 质量门禁引擎：门禁不是口号，是退出码

> 策略文档写得再好（[02 风险策略](../02_risk_strategy/README.md) 的准出标准），不能在流水线上
> 会红会绿就只是墙上的字。本实验把准出标准翻译成**规则引擎**：指标可采集、阈值可配置、
> 裁决可解释，最后落到 CI 能用的退出码。面试必考「质量红线怎么定、怎么推」——
> 本实验的答案是一条命令：`python gate.py; echo $?`。清单第 3/28 项。

## 1. 为什么需要它

- **门禁的语言是退出码**：报告说「覆盖率不足」没人怕，CI 挡住合并才是门禁。
- **无数据不许盲过**：required 规则缺数据 = FAIL——「指标系统挂了所以放行」是门禁被
  架空的第一步；非 required 缺数据则如实标注「未采集」。
- **规则与代码分离**：改阈值不改代码；评审吵规则文件而不是引擎实现。

13/20 号实验的未来产物——现在如实「未采集」，届时自动接入。

## 3. 快速开始

```bash
cd architect/03_quality_gate
./quality_gate.sh apply     # 自检 + 默认规则跑门禁（应 PASS）
./quality_gate.sh observe   # 报告表 → 变异演示(阈值 90→100) → FAIL 证据
./quality_gate.sh clean
```

默认规则实测输出（PASS，退出码 0）：

```
| 规则 | 说明 | 实测 | 阈值 | 裁决 | required | 备注 |
|:---|:---|:---:|:---:|:---:|:---:|:---|
| coverage_total | SUT 数据层行覆盖率 | 98 | 90 | PASS | 是 | 实测 98 >= 90 |
| tests_green | 门禁套件全绿（0 failed / 0 error） | True | True | PASS | 是 | 实测 True is_true True |
| severe_defects | Sev1/Sev2 未关闭缺陷数 | 0 | 0 | PASS | 是 | 实测 0 <= 0 |
| flaky_rate | 主干 flaky 用例率（%） | — | 2 | SKIP（未采集） | 否 | 数据源不存在——下游项目未产出，不编造 |
| perf_p95_ms | 下单接口 P95 延迟 (ms) | — | 800 | SKIP（未采集） | 否 | 数据源不存在——下游项目未产出，不编造 |
```

变异演示（observe 步真实执行）：覆盖率阈值 90→100 后重跑：

```
裁决：❌ FAIL · 耗时 0.5s · 退出码 1
| coverage_total | SUT 数据层行覆盖率 | 98 | 100 | FAIL | 是 | 实测 98 >= 100 |
>>> 严格规则退出码 = 1（非 0 即 CI 拦截）
```

## 4. 核心概念

### 4.1 规则四要素
`metric`（哪个采集器）+ `field`（采什么值）+ `op/threshold`（怎么比）+ `required`
（没数据算不算失败）。前三者表达「红线是什么」，required 表达「数据链路的严肃性」。

### 4.2 采集适配器化
三个 adapter：`suite_run`（一次 pytest 运行同时产出覆盖率与绿榜——覆盖率不是独立指标，
是套件运行的副产品）、`defects`（缺陷库导出替身，只数 Sev1/2 且 open）、`report`
（读下游实验的 JSON 产物）。新增指标 = 新 adapter，裁决器不动。

### 4.3 覆盖率度量的对象选择
度量目标选 SUT 数据层 `store` 模块，采集套件选 labs/13（进程内直连数据层）——**对哪个
模块、用哪些用例算覆盖率，本身就是门禁设计决策**，报告里必须写清（否则 98% 无从谈起）。

## 5. YAML 关键字段

| 字段 | 为什么 | 坑 |
|:---|:---|:---|
| `required` | 无数据时的裁决语义 | 全设 true 会因下游未产出而永久红；全设 false 则门禁形同虚设 |
| `coverage_suite`/`coverage_target` | 说清 98% 是「谁对谁」的覆盖率 | 换套件不换阈值，数字立刻失真 |
| `op` | 支持 >=/<=/is_true | 阈值方向写反（延迟用 >=）是最蠢也最常见的错 |
| `source` | 下游产物相对路径 | 缺文件时引擎要如实 SKIP/FAIL，绝不能按 0 分糊弄 |

## 7. 深入要点

**Q1：门禁太严阻塞交付怎么办？** 三级缓冲：required 分级（本次 flaky/性能就是非 required）、
豁免流程（清单项目 24 的豁免状态机）、阈值随策略迭代（P0/P1 功能不同阈值）。但「无数据
放行」永远不进缓冲——那是绕过门禁的万能钥匙。

**Q2：为什么 flaky 率和性能预算现在就进规则？** 门禁的价值在于「规则先于数据存在」：
13/20 号实验产出报告的那一刻，规则自动生效——这演示了门禁体系的**可扩展路径**，
也是给后续项目预埋的接线（`source` 路径就是接口契约）。

**Q3： Sev1/2 缺陷数为 0 这条规则现实吗？** 现实中必有例外（如大促前豁免），所以缺陷
门禁要配**豁免审批留痕**（项目 24 的状态机模式），而不是把阈值放宽到 3 个——
「允许 3 个严重缺陷上线」和「特殊情况审批放行」是两种质量文化。

**Q4：门禁套件为什么选 labs/13 而不是全部 20 个 pytest lab？** 门禁要快（0.8s）：
快反馈层只放数据层核心逻辑；全量留给夜间（项目 10 的三层流水线）。门禁套件的选择
就是「快与全」的折中，选什么要写在配置里被人评审。

**Q5：这套引擎和覆盖率工具自带的 `--cov-fail-under` 什么关系？** `--cov-fail-under` 只管
一条规则；门禁引擎管的是**规则集 + 数据链路 + 裁决语义**。labs/05 做过单条覆盖率门禁
（项目 1 审计里那个「默认命令不绿」的发现之一），本实验是把单点门禁升级成体系。

## 8. 总结

策略文档的每条准出标准，现在都对应 gate_rules.yaml 里的一行；引擎 0.8 秒给出
可解释的裁决和 CI 退出码。两条「未采集」规则是给 13/20 号实验预埋的接口——门禁体系
先立骨架、数据逐步接入，正是架构的推进方式。下一篇是清单项目 4「精准测试原型」：
把「回归要跑多久」的问题变成「变更影响多少」的算法题。

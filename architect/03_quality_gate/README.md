# 03 · 质量门禁引擎：门禁不是口号，是退出码

> 策略文档写得再好（[02 风险策略](../02_risk_strategy/README.md) 的准出标准），
> 不能在流水线上会红会绿就只是墙上的字。本实验把准出标准翻译成规则引擎：
> 指标（如覆盖率——自动化测试实际执行到的代码行占模块总行数的比例）可采集、
> 阈值可配置、裁决可解释，最后落到 CI 能用的退出码。
> 读完本篇你能配置一套带「无数据不盲过」语义的门禁，并用一条命令验证它。

## Background

门禁失败的第一种形态是「报告门禁」：每周质量报告里写"覆盖率不足"，
没有人怕它——报告改变不了任何人的合并行为。门禁真正的语言是**退出码**：
CI 挡住合并，红灯出现在提交者自己的终端里。

没有门禁引擎之前，红线散落在各处：覆盖率工具自带一个阈值（labs/05 的
`--cov-fail-under`）、CI 脚本里 grep 一个 "failed"、发版 checklist 里
人工勾一项"严重缺陷清零"。三件事互不知情、口径各异、绕过任何一条都无痕。

把红线收敛成**规则引擎**要回答三个设计问题：指标从哪来（数据链路）、
怎么比（规则四要素）、没数据算什么（裁决语义）。最后一条是门禁被架空
的第一道防线——「指标系统挂了所以放行」就是从这里开始的。

## What

质量门禁引擎是一套可配置的裁决系统：规则文件（yaml）声明红线，
采集适配器从各数据源取数，引擎逐条裁决（实测 vs 阈值），
产出报告 + 退出码。

可以把引擎想成机场安检的判读台：规则是"液体不超 100ml"（阈值），探测器是采集适配器（X 光机、液体检测仪），判读输出只有放行/拦截两种，且每一条拦截都要能指着数据说清为什么。

但和安检不同的是，「探测器坏了」在这里有明确语义：required 规则缺数据 = FAIL，非 required 缺数据如实标注「未采集」——**无数据不许盲过**。


规则四要素：`metric`（哪个采集器）+ `field`（采什么值）+
`op/threshold`（怎么比）+ `required`（没数据算不算失败）。
前三者表达「红线是什么」，required 表达「数据链路的严肃性」。

## When to Use

典型场景：

- 合并前自动拦截：覆盖率、套件绿、严重缺陷数三类红线进流水线。
- 指标体系分步建设：先立规则骨架，下游数据产出后自动接入
  （本实验给 flaky/性能预埋的两条规则就是这种接法）。
- 质量规则评审：规则文件进 git，改阈值走代码评审。

何时不用：单人仓库一条 `--cov-fail-under` 就够时，不必上引擎；
指标数据源还没有任何一处自动化产出时，先建数据链路再谈门禁——
引擎没有数据喂，只剩一副空壳。

同类方式对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 工具自带阈值（`--cov-fail-under`） | 单条规则，无跨指标裁决 | 单一红线 |
| CI 脚本手写判断 | 能跑，但规则藏进脚本难评审 | 一次性流水线 |
| 门禁引擎 | 规则集 + 数据链路 + 裁决语义集中可配 | 多红线、多数据源 |

## Quick Start

前置条件：labs/13 的门禁套件可跑（覆盖率数据源）；纯离线。

```bash
cd architect/03_quality_gate
./quality_gate.sh apply     # 自检 + 默认规则跑门禁（应 PASS）
./quality_gate.sh observe   # 报告表 → 变异演示(阈值 90→100) → FAIL 证据
./quality_gate.sh clean
```

默认规则实测输出（PASS，退出码 0）：

```
| 规则 | 说明 | 实测 | 阈值 | 裁决 | required | 备注 |
|:---|:---|:---:|:---:|:---:|:---:|:---|
| coverage_total | SUT（被测系统）数据层行覆盖率 | 98 | 90 | PASS | 是 | 实测 98 >= 90 |
| tests_green | 门禁套件全绿（0 failed / 0 error） | True | True | PASS | 是 | 实测 True is_true True |
| severe_defects | Sev1/Sev2 未关闭缺陷数 | 0 | 0 | PASS | 是 | 实测 0 <= 0 |
| flaky_rate | 主干 flaky 用例率（flaky：时好时坏的不稳定用例） | — | 2 | SKIP（未采集） | 否 | 数据源不存在——下游项目未产出，不编造 |
| perf_p95_ms | 下单接口 P95 延迟 (ms) | — | 800 | SKIP（未采集） | 否 | 数据源不存在——下游项目未产出，不编造 |
```

变异演示（observe 步真实执行）：覆盖率阈值 90→100 后重跑：

```
裁决：❌ FAIL · 耗时 0.5s · 退出码 1
| coverage_total | SUT 数据层行覆盖率 | 98 | 100 | FAIL | 是 | 实测 98 >= 100 |
>>> 严格规则退出码 = 1（非 0 即 CI 拦截）
```

诚实预期：默认规则应 PASS（退出码 0），两条「未采集」规则如实 SKIP
而不是编造数据；变异后严格规则退出码 1。门禁套件全绿耗时约 0.8 秒。

## How It Works

**采集适配器化**。

三个 adapter：`suite_run`（一次 pytest 运行同时产出覆盖率与绿榜——覆盖率不是独立指标，是套件运行的副产品）、`defects`（缺陷库导出替身，只数 Sev1/2 且 open）、`report`（读下游实验的 JSON 产物）。

新增指标 = 新 adapter，裁决器不动。


**覆盖率度量的对象选择**。度量目标选 SUT 数据层 `store` 模块，采集套件选
labs/13（进程内直连数据层）——**对哪个模块、用哪些用例算覆盖率，本身就是
门禁设计决策**，报告里必须写清（否则 98% 无从谈起）。

YAML 关键字段（这段在做什么：裁决语义与数据链路的声明）：

| 字段 | 为什么 | 坑 |
|:---|:---|:---|
| `required` | 无数据时的裁决语义 | 全设 true 会因下游未产出而永久红；全设 false 则门禁形同虚设 |
| `coverage_suite`/`coverage_target` | 说清 98% 是「谁对谁」的覆盖率 | 换套件不换阈值，数字立刻失真 |
| `op` | 支持 >=/<=/is_true | 阈值方向写反（延迟用 >=）是最蠢也最常见的错 |
| `source` | 下游产物相对路径 | 缺文件时引擎要如实 SKIP/FAIL，绝不能按 0 分糊弄 |

**规则先于数据存在**。flaky/性能两条规则现在就进规则文件：
13/20 号实验产出报告的那一刻，规则自动生效——`source` 路径就是接口契约，
这演示了门禁体系的可扩展路径，也是给后续项目预埋的接线。

## Pitfalls & Q&A

踩坑清单：

- **阈值方向写反**。现象：延迟指标用 `>=` 后永远 PASS 或永远 FAIL。
  解法：规则评审盯 `op` 与指标语义的匹配。
- **required 全开或全关**。现象：门禁永久红，或形同虚设。
  解法：按数据链路成熟度分级，下游未产出的先 `required: false` + 如实标注。
- **无数据时按 0 分糊弄**。现象：数据源挂了，指标按 0 参与裁决。
  解法：缺文件必须 SKIP/FAIL，绝不默认值顶上。

深入问答：

- **Q：门禁太严阻塞交付怎么办？**
  三级缓冲：required 分级（本次 flaky/性能就是非 required）、豁免流程
  （项目 24 的豁免状态机）、阈值随策略迭代（P0/P1 功能不同阈值）。
  但「无数据放行」永远不进缓冲——那是绕过门禁的万能钥匙。
- **Q：为什么 flaky 率和性能预算现在就进规则？**
  门禁的价值在于「规则先于数据存在」：13/20 号实验产出报告的那一刻，
  规则自动生效——这是给后续项目预埋的接线，也是可扩展路径的实证。
- **Q：Sev1/2 缺陷数为 0 这条规则现实吗？**
  现实中必有例外（如大促前豁免），所以缺陷门禁要配**豁免审批留痕**
  （项目 24 的状态机模式），而不是把阈值放宽到 3 个——「允许 3 个严重
  缺陷上线」和「特殊情况审批放行」是两种质量文化。
- **Q：门禁套件为什么选 labs/13 而不是全部 20 个 pytest lab？**
  门禁要快（0.8s）：快反馈层只放数据层核心逻辑；全量留给夜间
  （项目 10 的三层流水线）。门禁套件的选择就是「快与全」的折中，
  选什么要写在配置里被人评审。
- **Q：这套引擎和覆盖率工具自带的 `--cov-fail-under` 什么关系？**
  `--cov-fail-under` 只管一条规则；门禁引擎管的是**规则集 + 数据链路 +
  裁决语义**。labs/05 做过单条覆盖率门禁，本实验是把单点门禁升级成体系。

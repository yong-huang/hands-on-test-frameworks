# 27 · 效能全景看板：一条命令，全部证据

> 「你们测试体系整体什么样」——碎片化的讲述不如一块看板。本实验把前序项目的
> 产物聚合起来：`make architect-report` 一条命令，6 个面板、11 个指标、
> 37 秒跑完；缺失的面板明示原因（连轻量再生成都不支持的才叫缺失）。
> 这是 01-26 全部项目的**集成点**：每个产物的 JSON 就是看板的数据契约。

## Background

效能数据散在 20+ 个目录的 reports/ 里，没有聚合就等于没有——
评审会上的讲述全靠人肉记忆和临场翻目录。

「一条命令」是体系可运营的最低标准：看板要能挂进周会、挂进发版
checklist，做不到一条命令的看板，三个月后必然没人再跑——维护成本
是看板的隐性杀手。

缺失明示是诚实底线：看板的价值在「每个数字都有出处」，
编数的看板是负资产。

## What

效能全景看板是一套跨项目聚合系统：**JSON 即接口契约**——六路采集器
各读一个兄弟项目的产物；auto 模式下缺失的产物自动用对应项目的轻量模式
再生成（标注「本轮生成」）；no-auto 模式只读不生成，缺什么明示什么。

可以把看板想成驾驶舱仪表盘：时速（容量）、油量（门禁状态）、
故障灯（flaky 率——时好时坏的不稳定用例占比）来自车上的各个传感器
（兄弟项目的产物 JSON），仪表盘只读不造数；某传感器没接上，对应仪表
显示"—"并标注原因，而不是显示 0。

但和仪表盘不同的是，这台"仪表盘"跨了 6 辆"车"——传感器（兄弟项目产物）
各自独立演进，接口（JSON 字段）变了仪表会静默失灵，所以要靠采集器字典
与缺失面板兜住。

**auto 与 no-auto 两档语义**：auto =「给能给的，缺的现场生成」
（一次性能全貌）；no-auto =「只读不写」（纯展示，适合只读环境/归档）。
两档共享同一渲染器，区别只在采集器的行为。

## When to Use

典型场景：

- 周会/发版前检查：`make architect-report` 一条命令出当前全貌。
- 体系健康度巡视：某个面板长期缺失说明对应实践没在运行——
  看板兼任「机制活性监视器」（项目 26 的伏笔在此兑现）。
- 汇报与述职：六面板十一指标的全貌页，比口头讲述有说服力。

何时不用：只需要单一项目结果时直接看该项目的 reports/；
全量聚合一次（37s）对单点排查是浪费——看板是全貌工具不是排错工具。

实测输出（2026-09-20，6 面板 11 指标，聚合 37.5s）：


## Quick Start

前置条件：labs/00 体检通过；脚本自动起 SUT（20 压测容量的前置）。

```bash
cd architect/27_panorama_board
./panorama_board.sh apply     # 起 SUT（20 压测容量的前置）
./panorama_board.sh observe   # auto 聚合 → no-auto 缺失演示 → make 入口校验
./panorama_board.sh clean
# 或仓库根：make architect-report
```

诚实预期：auto 聚合应产出 6 面板 11 指标（缺失产物由轻量模式现场生成并
标注「本轮生成」）；no-auto 演示应看到「数据缺失（需 SUT 在 :8899）」
这样的明示——提示要指向具体动作，而不是只说缺了。

关键设计（这段在做什么：聚合可信度的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 采集器字典化 | 新面板=加一条 (项目， 产物， 提取器) | 兄弟项目改 JSON 结构会静默失败——解析异常也进「缺失」面板 |
| 轻量模式再生成 | 13 用 3 轮而非 10 轮、01 只计数不计时 | 全量再生成让「一条命令」变成一小时 |
| 缺失面板带原因 | 「为什么缺」比「缺了」更有用 | 提示要指向具体动作（起 SUT/先跑 X） |
| 聚合耗时入看板 | 37s 本身是运营成本 | 不标耗时的看板会悄悄膨胀 |

## How It Works

**JSON 即接口契约**。看板与兄弟项目之间唯一的耦合点是产物 JSON 的字段
路径（写在采集器字典里）。各项目的 reports 结构变更必须同步采集器
——这就是跨项目数据契约的维护纪律。

**递归执行的教训（本次踩坑）**。make 入口如果在 observe 步骤里**完整执行**
make architect-report，会递归触发本实验自身的全流程
（apply→observe→再 make→…），数十秒变无限。入口校验（grep 目标存在）
与入口执行要分开——演示脚本不等于自指执行。

**看板必须保留说 no 的能力**。刻意包含「形状判定：过渡形态 ⚠️」这类
负面结论——只聚合 GREEN 指标的看板是广告牌。

## Pitfalls & Q&A

踩坑清单：

- **自指执行**。现象：make 入口在演示里完整跑 make，无限递归。
  解法：入口校验（目标存在）与入口执行分开。
- **兄弟项目改 JSON 结构**。现象：面板静默变空。
  解法：解析异常也进「缺失」面板并带原因，不让静默失败溜走。
- **全量再生成拖垮聚合**。现象：一条命令变成一小时。
  解法：轻量模式（13 用 3 轮、01 只计数不计时）。
- **聚合耗时无标注**。现象：看板悄悄膨胀没人察觉。
  解法：耗时本身进看板。

深入问答：

- **Q：为什么聚合 01/02/03/13/20/22 六个？**
  覆盖四个视角：资产（01 分层/02 策略）、质量门禁（03/22）、稳定性
  （13 flaky）、容量（20 压测）。其余项目的产物是事件型而非状态型，
  适合进趋势面板而非状态面板——v2 扩展方向已留好。
- **Q：面板缺失是坏事吗？**
  不是，是**体系健康度的信号**：某个面板长期缺失说明对应实践没在运行
  ——看板因此兼任了「机制活性监视器」。
- **Q：距离「测试中台」还差什么？**
  差三样：数据沉淀（时序库替代一次性 JSON）、多团队隔离（租户模型）、
  自助分析（下钻查询）。但骨架——数据契约、采集、渲染、缺失语义
  ——本实验已经立起来，中台是它的规模化版本。

# 27 · ⛓️ 效能全景看板：一条命令，全部证据

> 面试官问「你们测试体系整体什么样」——碎片化的讲述不如一块看板。本实验把前序项目
> 的产物聚合起来：`make architect-report` 一条命令，6 个面板、11 个指标、37 秒跑完；
> 缺失的面板明示原因（连轻量再生成都不支持的才叫缺失）。这是 01-26 全部项目的
> **集成点**：每个产物的 JSON 就是看板的数据契约。清单第 27/28 项。

## 1. 为什么需要它

- 效能数据散在 20+ 个目录的 reports/ 里，没有聚合就等于没有；
- 「一条命令」是体系可运营的最低标准——看板要能挂进周会、挂进发版 checklist；
- 缺失明示是诚实底线：看板的价值在「每个数字都有出处」，编数的看板是负资产。


## 4. 核心概念

### 4.1 JSON 即接口契约
看板与兄弟项目之间唯一的耦合点是产物 JSON 的字段路径（写在采集器字典里）。各项目
的 reports 结构变更必须同步采集器——这就是跨项目数据契约的维护纪律。

### 4.2 auto 与 no-auto 两档语义
auto = 「给能给的，缺的现场生成」（一次性能全貌）；no-auto = 「只读不写」（纯展示，
适合只读环境/归档）。两档共享同一渲染器，区别只在采集器的行为。

### 4.3 递归执行的教训（本次踩坑）
make 入口如果在 observe 步骤里**完整执行** make architect-report，会递归触发本实验
自身的全流程（apply→observe→再 make→…），数十秒变无限。入口校验（grep 目标存在）
与入口执行要分开——演示脚本不等于自指执行。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 采集器字典化 | 新面板=加一条 (项目， 产物， 提取器) | 兄弟项目改 JSON 结构会静默失败——解析异常也进「缺失」面板 |
| 轻量模式再生成 | 13 用 3 轮而非 10 轮、01 只计数不计时 | 全量再生成让「一条命令」变成一小时 |
| 缺失面板带原因 | 「为什么缺」比「缺了」更有用 | 提示要指向具体动作（起 SUT/先跑 X） |
| 聚合耗时入看板 | 37s 本身是运营成本 | 不标耗时的看板会悄悄膨胀 |

## 7. 深入要点

**Q1：为什么聚合 01/02/03/13/20/22 六个？** 覆盖四个视角：资产（01 分层/02 策略）、
质量门禁（03/22）、稳定性（13 flaky）、容量（20 压测）。其余项目（04/05/…/26）的
产物是事件型而非状态型，适合进趋势面板而非状态面板——v2 扩展方向已留好。

**Q2：面板缺失是坏事吗？** 不是，是**体系健康度的信号**：某个面板长期缺失说明对应
实践没在运行——看板因此兼任了「机制活性监视器」（项目 26 Q4 的伏笔在此兑现）。

**Q3：看板会不会变成「只报喜」？** 会，如果只聚合 GREEN 指标。本实验刻意包含
「形状判定：过渡形态 ⚠️」这类负面结论——看板必须保留说 no 的能力，否则是广告牌。

**Q4：一条命令的工程意义？** 「可运营」的最小定义：任何人、任何时间、一条命令得到
当前全貌。做不到一条命令的看板，三个月后必然没人再跑——维护成本是看板的隐性杀手。

**Q5：距离「测试中台」还差什么？** 差三样：数据沉淀（时序库替代一次性 JSON）、
多团队隔离（租户模型）、自助分析（下钻查询）。但骨架——数据契约、采集、渲染、
缺失语义——本实验已经立起来，中台是它的规模化版本。

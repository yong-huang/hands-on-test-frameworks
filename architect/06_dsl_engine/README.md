# 06 · YAML DSL 接口用例引擎：降门槛的代价算得清吗

> 「让业务同学也能写接口用例」是每家测试平台都要回答的需求。本实验把
> httprunner 的思想做成 mini 版引擎：YAML 声明用例（变量/提取/断言），
> 引擎执行并把失败定位到 YAML 行号——平台用户不读 traceback。
> 做完本篇，「DSL 还是代码写用例」的权衡就有了一手依据。

## Background

接口用例的默认形态是代码（pytest + httpx），门槛是真实的：业务同学要会
Python、要懂 fixture、要能读 traceback。测试平台的回答通常是 DSL——
用声明式语言把「发请求、提变量、断言」压到人人可写的形态。

但 DSL 的代价常被回避：表达力上限（复杂流程控制在 YAML 里会变成图灵
完备的噩梦）、调试体验（报错隔了一层引擎）、引擎自身的维护成本。
这些代价不做一遍根本量不出来——**边界在哪，做完才知道**。

平台化前的必答题是报错给用户看什么：`cases.yaml:17` 和 40 行 traceback，
是两种产品。本实验把行号定位做成引擎的核心能力之一。

## What

YAML DSL 接口用例引擎是一个执行声明式接口用例的迷你引擎：
一条用例 = **替换变量 → 发请求 → 提取回写 → 逐条断言**。

可以把 DSL 引擎想成自动售货机：用户只按按钮（写 YAML 声明想要什么），
机器内部的机械臂（引擎）负责取货、掉落、找零。但和售货机不同的是，
故障时它必须告诉用户「哪一行按错了」——行号定位就是这台机器的显示屏。

本实验的引擎约 180 行：替换/执行/提取/断言/定位五段；10 条冒烟用例
74 行 YAML——与 pytest 等价实现（labs/12 的 211 行）的行数对比是 3:1。

## When to Use

典型场景：

- 业务同学参与接口冒烟：声明式用例 + 行号报错，不要求编程能力。
- 测试平台的心脏：cases.yaml 换成表单存储、行号定位换成页面高亮、
  CLI 换成调度器——平台是 DSL 的产品化外壳（项目 27 的全景）。
- 用例规模审计：DSL 层的用例清单天然结构化，盘点覆盖比翻代码快。

何时不用：复杂流程控制（条件/循环/跨服务编排）为主的场景——这些在
YAML 里写得难看且难调试，代码更合适；用例少且只有工程师维护时，
直接 pytest 更轻（省掉引擎这层）。

## Quick Start

前置条件：labs/00 体检通过；脚本自动起 SUT（System Under Test，被测系统）(:8899)。

```bash
cd architect/06_dsl_engine
./dsl_engine.sh apply     # 起 SUT(:8899)
```

诚实预期：10 条应全绿；变异演示把期望 201 改成 200 后应恰好 1 failed，
且报错定位到 `cases.yaml:17`——改 YAML 即可修复，全程不需要读 Python 栈。

YAML 关键字段（这段在做什么：声明层的四个核心字段与类型语义）：

| 字段 | 作用 | 坑 |
|:---|:---|:---|
| `variables` | 会话级变量表，支持 `${__uuid}` | 全局一个 uuid：同用户贯穿全链路是特性不是 bug |
| `extract` | 响应 → 变量（写回共享字典） | 忘了会话级语义，用例间就传不了值（本次踩过） |
| `validate.eq` | `[路径, 期望值]`，类型敏感 | 期望值写 `200`（int）不是 `"200"` |
| `$.headers.x-total-count` | 头键全小写进信封 | 大小写敏感查 `X-Total-Count` 会 KeyError |

## How It Works

**会话级变量与类型保留**。`${order_id}` 整串引用变量时保留原始类型（int），混在长字符串里才 str 化拼接——否则 `$.json.id == "${order_id}"`会变成 `3 == "3"` 永假。

**类型语义是 DSL 引擎的隐形地基**：YAML 一切皆字符串的直觉会让 `qty: "2"` 发给 Pydantic 后端仍能过（强转），但断言侧`3 == "3"` 永假——同一份宽松在请求侧无害、在断言侧致命。

引擎的 fullmatch 类型保留是把这些坑一次性埋掉。


**响应信封与迷你 jsonpath**。响应统一装进信封：
`$.status_code / $.headers.*（全小写）/ $.json.* / $.text`，
提取与断言共用一个 `$.a.b[0]` 迷你解析器。刻意不引 jsonpath-ng：
依赖越少，平台越好部署。

**行号定位：DSL 的产品力所在**。断言失败时在 YAML 原文里反查 `name:`
所在行，报错格式固定为 `文件:行号（用例名）+ 实际 vs 期望`。引擎内部异常
（连接拒绝等）同样归位到用例行号——**用户永远不需要看 Python 栈**。

**fail-fast 的取舍**。一条用例首个失败断言即停——定位清晰优先于断言齐全。
要「全量断言收集」的平台语义，把 `run_validate` 的短路改成收集即可，
这是一行改动的产品决策。

## Pitfalls & Q&A

踩坑清单：

- **期望值写成字符串**。现象：`eq` 断言永假（`3 == "3"`）。
  解法：类型敏感——期望 `200`（int）不是 `"200"`。
- **头键大小写**。现象：`X-Total-Count` 查询 KeyError。
  解法：信封统一小写，用 `x-total-count`。
- **忘了 extract 的会话级语义**。现象：跨用例传值失败（本次踩过）。
  解法：extract 写回共享字典，后续用例直接引用。
- **把 DSL 写成图灵完备语言**。现象：YAML 里长出循环与条件，没人维护得动。
  解法：断言集按「90% 断言模式」设计最小集，长尾留给 hook 扩展点。

深入问答：

- **Q：DSL 省了 137 行，代价是什么？**
  三笔账：表达力上限（复杂编排写不了或写得难看）、调试体验（引擎报错
  隔了一层，依赖行号定位做产品补偿）、引擎本身的维护成本（本实验 180 行
  只是最小集）。用例少用代码，规模大了上平台——边界由团队构成决定，
  不由技术审美决定。
- **Q：为什么断言集只有 eq/contains/len_le/exists 四个？**
  断言集是 DSL 的「标准库」，每加一个都有文档/测试/用户心智成本。
  按最小集设计，长尾需求留给 hook（后续可加 `python:` 扩展点），
  别把 DSL 变成差劲的编程语言。
- **Q：和「低代码测试平台」什么关系？**
  本引擎就是平台的心脏：cases.yaml 换成表单存储、行号定位换成页面高亮、
  CLI 换成调度器——「从 0 到 1 搭测试平台」的骨架就是这个（项目 27 全景）。

# 24 · 新代码覆盖率卡点与豁免流：推动写单测，靠机制不靠口号

> 「怎么推动研发写单测」是架构师的高频开放题，高分答案是**机制组合**：
> 门禁卡增量（新账零容忍）+ 豁免流程留痕（紧急通道不堵死）+ 工具降本
> （写测试足够容易）。本实验把机制做成可运行 demo：一版零覆盖的新函数 diff
> 被 bot 拦截并列出未覆盖行；豁免申请→审批→放行全程留痕，
> 放行携带豁免徽章。

## Background

存量覆盖率低不可怕，可怕的是增量也不覆盖。全量阈值的老路走不通：
存量 60% 的仓库设 80% 全量阈值，逼出来的不是补测试，而是删代码、
写无断言测试——「新账新办法、老账按风险慢慢还」是唯一推得动的路径。

没有豁免流程的门禁，会在第一次大促前夜被整体拆除：紧急修复必须能走，
但走了必须留痕——豁免是状态机不是口头承诺。

还有一层产品思维：bot 评论要给人整改路径（未覆盖行清单 + 怎么补），
不是甩一句「覆盖率不足」。推动机制的成败一半在「被拦的人看到什么」。

## What

新代码覆盖率卡点是一套增量门禁机制：**git diff 新增行 ∩ 套件覆盖行 =
增量覆盖**——只对「你新写的那几行」负责，存量烂账不追。
未达标 → bot 拦截评论（现状数值 + 未覆盖行 + 整改建议）；
紧急通道走豁免状态机（申请→审批→留痕），放行带徽章可审计。

可以把增量卡点想成垃圾分类的新规：只检查今天新产生的垃圾（diff 新增行），历史堆积（存量）另立清运计划——新规第一天就能执行，不逼居民先清完十年的旧账。

但和新规不同的是，「例外通行证」要审批、要登记、有过期时间——豁免后的放行是 PASS_EXEMPT 徽章，与干净的 PASS 是两种裁决。


**增量覆盖率的分子分母**：分子 = 新增行中「被套件执行过」的行；
分母 = diff 全部新增行。与全量覆盖率解耦——存量 60% 不影响拦截判断，
团队从 30% 起步也能立即上卡点（只盯新代码）。

## When to Use

典型场景：

- 推动单测落地的团队：增量卡点立即生效，不需要等存量补完。
- 紧急修复通道：热修 PR 走豁免审批，补偿计划挂工单，留痕可审计。
- 覆盖率治理的度量：豁免率（豁免 PR/总 PR）本身是指标——
  豁免泛滥是门禁失效的领先信号。

何时不用：团队已有成熟单测文化、PR 全带测试时，卡点是冗余保险；
存量近零且无人投入的维护期项目，先谈资源再谈卡点——
机制推不动是因为没有投入承诺，不是机制不对。

实测输出（节选）：

```
② CI bot 裁决：9% < 80% → 拦截
   ## ❌ 增量覆盖率未达标：9% < 80%
   以下新增行没有任何测试覆盖：
   - 第 92 行（store.py）…（共 10 行）
   整改建议：为新逻辑补单元测试（mock 外部依赖，参考 labs/04 模式）；…
   裁决：BLOCK，退出码 1
③ 豁免流：申请（大促热修，补偿计划挂 JIRA-233）→ qa-lead 审批 →
   ⚠️ 放行携带豁免徽章，豁免记录永久留痕可审计（PASS_EXEMPT，退出码 0）
   审计留痕：requested → approved by qa-lead
```

## Quick Start

前置条件：labs/13 套件与 SUT store 模块（基线覆盖的数据源）；
脚本 trap 保证 store.py 永远被还原。

```bash
cd architect/24_coverage_gate
./coverage_gate.sh apply     # 建 PR 前基线覆盖（labs/13 × store）
./coverage_gate.sh observe   # 模拟 PR（零测试新函数）→ 拦截 → 豁免流 → 还原
./coverage_gate.sh clean     # trap 保证 store.py 还原
```

诚实预期：模拟 PR（零测试新函数）应被拦截，bot 评论精确列出未覆盖行（到行号）；豁免流走完 申请→审批→放行 后应带 PASS_EXEMPT 徽章、审计留痕完整。

注意 demo 里新函数覆盖率是 9% 而不是 0%——因为覆盖数据取自套件运行，demo 里 observe 步的手动调用不构成测试（未纳入套件的调用不进覆盖），这正说明「进程内冒烟不算数」。


关键设计（这段在做什么：机制可信度的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 覆盖数据取自套件运行 | 进程内冒烟不算数（未纳入套件的调用不进覆盖） | demo 里 9% 而非 50% 正说明：手动调用不构成测试 |
| 豁免状态机落 JSON | 审计要可机读、可统计豁免率 | 状态只有 approved 没有到期时间=永久后门 |
| trap 还原 store.py | 实验不污染被测仓库 | 忘还原的下次 diff 全乱 |
| 新增行从 diff -U0 解析 | 与 GitHub 的 diff 行号同源 | diff 上下文行不算新增（空格变更不算欠账） |

## How It Works

**豁免是状态机不是口头承诺**。requested → approved（审批人身份进记录）
→ 留痕永久可审计。豁免后的放行带 EXEMPT 徽章（PASS 与 PASS_EXEMPT
是不同裁决），度量上分开统计——豁免率本身也是指标。

**bot 评论是产品界面**。拦截评论三要素：现状数值、未覆盖行清单
（精确到行）、整改路径（怎么补/怎么豁免）——羞辱式评论只会催生绕过技巧。

**与测试平台的联动**。拦截评论里可直接给「一键生成测试骨架」入口
（结合项目 25 的 LLM 用例生成）——把「补测试的成本」降到
「审一段生成的代码」，推动机制的第三根支柱（降本）就有了着落。

## Pitfalls & Q&A

踩坑清单：

- **阈值设 100%**。现象：催生无断言测试和防御性删除。
  解法：80% 留出 getters/防御分支的空间，并配合断言强度审查
  （呼应项目 25）。
- **豁免没有到期时间**。现象：永久后门。解法：豁免带有效期，
  过期自动回收。
- **diff 上下文行算欠账**。现象：改个空格也被拦。
  解法：新增行从 `diff -U0` 解析，与 GitHub 行号同源。
- **实验污染被测仓库**。现象：store.py 忘还原，下次 diff 全乱。
  解法：trap EXIT 双保险（项目 04 同款纪律）。

深入问答：

- **Q：老人历史代码怎么办？**
  新账新办法（增量卡点立即生效），老账按风险排序补（项目 2 策略：
  P0 功能的存量模块优先），并用 01 审计的分层画像追踪进度——
  「新账不管旧账」的正确姿势是旧账有偿还计划，而不是永久豁免。
- **Q：豁免泛滥怎么治？**
  三个度量：豁免率（豁免 PR/总 PR）、豁免存续时长、豁免后缺陷率
  （豁免代码后来出事故的比例）。豁免率进周报——机制防呆靠的是
  「豁免也要被看见」。
- **Q：为什么不用 diff-cover 现成工具？**
  diff-cover 只算数字；本实验的完整机制包含 bot 评论产品化（行级清单+
  建议）、豁免状态机、豁免徽章语义——工具算数，机制管人，
  架构师的活儿在后者。

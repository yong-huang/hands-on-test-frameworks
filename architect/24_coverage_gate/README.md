# 24 · 新代码覆盖率卡点与豁免流：推动写单测，靠机制不靠口号

> 「怎么推动研发写单测」是架构师面试的必问开放题，高分答案是**机制组合**：
> 门禁卡增量（新账零容忍）+ 豁免流程留痕（紧急通道不堵死）+ 工具降本（写测试足够容易）。
> 本实验把机制做成可运行 demo：一版零覆盖的新函数 diff 被 bot 拦截并列出未覆盖行；
> 豁免申请→审批→放行全程留痕，放行携带豁免徽章。清单第 24/28 项。

## 1. 为什么需要它

- 存量覆盖率低不可怕，可怕的是增量也不覆盖——「新账新办法、老账按风险慢慢还」
  是唯一推得动的路径（全量阈值会逼出删代码）；
- 豁免必须留痕：没有豁免流程的门禁，会在第一次大促前夜被整体拆除；
- bot 评论要给人整改路径（未覆盖行清单 + 怎么补），不是甩一句「覆盖率不足」。

心智模型一句话：**git diff 新增行 ∩ 套件覆盖行 = 增量覆盖**——只对「你新写的那几行」
负责，存量烂账不追。未达标 → bot 拦截评论（未覆盖行+建议）；紧急通道走豁免状态机
（申请→审批→留痕），放行带徽章可审计。

## 3. 快速开始

```bash
cd architect/24_coverage_gate
./coverage_gate.sh apply     # 建 PR 前基线覆盖（labs/13 × store）
./coverage_gate.sh observe   # 模拟 PR（零测试新函数）→ 拦截 → 豁免流 → 还原
./coverage_gate.sh clean     # trap 保证 store.py 还原
```

实测输出（节选）：


## 4. 核心概念

### 4.1 增量覆盖率的分子分母
分子 = 新增行中「被套件执行过」的行；分母 = diff 全部新增行。与全量覆盖率解耦——
存量 60% 不影响拦截判断，团队从 30% 起步也能立即上卡点（只盯新代码）。

### 4.2 豁免是状态机不是口头承诺
requested → approved（审批人身份进记录）→ 留痕永久可审计。豁免后的放行带 EXEMPT
徽章（PASS 与 PASS_EXEMPT 是不同裁决），度量上分开统计——豁免率本身也是指标
（豁免泛滥=门禁失效的领先信号）。

### 4.3 bot 评论是产品界面
拦截评论三要素：现状数值、未覆盖行清单（精确到行）、整改路径（怎么补/怎么豁免）。
推动机制的成败一半在「被拦的人看到什么」——羞辱式评论只会催生绕过技巧。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 覆盖数据取自套件运行 | 进程内冒烟不算数（未纳入套件的调用不进覆盖） | demo 里 9% 而非 50% 正说明：手动调用不构成测试 |
| 豁免状态机落 JSON | 审计要可机读、可统计豁免率 | 状态只有 approved 没有到期时间=永久后门 |
| trap 还原 store.py | 实验不污染被测仓库 | 忘还原的下次 diff 全乱 |
| 新增行从 diff -U0 解析 | 与 GitHub 的 diff 行号同源 | diff 上下文行不算新增（空格变更不算欠账） |

## 7. 深入要点

**Q1：为什么阈值 80% 而不是 100%？** 100% 逼出「无断言测试」和「防御性删除」；
80% 留出 getters/防御分支的空间。阈值必须配合「断言强度」审查——只看数字的卡点
一个月就会被废话测试攻陷（呼应项目 25 的 LLM 断言强度评测）。

**Q2：老人历史代码怎么办？** 新账新办法（增量卡点立即生效），老账按风险排序补
（项目 2 策略：P0 功能的存量模块优先），并用 01 审计的分层画像追踪进度——
「新账不管旧账」的正确姿势是旧账有偿还计划，而不是永久豁免。

**Q3：豁免泛滥怎么治？** 三个度量：豁免率（豁免 PR/总 PR）、豁免存续时长、
豁免后缺陷率（豁免代码后来出事故的比例）。豁免率进周报——机制防呆靠的是
「豁免也要被看见」。

**Q4：为什么不用 diff-cover 现成工具？** diff-cover 只算数字；本实验的完整机制
包含 bot 评论产品化（行级清单+建议）、豁免状态机、豁免徽章语义——工具算数，
机制管人，架构师的活儿在后者。

**Q5：这条机制怎么和测试平台联动？** 拦截评论里直接给「一键生成测试骨架」入口
（结合项目 25 的 LLM 用例生成）——把「补测试的成本」降到「审一段生成的代码」，
推动机制的第三根支柱（降本）就有了着落。

## 8. 总结

一版零测试的新函数 diff 被拦（未覆盖行点名到行号），豁免走完审批留痕后带徽章放行
——「推动写单测」从催办变成一个有边界、有逃生门、可审计的机制。下一篇是清单项目
25「LLM 用例生成与质量评测」：AI 生成的测试敢不敢用，先造一台量尺。

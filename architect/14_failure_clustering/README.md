# 14 · 失败聚类与根因归并：先修一个根因，消掉 37 条红

> 一次提交挂 50 条用例，逐条看 traceback 是灾难现场的标准剧本。本实验实现大规模
> 失败管理的正确姿势：**traceback 指纹归一化 → 相似度聚类 → 「先修谁」排序**。
> 实测：50 条模拟失败（3 个真实根因 + 订单号/时间戳/路径噪声）聚成 3 簇
>（37/11/2），每簇纯度 100%，换种子重跑簇数稳定。清单第 14/28 项。

## 1. 为什么需要它

- 失败的价值不在条数在根因：修一个 gateway_timeout，37 条红同时转绿；
- 人眼看 traceback 会先被噪声骗（订单号/时间戳/临时目录每次不同）；
- 「先修谁」需要量化：每簇成员数就是修复的 ROI 排行。

心智模型一句话：**归一化是去掉「每次都不同的噪声」，指纹是留下「每次都相同的病因」**——
数字→N、路径→PATH、hex→HEX、引号内容→'S'，剩下的 异常类型+末帧+消息模板 就是指纹。

## 4. 核心概念

### 4.1 归一化的边界感
噪声替换清单（数字/路径/hex/引号内容）是本工具的灵魂：删多了把「不同根因」合成一簇
（误合并），删少了把「同根因」拆成多簇（碎片化）。两类陷阱各有代价，阈值与清单都该
随真实失败流校准。

### 4.2 二次相似合并
精确指纹只解决「同模板」；不同团队/不同写法的相似 traceback（多一个空行、换一个
变量名）靠 difflib 相似度 ≥0.85 归并。相似度阈值是本工具唯一的重要旋钮。

### 4.3 先修排序 = 修复 ROI
簇大小即收益：修 P1 消 37 红、修 P3 消 2 红——「先修谁」不用吵，排序说话。
这也是向管理层汇报质量事故的标准格式：根因 × 影响面 × 修复状态。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 固定种子生成 | 失败可复现，验收可断言 | 真实失败流的分布漂移要定期重训模板 |
| 簇内真值纯度自检 | 用「聚类器看不见的真值」验收自己 | 生产环境没有真值，用人工抽检替代 |
| 代表 traceback 每簇一条 | 人只看代表，不刷屏 | 代表选取用簇内最长 traceback（信息量最大） |
| difflib 而非编辑距离 | 标准库零依赖，行为可解释 | 超长 traceback 的 O(n²) 需先截断末 20 帧 |

## 7. 深入要点

**Q1：为什么不用 LLM 做失败聚类？** 可以做，但应该是第二层：先用确定性指纹把 50 条
收成 3 簇（便宜、可解释、可复现），再让 LLM 给每簇写「人话根因假设」。跳过第一层
直接 LLM，成本高且每次答案不同——「确定性优先，智能补足」是 AI 工程的通用次序。

**Q2：混簇（一个簇两种根因）怎么办？** 相似度阈值下调必致混簇。治理：簇内抽查发现
混簇 → 对该簇细分（提高阈值或换指纹字段，如带上源文件路径）；报告里纯度自检
（本实验的 purity）就是混簇探测器。

**Q3：测试名参与聚类吗？** 不。test_case_000 和 001 可能是同一根因，test_000 和 002
也可能是两个根因——名字是噪声，traceback 才是证据。用名字聚类是新手最常见的错误。

**Q4：和项目 13 的 flaky 治理怎么衔接？** 聚类先把失败分簇，簇内再区分「每轮都挂
（真失败，进本工具）」与「时过时不过（flaky，进项目 13 隔离区）」。两个平台的
交界处是一条数据契约：失败条目都要带 nodeid + traceback 指纹。

**Q5：线上事故复盘里这工具怎么用？** 事故后的失败海啸（监控触发全量回归全红）正是
它的主场：5 分钟内给出「3 个根因、37 条与支付相关」的结论，把「恢复优先修什么」
的决策时间从小时级压到分钟级——MTTR 里最大的一块往往是「定位该修谁」。

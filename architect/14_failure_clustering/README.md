# 14 · 失败聚类与根因归并：先修一个根因，消掉 37 条红

> 一次提交挂 50 条用例，逐条看 traceback 是灾难现场的标准剧本。本实验实现
> 大规模失败管理的正确姿势：**traceback 指纹归一化 → 相似度聚类 → 「先修谁」
> 排序**。实测：50 条模拟失败（3 个真实根因 + 订单号/时间戳/路径噪声）聚成
> 3 簇（37/11/2），每簇纯度 100%，换种子重跑簇数稳定。

## Background

大规模失败的管理困境：一次提交挂 50 条用例，逐条看 traceback 要几小时；
更糟的是人眼会先被噪声骗——订单号、时间戳、临时目录每次都不同，
把同根因的失败看成不同的失败。

失败的价值不在条数在根因：修一个 gateway_timeout，37 条红同时转绿。
但「先修谁」需要量化——没有归并，修复顺序就是"谁嗓门大修谁"。

归一化的两难是本工具的核心设计张力：删多了把「不同根因」合成一簇
（误合并），删少了把「同根因」拆成多簇（碎片化）。两类陷阱各有代价，
阈值与替换清单都该随真实失败流校准。

## What

失败聚类器是一套确定性归并系统：traceback 归一化（数字→N、路径→PATH、
hex→HEX、引号内容→'S'）→ 指纹（异常类型 + 末帧 + 消息模板）→
精确指纹分组 + difflib 相似度（≥0.85）二次合并 → 按「簇大小 = 修复 ROI」
排序输出。

可以把聚类器想成急诊分诊台：50 个伤员（失败）进来，先按症状体征（归一化后的指纹）分诊到三个诊室（根因簇），每个诊室贴一张最典型的病历（代表 traceback），抢救顺序按人数排（先修谁）。

但和分诊不同的是，这里的"病历"必须先把噪声洗掉——否则每个伤员看起来都是新病种。


心智模型一句话：**归一化是去掉「每次都不同的噪声」，指纹是留下
「每次都相同的病因」**。

## When to Use

典型场景：

- CI 失败海啸：一次提交挂几十上百条，聚类后按簇修，先修 P1 消 37 红。
- 线上事故复盘：监控触发全量回归全红时，5 分钟给出「3 个根因、37 条与
  支付相关」的结论——MTTR 里最大的一块往往是「定位该修谁」。
- 质量汇报：根因 × 影响面 × 修复状态，是向管理层汇报事故的标准格式。

何时不用：失败量小（三五条，人眼直接看更快）；traceback 缺失或被截断的
失败（没证据就无法归并）。

关键设计（这段在做什么：聚类可信度的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 固定种子生成 | 失败可复现，验收可断言 | 真实失败流的分布漂移要定期重训模板 |
| 簇内真值纯度自检 | 用「聚类器看不见的真值」验收自己 | 生产环境没有真值，用人工抽检替代 |
| 代表 traceback 每簇一条 | 人只看代表，不刷屏 | 代表选取用簇内最长 traceback（信息量最大） |
| difflib 而非编辑距离 | 标准库零依赖，行为可解释 | 超长 traceback 的 O(n²) 需先截断末 20 帧 |

## Quick Start

前置条件：纯离线（固定种子生成模拟失败），零依赖。

```bash
cd architect/14_failure_clustering
./failure_clustering.sh apply     # 纯离线：固定种子生成 50 条模拟失败
./failure_clustering.sh observe   # 指纹聚类 → 验收断言 → 换种子可复现性
./failure_clustering.sh clean
```

实测输出（节选）：

```
| 优先级 | 根因簇（代表异常）          | 成员数 | 修掉能消掉的红 |
| P1     | requests.exceptions.ReadTimeout | 37 | 37 条 |
| P2     | sqlite3.OperationalError        | 11 | 11 条 |
| P3     | AssertionError                  |  2 |  2 条 |
纯度：每簇内同根因占比 100%（指纹纯度）
>>> 验收：3 簇（≤5）✅；最大簇纯度 100%（≥80%）✅ → 验收通过
换种子（60 条）重跑：仍 3 簇，验收通过——聚类对样例扰动稳定
```

诚实预期：验收双指标——簇数 ≤5、最大簇纯度 ≥80%；换种子重跑簇数应稳定
（对样例扰动不敏感）。簇内真值纯度是用「聚类器看不见的真值」验收自己，
生产环境没有真值时用人工抽检替代。

## How It Works

**归一化的边界感**。噪声替换清单（数字/路径/hex/引号内容）是本工具的灵魂：
两类陷阱（误合并/碎片化）各有代价——这正是阈值与清单要随真实失败流
校准的原因。

**二次相似合并**。精确指纹只解决「同模板」；不同团队/不同写法的相似
traceback（多一个空行、换一个变量名）靠 difflib 相似度 ≥0.85 归并。
相似度阈值是本工具唯一的重要旋钮：阈值下调必致混簇，上调则碎片化。

**先修排序 = 修复 ROI**。簇大小即收益：修 P1 消 37 红、修 P3 消 2 红
——「先修谁」不用吵，排序说话。

**与 flaky 治理的衔接**。聚类先把失败分簇，簇内再区分「每轮都挂
（真失败，进本工具）」与「时过时不过（flaky，进项目 13 隔离区）」。
两个平台的交界处是一条数据契约：失败条目都要带 nodeid + traceback 指纹。

## Pitfalls & Q&A

踩坑清单：

- **用测试名聚类**。test_case_000 和 001 可能是同一根因，名字是噪声，
  traceback 才是证据——用名字聚类是新手最常见的错误。
- **相似度阈值一刀切**。现象：混簇（一个簇两种根因）。
  解法：簇内抽查发现混簇 → 对该簇细分（提高阈值或换指纹字段，
  如带上源文件路径）；纯度自检就是混簇探测器。
- **超长 traceback 拖垮相似度计算**。现象：O(n²) 比对卡死。
  解法：先截断末 20 帧再比对。
- **把 LLM 放在第一层**。现象：每次聚类结果不同、成本高。
  解法：确定性指纹先收簇，LLM 只写「人话根因假设」——
  「确定性优先，智能补足」是 AI 工程的通用次序。

深入问答：

- **Q：为什么不用 LLM 做失败聚类？**
  可以做，但应该是第二层：先用确定性指纹把 50 条收成 3 簇（便宜、可解释、
  可复现），再让 LLM 给每簇写「人话根因假设」。跳过第一层直接 LLM，
  成本高且每次答案不同。
- **Q：混簇（一个簇两种根因）怎么办？**
  相似度阈值下调必致混簇。治理：簇内抽查发现混簇 → 对该簇细分
  （提高阈值或换指纹字段）；报告里纯度自检就是混簇探测器。
- **Q：测试名参与聚类吗？**
  不。test_case_000 和 001 可能是同一根因，test_000 和 002 也可能是两个
  根因——名字是噪声，traceback 才是证据。
- **Q：和项目 13 的 flaky 治理怎么衔接？**
  聚类先把失败分簇，簇内再区分「每轮都挂（真失败）」与「时过时不过
  （flaky，进项目 13 隔离区）」。交界处是一条数据契约：
  失败条目都要带 nodeid + traceback 指纹。
- **Q：线上事故复盘里这工具怎么用？**
  事故后的失败海啸正是它的主场：5 分钟内给出「3 个根因、37 条与支付相关」
  的结论，把「恢复优先修什么」的决策时间从小时级压到分钟级。

# 22 · 安全左移门禁：SCA + SAST + DAST 三层拦在流水线上

> 安全不必是专家专属——三层扫描把最常见的风险拦在流水线上：
> **SCA 拦已知漏洞依赖**（对 CVE——公开安全漏洞编号库——比对）、**SAST 拦危险代码模式**、
> **轻量 DAST 拦部署层低级失误**。实测：基线 PASS；植入 requests==2.19.0 后
> 门禁 FAIL 并点名 5 条 CVE；DAST 还揪出一个真实发现——SUT 的
> /admin.html 未登录即可访问。

## Background

Log4Shell 式事故的共性：漏洞公布时，没人知道自家依赖中招——从 CVE 公布到工单产生之间的真空期，就是事故窗口。

SCA（Software Composition Analysis，软件成分分析）把这段真空自动化：依赖清单对 CVE/GHSA 库（GHSA，GitHub 的安全公告库，与 CVE 编号一一对应）实时比对，中招即点名。


扫描的价值在**汇入门禁**：单独跑的扫描器只是报表（没人每周看），
接上退出码才是防线——红不过夜。

三层的分工与局限要讲清楚：SCA 看依赖清单、SAST 看代码模式、
DAST 看**运行中的真实行为**——本实验 DAST 抓到的 /admin.html 裸奔
就是前两层永远看不见的部署层问题。安全体系是谱系不是工具名。

## What

安全左移门禁是一套三层扫描 + 汇总裁决系统：**三个扫描器并行、
一份门禁裁决**——SCA/SAST 有红线必拦；轻量 DAST 发现默认警告不拦
（部署层问题由发布 checklist 兜底），阈值可加严。

可以把三层扫描想成机场的三道安检：查行李清单（SCA——箱子里有没有违禁品）、查随身物品（SAST——口袋里有没有刀）、全身扫描（DAST——穿在身上的东西实际是什么）。

但和安检不同的是，三道关共用一个裁决台：分级响应（红线拦/中危记账/发现警告）——一把尺子量所有发现，两周后就会被整体豁免。


**扫描器崩溃 ≠ 无漏洞**：pip-audit 崩溃/断网时，fail-safe 语义必须是
**FAIL（SCANNER-FAILED）**而不是 PASS——「扫不了」按「无问题」处理
是安全门禁最危险的反模式。

## When to Use

典型场景：

- 依赖安全治理：精确 pin（固定到精确版本号，不用 >= 范围）的依赖清单定期扫描，
  CVE 公布即出工单。
- 代码合入前的 SAST 检查：高危必拦、中危记账、低危忽略。
- 部署层巡检：安全响应头、未鉴权页面、目录列表——轻量 DAST 只做
  只读探测，够拦低级失误，不做攻击模拟。

何时不用：无运行环境可探（纯库项目）时 DAST 缺席；
安全扫描规则未分级就全量拦截，团队两周内会学会绕过门禁——
先建分级响应再上扫描。

实测输出（节选）：

```
① 基线：裁决 ✅ PASS
   L2 SAST：高危 0 项 / 中危 2 项
   L3 DAST：⚠️ /admin.html 未登录即可访问（HTTP 200，无鉴权跳转）——真实发现
② 植入 requests==2.19.0 后：裁决 ❌ FAIL（退出码 1）
   - requests: CVE-2018-18074（修复 2.20.0）
   - requests: CVE-2023-32681（修复 2.31.0）
   - requests: CVE-2024-35195 / CVE-2024-47081 / CVE-2026-25645 …
```

## Quick Start

前置条件：labs/00 体检通过；脚本自动装 pip-audit/bandit 并起 SUT。

```bash
cd architect/22_security_gate
./security_gate.sh apply     # 装 pip-audit/bandit + 起 SUT
./security_gate.sh observe   # 基线 PASS → 植入 CVE 依赖 → FAIL 点名 → DAST 发现
./security_gate.sh clean
```

诚实预期：基线应 PASS（SUT 干净：SAST 高危 0、DAST 有一个真实警告）；
植入旧版 requests 后应 FAIL 并精确点名 CVE 与修复版本——
「CVE 公布」到「工单产生」的自动化由此成立。

关键设计（这段在做什么：门禁可信度的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 依赖清单精确 pin | pip-audit --no-deps 只接受精确版本（`>=` 范围直接报错） | 扫描对象版本漂移会让结果失真 |
| CVE 去重（别名取 CVE- 前缀） | GHSA/CVE 双编号同漏洞会刷屏 | 重复告警加速告警疲劳 |
| DAST 默认不拦 | 部署层问题归属发布流程 | 若接拦，需要豁免流程配套（项目 24） |
| 扫描器崩溃=FAIL | 扫不了 ≠ 没问题 | try/except 吞异常返回 PASS 是最危险的反模式 |

## How It Works

**三层各自看得见什么**。SCA 看依赖清单（pip-audit 对 CVE/GHSA 库）；
SAST 看代码模式（bandit 规则：eval/弱随机/硬编码密码）；轻量 DAST 看
**运行中的真实行为**（安全响应头、未鉴权页面、目录列表）。

**拦截分级**。SCA 有 CVE → 必拦（红线）；SAST 高危 → 必拦，中危记账；
DAST 发现 → 警告+工单。分级响应是安全门禁能活下去的关键。

**fail-safe 语义**。扫描器崩溃/断网时裁决 FAIL（SCANNER-FAILED）——
门禁宁可误拦也不放行「未扫描」状态。

## Pitfalls & Q&A

踩坑清单：

- **依赖范围版本（`>=`）喂扫描器**。现象：pip-audit 直接报错。
  解法：扫描对象精确 pin（`requirements_scan.txt`）。
- **GHSA/CVE 双编号刷屏**。现象：同一漏洞两条告警。
  解法：别名去重（取 CVE- 前缀）。
- **扫描器异常返回 PASS**。现象：断网期间门禁全绿。
  解法：fail-safe = FAIL，异常显式标注 SCANNER-FAILED。
- **中危自动拦截**。现象：门禁长期红，团队学会豁免一切。
  解法：中危记账 + 人工 triage（人工分诊评估，决定修/缓/忽略），自动只拦高危。

深入问答：

- **Q：SAST/DAST/SCA 之外还有什么？**
  IaC 扫描（terraform/k8s manifest 的错误配置）、密钥扫描（git 历史里的
  API key，gitleaks）、容器镜像扫描（trivy，项目 16 的镜像可直接接）。
  安全左移是谱系，选型按风险排序接入，不必一次全上。
- **Q：误报太多怎么办？**
  三步：基线管理（存量问题登记豁免，只对新增量零容忍）、规则分级
  （高危拦/中危记账/低危忽略）、定期回收豁免（「临时豁免」要有过期时间）。
  豁免流程与项目 24 的覆盖率豁免状态机同构。
- **Q：DAST 会不会把测试环境打挂？**
  会——所以生产级 DAST 要限速、白名单路径、避开数据写接口。
  本实验的轻量 DAST 只做只读探测（GET + 响应头检查），这是「轻量」
  的全部含义。
- **Q：安全门禁和项目 3 质量门禁什么关系？**
  同一个引擎（项目 3 的规则模型）不同数据源：安全扫描结果作为 adapter
  接入即可复用裁决与报告——本实验独立跑是为了演示三层扫描器本身；
  平台化合并是自然演进。

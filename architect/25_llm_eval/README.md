# 25 · LLM 用例生成与质量评测：AI 生成的测试敢不敢用，先造量尺

> 「LLM 生成用例能不能替代测试工程师」的讨论太多，动手的太少。本实验的立场是
> **先造量尺再谈替代**：四维评测（可执行性/断言有效性/边界覆盖/重复率）量化生成
> 质量，达标的才进人工审核池。mock 模式离线确定性（量尺自身的回归基线），真实
> LLM 走 OpenAI 兼容接口可选接入。实测：mock 生成 10 条，四维 100/100/100/0。
> 清单第 25/28 项，2025-26 面试热点题。

## 1. 为什么需要它

- LLM 生成的用例有三类坑：跑不起来（幻觉字段）、断言错误（期望值与实现不符）、
  换皮重复（10 条其实是 2 条）——没有量尺就无法区分好坏生成；
- 「敢不敢用」的正确姿势不是信任或拒绝，是**分级准入**：量尺合格 → 人工审核池；
- 量尺本身必须可回归：mock 模式保证评测器在任何时刻可验证自己没坏。

边界覆盖看规格维度盖了几个、重复率看签名去重。


## 4. 核心概念

### 4.1 四维量尺各防一种坑
可执行性防「幻觉字段/错误路径」；断言有效性防「期望值与实现不符」（对真 SUT 执行
才能验证）；边界覆盖防「生成一堆快乐路径」；重复率防「换皮凑数」。四维各自独立
打分，综合判定「进人工审核池」或「打回重新生成」。

### 4.2 mock 生成器是量尺的回归基线
确定性模板生成必然满分（100/100/100/0）——如果某天评测器对 mock 输出打了低分，
说明**评测器坏了**。这是「量尺先于被测物」的工程化表达：先有可回归的基准，
再接不确定的智能。

### 4.3 边界真值来自实测而非规格幻想
评测器的期望状态码全部来自对 SUT 的真实探针（qty≤0→422、price=0→201、空 customer
→422）——探针还顺带发现规格没写 price 下限，SUT 接受 0 元商品，这是规格-实现的
一致性缺口（真发现，README 如实记录）。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| mock 为默认路径 | 评测器可离线回归，真实 LLM 只是插拔件 | 真实模式必须显式 --llm，防止 CI 意外花钱 |
| POST 自清理 | 评测流量不污染数据（项目 7 纪律） | 评测器自己变成数据污染源就本末倒置 |
| 重复签名 = method+path+payload | 换皮用例的本质是签名相同 | 只比 name 会把「改名不改内容」当成新用例 |
| 期望值由探针校准 | 生成物的期望必须与实现核对 | 直接信 LLM 的期望值，断言有效性无从谈起 |

## 7. 深入要点

**Q1：AI 时代测试工程师会被替代吗（面试必问）？** 本实验的答案框架：被替代的是
「写重复边界用例」的动作，不被替代的是三件事——定义规格与边界清单（生成器的输入）、
设计量尺（判定生成质量）、对业务风险的判断。LLM 是杠杆，支点还是测试思维。

**Q2：为什么合格线是「进人工审核池」而不是直接合入？** 四维量尺能验「技术上可用」，
验不了「业务上重要」。人审的价值在排序与取舍——AI 提产能，人对覆盖率与风险负责，
这条边界写进流程而不是写进口号。

**Q3：断言有效性 100% 是不是说明 LLM 没风险？** mock 生成器的 100% 只证明量尺没坏。
真实 LLM 的断言有效性通常 70-90%（幻觉字段名、错状态码）——这正是量尺存在的意义：
每次生成自动过一遍尺子，不达标打回。研发流程里它就是生成器后面的那道自动闸门。

**Q4：量尺的四个维度够吗？** 对「接口边界用例」够用；对 UI 生成脚本还要加「定位
有效性」（配合项目 9 自愈）、对单元测试要加「变异测试得分」（杀死变异体的比例）。
量尺随被测物形态扩展，思想不变：**生成的质量必须被另一个可复现的过程度量**。

**Q5：评测器自己用了 LLM 吗？** 刻意没用——评测的四个维度全部确定性计算（发请求、
比状态码、集合运算、签名去重）。确定性优先原则（同项目 14 聚类）：能算的不推理，
推理只用于「根因假设」「修复建议」这类无法计算的输出。

## 8. 总结

一台四维量尺、双模式生成、一份可审计的评测报告——「AI 生成的测试敢不敢用」从
站队问题变成阈值问题（可执行 ≥80%、重复 ≤20% → 进审核池）。评测器顺带揪出规格
缺口（price=0 合法），AI 时代测试工程师的新位置清晰可见。下一篇是清单项目 26
「逃逸缺陷分析与策略迭代」：从 labs 的教学翻车点反推策略改进。

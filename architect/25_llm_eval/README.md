# 25 · LLM 用例生成与质量评测：AI 生成的测试敢不敢用，先造量尺

> 「LLM 生成用例能不能替代测试工程师」的讨论太多，动手的太少。本实验的立场是
> **先造量尺再谈替代**：四维评测（可执行性/断言有效性/边界覆盖/重复率）量化
> 生成质量，达标的才进人工审核池。mock 模式离线确定性（量尺自身的回归基线），
> 真实 LLM 走 OpenAI 兼容接口可选接入。实测：mock 生成 10 条，
> 四维 100/100/100/0。

## Background

LLM 生成的用例有三类坑：跑不起来（幻觉字段）、断言错误（期望值与实现
不符）、换皮重复（10 条其实是 2 条）。没有量尺，就无法区分好的生成和
坏的生产——「敢不敢用」的讨论永远停在站队。

正确的姿势不是信任或拒绝，是**分级准入**：量尺合格 → 人工审核池；
不达标 → 打回重新生成。量尺本身必须可回归：mock 模式保证评测器在任何
时刻可验证自己没坏——先有可回归的基准，再接不确定的智能。

## What

LLM 用例评测器是一台四维量尺 + 双模式生成器：
**生成层双模式（mock 确定性 / LLM 真实），评测层四维打分**——评测对着
真 SUT 执行生成的用例：可执行性看能不能发、断言有效性看期望对不对、
边界覆盖看规格维度盖了几个、重复率看签名去重。

可以把量尺想成质检的卡尺：生成器（不管人写还是 AI 写）交上来的零件（用例），先过四道卡（能不能用、断言对不对、盖没盖边界、是不是重复件），合格进人工审核池，不合格打回。

但和卡尺不同的是，这台量尺有自己的回归基线——mock 生成器的确定性输出必然满分（100/100/100/0），哪天它被打出低分，说明**量尺坏了**，不是零件坏了。


**四维量尺各防一种坑**：可执行性防「幻觉字段/错误路径」；断言有效性防
「期望值与实现不符」（对真 SUT 执行才能验证）；边界覆盖防「生成一堆
快乐路径」；重复率防「换皮凑数」（验收线 ≤20%）。

## When to Use

典型场景：

- 生成式测试的准入闸门：研发流程里生成器后面的那道自动闸门——
  每次生成自动过尺，可执行 ≥80%、重复 ≤20% 进审核池。
- 规格一致性审计：校准探针（向真 SUT 发真实请求、用实际响应校准期望值的探测
  请求；与项目 19 的定时合成探针不同）校准期望值时顺带发现规格缺口
  （本实验真发现：规格没写 price 下限，SUT 接受 0 元商品）。
- 量尺扩展：UI 生成脚本加「定位有效性」（配合项目 9 自愈）、
  单元测试加「变异测试得分」（变异测试：把代码故意改坏的副本叫变异体，
  看测试能否发现——发现比例即得分）。

何时不用：生成量极小（人工逐条看更快）；评测期望无法校准
（无真实 SUT 可探针）时，断言有效性维度无从谈起。

实测输出：

```
# 🤖 LLM 用例生成评测报告（模式：mock）· 生成 10 条 · 判定：✅ 可进入人工审核池
| 可执行性   | 100% | 不改代码即可发出的比例 |
| 断言有效性 | 100% | 期望状态码与真实行为一致的比例 |
| 边界覆盖   | 100% | 规格边界维度（空串/缺失/零/负数/正常）的覆盖 |
| 重复率     |   0% | 同方法+路径+payload 签名的重复（验收 ≤20%） |
③ 真实 LLM 探活：LLM_BASE_URL/LLM_MODEL 未配置 → 真实模式跳过（mock 为默认路径，不编造）
```

## Quick Start

前置条件：labs/00 体检通过；脚本自动起 SUT（评测要真实打请求）；
真实 LLM 模式需配置 LLM_BASE_URL/LLM_MODEL（可选）。

```bash
cd architect/25_llm_eval
./llm_eval.sh apply     # 起 SUT（评测要真实打请求）
./llm_eval.sh observe   # mock 生成+评测 → 断言 → 真实 LLM 探活（未配置如实跳过）
./llm_eval.sh clean
```

诚实预期：mock 模式应四维满分（它本身是量尺的回归基线）；真实 LLM
未配置时探活如实跳过——不编造。真实 LLM 的断言有效性通常 70-90%
（幻觉字段名、错状态码）——这正是量尺存在的意义。

关键设计（这段在做什么：量尺可信度的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| mock 为默认路径 | 评测器可离线回归，真实 LLM 只是插拔件 | 真实模式必须显式 --llm，防止 CI 意外花钱 |
| POST 自清理 | 评测流量不污染数据（项目 7 纪律） | 评测器自己变成数据污染源就本末倒置 |
| 重复签名 = method+path+payload | 换皮用例的本质是签名相同 | 只比 name 会把「改名不改内容」当成新用例 |
| 期望值由探针校准 | 生成物的期望必须与实现核对 | 直接信 LLM 的期望值，断言有效性无从谈起 |

## How It Works

**mock 生成器是量尺的回归基线**。确定性模板生成必然满分——如果某天
评测器对 mock 输出打了低分，说明**评测器坏了**。这是「量尺先于被测物」
的工程化表达：先有可回归的基准，再接不确定的智能。

**边界真值来自实测而非规格幻想**。评测器的期望状态码全部来自对 SUT 的
真实探针（qty≤0→422、price=0→201、空 customer→422）——探针还顺带发现
规格没写 price 下限，SUT 接受 0 元商品，这是规格-实现的一致性缺口
（真发现，如实记录）。

**评测器自己不用 LLM**。刻意没用——评测的四个维度全部确定性计算
（发请求、比状态码、集合运算、签名去重）。确定性优先原则（同项目 14
聚类）：能算的不推理，推理只用于「根因假设」「修复建议」这类无法计算
的输出。

## Pitfalls & Q&A

踩坑清单：

- **真实 LLM 模式混进 CI**。现象：CI 意外烧钱、结果不确定。
  解法：真实模式必须显式 `--llm`，mock 为默认路径。
- **只比用例名判重复**。现象：「改名不改内容」被当成新用例。
  解法：签名 = method+path+payload。
- **直接信 LLM 的期望值**。现象：断言有效性无从验证。
  解法：期望值由探针校准后再比对。
- **评测器污染数据**。现象：评测跑几轮库被塞满。
  解法：POST 自清理。

深入问答：

- **Q：AI 时代测试工程师会被替代吗？**
  本实验的答案框架：被替代的是「写重复边界用例」的动作，不被替代的是
  三件事——定义规格与边界清单（生成器的输入）、设计量尺（判定生成质量）、
  对业务风险的判断。LLM 是杠杆，支点还是测试思维。
- **Q：为什么合格线是「进人工审核池」而不是直接合入？**
  四维量尺能验「技术上可用」，验不了「业务上重要」。人审的价值在排序与
  取舍——AI 提产能，人对覆盖率与风险负责，这条边界写进流程而不是
  写进口号。
- **Q：断言有效性 100% 是不是说明 LLM 没风险？**
  mock 生成器的 100% 只证明量尺没坏。真实 LLM 的断言有效性通常 70-90%
  （幻觉字段名、错状态码）——每次生成自动过一遍尺子，不达标打回。
- **Q：量尺的四个维度够吗？**
  对「接口边界用例」够用；对 UI 生成脚本还要加「定位有效性」（配合
  项目 9 自愈）、对单元测试要加「变异测试得分」。量尺随被测物形态扩展，
  思想不变：**生成的质量必须被另一个可复现的过程度量**。

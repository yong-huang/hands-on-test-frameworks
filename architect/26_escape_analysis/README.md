# 26 · 逃逸缺陷分析与策略迭代：复盘的终点是机制，不是会议

> 「讲一次线上事故复盘」的潜台词是：**你的策略因为这次事故改了什么？**
> 本实验从 labs 的教学翻车点取材 10 个逃逸案例（定位器碎裂/锁冲突/快照跳过/
> 配置漂移…），四维归因（漏测层/环境/数据/时序），每条归因挂接可执行改进
> ——且改进必须映射到磁盘上真实存在的产物（architect/09/13/15…），
> 映射不存在即校验失败。

## Background

复盘最大的浪费：分析头头是道、行动项全部蒸发——会议记录躺在网盘里，
半年后同样的事故换个马甲再来一次。复盘的终点不该是会议，是机制。

逃逸缺陷（escape defect，生产才发现、本可在测试阶段拦截的缺陷）是复盘
的优质原料：每个逃逸都是测试体系的一次真实露怯。归因分布是策略迭代的
方向盘——漏测层 4 个说明分层设计要调，时序 3 个说明并发测试欠账。

行动项要可验证，不能靠自觉：「改进项必须指向真实产物」把承诺变成
机器可检查的事实——映射的产物目录不存在，校验直接失败。

## What

逃逸缺陷分析器是一套复盘闭环工具：**每个翻车点 → 归因到层 → 挂改进 → 改进指向真实产物**。

四维归因互斥（一个案例只落一类主因）且近似完备（绝大多数逃逸都能落进这四类之一）：漏测层（该有的用例没有）、环境（环境不一致导致测了白测）、数据（数据污染/缺造数）、时序（并发/等待/顺序依赖）。


可以把归因想成交通事故的责任认定：不说"司机不小心"（归因到人），而是定位到"路口没有红绿灯"（漏测层）、"路面积水没清理"（环境）、"两车抢道无让行规则"（时序）——每类原因对应一类工程改进。

但和事故认定不同的是，这里的改进项必须挂到真实存在的机制产物上（`maps_to` 字段指向磁盘目录，分析器逐条校验）——指向不存在产物的改进直接校验失败。


**归因到人不产生改进，归因到机制才产生产物**——疏忽是症状不是原因，
问「为什么能疏忽」：没有卡点（24）、没有右移探针（19，上线后持续巡检的
合成探针）、没有门禁（03）
才是因。

## When to Use

典型场景：

- 线上事故复盘：每个逃逸缺陷入库 + 归因 + 挂改进，改进映射可校验。
- 策略季度评审：归因分布随季度滚动对比，某一维持续走高就是策略欠账
  的警报。
- 复盘产出标准化：一页纸「维度 × 迭代前 vs 迭代后」对比表给管理层，
  技术细节留明细。

何时不用：逃逸样本极少（个位数）时分布无统计意义；
组织尚无无责复盘文化（blameless，人们只在没有惩罚的环境里说真话）时，
案例库会变成甩锅库——先立文化再上工具。

实测输出（节选）：

```

- 漏测层：████ 4 个
- 时序：███ 3 个
- 环境：██ 2 个
- 数据：█ 1 个

 ## 策略迭代前后对比（一页纸）
```

## Quick Start

前置条件：纯离线（案例清单见 configs/cases.yaml，取材 labs 真实翻车点）；
映射校验依赖本仓库其他项目目录真实存在。

```bash
cd architect/26_escape_analysis
./escape_analysis.sh apply     # 纯离线：案例清单见 configs/cases.yaml
./escape_analysis.sh observe   # 归因分析 + 映射校验 + 迭代对比页
./escape_analysis.sh clean
```

诚实预期：10 个案例应全部归因成功、全部通过映射校验（改进指向的产物
目录真实存在）；迭代对比页应生成。注意映射校验的语义：产物被删后
历史案例会校验失败——改进应指向「机制」而非「代码」。

关键设计（这段在做什么：复盘闭环的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 取材 labs 真实翻车点 | 踩过的坑才有分析深度，编的案例是空转 | 真实不等于隐私：脱敏后再入库 |
| maps_to 校验存在性 | 行动项可验证 | 产物被删后历史案例会校验失败——应指向「机制」而非「代码」 |
| 四维互斥近似 | 多维归因没法聚合 | 复杂事故允许多标签，但主归因唯一 |
| 迭代对比固定表格 | 同构对比才可跨期追踪 | 每期格式变来变去就没法看趋势 |

## How It Works

**四维归因**。漏测层/环境/数据/时序互斥且近似完备——比「人为疏忽」这类
甩锅归因有用一个量级：每维对应一类机制改进。复杂事故允许多标签，
但主归因唯一（否则没法聚合出方向盘）。

**改进映射的校验纪律**。`maps_to` 字段指向磁盘产物目录，分析器逐条
校验——这是「复盘承诺的产物」的机器化检查。真实团队的等价物：
行动项挂 JIRA 单、缺陷关联修复 PR，同一思想。

**迭代对比页是一页纸产物**。复盘输出压成一页「维度 × 迭代前 vs 迭代后」
——给管理层的版本。技术细节留在明细，决策信息上浮到对比表，
这是报告的分层设计。

## Pitfalls & Q&A

踩坑清单：

- **归因到人**。现象：复盘变成追责会，真话消失。
  解法：四维机制归因，无责复盘是前提。
- **主归因多选**。现象：分布图没法聚合。
  解法：允许多标签但主归因唯一。
- **映射指向具体代码文件**。现象：代码重构后历史案例校验失败。
  解法：指向机制产物目录（architect/13 这样的机制），不指向易变代码。
- **对比表每期换格式**。现象：没法跨期看趋势。
  解法：维度行固定，前后列固定。

深入问答：

- **Q：逃逸率和这个分析什么关系？**
  项目 23 的逃逸率是定量信号（多少逃了），本实验是定性归因（为什么逃、
  怎么堵）。定量先报警，定性再改进——两者共享「逃逸缺陷」这个事实定义，
  口径不一致会让两个体系打架。
- **Q：为什么归因里没有「测试工程师疏忽」？**
  疏忽是症状不是原因：问「为什么能疏忽」——没有卡点（24）、没有右移
  探针（19）、没有门禁（03）才是因。归因到人不产生改进，
  归因到机制才产生本清单这样的产物。
- **Q：10 个案例够代表吗？**
  对教学足够，对真实组织不够——生产化后案例池应持续积累（每个逃逸
  缺陷入库+归因），归因分布随季度滚动对比。
- **Q：改进映射会不会变成形式主义？**
  会，如果只校验「目录存在」。更强的校验是「产物最近有运行证据」
  （reports 时间戳）——复盘改进项和真实使用挂钩，这个升级留给读者
  （也正是看板 27 应该展示的「机制活性」）。
- **Q：复盘文化和工具哪个重要？**
  工具降低复盘成本，文化决定复盘是否发生——无责复盘（blameless）是
  前提：人们只在没有惩罚的环境里说真话。本实验的案例脱敏取材就是
  无责文化的产物。

# 13 · flaky 检测与隔离平台：让红色重新有信用

> 「重跑就过了」——这句话说出口的瞬间，CI 的红色已经一文不值。flaky 治理是
> 大规模自动化的生死线，本实验把治理做成四步闭环：**同 commit 10 轮重跑检测
> （结果不一致即 flaky）→ 自动 quarantine（失败不挡主干但每次亮灯）→ 门禁联动
> （flaky 率喂给项目 3）→ 修复后摘牌恢复全量监视**。实测：植入的随机失败与
> 顺序依赖两个 flaky 10 轮内全部检出、稳定对照零误报；隔离后主干 3 连绿；
> 摘牌瞬间恢复阻断。

## Background

flaky 的定义：被测对象与测试条件不变，结果时过时不过。它的危害链条是
级联的：flaky 用例存在 → 团队习惯性重跑 → 假绿与真红不分 → 
质量信号全面失真——当红色不再可信，绿色同样失去意义。

没有治理平台时，flaky 的常见归宿有三种，全都是坏结局：
留在主干反复制造误报；被人注释跳过（保护网破洞）；进"已知问题"清单
然后没人再提。三者都缺同一样东西：**闭环**——检测→隔离→有人修→摘牌，
缺任何一步都会退化成「隔离区垃圾场」。

quarantine（隔离区）的定位是医院不是坟墓：进去要亮灯、要有人跟、能出来。

## What

flaky 检测与隔离平台是一套治理闭环工具，三个命令对应三步：

- **detect**：同一 commit 重跑 10 轮，结果不一致即 flaky——判据来自定义
  本身（同输入不同输出）。
- **gate**：门禁三态裁决 passed / QUARANTINED / BLOCKING——隔离的失败不算
  blocking，**但必须在报告里亮灯**：隔离不是消失。
- **remove**：修复后摘牌，恢复全量监视（重新具备阻断能力）。

可以把隔离区想成伤兵疗养区：伤员（flaky 用例）不上一线（主干门禁），
但胸牌永远亮着（每次运行显示 QUARANTINED），有查房记录（摘牌流程留痕），
治好了就归队（--remove 恢复）。但和疗养区不同的是，「自动摘牌」被明确
禁止——摘牌必须 pattern 显式指定，等于恢复阻断，必须是有意识的动作。

## When to Use

典型场景：

- 主干误报频发：夜间层跑 10 轮检测（成本 10 倍执行，只配夜间），
  检出的 flaky 自动入隔离区。
- 门禁需要 flaky 率数据源：本平台写 `flaky.json`（固定路径跨项目契约），
  项目 3 门禁的 `flaky_rate ≤ 2%` 规则自此有数。
- flaky 修复验证：修完的用例摘牌重进全量监视，回归验证有据可查。

何时不用：套件只有几十条且从没出现过 flaky 时，平台的维护成本大于收益；
重试机制不能替代本平台——重试是掩盖不是治理（见 Q&A）。

实测关键数字：植入的随机失败形态 6/10 过、共享状态残留形态 1/10 过，
10 轮内双双检出；3 条稳定对照零误报；隔离后主干 3 连绿；摘牌瞬间恢复
BLOCKING。

## Quick Start

前置条件：labs/00 体检通过；植入的 flaky 用例常驻 tests/
（注释即声明，检测器的对照组）。

```bash
cd architect/13_flaky_platform
./flaky_platform.sh apply     # 清空隔离区与 .shared_state（靶子常驻，注释即声明；残留会让顺序依赖型永不现形）
./flaky_platform.sh observe   # 10 轮检测 → 自动隔离 → 门禁联动 → 3 连绿 → 摘牌
./flaky_platform.sh clean
```

实测输出（节选）：

```
① 10 轮检测：flaky 率 40.0%（5 条中 2 条）
   ❗ test_random_flake：6/10 过（随机失败形态）
   ❗ test_order_dependent_victim：1/10 过（共享状态残留形态）
   ➡️ 双双自动入隔离区；3 条稳定对照零误报 ✅
③ 门禁联动：3 过 / 2 隔离 / 0 阻断 → 裁决 PASS（亮灯不挡路）
④ 主干连续 3 次 PASS ✅
⑤ 摘牌 test_random_flake 后重跑门禁：❌ BLOCKING（恢复全量监视）
```

诚实预期：⑤ 的 BLOCKING 是验收的收官——摘牌 = 恢复阻断，
未修复的 flaky 回到全量监视后门禁立刻红，这证明隔离与摘牌的语义闭环。

关键设计（这段在做什么：闭环可信度的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 植入用例常驻 tests/ | 检测器的对照组 + 永久的回归验证 | 注释声明「植入」，别让后人困惑 |
| junit file=None 用 classname 兜底 | 某些插件注入的用例没有 file 属性 | 不兜底会出现 `None::test_x` 幽灵条目 |
| 摘牌要 pattern 显式指定 | 摘牌 = 恢复阻断，必须是有意识的动作 | 自动摘牌等于没有隔离 |
| flaky.json 固定路径 | 跨项目数据契约（03 门禁直接读） | 契约字段（flaky_rate_pct）改动要同步两侧 |

## How It Works

**检测的判据与成本**。同 commit 10 轮重跑，任何一轮结果不同即 flaky。
10 轮是统计与成本的折中——检出概率 1-(1-p)^10，40% 失败率的用例 10 轮内
检出率 99.4%。成本是 10 倍执行，所以检测只跑夜间层（项目 10 tier3），
主干层只消费隔离清单。

**植入的两种经典形态**。随机失败（`random()<0.4` 断言失败）与共享状态
残留（首轮通过但写脏文件，之后每轮因残留必挂——「单独跑绿、连跑红」的
经典）。两种在实测里分别呈现 6/10 与 1/10 的通过率，
检测器对两种形态一视同仁。

**门禁的三态裁决**。passed / QUARANTINED / BLOCKING——隔离的失败不算blocking，但报告里必须亮灯。

PASS 的语义由此变化：主干回答「变更有没有引入新问题」，隔离区回答「已知的 flaky 修好了没」——两个问题分开回答，信号反而更干净，前提是隔离区数量受控（flaky 率门禁 2% 就是总量闸门）。


## Pitfalls & Q&A

踩坑清单：

- **失败后自动重试当治理**。现象：重试率攀升，真问题被延迟。
  解法：重试只用于已知外部抖动（网络闪断）且计数上报——重试率本身就是
  flaky 率的代理指标。
- **隔离区只进不出**。现象：隔离区变成垃圾场，flaky 率缓慢上涨。
  解法：隔离时自动建单、限期修复、超期进周报上会。
- **junit 幽灵条目**。现象：`None::test_x` 进清单。解法：file 缺失时用
  classname 兜底。
- **自动摘牌**。现象：未修复的用例自动回主干制造误报。
  解法：摘牌必须显式 pattern 指定。

深入问答：

- **Q：失败后自动重试是不是 flaky 治理？**
  不是，是掩盖。重试把信号延迟而不是消除，还引入「第二次执行环境已变」
  的新偏差。重试只该用于已知外部抖动的场景（网络闪断），且要计数上报。
- **Q：检测出 flaky 之后的责任归属？**
  quarantine 只是止血。规范做法：隔离时自动建单、标注疑似根因分类
  （等待/竞态/数据/环境/依赖）、限期修复；超期未修的 flaky 进周报上会。
  工具只保证「不丢不瞒」，推进靠人。
- **Q：flaky 率的分母是什么？**
  本实验 = flaky 用例数 / 总用例数（存量口径）。另一个口径是「主干误报率
  = flaky 引发的红 / 总红次数」（事件口径）——后者更能反映开发者痛感，
  两者都该看。度量口径之争要先于数值之争（呼应项目 23）。
- **Q：顺序依赖的 flaky 怎么根治？**
  三板斧：数据库/文件级隔离（项目 7 的命名空间 + 生命周期）、进程级随机化
  （pytest-randomly 让顺序依赖无处藏身）、显式依赖声明（pytest-dependency）。
  本实验的植入形态就是 labs/09 并行污染的教学续集。

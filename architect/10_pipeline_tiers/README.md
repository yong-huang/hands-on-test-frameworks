# 10 · 分层流水线架构：失败信号要多久回来

> 前面 9 个实验造的零件——分层标记、质量门禁、覆盖档案——现在要接进流水线。
> 本实验回答流水线设计的核心问题：**不是「跑什么」，而是「失败信号多久回来」**。
> PR 等 3 分钟（tier1 冒烟）、合并等 10 分钟（tier2 全量+门禁）、夜间慢层不挡人
> （tier3 档案刷新）。act 本地实跑 tier1：23 秒全绿，语义与 CI 同源。

## Background

单层流水线只有两种死法：太慢（全量塞进 PR，人人想办法绕过）或太浅
（PR 只跑冒烟，主干天天红）。根源是把「什么时候跑」和「跑什么」压进了
同一个决定——所有触发时机共用一套用例集合。

「PR 上跑不跑全量」是流水线设计的第一辩题。答案不是比例是**分层**：
每层都有明确的触发时机、超时预算和失败语义——PR 层求快、合并层求全、
夜间层求趋势。层与层之间用 needs/触发器表达依赖，而不是靠人自觉。

CI 调试的传统姿势是 push 祈祷：改一行 workflow，push，等云端结果，
错了再改。act（本地复跑 GitHub Actions 的工具）把「CI 语义的验证」
搬到本地——调试不再靠 push。

## What

三层流水线是一套按反馈时间切分的执行架构：

- **tier1 快反馈**（PR 触发，预算 <300s）：P0 冒烟，红 = 「你的改动碰了
  P0 路径，现在就修」。
- **tier2 合并门禁**（合并前，约 10 分钟）：全量 + 质量门禁，红 = 「主干
  不能有你这个变更」。
- **tier3 夜间慢层**（定时触发）：档案刷新、慢排行归档，红 = 「趋势问题，
  明早看」——不挡任何人。

可以把三层想成医院的分诊体系：分诊台 1 分钟判断要不要急诊（tier1）、急诊全面检查（tier2）、年度体检出趋势报告（tier3）。**同是红色，含义完全不同**——单层流水线给不了这个语义密度。

但和医院分诊不同的是，三层跑的是同一套用例池的不同子集与时机——分层的成本主要是给用例打标记，不是养三套测试。


心智模型一句话：**主路径就是时间轴**——push 后 3 分钟冒烟回信号，
合并前全量+门禁兜底，夜间档案/慢排行归档不挡任何人。
每层的取舍写在 workflow 注释里被人评审。

## When to Use

典型场景：

- PR 反馈超过 10 分钟的仓库：先分层，冒烟圈选 + 超时预算写进契约。
- 夜间任务堆积无人看：给慢层配日间消化机制（慢排行进站会、flaky 进
  隔离平台）。
- workflow 改动频繁：act 本地验证 yaml 语法与步骤语义，tier1 本地必绿。

何时不用：仓库很小（全量 2 分钟）时一层足够；tier 划分没有配套的
用例标记体系（项目 05 的分层标记）时，先补标记再分层——
分层是消费方，标记是供给方。

## Quick Start

前置条件：git 仓库、Docker、act、yaml 解析器四项（脚本 apply 自检）。

```bash
cd architect/10_pipeline_tiers
./pipeline_tiers.sh apply     # git/docker/act/yaml 四项前置自检
./pipeline_tiers.sh observe   # act 复跑 tier1 → 冒烟比例验收 → 三层语义速览
./pipeline_tiers.sh clean
```

实测输出（2026-09-20）：

```
① act 本地复跑 tier1（Docker 内，与 CI 同源）：
   ✅ Set up job → ✅ checkout → ✅ 安装最小依赖(9s) → ✅ P0 冒烟
>>> act 退出码 0，tier1 耗时 23s（验收线 <300s）
② 冒烟层比例验收：smoke=2 / 全量=10 → 冒烟占比 20% ≤ 20% ✅
   P0 下单路径在冒烟层 ✅
```

诚实预期：act 复跑需要 Docker 运行（本实验作者实测 23s 全绿；
Docker 未启动时 act 在 Set up job 处失败——labs/30 有同款前置说明）。
冒烟圈选验收是双约束：比例 ≤20% 且必含 P0 下单路径。

workflow 关键字段（这段在做什么：把时间预算与依赖写进契约）：

| 字段 | 为什么 | 坑 |
|:---|:---|:---|
| `timeout-minutes: 5` | tier1 的时间预算写进契约 | 不写超时的快反馈层一定会慢死 |
| `needs: tier1-quick-feedback` | tier2 依赖 tier1 绿 | 想要「并行跑但合并前都绿」就不加 needs，语义完全不同 |
| `working-directory` | 步骤级 cwd | act 把 cwd 当项目根：从仓库根跑才挂对工作区 |
| `--pull=false`（act 参数） | 用本地镜像缓存 | 镜像源抽风时一次 pull 卡 17 分钟 |

## How It Works

**冒烟圈选：比例 + 覆盖双约束**。`-k "create_and_get_fresh or init_db_repeatable"` 圈出 2/10=20%（比例达标）且必含 create（P0 下单路径）。

只有比例约束会被钻空子（圈 10 条最慢的也行），双约束才完整。圈选依据 = 项目 2 策略文档的 P0 功能映射到用例；规模大了换项目 5 的 case_level 标记 + 项目 4 的精准推荐。


**act：CI 语义的本地等价**。`act -W <workflow> -j tier1-quick --pull=false`在 Docker 内复跑同一个 yaml——「本地绿 CI 红」的环境差异被消灭大半。

两个本地化的坑：act 以 cwd 为项目根（必须从仓库根跑），容器内 pip 需要 `--break-system-packages`（PEP 668）。


**tier2 的串行由数据流决定**。门禁消费的是全量的覆盖率产物，天然串行
（needs 链）；若门禁数据来自独立采集，可并行再 merge 裁决——
「数据流决定任务图」是流水线设计的一般原则。

## Pitfalls & Q&A

踩坑清单：

- **快反馈层不写超时**。现象：tier1 从 3 分钟漂移到 30 分钟没人发现。
  解法：`timeout-minutes` 写进 workflow，超时即红。
- **needs 用法与预期语义不符**。现象：想要"并行跑但合并前都绿"却加了
  needs，或反之。解法：先写清层间语义，再选 needs 或独立触发。
- **act 从子目录跑**。现象：容器内找不到仓库文件。
  解法：act 以 cwd 为项目根，从仓库根执行。
- **夜间层变成红色垃圾场**。现象：tier3 红了没人管，红失去含义。
  解法：夜间问题必须有日间消化机制（见 Q&A）。

深入问答：

- **Q：tier1 为什么圈 2 条而不是 5 条？**
  20% 是比例上限，P0 覆盖是内容下限；条数越少信号越快，但每砍一条都在赌
  它不出事。圈选依据 = 项目 2 策略文档的 P0 功能映射到用例。
- **Q：tier2 全量+门禁串行还是并行？**
  串行（本实验 needs 链）：门禁消费的是全量的覆盖率产物，天然串行。
  若门禁数据来自独立采集，可并行再 merge 裁决——「数据流决定任务图」。
- **Q：夜间层红了怎么办？**
  夜间层的问题必须有日间的消化机制：慢排行进每日站会、flaky 报告进
  项目 13 的隔离平台、档案刷新失败自动重试。夜间层变成「红色垃圾场」
  是所有质量体系的死亡螺旋起点。
- **Q：act 和真 CI 还差什么？**
  密钥/缓存/并发组/矩阵策略是 act 覆盖不到的四件——本地能验证
  「yaml 语法+步骤语义」，验证不了「云端资源模型」。所以 tier1 本地必绿、
  tier2/3 推上去让 CI 跑，是成本最低的验证分层。
- **Q：为什么流水线不是从这 28 项里最优先做？**
  流水线是零件的组装厂：没有分层标记（05）、门禁（03）、覆盖档案（04）
  之前，三层只是三个空壳。先零件后流水线，是本清单阶段排序的用意。

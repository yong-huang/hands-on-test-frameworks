# 11 · 耗时均衡分片调度器：把 14 分钟砍进 4 分钟

> 并行跑测试人人会（`-n auto`），但「按用例数均分」在有一条 10 秒的长用例时
> 立刻翻车——木桶效应让三片等一片。本实验实现工程效能的标准答案：
> **junit 历史耗时 → LPT 贪心分片 → N 进程并行 → junit 合并 + 守恒校验**。
> 实测 246 条用例：串行 14.0s → 并行 3.4s（提速 76%），片间最大/最小比 1.08。

## Background

CI 等待是工程师注意力的黑洞：套件每慢 1 分钟，全队每天多等几十分钟。
并行化是标准答案，但「按用例数均分」是最常见的错误实现——三片里一片
恰好抓到几条慢用例，另外两片干等，木桶效应吃掉全部理论收益。

均衡的前提是**知道每条用例多贵**：耗时数据从哪来（junit 历史）、
怎么分（贪心策略）、分错了怎么办（守恒校验）。还有一个诚实问题：
没有历史数据时怎么办——悄悄均分装准，还是显式降级并标注。

本实验的答案链：串行全量建耗时档案（投资）→ LPT 贪心分片（利息）→
合并 + 守恒校验（兜底）→ 无历史时降级均分并如实标注（宁均衡、不装准）。

## What

耗时均衡分片调度器是一套静态分片系统：从 junit（测试框架通用的 XML 结果格式，
每条用例自带结果与耗时）历史读取每条用例的实测
耗时，按 LPT（Longest Processing Time first，最长耗时优先）贪心算法分成
N 片，N 个进程并行执行，结果合并回一个 junit 并做用例数守恒校验。

可以把 LPT 想成搬家装车：先搬大件（最重的家具各自占一辆车），再用小件（书、衣物）填缝——每辆车都装到差不多满。

但和装车不同的是，分片有「用例数守恒」这条硬约束：分片执行的总用例数必须等于档案条数，不等就拒绝出报告（退出码 2）——静默丢用例是分片系统最阴的 bug：CI 绿了，其实有一片从来没跑过。


同口径对比是提速类汇报的底线：串行基线用**实测墙钟**（含 pytest 启动），
并行墙钟同样含启动——拿 junit 时间合计（12s）对比含启动的并行墙钟（5.7s）
会算出虚高提速。

## When to Use

典型场景：

- 套件 10 分钟以上、机器核数富余的 CI：LPT 分片后按片分发到多执行机。
- 跨机器分发：xdist 是进程内工作窃取（单机、动态、不能跨机器），
  静态分片可跨执行机、可复现、可按机器算力加权——大规模 CI 两者叠加。
- 提速验收：片间最大/最小比（本实验 1.08，验收线 ≤1.30）+ 提速比
  （76%，验收线 ≥60%）双指标。

何时不用：套件本来就快（几十秒）时分片的启动开销吃掉收益
（N 片 = N 份 pytest 启动）；耗时数据方差极大且无法稳定采样时，
先治 flaky 耗时再谈均衡。

## Quick Start

前置条件：labs/09+03+13 的用例池可跑（246 条）；无 Docker 依赖。

```bash
cd architect/11_shard_scheduler
./sharding_scheduler.sh apply     # 串行跑池子（labs/09+03+13，246 条）建耗时档案
./sharding_scheduler.sh observe   # LPT 4 片并行 → 提速/均衡验收 → 无历史兜底演示
./sharding_scheduler.sh clean
```

实测输出：

```
- 串行基准（实测串行墙钟（同口径含启动））：14.0s
- 并行墙钟：3.4s → 提速 76%（验收线 ≥60%）
- 片间墙钟：['3.1', '3.3', '3.4', '3.3'] → 最大/最小比 1.08（验收线 ≤1.30）
- 用例：246 条，失败 0
无历史兜底：降级为按用例数均分并如实标注 estimated（宁均衡、不装准）
```

诚实预期：提速与均衡两条验收线（≥60%、≤1.30）应同时达标；
无历史兜底演示里，档案被删后调度器降级为按用例数均分并在报告标注
`estimated`——降级是显式的，不是悄悄装准。

关键设计（这段在做什么：跨 lab 采集与执行的四个工程决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| junit `file` 属性还原 node id | 比 classname 反推稳 | 个别插件注入的用例无 file，需 classname 兜底 |
| PYTHONPATH 注入各 lab 根 | 跨 lab 从仓库根跑会丢 ini 的 pythonpath 语义 | 表现为 ModuleNotFoundError，且只在分片跑出现 |
| `-p no:hypothesis` 压启动 | 池子用不到的重插件是纯开销 | 禁错了依赖插件的用例会挂——禁前确认池子无依赖 |
| 档案常刷新 | 代码变了耗时分布会漂 | 每次夜间全量（项目 10 tier3）顺带重建 |

## How It Works

**LPT 贪心**。按耗时从大到小排序，依次把用例放进「当前最轻」的片——
大件先安排，小件填缝。246 条小粒度用例下均衡度轻松进 1.1；若池子里有
一条 60s 的巨型用例，LPT 也只能保证它单独成片——那时该做的是拆用例
（白盒提速），不是加机器。

**顺序依赖的模块先合成一件再分**。分片的前提是用例独立：labs/09 的
污染演示用例 step_2/3 靠 step_1 留下的全局状态才能过，按单条用例 LPT
会把它们拆进不同进程、必红——调度器对这类模块（`KEEP_TOGETHER`）
先整体合成一个「大件」参与贪心，分完再展开回原 node id。

**用例数守恒校验**。合并 junit 时校验总用例数与档案条数一致，不一致拒绝
出报告。守恒校验兜住的是「分片丢了用例」这类静默事故——CI 绿了但
保护网破了。

**无历史降级**。档案不存在时，调度器显式降级为按用例数均分，报告标注
`estimated`——宁可均衡不精确，不可精确地假装。

## Pitfalls & Q&A

踩坑清单：

- **跨 lab 跑丢 pythonpath**。现象：分片跑 `ModuleNotFoundError`、单跑正常。
  原因：仓库根运行时各 lab 的 ini 语义丢失。解法：PYTHONPATH 注入各 lab 根。
- **禁插件禁出依赖事故**。现象：`-p no:hypothesis` 后依赖它的用例挂。
  解法：禁插件前确认池子无依赖（本实验池子确认后禁）。
- **口径不一致的提速汇报**。现象：junit 合计 vs 墙钟混比，提速虚高。
  解法：两边都用含启动的实测墙钟。
- **守恒校验缺席**。现象：某片 crash 后报告照样出，用例静默丢失。
  解法：总数不等即退出码 2，拒绝出报告。

深入问答：

- **Q：pytest-xdist 和自研分片什么关系？**
  xdist 是进程内工作窃取（单机、动态、不能跨机器）；自研分片是静态规划
  （可跨执行机、可复现、可按机器算力加权）。大规模 CI 两者叠加：平台层
  分片到多机，机内 xdist 吃满核。
- **Q：为什么启动开销不能忽略？**
  4 个分片进程 = 4 份 pytest 启动 + conftest 导入（本实验约 1s/片）。
  池子越小，开销占比越高——「微套件测不出提速」，验收必须用 246 条的
  池子跑。同理，分片数不是越多越快：N 片 = N 份启动。
- **Q：档案里的耗时会骗人吗？**
  会——用例耗时受机器负载/IO 缓存影响抖动 ±20%。工程做法：取最近 N 次
  运行的移动平均；离群（超 3σ）按 3σ 截断。本实验单次采样，
  如实说明这是教学简化。
- **Q：失败重跑怎么不拖垮均衡？**
  重跑放大失败片的耗时。标准做法：失败用例即时标记、当轮不重跑，
  统一进「重试层」串行确认（flaky 判定是项目 13 的事）——分片层保持
  纯函数语义：输入片单，输出报告。
- **Q：提速 76% 之后还能再快吗？**
  三板斧只剩两板：白盒优化（剖析慢用例本身，见 performance/04/05 的
  方法论）与精准跳过（项目 4/12 的变更选择，直接不跑无关用例）。
  分片的天花板是「用例本身的总计算量」，它是常数，除非用例变少或变快。

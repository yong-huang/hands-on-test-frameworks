# 11 · 耗时均衡分片调度器：把 14 分钟砍进 4 分钟

> 并行跑测试人人会（`-n auto`），但「按用例数均分」在有一条 10 秒的长用例时立刻翻车——
> 木桶效应让三片等一片。本实验实现工程效能的标准答案：**junit 历史耗时 → LPT 贪心分片 →
> N 进程并行 → junit 合并 + 守恒校验**。实测 246 条用例：串行 14.0s → 并行 3.4s
>（提速 76%），片间最大/最小比 1.08。清单第 11/28 项。

## 1. 为什么需要它

- CI 等待是工程师注意力的黑洞：套件每慢 1 分钟，全队每天多等几十分钟；
- 均分是错的，均衡才是对的——而均衡的前提是**知道每条用例多贵**；
- 「无历史数据」必须显式降级而不是悄悄均分装准（本实验的诚实底线）。


## 4. 核心概念

### 4.1 LPT 贪心（Longest Processing Time first）
按耗时从大到小排序，依次把用例放进「当前最轻」的片——大件先安排，小件填缝。
246 条小粒度用例下均衡度轻松进 1.1；若池子里有一条 60s 的巨型用例，LPT 也只能
保证它单独成片——那时该做的是拆用例（白盒提速），不是加机器。

### 4.2 用例数守恒校验
分片执行的总用例数必须等于档案条数，不等就拒绝出报告（退出码 2）。静默丢用例是
分片系统最阴的 bug：CI 绿了，其实有一片从来没跑过。

### 4.3 同口径对比
串行基线用**实测墙钟**（含 pytest 启动），并行墙钟同样含启动——拿 junit 时间合计
（12s）对比含启动的并行墙钟（5.7s）会算出虚高提速。口径统一是提速类汇报的底线。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| junit `file` 属性还原 node id | 比 classname 反推稳 | 个别插件注入的用例无 file，需 classname 兜底 |
| PYTHONPATH 注入各 lab 根 | 跨 lab 从仓库根跑会丢 ini 的 pythonpath 语义 | 表现为 ModuleNotFoundError，且只在分片跑出现 |
| `-p no:hypothesis` 压启动 | 池子用不到的重插件是纯开销 | 禁错了依赖插件的用例会挂——禁前确认池子无依赖 |
| 档案常刷新 | 代码变了耗时分布会漂 | 每次夜间全量（项目 10 tier3）顺带重建 |

## 7. 深入要点

**Q1：pytest-xdist 和自研分片什么关系？** xdist 是进程内工作窃取（单机、动态、不能跨
机器）；自研分片是静态规划（可跨执行机、可复现、可按机器算力加权）。大规模 CI 两者
叠加：平台层分片到多机，机内 xdist 吃满核。labs/09 学 xdist 用法，本实验学调度。

**Q2：为什么启动开销不能忽略？** 4 个分片进程 = 4 份 pytest 启动 + conftest 导入
（本实验约 1s/片）。池子越小，开销占比越高——「微套件测不出提速」，验收必须用
246 条的池子跑。同理，分片数不是越多越快：N 片 = N 份启动。

**Q3：档案里的耗时会骗人吗？** 会——用例耗时受机器负载/IO 缓存影响抖动 ±20%。
工程做法：取最近 N 次运行的移动平均；离群（超 3σ）按 3σ 截断。本实验单次采样，
README 如实说明这是教学简化。

**Q4：失败重跑怎么不拖垮均衡？** 重跑放大失败片的耗时。标准做法：失败用例即时标记、
当轮不重跑，统一进「重试层」串行确认（flaky 判定是项目 13 的事）——分片层保持
纯函数语义：输入片单，输出报告。

**Q5：提速 76% 之后还能再快吗？** 三板斧只剩两板：白盒优化（剖析慢用例本身，见
performance/04/05 的方法论）与精准跳过（项目 4/12 的变更选择，直接不跑无关用例）。
分片的天花板是「用例本身的总计算量」，它是常数，除非用例变少或变快。

## 8. 总结

LPT 分片把 246 条用例从 14.0s 压到 3.4s（76%），均衡比 1.08，守恒校验兜住静默丢用例，
无历史时如实降级——「测试提速」从口号变成一组可验收的数字。下一篇是清单项目 12
「静态增量测试选择器」：比分片更狠的提速是根本不跑无关的测试。

# 01 · 测试资产分层审计：给 30 个实验画一张「金字塔画像」

> 你已经用 30 个实验把 pytest / Playwright / Cypress / Selenium 全部跑通了——但「会用工具」
> 和「会设计体系」之间隔着一道坎：架构师接手一个团队，第一件事不是写测试，而是**让数据回答
> "家底长什么样"**。本实验不新增任何测试，只对你亲手做过的 labs/ 资产做一次架构师视角的审计：
> 三层各有多少用例、各吃多少时间、形状是金字塔还是冰淇淋。这是 [测试架构师清单](../../docs/test_architect.md)
> 28 个项目的第 1 个，产出的分层画像也是后续门禁（项目 3）、流水线（项目 10）、看板（项目 23）的数据源。

## 1. 为什么需要它

「测试金字塔」人人会背（多单测、少集成、更少 E2E），但背出来和算出来是两回事：

- **没有画像就没有话语权**：面试官问「你们自动化分层合理吗」，答「大概六三一吧」和答
  「实测 418 条用例，单元 74.4% / 集成 11.5% / E2E 12.2%，E2E 用例只占 12% 却吃掉 48.7% 的
  耗时」，是两个物种。
- **数量占比 ≠ 成本占比**：这正是金字塔「少留 E2E」的真实依据——本次实测里 E2E 层每条用例
  的平均成本约是单元层的 9 倍（见 §2 的耗时占比背离）。
- **审计本身可复用**：换个仓库、改改 `layer_rules.yaml`，这套工具直接迁移——架构师的
  第一件行李。

## 3. 快速开始

```bash
cd architect/01_pyramid_audit
./pyramid_audit.sh apply     # 种子数据 + 起 SUT(:8899) + 健康轮询
./pyramid_audit.sh observe   # ① 秒级快速画像(--no-timed) ② 全量审计(实测一轮约 53s) ③ 产物清点
./pyramid_audit.sh clean     # 停 SUT、删报告，目录回到实验前状态
# 或一条龙：./pyramid_audit.sh all
```

验收自查（清单原文要求）：报告含三层「数量占比 + 耗时占比」共 6 个数字；任选 ≥2 项跑

每条带证据数字与落地映射）。

## 4. 核心概念

### 4.1 三层 + 塔外：口径先于数字

单元层（进程内验证一个函数/模块）、接口/集成层（对运行中服务或真实依赖）、UI E2E 层
（浏览器驱动真实用户路径）。**性能 / a11y / 安全 / CI 不画进金字塔但不假装它们不存在**——
单列为「塔外资产」（26_locust、27_k6、29_a11y_security 等），这也是 §7 建议的入口。
易错点：把「有 UI 的步骤」都算 E2E。本审计按 **被测对象与依赖** 分层（进程内=单元，
打服务=集成，开浏览器=E2E），不按测试文件命名分。

### 4.2 计数：collect-only 精确到参数化展开

pytest 侧用 `--collect-only -q` 拿展开后的用例数（labs/03 的 24 条 = 参数化展开结果；
labs/09 的 212 条 = 200 条 workload + 12 条污染演示），cypress 用正则数 `it()`，
locust 数 `@task`，k6 数场景脚本。易错点：** labs/09、29 的 pytest.ini 自带 `addopts = -q`，
叠加后输出变成逐文件格式且汇总行消失——所以计数器兼容两种输出格式**（工具里写死了注释）。

### 4.3 计时：junit-xml 标准产物，不猜屏幕输出

实测一轮 = 对每个有资格的 lab 真跑 `pytest -q`，墙钟用 `perf_counter`，
通过/失败数从 **junit-xml 解析**而不是 grep 控制台——屏幕输出随 verbosity 变，
标准产物不变。这是本项目最重要的工程决策：审计工具自己不能是「猜输出」的脆弱脚本。

### 4.4 计时口径与诚实标注

v1 口径：**只有 pytest 栈实测计时**（20 个 lab）；cypress / selenium / 移动栈（6 个 lab
共 35 条用例）只计数，报告里每个未实测 lab 都带原因（非 pytest 栈 / 服务端口未起 /
资格未开启）。测不了的不编造——这条红线来自清单技能本身，也是架构师汇报的基本功。

## 5. YAML 关键字段（configs/layer_rules.yaml）

| 字段 | 为什么需要 | 坑 |
|:---|:---|:---|
| `layer` | 归属层 unit/integration/e2e/outside，报告按它归并 | 按「依赖什么」分，不按目录名分 |
| `counter` | 每栈一个计数策略；`none` 表示无用例资产 | cypress 计数是静态近似，动态生成的用例不计 |
| `timed` | 计时资格开关；`false` 的 lab 只计数 | 忘了关会让 `counter: none` 的 lab 白跑一轮 pytest |
| `service` | 计时前置端口，探测不通就如实跳过 | 6 个 lab 各一个端口（8899~8929）——本身就是审计发现 №2 |
| `pytest_args` | Playwright lab 需要 `--base-url` + `--browser chromium` | 缺 `--base-url` 时 `page.goto("/")` 直接报错 |
| `expected_fail` | 教学演示含故意失败用例（labs/01/06/10/17/20） | 不声明的话，「默认不绿」会被误报成审计发现 |
| `timeout` | testcontainers 首跑要拉镜像 | 给 14 单独配 600s，默认 300s |

## 7. 深入要点

**Q1：E2E 只占 12.2% 数量却占 48.7% 耗时，这个背离说明什么？**
金字塔的本质不是美学而是**成本曲线**：本审计里单元层单用例均值 0.05s（311 条/16.96s），
E2E 层 0.51s（51 条/25.96s），差一个数量级——还不算 E2E 的脆弱性维护成本（labs/17 的
sleep 反模式就是活例子）。所以「下沉」省的是最贵的钱：只验证业务规则的 UI 用例改成接口
用例，断言不变、成本 1/10。

**Q2：为什么判定是「过渡形态」而不是「冰淇淋」？**
判定规则是分档的：E2E ≤10% 且单元 ≥60% 才是金字塔；**单元 < E2E** 才是冰淇淋（上层浮肿）；
本次 74.4% vs 12.2%，基础其实扎实，只是 E2E 超标 2 个点——所以给「过渡形态 ⚠️」并指方向
（下沉），而不是吓唬人推倒重来。架构师汇报要区分「不及格」和「未满分」。

**Q3：testcontainers 那个 lab 首跑 144s、二跑 6.2s，报告该怎么呈现？**
首跑耗时是**环境成本**（拉 Postgres 镜像），不是套件成本。诚实做法是像本工具一样：
把口径写清（墙钟含容器拉起），JSON 里留 `wall_s` 原始值，报告备注「首跑可能拉镜像」。
面试高频题「压测数据怎么才可信」同源：**测量口径本身就是质量属性**。

**Q4：6 个 lab 各自约定 SUT 端口（8899/8921/8923/8924/8928/8929），为什么算发现？**
一份应用起了六份「私有实例约定」，意味着没有统一的环境供给层——谁起的服务、数据是否
隔离、端口冲突谁管，全靠脚本自觉。这条证据直接引出清单项目 16「Ephemeral 环境工厂」；
面试里「测试环境怎么管」的答案就从这类审计证据里来。

**Q5：报告里「默认不绿」的 lab（故意失败演示）对真实团队有什么映射？**
labs/01/06/10/17/20 默认跑就挂（教学演示设计如此），工具用 `expected_fail` 声明后区分
「设计内的红」和「意外的红」。真实团队同构：主干上长期挂着的用例会让红/绿信号失效，
门禁（清单项目 3）与 flaky 隔离（项目 13）解决的就是「什么颜色才可信」。

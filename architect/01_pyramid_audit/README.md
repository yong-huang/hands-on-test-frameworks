# 01 · 测试资产分层审计：给 30 个实验画一张「金字塔画像」

> 接手一个团队，架构师的第一件事不是写测试，而是让数据回答"家底长什么样"。
> 本实验对 labs/ 资产做一次架构师视角的审计：三层各有多少用例、各吃多少时间、
> 形状是金字塔还是冰淇淋。读完本篇你能复现这份分层画像，并把它迁移到任意仓库。

## Background

「测试金字塔」人人会背：多单测、少集成、更少 E2E（端到端测试：驱动真实浏览器走完整用户流程）。但背出来和算出来是两回事——
没有画像的团队讨论分层只能靠印象，"大概六三一吧"既无法验证也无法追踪。

没有它之前，摸家底靠两条路：翻目录数文件数（数字与真实用例数对不上，
参数化展开后的用例根本数不准）；跑全量看墙钟（只得到总耗时，分层的成本
分布照样是黑箱）。

痛点的核心是**数量占比 ≠ 成本占比**：这正是金字塔"少留 E2E"的真实依据——
本次实测里 E2E 层每条用例的平均成本约是单元层的 9 倍。不知道这个背离，
"下沉用例"就永远只是口号。

审计本身可复用：换个仓库、改改 `layer_rules.yaml`，这套工具直接迁移——
架构师的第一件行李。

## What

测试资产分层审计是对既有测试套件的盘点：按层（单元 / 集成 / E2E / 塔外）
计数、计时、算占比，并给出形状判定与重分层建议。

可以把审计想成年度体检：分层画像就是血压血脂的化验单（数字 + 参考区间），
形状判定就是医生的诊断意见。但和体检不同的是，审计只产证据不治病——
治理动作（下沉用例、上门禁）是后续实验的领地。

心智模型一句话：**规则在配置里（layer_rules.yaml），工具只负责数数、计时、
算账**——每个数字都能用一条 pytest 命令人工抽查，测不了的如实标注
「未实测 + 原因」。

## When to Use

典型场景：

- 接手陌生团队的第一周：跑一次审计，用数字开架构评审，代替主观印象。
- 建门禁与看板前的数据源盘点：分层数据是后续门禁（项目 3）、流水线
  （项目 10）、看板（项目 23）的输入。
- 跨仓库迁移：改改 `layer_rules.yaml` 的规则映射即可复用。

何时不用：全新项目还没有测试资产时，先写测试再谈画像；
团队对"什么算单元、什么算集成"没有共识时，先定口径再跑数字——
口径错了数字只会放大错误。

同类方案对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 翻目录数文件 | 快，但数不准参数化展开 | 粗略估摸 |
| 跑全量看墙钟 | 只有总耗时，无分层分布 | 冒烟体检 |
| 本审计 | 分层计数 + 实测计时 + 形状判定 | 架构决策前的家底盘 |

## Quick Start

前置条件：labs/ 系列 30 个实验已就位（审计对象是它们）；SUT（System Under
Test，被测系统——本系列的订单应用）服务由脚本自动拉起。

```bash
cd architect/01_pyramid_audit
./pyramid_audit.sh apply     # 种子数据 + 起 SUT(:8899) + 健康轮询
./pyramid_audit.sh observe   # ① 秒级快速画像(--no-timed) ② 全量审计(实测一轮约 53s) ③ 产物清点
./pyramid_audit.sh clean     # 停 SUT、删报告，目录回到实验前状态
# 或一条龙：./pyramid_audit.sh all
```

全量审计的真实输出（2026-09-19 实测，节选）：

```
 ## 形状判定：过渡形态 ⚠️（偏 E2E）

- 单元 74.4% / 集成 11.5% / E2E 12.2%（参考 70/20/10）
- 判定依据：E2E 12.2% 超出参考上限 10%

 ## 三层画像（数量占比 + 耗时占比）

| 层 | 用例数 | 数量占比 | 参考 | 实测耗时 | 耗时占比 |
|:---|---:|---:|:---:|---:|---:|
| 单元层（pytest） | 311 | 74.4% | 70% | 16.96s | 31.8% |
| 接口/集成层（API/DB/契约） | 48 | 11.5% | 20% | 10.43s | 19.5% |
| UI E2E 层 | 51 | 12.2% | 10% | 25.96s | 48.7% |
| 塔外·非功能与流水线 | 8 | 1.9% | — | 未实测 | 0.0% |
```

诚实预期：全量审计一轮约 53 秒（对每个有资格的 lab 真跑一轮 pytest）；labs/01/06/10/17/20 默认跑就挂（教学演示设计如此），工具用 `expected_fail`声明后区分「设计内的红」和「意外的红」——所以审计报告里"默认不绿"的 lab不是异常。

报告末尾自带「抽查命令」，任选 ≥2 项人工核对。


## How It Works

**口径先于数字**：分层按**被测对象与依赖**判定（进程内 = 单元，打服务 =集成，开浏览器 = E2E），不按测试文件命名分。易错点：把「有 UI 的步骤」都算 E2E。

性能 / a11y / 安全 / CI 不画进金字塔但不假装它们不存在——单列为「塔外资产」（性能 / a11y——accessibility，无障碍测试——/ 安全 / CI 都属于此类），这也是重分层建议的入口。


**计数：collect-only 精确到参数化展开**。

pytest 侧用 `--collect-only -q`拿展开后的用例数（labs/03 的 24 条 = 参数化展开结果；labs/09 的 212 条 =200 条 workload + 12 条污染演示），cypress 用正则数 `it()`，locust 数`@task`，k6 数场景脚本。

labs/09、29 的 pytest.ini 自带 `addopts = -q`，叠加后输出变成逐文件格式且汇总行消失——所以计数器兼容两种输出格式。


**计时：junit-xml 标准产物，不猜屏幕输出**。墙钟用 `perf_counter`，
通过/失败数从 junit-xml 解析而不是 grep 控制台——屏幕输出随 verbosity 变，
标准产物不变。这是本工具最重要的工程决策：审计工具自己不能是「猜输出」
的脆弱脚本。

**计时口径与诚实标注**：v1 口径只有 pytest 栈实测计时（20 个 lab）；
cypress / selenium / 移动栈（6 个 lab 共 35 条用例）只计数，报告里每个
未实测 lab 都带原因（非 pytest 栈 / 服务端口未起 / 资格未开启）。
测不了的不编造。

**layer_rules.yaml 关键字段**（这段在做什么：把分层判断全部声明化）：

| 字段 | 为什么需要 | 坑 |
|:---|:---|:---|
| `layer` | 归属层 unit/integration/e2e/outside，报告按它归并 | 按「依赖什么」分，不按目录名分 |
| `counter` | 每栈一个计数策略；`none` 表示无用例资产 | cypress 计数是静态近似，动态生成的用例不计 |
| `timed` | 计时资格开关；`false` 的 lab 只计数 | 忘了关会让 `counter: none` 的 lab 白跑一轮 pytest |
| `service` | 计时前置端口，探测不通就如实跳过 | 6 个 lab 各一个端口（8899~8929）——本身就是审计发现 №2 |
| `pytest_args` | Playwright lab 需要 `--base-url` + `--browser chromium` | 缺 `--base-url` 时 `page.goto("/")` 直接报错 |
| `expected_fail` | 教学演示含故意失败用例（labs/01/06/10/17/20） | 不声明的话，「默认不绿」会被误报成审计发现 |
| `timeout` | testcontainers 首跑要拉镜像 | 给 14 单独配 600s，默认 300s |

## Pitfalls & Q&A

踩坑清单：

- **把「有 UI 的步骤」都算 E2E**。后果：E2E 占比虚高，治理方向跑偏。
  解法：按被测对象与依赖分层，不按文件名或"有没有点浏览器"。
- **cypress 计数当成精确值**。`it()` 静态计数是近似，动态生成的用例不计——
  报告里如实标注口径。
- **忘了关 `timed`**。`counter: none` 的 lab 被白跑一轮 pytest，审计时间翻倍。

深入问答：

- **Q：E2E 只占 12.2% 数量却占 48.7% 耗时，这个背离说明什么？**
  金字塔的本质不是美学而是**成本曲线**：单元层单用例均值 0.05s（311 条 /  16.96s），E2E 层 0.51s（51 条 / 25.96s），差一个数量级——还不算 E2E 的  脆弱性维护成本（labs/17 的 sleep 反模式就是活例子）。

所以「下沉」省的是  最贵的钱：只验证业务规则的 UI 用例改成接口用例，断言不变、成本 1/10。

- **Q：为什么判定是「过渡形态」而不是「冰淇淋」？**
  判定规则是分档的：E2E ≤10% 且单元 ≥60% 才是金字塔；**单元 < E2E** 才是
  冰淇淋（上层浮肿）；本次 74.4% vs 12.2%，基础其实扎实，只是 E2E 超标
  2 个点——给「过渡形态 ⚠️」并指方向（下沉），而不是吓唬人推倒重来。
  架构师汇报要区分「不及格」和「未满分」。
- **Q：testcontainers 那个 lab 首跑 144s、二跑 6.2s，报告该怎么呈现？**
  首跑耗时是**环境成本**（拉 Postgres 镜像），不是套件成本。诚实做法是把
  口径写清（墙钟含容器拉起），JSON 里留 `wall_s` 原始值，报告备注
  「首跑可能拉镜像」。「压测数据怎么才可信」同源：**测量口径本身就是质量属性**。
- **Q：6 个 lab 各自约定 SUT 端口（8899/8921/8923/8924/8928/8929），为什么算发现？**
  一份应用起了六份「私有实例约定」，意味着没有统一的环境供给层——谁起的服务、
  数据是否隔离、端口冲突谁管，全靠脚本自觉。这条证据直接引出项目 16
  「Ephemeral 环境工厂」；「测试环境怎么管」的答案就从这类审计证据里来。
- **Q：报告里「默认不绿」的 lab 对真实团队有什么映射？**
  labs/01/06/10/17/20 默认跑就挂（教学演示设计如此），工具用 `expected_fail`
  声明后区分「设计内的红」和「意外的红」。真实团队同构：主干上长期挂着的
  用例会让红/绿信号失效，门禁（项目 3）与 flaky 隔离（项目 13）解决的
  就是「什么颜色才可信」。

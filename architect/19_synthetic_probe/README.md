# 19 · 合成监控探针：上线之后，测试团队还管什么

> 发布不是终点。合成监控用脚本**模拟真实用户走关键链路**（健康/登录/下单全链路），
> 探针失败 = 用户即将失败——比等客诉快一个量级。本实验实现完整探针系统：定时合成
> 事务 + sqlite 时序 + 连续失败告警 + 恢复自动消除。实测：15 轮 100% 成功落库；
> 搞挂 SUT 后 2 个周期内 3 条探针全部告警；重启后告警自动消除。清单第 19/28 项，
> 阶段四收官。

## 1. 为什么需要它

- 「上线之后测试团队还做什么？」的标准答案第一句就是合成监控（右移）；
- 真实用户监控（RUM）要等真用户踩坑，合成监控**主动制造流量**，覆盖低频关键路径；
- 告警噪音是监控体系的死穴：单次抖动就报警，一周后没人看告警了。


## 4. 核心概念

### 4.1 合成事务不是 ping
三条探针三种深度：health（进程活着）、login_page（页面能渲染出表单）、order_flow
（**下单→查询→删单全链路业务事务**，自清理不污染数据）。ping 只能证明机器没死，
合成事务才能证明「用户还能下单」。

### 4.2 连续失败状态机
连挂 ≥2 次才触发（单次网络抖动不吵人）；一次成功即消除（活过来了就闭嘴）。
阈值 2 是「告警延迟 vs 噪音」的旋钮：探针周期 1 分钟时，2 连挂 = 2 分钟检出——
SLA 决定阈值，不是感觉。

### 4.3 状态持久化在 sqlite
告警状态如果只在内存，探针重启就失忆（告着警却再也不触发）。落库后进程随时重启，
触发/消除的时间线完整可审计——报告里的「告警已消除（时间）」就是这份审计。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 探针事务自清理 | 探针流量不能变成数据污染（项目 7 纪律） | 下单探针跑一周，库里的「probe」订单就是垃圾场 |
| 连续失败而非单次失败 | 抖动与故障要区分 | 阈值=1 时告警噪音会把值班逼疯 |
| 独立 cursor 查统计 | sqlite 外层迭代中再 execute 会掐断迭代（本次踩坑） | 静默表现为「只统计到第一条」，极难察觉 |
| 恢复自动消除告警 | 恢复不消除=狼来了疲劳 | 只消除不记录恢复时间，复盘就没有 MTTR |

## 7. 深入要点

**Q1：合成监控和 RUM（真实用户监控）怎么分工？** 合成：主动、确定性、覆盖低频关键
路径、可跑在任何环境（含灰度）；RUM：真实分布、覆盖长尾设备/网络，但只能被动等。
两者互补：合成保「关键路径随时可用」，RUM 答「真实体验分布如何」。

**Q2：探针多久跑一次合适？** 由「不可用多久算事故」倒推：MTTD 目标 2 分钟 → 周期
1 分钟 + 连挂 2 次阈值。探针太密对下游是 DDoS（尤其重事务），太疏告警变马后炮——
周期 × 阈值 = 最早检出时间，这是个乘法题不是拍脑袋。

**Q3：下单探针往生产库写数据？** 隔离：探针账号 + 测试命名空间（项目 7 的 QA- 前缀）
+ 专用支付沙箱。探针自清理是纪律，但万一探针挂在中途，残留数据要能被 GC 识别——
又是命名空间打标的用处。

**Q4：告警触发后要不要自动重启/切换？** 分级：探针失败 → 先自动重试确认（防探针
自身故障）；确认故障 → 触发预案（重启/切流），预案由人评审过并演练过。没演练过的
自动预案是最大风险源——「自动恢复」把小故障放大成大故障的案例不少见。

**Q5：报告里成功率 83.3% 是不是太低？** 窗口里包含了故意搞挂 SUT 的故障期（24 轮
中 5 轮挂）——83.3% 是**含故障的窗口统计**，故障前基线是 100%。监控指标的口径
（窗口/分位）必须随数字一起报，否则就是误导（呼应项目 14 的口径纪律）。

## 8. 总结

15 轮 100%、2 周期告警、恢复自动消除——「上线之后还活着吗」从一个担忧变成一张
时序表。至此阶段四（环境/配置/灰度/探针）全部收官，测试体系完成了从左移到右移的
完整覆盖。下一篇进入阶段五：清单项目 20「从业务流量到压测模型」——压测方案题的
标准答法。

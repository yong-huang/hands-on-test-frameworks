# 19 · 合成监控探针：上线之后，测试团队还管什么

> 发布不是终点。合成监控用脚本**模拟真实用户走关键链路**
> （健康/登录/下单全链路），探针失败 = 用户即将失败——比等客诉快一个量级。
> 本实验实现完整探针系统：定时合成事务 + sqlite 时序 + 连续失败告警 +
> 恢复自动消除。实测：15 轮 100% 成功落库；停掉 SUT 后 2 个周期内 3 条探针
> 全部告警；重启后告警自动消除。阶段四收官。

## Background

「上线之后测试团队还做什么？」的标准答案第一句就是合成监控（右移）。
测试左移保证了发布那一刻的质量，发布之后系统的健康没有人主动盯着——
直到真实用户踩坑、客诉进来。

真实用户监控（RUM）要等真用户踩坑，覆盖靠运气；合成监控**主动制造流量**，
按固定周期把关键链路走一遍——低频关键路径（登录、下单）也能被持续覆盖。

告警噪音是监控体系的死穴：单次网络抖动就报警，一周后没人看告警了。
告警系统要同时回答两个问题：什么时候响（连续失败阈值）、什么时候闭嘴
（恢复自动消除）。

## What

合成监控探针是一套主动巡检系统：**定时器 → 三条合成事务 → 连续失败
状态机（连挂 2 触发、1 成消除）→ sqlite 留痕**。

可以把探针想成商场的定时巡逻保安：按固定路线每分钟巡一遍（健康/登录/下单三条路线），发现异常不立刻拉警报——连着两圈都异常才响（单次可能是顾客撞了一下），恢复正常就闭嘴（活过来了就消除告警）。

但和保安不同的是，巡逻记录全部落库（sqlite 时序）——什么时候响的、什么时候消的，复盘有完整时间线。


告警状态持久化在 sqlite——探针进程随时死掉重启，状态不能丢；
告着警却失忆是监控的灵异事故。

## When to Use

典型场景：

- 上线后的持续巡检：关键链路（登录/下单）分钟级覆盖，探针失败先于用户。
- 灰度发布的后续观测：项目 18 判定放量后，探针接管天级巡检
  ——右移的两段时间线。
- SLA 报告（服务等级协议，对可用性/延迟的正式承诺）：探针时序表就是履约证据
  （本实验 24 轮、平均延迟 2-5ms）。

何时不用：没有可自动化的关键链路（纯人工操作的业务）时无从合成；
探针事务对下游压力过大（重事务、高成本）时要先做隔离与降频设计。

实测输出（节选）：

```
① 基线：round 15/15 health=✅ login_page=✅ order_flow=✅
   3 条探针链路全部 100% 成功、无告警 ✅
② 停 SUT 后 4 轮内：
   🚨 ALERT 触发：health 连续 2 次失败（ConnectError: Connection refused）
   🚨 ALERT 触发：login_page / order_flow 同样触发 → 告警活跃 3 条 ✅
③ 重启 SUT：
   ✅ RECOVERED 告警消除：health / login_page / order_flow 探针恢复 ✅
④ 报告：24 轮，成功率 83.3%（含故障窗口），平均延迟 2-5ms
```

诚实预期：④ 的 83.3% 不是质量差——窗口里包含了故意停掉 SUT 的故障期
（24 轮中 5 轮挂），故障前基线是 100%。监控指标的统计口径（按哪个时间窗口、
按哪个分位数统计）必须随数字一起报，否则就是误导。

## Quick Start

前置条件：labs/00 体检通过；脚本自动起 SUT 并清空探针库。

```bash
cd architect/19_synthetic_probe
./synthetic_probe.sh apply     # 起 SUT + 清空探针库
./synthetic_probe.sh observe   # 15 轮基线 → 搞挂 SUT 看告警 → 重启看恢复 → 报告
./synthetic_probe.sh clean
```

关键设计（这段在做什么：告警可信度的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 探针事务自清理 | 探针流量不能变成数据污染（项目 7 纪律） | 下单探针跑一周，库里的「probe」订单就是垃圾场 |
| 连续失败而非单次失败 | 抖动与故障要区分 | 阈值=1 时告警噪音会把值班逼疯 |
| 独立 cursor 查统计 | sqlite 外层迭代中再 execute 会掐断迭代（本次踩坑） | 静默表现为「只统计到第一条」，极难察觉 |
| 恢复自动消除告警 | 恢复不消除=狼来了疲劳 | 只消除不记录恢复时间，复盘就没有 MTTR（平均恢复时间） |

## How It Works

**合成事务不是 ping**。三条探针三种深度：health（进程活着）、login_page
（页面能渲染出表单）、order_flow（**下单→查询→删单全链路业务事务**，
自清理不污染数据）。ping 只能证明机器没死，合成事务才能证明
「用户还能下单」。

**连续失败状态机**。连挂 ≥2 次才触发（单次网络抖动不吵人）；一次成功即
消除（活过来了就闭嘴）。阈值 2 是「告警延迟 vs 噪音」的旋钮：探针周期
1 分钟时，2 连挂 = 2 分钟检出——SLA 决定阈值，不是感觉。
周期 × 阈值 = 最早检出时间，这是个乘法题。

**状态持久化在 sqlite**。告警状态如果只在内存，探针重启就失忆
（告着警却再也不触发）。落库后进程随时重启，触发/消除的时间线完整可审计
——报告里的「告警已消除（时间）」就是这份审计，它同时给出了 MTTR
（平均恢复时间）的原料。

## Pitfalls & Q&A

踩坑清单：

- **探针流量变成数据污染**。现象：生产库堆积 probe 订单。
  解法：探针账号 + 测试命名空间（QA- 前缀）+ 事务自清理。
- **单次失败就告警**。现象：告警噪音把值班逼疯，告警被无视。
  解法：连续失败阈值 ≥2，抖动与故障分开。
- **sqlite 迭代中再 execute**。现象：统计只到第一条（本次踩坑，静默难察）。
  解法：外层迭代与内层查询用独立 cursor。
- **恢复不消除、消除不留痕**。现象：狼来了疲劳，或复盘没有 MTTR。
  解法：恢复自动消除 + 消除时间落库。

深入问答：

- **Q：合成监控和 RUM（真实用户监控）怎么分工？**
  合成：主动、确定性、覆盖低频关键路径、可跑在任何环境（含灰度）；
  RUM：真实分布、覆盖长尾设备/网络，但只能被动等。两者互补：合成保
  「关键路径随时可用」，RUM 答「真实体验分布如何」。
- **Q：探针多久跑一次合适？**
  由「不可用多久算事故」倒推：MTTD（平均检出时间，从故障发生到告警响起的时长）目标 2 分钟 → 周期 1 分钟 + 连挂 2 次
  阈值。探针太密对下游是 DDoS（尤其重事务），太疏告警变马后炮。
- **Q：下单探针往生产库写数据？**
  隔离：探针账号 + 测试命名空间（项目 7 的 QA- 前缀）+ 专用支付沙箱。
  探针自清理是纪律，但万一探针挂在中途，残留数据要能被 GC 识别
  ——又是命名空间打标的用处。
- **Q：告警触发后要不要自动重启/切换？**
  分级：探针失败 → 先自动重试确认（防探针自身故障）；确认故障 → 触发
  预案（重启/切流），预案由人评审过并演练过。没演练过的自动预案是最大
  风险源——「自动恢复」把小故障放大成大故障的案例不少见。

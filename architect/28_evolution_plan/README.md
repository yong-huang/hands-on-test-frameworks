# 28 · 🏁 测试架构演进方案：从 PPT 到可运行的程序

> 终极串联：现状审计（01 实测）→ 目标架构（四层）→ 90 天路线（映射 18 个真实产物）
> → 答辩 Q&A 30 问（每问指向证据）。方案的诚信由复核器保证：`python verify.py`
> 逐条跑 30 条证据命令（9 条现场重跑 + 21 条结构证据），100% 通过才允许提交——
> 主张与产物对不上会被当场暴露。清单第 28/28 项，系列收官。

## 1. 为什么需要它

- 面试压轴大题：「如果你来负责我们团队的测试体系，你怎么规划？」——考的是
  现状诊断 → 优先级 → 演进节奏 → 如何证明有效，四段缺一不可；
- 方案最大的敌人是「愿望清单」：写「引入精准测试」却不指向任何可运行的东西——
  本方案的每条主张都能被一条命令当场证明；
- 复核器是方案的 CI：产物被删/结论过时/主张夸大，复核立刻变红。

## 4. 核心概念

### 4.1 四层目标架构
度量层（23/27）→ 门禁层（03/24）→ 执行层（10/11/12/13/14/09）→ 基建层（16/17/07/
08/02/04/05/25），右移线（18/19）纵贯。四层各自可独立演进，层间只通过产物 JSON
对话——这也是全景看板能一条命令聚合的原因。

### 4.2 90 天路线 = 已验证能力的编排
P1 止血（flaky+门禁）→ P2 提速（流水线+分片+精准）→ P3 体系（环境/契约/策略驱动
补测）→ P4 右移（灰度/探针/混沌/安全/LLM）。排序依据是 ROI：CI 信用先于速度，
速度先于覆盖广度。**路线没有一项是愿望**：每项都指向已跑通的产物。

### 4.3 答辩 30 问的弹药索引
每个高频问题指向对应实验的产物（表格见方案 §5）——面试答题从「我记得」升级为
「我做过，证据在这」。这正是 28 个实验的终极组织方式。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| LIVE/PROOF 双级证据 | 离线工具现场重跑最硬；服务型实验不重复起环境 | PROOF 退化为「文件存在」就失去意义——README 必须记录实测 |
| 通过率 100% 才放行 | 方案的诚信是全有或全无 | 99% 通过率的方案比 0% 更危险（假装被验证过） |
| 路线映射校验 | 每项动作指向磁盘真实目录 | 只写「13_flaky_platform」不带 architect/ 前缀会让校验漏报（本次踩坑后修正） |
| 数据源生成有顺序 | 13 的 flaky 数据先产出，03 门禁才不会按旧数据拦截 | 数据依赖的拓扑序，乱序就是间歇性红 |

## 7. 深入要点

**Q1：90 天路线为什么这个顺序？** ROI 三级：止血类（flaky/门禁）恢复信号信用，
信用是一切改进的政治前提；提速类（流水线/分片/精准）立刻兑现体感；体系类
（环境/契约/策略补测）需要跨团队协作所以放后——先赢小仗再打大仗。

**Q2：方案怎么应对「计划赶不上变化」？** 复核器让方案变成**可重估的程序**：每季度
重跑一次 verify + 重刷 01 审计，现状变了路线就重排——方案的版本控制对象是
「主张+证据」对，不是 PPT 页面。

**Q3：28 个实验里最值得先向面试官展示哪三个？** 01（会用数据说话）、11（246 条
实测提速 76% 的硬数字）、27（一条命令跑出体系全貌）——分别证明思考力、工程力、
运营力，其余按岗位 JD 定向展开。

**Q4：这套体系的边界/已知简化？** 诚实清单：耗时档案单次采样（未做移动平均）、
轻量 DAST 只做只读探测、契约矩阵未接真 Broker、LLM 评测以 mock 为主。方案里写
边界比吹全能更能建立信任——这也是全系列「不编造」红线的收官表达。

**Q5：下一步（28 之后）还做什么？** 三条自然延伸：产物时序化（趋势而非快照）、
机制活性监视（26 Q4 的升级）、多团队租户化（27 Q5 的中台化）——本清单结束的
不是学习，是把这套体系搬到真实组织的开始。

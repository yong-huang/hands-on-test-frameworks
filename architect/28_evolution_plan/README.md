# 28 · 测试架构演进方案：从 PPT 到可运行的程序

> 终极串联：现状审计（[01 实测](../01_pyramid_audit/README.md)）→ 目标架构
> （四层）→ 90 天路线（映射 18 个真实产物）→ 答辩 Q&A 30 问（每问指向证据）。
> 方案的诚信由复核器保证：`python verify.py` 逐条跑 30 条证据命令
> （9 条现场重跑 + 21 条结构证据），100% 通过才允许提交——主张与产物对不上
> 会被当场暴露。系列收官。

## Background

「如果你来负责我们团队的测试体系，你怎么规划？」——考的是四段完整链路：
现状诊断 → 优先级 → 演进节奏 → 如何证明有效，缺一不可。

方案最大的敌人是「愿望清单」：写「引入精准测试（按本次代码改动范围、只回归
受影响用例的测试策略）」却不指向任何可运行的
东西。愿望清单式方案的通病是无法证伪——写的人永远"在推进"，
看的人永远无法验证。

解法是把方案做成**可复核的程序**：每条主张挂一条证据命令，复核器逐条
执行——产物被删、结论过时、主张夸大，复核立刻变红。
复核器是方案的 CI。

## What

测试架构演进方案是一套「主张→证据→复核」闭环：**主张（方案）→
证据（产物）→ 复核（verify.py）**——9 条 LIVE 证据现场重跑离线工具，
21 条 PROOF 证据核对真实运行记录；30/30 全过方案才成立。

可以把这套闭环想成学术研究的可复现性要求：论文的每个结论都附实验代码，
审稿人（复核器）跑一遍代码验证结论。但和论文不同的是，这里的复核是
常态化的——每季度重跑一次 verify + 重刷 01 审计，现状变了路线就重排，
方案的版本控制对象是「主张+证据」对，不是 PPT 页面。

**四层目标架构**：度量层（23/27）→ 门禁层（03/24）→ 执行层
（10/11/12/13/14/09）→ 基建层（16/17/07/08/02/04/05/25），
右移线（18/19）纵贯。四层各自可独立演进，层间只通过产物 JSON 对话
——这也是全景看板能一条命令聚合的原因。

## When to Use

典型场景：

- 测试体系规划：现状审计 → 四层架构 → 90 天路线 → 证据复核，
  四段一体的方案骨架。
- 答辩汇报：30 个高频问题每个指向对应实验的产物——答题从「我记得」
  升级为「我做过，证据在这」。
- 季度重估：重跑 verify 重排路线——方案是可重估的程序，不是一次性 PPT。

何时不用：团队只有三五个人、体系尚未起步时，四层架构是过度设计——
先按 90 天路线的 P1 止血项动手，架构随产物生长。

实测输出（节选）：

```
✅ [LIVE]  C01 资产分层画像可复算（418 用例过渡形态）
✅ [LIVE]  C03 质量门禁可裁决（覆盖率实测 98% PASS）
✅ [LIVE]  C17 配置漂移可检测（三环境基线 0 漂移）

✅ [PROOF] C27 全景看板完成（make 一键 11 指标）

```

## Quick Start

前置条件：纯离线（LIVE 证据是离线工具的现场重跑，无需 Docker/网络）。

```bash
cd architect/28_evolution_plan
./evolution_plan.sh apply     # 生成六路数据源（离线轻量）
./evolution_plan.sh observe   # 30 条证据复核 + 路线映射校验
./evolution_plan.sh clean
# 方案正文：plan/evolution_plan.md（现状审计/四层架构/90 天路线/Q&A 30 问）
```

诚实预期：30 条证据应全部通过（100% 达标，本实验作者实测复核耗时 9.5s）；
路线图映射的 18 个产物目录应全部真实存在。方案的已知简化诚实清单：
耗时档案单次采样（未做移动平均）、轻量 DAST 只做只读探测、契约矩阵未接
真 Broker、LLM 评测以 mock 为主——**写边界比吹全能更能建立信任**。

**90 天路线 = 已验证能力的编排**：P1 止血（flaky+门禁）→ P2 提速（流水线+分片+精准）→ P3 体系（环境/契约/策略驱动补测）→ P4 右移（灰度/探针/混沌/安全/LLM）。

排序依据是 ROI（投入产出比）：CI 信用先于速度，速度先于覆盖广度。**路线没有一项是愿望**：每项都指向已跑通的产物。


关键设计（这段在做什么：方案诚信的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| LIVE/PROOF 双级证据 | 离线工具现场重跑最硬；服务型实验不重复起环境 | PROOF 退化为「文件存在」就失去意义——文档必须记录实测 |
| 通过率 100% 才放行 | 方案的诚信是全有或全无 | 99% 通过率的方案比 0% 更危险（假装被验证过） |
| 路线映射校验 | 每项动作指向磁盘真实目录 | 只写「13_flaky_platform」不带 architect/ 前缀会让校验漏报（本次踩坑后修正） |
| 数据源生成有顺序 | 13 的 flaky 数据先产出，03 门禁才不会按旧数据拦截 | 数据依赖的拓扑序，乱序就是间歇性红 |

## How It Works

**LIVE/PROOF 双级证据**。LIVE：离线工具现场重跑（最硬——当着你的面
再算一遍）；PROOF：服务型实验不重复起环境，核对真实运行记录
（reports 时间戳/产物结构）——PROOF 的底线是文档记录过实测，
退化为「文件存在」就失去意义。

**通过率 100% 才放行**。99% 通过率的方案比 0% 更危险——
它假装被验证过。方案的诚信是全有或全无。

**数据源生成的拓扑序**。13 的 flaky 数据先产出，03 门禁才不会按旧数据
拦截——数据依赖决定生成顺序，乱序就是间歇性红（间歇性 CI 红的
一种常见根源）。

## Pitfalls & Q&A

踩坑清单：

- **PROOF 证据退化成文件检查**。现象：复核 100% 通过但什么也没证明。
  解法：PROOF 至少核对真实运行记录（时间戳/产物字段值）。
- **路线映射路径不带前缀**。现象：校验漏报（本次踩坑后修正）。
  解法：映射写全 `architect/13_flaky_platform` 相对路径。
- **数据源乱序生成**。现象：门禁按过期数据拦截，复核间歇性红。
  解法：按数据依赖拓扑序生成。
- **方案只写愿景不写边界**。现象：信任崩塌。
  解法：已知简化诚实清单随方案交付。

深入问答：

- **Q：90 天路线为什么这个顺序？**
  ROI 三级：止血类（flaky/门禁）恢复信号信用，信用是一切改进的政治前提；
  提速类（流水线/分片/精准）立刻兑现体感；体系类（环境/契约/策略补测）
  需要跨团队协作所以放后——先赢小仗再打大仗。
- **Q：方案怎么应对「计划赶不上变化」？**
  复核器让方案变成**可重估的程序**：每季度重跑一次 verify + 重刷 01 审计，
  现状变了路线就重排——方案的版本控制对象是「主张+证据」对。
- **Q：28 个实验里最值得先展示哪三个？**
  01（会用数据说话）、11（246 条实测提速 76% 的硬数字）、27（一条命令
  跑出体系全貌）——分别证明思考力、工程力、运营力，其余按岗位 JD
  定向展开。
- **Q：这套体系的边界/已知简化？**
  诚实清单：耗时档案单次采样、轻量 DAST 只读探测、契约矩阵未接真 Broker、
  LLM 评测以 mock 为主。方案里写边界比吹全能更能建立信任——
  这也是全系列「不编造」红线的收官表达。
- **Q：下一步还做什么？**
  三条自然延伸：产物时序化（趋势而非快照）、机制活性监视（项目 26 的
  升级）、多团队租户化（项目 27 的中台化）——本清单结束的不是学习，
  是把这套体系搬到真实组织的开始。系列收官：**会用工具（labs）→
  会做性能（performance）→ 会设计体系（architect）**。

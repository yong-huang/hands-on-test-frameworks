# 09 · 自愈 UI 定位器实验：脆的不是测试，是耦合

> UI 自动化最大痛点：前端一改 class，几十条用例全红。自愈（self-healing）的
> 回答是把「定位」从单点选择器升级为**带记忆的策略链**：css → role →
> placeholder → 文本 → 档案。实测：5 个改版页面自愈率 1.0；语义全毁的页面
> **拒绝误愈如实红**；第二轮重跑 8 次定位直接命中档案免愈。
> UI 栈的定位/等待基础见 labs/16-20。

## Background

选择器硬编码是用例与前端实现的耦合：前端改一个 class，几十条用例全红，
改版成本被测试团队单方面承担。更隐蔽的是，这种脆性让团队不敢重构前端——
测试套件从保护网变成了绊马索。

「AI 自愈」是当下测试平台的热门能力，但讨论多停留在"自愈是什么"，
真正落地要回答的是工程问题：**自愈的误报风险怎么控**？语义都没了的元素，
任何"愈"都是把用例指到错误控件上——误愈比失败更贵。

自愈的工程骨架不需要 AI：一条按语义稳定性排序的策略链 +
一个记录工程判断的档案 + 一条拒绝误愈的底线，就能把改版自愈率做到 1.0。

## What

自愈定位器是一个带记忆的定位策略链：首选策略（原 css）失败后依次尝试
role → placeholder → 文本 → 档案，命中即返回并写档案。

可以把策略链想成问路的备选方案：直接报门牌号（css）找不到时，改说"卖手机的那个柜台"（role/文本——语义描述），找到后把新门牌号记在小本上（档案），下次直接报新门牌。

但和问路不同的是，所有描述都失效时（语义全毁），正确行为是**承认找不到**，而不是随便指一个柜台——拒绝误愈是底线。


心智模型一句话：**首选策略命中不算自愈，链上越靠后命中越是自愈**；
命中即写档案（改版页第二跑免愈）；策略链走完仍无命中 → 拒绝误愈，
报红并给出完整尝试记录。

## When to Use

典型场景：

- 前端持续改版的项目：改版自愈率实测 1.0（验收线 ≥0.8），
  用例不随 class 改名而红。
- 自愈平台的骨架评估：先搭策略链 + 档案，再考虑接 LLM 增强
  （语义匹配从 aria-label 扩到视觉相似度）。
- 前端规范的治理证据：自愈率高说明前端在无规范地改版——
  治理对象是前端规范，不是把自愈率当 KPI。

何时不用：定位器已经是语义化的（labs/16-20 的 role 优先实践到位）时，
自愈的增量收益有限；关键业务路径建议人工确认自愈事件——
档案是缓存不是真理。

关键设计（这段在做什么：自愈可信度的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 可见才算命中 | 只验证「找得到」不验证「找得对」会假阳性 | 加 `state=visible` + 后续 fill 断言 |
| 首选命中不计自愈率 | 自愈率衡量的是容错能力不是定位能力 | 把首选命中算进去会高估 |
| 档案按 页面+语义键 存 | 同一控件在多页面的定位互不干扰 | 语义键（客户名输入框）要团队规范，不能随便起 |
| file:// 页面 | 无需服务，实验室零依赖 | 需要登录态的页面要走真服务（项目 16 的环境工厂） |

## Quick Start

前置条件：labs/16 的 Playwright 浏览器就绪；纯 file:// 页面，无需服务。

```bash
cd architect/09_self_healing
./self_healing.sh apply     # 清档案（冷启动，纯 file:// 页面无需服务）
./self_healing.sh observe   # 自愈套件 → 自愈率验收 → 档案学习效果
./self_healing.sh clean
```

实测输出（6 条用例 = 5 改版页 + 1 语义全毁页）：

```
① 首轮：尝试 11 次：首选命中 2 / 自愈 8 / 失败 1
        改版自愈率: 1.0（验收线 ≥0.8）→ 验收断言通过 ✅
② broken 页：策略链走尽后 AssertionError（拒绝误愈）
   ——由元测试捕获断言「确实拒绝」；真实套件中它等价于一条红用例
③ 档案学习：第二轮重跑 5.22s，8 次定位直接命中档案（免愈）
```

诚实预期：① 的自愈率 1.0 覆盖 5 种改版（改 class/改 id/删 placeholder/
嵌套重构/整体换皮）；② 的"失败"是设计内行为——语义全毁页必须拒绝误愈；
③ 验证档案的记忆效果：自愈成本只付一次。

## How It Works

**策略链按语义稳定性排序**。css（绑定实现，最脆）→ role（ARIA 语义，
最稳）→ placeholder/文本（用户可见语义）→ 档案（上次的工程判断）。
顺序不可换：**越不依赖实现细节的策略越优先**，但首选仍保留原 css
以最小化行为漂移。

**档案是自愈的记忆**。命中非首选策略时，从元素反推一个稳定 css
（name/id/placeholder 属性）写入 `locator_archive.json`。下一轮直接走
档案——8 次定位免愈就是档案在起作用。档案条目命中失败会自动落到策略链
重试并更新，档案是缓存不是真理。

**拒绝误愈的边界**。语义全毁页（id/class/placeholder/aria-label 全换且
无关联）策略链走尽 → 显式 AssertionError 带全部尝试记录。**误愈比失败
更贵**：把用例静默指到错误控件上，测试就失去了存在的意义。

**元测试的包装**。演示套件把「必须红」做成对拒绝机制的断言（元测试
捕获 AssertionError 并断言"确实拒绝"）——这是为了让 `all` 一键跑完；
真实项目中没有这层包装，find() 抛错就是用例红，两种形态等价。

## Pitfalls & Q&A

踩坑清单：

- **只验证「找得到」不验证「找得对」**。现象：自愈命中了同名但不可见的
  元素，后续断言莫名失败。解法：命中条件加 `state=visible` + fill 断言。
- **自愈率当 KPI**。现象：指标被 gaming，前端继续乱改版。
  解法：报告拆「首选命中 / 自愈 / 失败」三列，治理对象是前端规范。
- **语义键随便起**。现象：档案键冲突，多页面定位互相污染。
  解法：语义键（"客户名输入框"）进团队规范。
- **档案永不失效**。现象：两个元素互换属性后档案指错控件。
  解法：关键路径人工确认自愈事件（报告 events 列表就是 review 入口）。

深入问答：

- **Q：自愈和「等 AI 来做」什么关系？**
  本实验的策略链 + 档案就是自愈的工程骨架；LLM 只是把「语义匹配」那段
  做得更强（从 aria-label 扩到视觉/语义相似度）。骨架不搭好，
  接什么模型都是黑盒抽卡——先讲骨架再讲 AI。
- **Q：为什么元测试捕获 AssertionError 而不是让套件真红？**
  演示套件要能一键跑完，把「必须红」做成对拒绝机制的显式断言。
  真实项目中 find() 抛错就是用例红——两种形态等价。
- **Q：档案会不会过期？**
  会——档案条目命中失败会自动落到策略链重试并更新，档案是缓存不是真理。
  极端情况下（两个元素互换属性）档案可能指错，所以关键业务路径建议
  人工确认自愈事件。
- **Q：labs/16-20 已经讲了等待/定位，本实验加了什么？**
  加了**架构**：labs 讲「怎么写一个稳定的定位」，本实验讲「定位体系怎么在
  前端持续改版下自我维持」——单点技巧 vs 平台能力。自愈的正确 KPI 不是
  成功率而是「语义改版的暴露速度」：自愈把火警变成烟感，治理仍要去灭火源。

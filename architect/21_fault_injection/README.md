# 21 · 故障注入与降级验证：降级开关要真的能降级

> 「依赖挂了系统会怎样？」大多数团队的答案是「不知道，没试过」。混沌工程把答案
> 变成实验：**稳态假设 → 注入故障 → 断言行为 → 恢复验证**。本实验对标准防御
> 三件套（重试 + 熔断——连续失败达到阈值后暂时切断调用直接走备用路径 +
> 降级——返回有损的兜底结果）做四阶段注入实验，实测：500ms 延迟注入后延迟
> 8ms→525ms 有界退化零降级；持续 503 打开熔断、fallback（备用响应逻辑）兜底
> 不抛异常；
> 撤销故障后熔断自愈闭合。

## Background

降级开关「理论上能降级」和「验证过能降级」隔着一个混沌实验：重试参数、
熔断阈值、fallback 逻辑在生产事故发生前从未被真正触发过——
依赖故障是生产事故第一大户，而这些防御组件全是没打过仗的纸面配置。

混沌工程（chaos engineering）的方法论把「试试看」变成有纪律的实验：
先声明稳态假设（正常时系统什么表现）、注入受控故障、断言防御行为、
验证恢复——四步缺一不可。实验纪律本身就是能力：稳态假设、
最小爆炸半径（每次实验故意制造的影响范围要尽量小）、可撤销、可观测。

本实验的实验对象是防御组件的行为契约：**有界退化、失败兜底、自愈恢复**
——三段各自断言、全程时间线留痕。

## What

故障注入实验是一套对防御组件的验证系统：故障代理站在 SUT 前面，
模式由控制文件热切换（延迟/503/拒绝），客户端穿过代理访问 SUT，
实验编排器按四阶段断言行为。

可以把故障代理想成打靶训练的移动靶机：教练（实验编排器）控制靶机（代理）出慢球（延迟）、坏球（503）、消失球（拒绝连接），观察射手的应对（重试/熔断/降级）是否按训练大纲执行。

但和打靶不同的是，实验要求靶机随时可停（可撤销）、射手状态全程记录（可观测）——**实验对象是防御行为，不是「系统能不能扛住」这种模糊命题**。


故障注入的四种模式：latency（慢而不死，最阴险：重试定时器/超时预算
全被拉长）、error503（过载语义，应触发熔断）、refuse（宕机语义，
应触发快速失败）、正常（对照组）。每种故障考验防御组件的不同侧面
——只测一种等于没测。

## When to Use

典型场景：

- 降级开关验收：fallback 逻辑在真实 503 流量下不抛异常、返回兜底值。
- 熔断参数调优：连败阈值、冷却窗口在实验时间线上直接观察效果。
- 生产演练前彩排：同一套实验编排先在预发（预发布环境）跑通，生产演练复用纪律
  （爆炸半径与信心成正比）。

何时不用：系统还没有防御组件（无重试/熔断/降级）时先建防御再注入
——给裸奔的系统注故障只得到「挂了」一个结论；未评审撤销机制的
生产环境不能做注入。

实测输出（四阶段时间线，节选）：

```
P0 基线：中位延迟 8ms，熔断未开——稳态假设成立
P1 注入 500ms 延迟：退化后中位延迟 525ms——上升但有界 ✅（零 fallback）
P2 注入持续 503：熔断打开（第 1 次），fallback 服务 5 次——失败降级 ✅
P3 撤销故障：恢复后中位延迟 9ms，熔断闭合——自愈 ✅
✅ 四阶段实验全部通过
```

## Quick Start

前置条件：labs/00 体检通过；脚本自动起 SUT(:8899) + 故障代理(:8904)。

```bash
cd architect/21_fault_injection
./fault_injection.sh apply     # 起 SUT(:8899) + 故障代理(:8904)
./fault_injection.sh observe   # 四阶段实验：基线→延迟→503→恢复（每阶段断言）
./fault_injection.sh clean
```

诚实预期：四阶段各有一段断言——P1 验证有界退化（延迟上升但零降级）、
P2 验证熔断打开与 fallback 兜底、P3 验证自愈闭合；每阶段结论精确到
「哪个行为没兑现」，而不是只看最终状态。

关键设计（这段在做什么：实验纪律的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 故障模式走控制文件 | 实验中途热切换，无需重启（等价 toxiproxy 的 API） | 控制文件要进 reports/，别污染 configs/ |
| 每阶段独立断言 | 实验结论精确到「哪个行为没兑现」 | 只断言最终状态，中间失控会被掩盖 |
| 时间线全程留痕 | 复盘要能对齐「注入时刻 vs 熔断时刻」 | 没有时间戳的实验报告不可信 |
| 撤销后等半开窗口 | 熔断恢复有冷却期，立即探测会假失败 | sleep 是实验语义（等冷却），不是等服务 |

## How It Works

**熔断器的三个状态**。闭合（正常放行）→ 打开（连续 3 败后 3 秒内直接走
fallback，不再打依赖）→ 半开（窗口过后放一次探测，成功即闭合）。
实验 P2 断言「打开」、P3 断言「闭合」——两个方向都要验，
半开探测是最容易被写错的实现细节。

**降级的语义是「有损可用」**。fallback 返回的是兜底值（缓存/默认/空结果），
业务从「实时正确」降级为「离线正确」——降级决策是产品决策，
实验只验证「开关真的能扳动」。

**时间线即证据**。注入时刻、熔断时刻、恢复时刻全部落 reports/timeline.md
——复盘能对齐「503 注入后第几秒熔断打开」，没有时间戳的实验报告不可信。

## Pitfalls & Q&A

踩坑清单：

- **撤销后立即探测**。现象：熔断没闭合被误判为不自愈。
  原因：熔断恢复有冷却期（半开窗口）。解法：实验显式等待冷却期
  （这里的 sleep 是实验语义，不是等服务）。
- **重试风暴放大故障**。现象：依赖过载时全量客户端同时重试，流量×3
  把过载变雪崩。解法：退避+抖动、重试预算、重试失败计入熔断计数。
- **熔断阈值全局一个值**。现象：低频高价值依赖钝感、高频依赖过敏。
  解法：阈值按依赖分级配置，全局一个值等于没配置。
- **只断言最终状态**。现象：中间阶段失控被掩盖。解法：每阶段独立断言。

深入问答：

- **Q：toxiproxy 和自研代理怎么选？**
  toxiproxy 是 TCP 层标准工具（toxics——它预置的故障类型插件，如延迟/超时/
  断连——丰富、API 成熟，arm64 镜像已验证可用）；自研 HTTP 代理胜在零依赖、
  模式语义可定制。生产用 toxiproxy
  做常态故障演练平台，本实验自研是为了把「注入点选在哪」想清楚。
- **Q：混沌实验在生产能不能做？**
  能且应该（混沌工程由 Netflix 的 Chaos Monkey 开创，主张生产环境也要做实验），
  但有前置：生产演练半径控制（先影子流量——把真实请求复制一份发给试验系统、
  不影响真实用户——或单实例）、一键撤销、业务方知情、值班在岗。本实验在本地跑，
  是同一套纪律的最小实现。
- **Q：和项目 19 探针怎么配合？**
  故障注入实验验证「防御组件在注入下行为正确」；合成探针验证
  「生产环境长期健康」。生产混沌演练的观测器正是探针——注入期间探针
  应该告警、恢复后消除，一次演练同时验证两套系统。

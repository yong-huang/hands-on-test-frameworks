# 21 · 故障注入与降级验证：降级开关要真的能降级

> 「依赖挂了系统会怎样？」大多数团队的答案是「不知道，没试过」。混沌工程把答案变成
> 实验：**稳态假设 → 注入故障 → 断言行为 → 恢复验证**。本实验对标准防御三件套
>（重试+熔断+降级）做四阶段注入实验，实测：500ms 延迟注入后延迟 8ms→525ms 有界退化
> 零降级；持续 503 打开熔断、fallback 兜底不抛异常；撤销故障后熔断自愈闭合。
> 清单第 21/28 项。

## 1. 为什么需要它

- 降级开关「理论上能降级」和「验证过能降级」隔着一个混沌实验；
- 依赖故障是生产事故第一大户：没有注入实验，重试/熔断参数全是没打过仗的纸面配置；
- 实验纪律本身就是面试考点：稳态假设、最小爆炸半径、可撤销、可观测。

## 3. 快速开始

```bash
cd architect/21_fault_injection
./fault_injection.sh apply     # 起 SUT(:8899) + 故障代理(:8904)
./fault_injection.sh observe   # 四阶段实验：基线→延迟→503→恢复（每阶段断言）
./fault_injection.sh clean
```

实测输出（四阶段时间线，节选）：

```
P0 基线：中位延迟 8ms，熔断未开——稳态假设成立
P1 注入 500ms 延迟：退化后中位延迟 525ms——上升但有界 ✅（零 fallback）
P2 注入持续 503：熔断打开（第 1 次），fallback 服务 5 次——失败降级 ✅
P3 撤销故障：恢复后中位延迟 9ms，熔断闭合——自愈 ✅
✅ 四阶段实验全部通过
```

## 4. 核心概念

### 4.1 故障注入的四种模式
latency（慢而不死，最阴险：重试定时器/超时预算全被拉长）、error503（过载语义，
应触发熔断）、refuse（宕机语义，应触发快速失败）、正常（对照组）。每种故障考验
防御组件的不同侧面——只测一种等于没测。

### 4.2 熔断器的三个状态
闭合（正常放行）→ 打开（连续 3 败后 3 秒内直接走 fallback，不再打依赖）→ 半开
（窗口过后放一次探测，成功即闭合）。实验 P2 断言「打开」、P3 断言「闭合」——
两个方向都要验，半开探测是最容易被写错的实现细节。

### 4.3 降级的语义是「有损可用」
fallback 返回的是兜底值（缓存/默认/空结果），业务从「实时正确」降级为「离线正确」——
降级决策是产品决策，实验只验证「开关真的能扳动」。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 故障模式走控制文件 | 实验中途热切换，无需重启（等价 toxiproxy 的 API） | 控制文件要进 reports/，别污染 configs/ |
| 每阶段独立断言 | 实验结论精确到「哪个行为没兑现」 | 只断言最终状态，中间失控会被掩盖 |
| 时间线全程留痕 | 复盘要能对齐「注入时刻 vs 熔断时刻」 | 没有时间戳的实验报告不可信 |
| 撤销后等半开窗口 | 熔断恢复有冷却期，立即探测会假失败 | sleep 是实验语义（等冷却），不是等服务 |

## 7. 深入要点

**Q1：toxiproxy 和自研代理怎么选？** toxiproxy 是 TCP 层标准工具（toxics 丰富、
API 成熟，arm64 镜像已验证可用）；自研 HTTP 代理胜在零依赖、模式语义可定制。
生产用 toxiproxy 做常态故障演练平台，本实验自研是为了把「注入点选在哪」想清楚。

**Q2：重试为什么可能让事故更糟？** 重试风暴：依赖过载时全量客户端同时重试，
流量×3 把过载变雪崩。治理三件：退避+抖动（本实验 100ms 固定退避是简化）、重试预算
（重试流量占比上限）、熔断联动（重试失败计入熔断计数）。

**Q3：熔断阈值怎么定？** 连败阈值低（3 次）→ 敏感但易误开；高（20 次）→ 迟钝。
正确依据是依赖的基准错误率与流量：低频高价值依赖要更敏感。核心是**阈值必须按依赖
分级配置**，全局一个值等于没配置。

**Q4：混沌实验在生产能不能做？** 能且应该（Netflix 原教旨），但有前置：生产演练
半径控制（先影子流量/单实例）、一键撤销、业务方知情、值班在岗。本实验在本地跑，
是同一套纪律的最小实现——「爆炸半径与信心成正比」。

**Q5：和项目 19 探针怎么配合？** 故障注入实验验证「防御组件在注入下行为正确」；
合成探针验证「生产环境长期健康」。生产混沌演练的观测器正是探针——注入期间探针
应该告警、恢复后消除，一次演练同时验证两套系统。

# 16 · Ephemeral 环境工厂：环境抢占的终极解法是不共享

> 01 号审计揪出的「6 个端口 6 份私有 SUT」在这里得到正解：**环境不分配、按需克隆、
> 用完即焚**。一份 SUT 镜像，每个 PR 一套全隔离实例（独立容器/端口/数据目录），
> 并发互不干扰，销毁零残留。实测：两套环境并行，101 有单 102 为 0；全周期 4 秒
>（验收线 180s）。清单第 16/28 项，阶段四开篇。

## 1. 为什么需要它

- 「环境被占了」= 测试团队的日常吵架主题，根因是把环境当**稀缺资源**分配；
- 共享环境的两种病：数据互相污染（你删我的测试单）与配置漂移（谁改了 staging）；
- ephemeral 的哲学：环境的生命周期 = PR 的生命周期，一次性、可丢弃、无状态负担。

+独立数据目录，compose project（-p env-pr-NNN）把网络/容器/数据三样全钉在 PR 号上。

## 3. 快速开始

```bash
cd architect/16_env_factory
./env_factory.sh apply     # 构建 SUT 镜像（有缓存秒级）
./env_factory.sh observe   # 并发起 2 套 → 隔离断言 → 计时 → 无残留验收
./env_factory.sh clean     # 删镜像，宿主机回实验前状态
```

实测输出：

```
① 并发起 2 套：env-pr-101(healthy) / env-pr-102(healthy)
② 隔离验证：PR-101 创建订单 → 订单数 PR-101=1，PR-102=0 ✅
③ 全周期耗时 4s（验收线 ≤180s）
④ 残留容器 0 个，残留卷 0 个，数据目录已清空 ✅
```

## 4. 核心概念

### 4.1 环境的三重隔离
容器名（env-pr-NNN）、端口（18800+NN）、数据目录（configs/data-pr-NNN/）三样全部
以 PR 号命名——隔离不是「大家自觉」，是**命名空间物理隔离**。compose project 名
（-p env-pr-NNN）再把网络层一起圈进去。

### 4.2 健康就绪而非裸 sleep
`up -d --wait` 等 compose healthcheck（urlopen /api/health）通过才返回——环境工厂
的 SLA 是「给出去就能用」，不是「容器起了但还没监听」。

### 4.3 bind mount 的路径陷阱（本次踩坑）
compose 里 `./data-pr-X` 相对的是 **compose 文件所在目录**（configs/），不是执行
cwd——清理脚本删错位置，残留数据让「全新环境」带着上一轮的订单。环境管理的坑
大多长这样：路径、名字、生命周期的错位。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 一份镜像 N 实例 | 镜像即环境定义，改环境=改 Dockerfile | 镜像层缓存会烤进旧数据——COPY 的目录别放运行时数据 |
| down -v + rm 数据目录 | bind mount 不归 compose 卷管理 | down -v 只删 named volume，bind 目录要自己删 |
| 端口 = 18800+PR 号 | 并发不冲突且可预测 | 端口分配器在大规模下该换成注册发现 |
| 清场永远在启动前 | 上次中断的残留会污染本次验证 | 服务类实验的通用第一定律 |

## 7. 深入要点

**Q1：为什么这套环境没有 Postgres/Redis？** 刻意最小化：SUT 是 sqlite 单文件应用，
隔离验证只需要「应用实例 + 独立存储」。生产级环境工厂同一骨架扩 compose 服务列表
即可——骨架（命名/生命周期/健康检查）才是本实验的重点，服务清单是配置。

**Q2：ephemeral 环境的数据从哪来？** 三选一：空库+工厂造数（最干净，配合项目 7）、
匿名化生产快照（最真实，脱敏是底线）、种子脚本（本实验 SUT 自带 seed）。原则：
环境越接近生产，数据治理成本越高——按测试目的选，不要无脑追真实。

**Q3：成本怎么算？** 本实验两套环境 4 秒、镜像 247MB——容器环境的边际成本接近零；
真正的成本是镜像构建（缓存后秒级）与宿主机资源上限。K8s 场景用 namespace=PR 号
同构实现，资源配额是新增的管理面。

**Q4：PR 合并后环境谁销毁？** 生命周期钩子：CI 的 post-merge 步骤调 down；CI 保险
+定时巡检（每天清扫存活超过 24h 的 env-pr-*）。本实验的「无残留验收」脚本就是
巡检器原型——环境工厂必须配「环境墓园清理工」，否则又是数据越跑越多的环境版。

**Q5：和测试平台什么关系？** 环境工厂是平台的底座模块：用例管理/调度/报告都假设
「环境随叫随到」。01 审计发现端口蔓延 → 本实验给出供给层 → 项目 24 的卡点机制
保证大家用它——基础设施三段论：发现痛点、供给能力、机制推广。

## 8. 总结

4 秒起两套全隔离环境、用完即焚零残留——「环境不够用」作为一个问题类别被消灭了。
端口蔓延的病根（共享稀缺资源）被「按需克隆」的供给模型替代。下一篇是清单项目 17
「多环境配置矩阵与漂移检测」：环境有了，配置的一致性怎么守。

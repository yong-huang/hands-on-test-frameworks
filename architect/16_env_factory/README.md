# 16 · Ephemeral 环境工厂：环境抢占的终极解法是不共享

> [01 审计](../01_pyramid_audit/README.md) 揪出的「6 个端口 6 份私有 SUT」
> 在这里得到正解：**环境不分配、按需克隆、用完即焚**。一份 SUT 镜像，
> 每个 PR 一套全隔离实例（独立容器/端口/数据目录），并发互不干扰，
> 销毁零残留。实测：两套环境并行，101 有单 102 为 0；全周期 4 秒
> （验收线 180s）。阶段四开篇。

## Background

「环境被占了」是测试团队的日常吵架主题，根因是把环境当**稀缺资源**分配：
一个测试环境大家抢，谁占了谁说了算。共享环境还有两种慢性病：
数据互相污染（你删我的测试单）与配置漂移（谁改了 staging 没人知道）。

环境分配制的本质矛盾：环境数量固定、需求随机——高峰期排队，低谷期闲置。

ephemeral（临时）环境的哲学把矛盾消解掉：**环境的生命周期 = PR 的
生命周期**，一次性、可丢弃、无状态负担。环境不再是稀缺资源，
而是按需克隆的消耗品——镜像构建一次，实例按需起 N 个。

## What

Ephemeral 环境工厂是一套环境供给系统：一份 SUT 镜像（环境定义）+
compose 模板（PR_ID/PORT 插值），每个 PR 克隆一套全隔离实例。

容器名（env-pr-NNN）、端口（18800+NN）、数据目录（configs/data-pr-NNN/）
三样全部以 PR 号命名，compose project 名（`-p env-pr-NNN`——Docker Compose
用它把一组容器和它们的内部网络归到同一个隔离单元）再把网络层一起圈进去。

可以把环境工厂想成一次性相机的发放处：不用排队借那几台贵重相机
（共享环境），人人领一台用完就扔（每 PR 一套实例）。
但和一次性相机不同的是，这里的"相机"由同一份图纸（镜像）批量克隆——
环境定义收敛在镜像里，改环境 = 改 Dockerfile，不存在"某台相机被人改过"。

**隔离不是「大家自觉」，是命名空间物理隔离**。

## When to Use

典型场景：

- PR 级验证环境：每个 PR 一套带独立数据的完整环境，reviewer 直接点开看。
- 并发测试执行：多套环境同时跑，互不污染（实测 101 有单 102 为 0）。
- 演示与排查：复现 bug 时克隆一套干净环境，五分钟内给出现场。

何时不用：长驻的性能压测基线环境（要控制变量、长期稳定）不适合
用完即焚；无法容器化的重型依赖（大型中间机、物理设备）暂时进不了
这个模型。

实测输出：

```
① 并发起 2 套：env-pr-101(healthy) / env-pr-102(healthy)
② 隔离验证：PR-101 创建订单 → 订单数 PR-101=1，PR-102=0 ✅
③ 全周期耗时 4s（验收线 ≤180s）
④ 残留容器 0 个，残留卷 0 个，数据目录已清空 ✅
```

## Quick Start

前置条件：Docker 运行中（labs/00 体检项；Docker 未启动时本实验无法执行）。

```bash
cd architect/16_env_factory
./env_factory.sh apply     # 构建 SUT 镜像（有缓存秒级）
./env_factory.sh observe   # 并发起 2 套 → 隔离断言 → 计时 → 无残留验收
./env_factory.sh clean     # 删镜像，宿主机回实验前状态
```

诚实预期：③ 的全周期 4 秒依赖镜像缓存（首构建要拉基础镜像，分钟级）；④ 的无残留验收是实验作者实测结论。

健康就绪用 `up -d --wait` 等 compose 的 healthcheck（容器内定期请求 /api/health
接口的探活配置）通过才返回——环境工厂的服务承诺（SLA，Service Level Agreement）
是「给出去就能用」，不是「容器起了但还没监听」。

裸 sleep 是禁忌，labs/11 的健康检查原则在此复用。


关键设计（这段在做什么：供给模型与清场的五个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 一份镜像 N 实例 | 镜像即环境定义，改环境=改 Dockerfile | 镜像层缓存会烤进旧数据——COPY 的目录别放运行时数据 |
| down -v + rm 数据目录 | bind mount 不归 compose 卷管理 | down -v 只删 named volume，bind 目录要自己删 |
| 端口 = 18800+PR 号 | 并发不冲突且可预测 | 端口分配器在大规模下该换成注册发现 |
| 清场永远在启动前 | 上次中断的残留会污染本次验证 | 服务类实验的通用第一定律 |

## How It Works

**环境的三重隔离**。容器名、端口、数据目录三样全部以 PR 号命名，
compose project 名再把网络层圈进去——隔离靠命名空间，不靠自觉。

**bind mount 与 named volume 的清理分工**。

bind mount（把宿主机目录直接映射进容器的挂载方式，本实验的 `./data-pr-X`）
不归 compose 卷管理；named volume（由 Docker 创建并命名管理的数据卷）
才受 `down -v` 删除——清理逻辑必须覆盖两种存储形态，否则「无残留」验收必挂。

**bind mount 的路径陷阱（本次踩坑）**。compose 里 `./data-pr-X` 相对的是
**compose 文件所在目录**（configs/），不是执行 cwd——清理脚本删错位置，
残留数据让「全新环境」带着上一轮的订单。环境管理的坑大多长这样：
路径、名字、生命周期的错位。

**bind mount 与 named volume 的清理分工**。`down -v` 只删 named volume；
bind mount 的数据目录要脚本自己删——清理逻辑必须覆盖两种存储形态，
否则「无残留」验收必挂。

## Pitfalls & Q&A

踩坑清单：

- **镜像层缓存烤进旧数据**。现象：新克隆的环境带着历史订单。
  解法：COPY 进镜像的目录不放运行时数据，运行时数据全部走挂载。
- **清理只删 named volume**。现象：bind mount 的数据目录残留。
  解法：`down -v` + 显式 rm 数据目录，两样都做。
- **健康检查用裸 sleep**。现象：环境"起好了"但请求 502。
  解法：`up -d --wait` + healthcheck，就绪才返回。
- **环境只有生没有死**。现象：env-pr-* 容器堆积成"环境墓园"。
  解法：CI post-merge 钩子销毁 + 定时巡检清扫存活超 24h 的实例。

深入问答：

- **Q：为什么这套环境没有 Postgres/Redis？**
  刻意最小化：SUT 是 sqlite 单文件应用，隔离验证只需要「应用实例 +
  独立存储」。生产级环境工厂同一骨架扩 compose 服务列表即可——
  骨架（命名/生命周期/健康检查）才是本实验的重点，服务清单是配置。
- **Q：ephemeral 环境的数据从哪来？**
  三选一：空库+工厂造数（最干净，配合项目 7）、匿名化生产快照（最真实，
  脱敏是底线）、种子脚本（本实验 SUT 自带 seed）。原则：环境越接近生产，
  数据治理成本越高——按测试目的选，不要无脑追真实。
- **Q：成本怎么算？**
  本实验两套环境 4 秒、镜像 247MB——容器环境的边际成本接近零；
  真正的成本是镜像构建（缓存后秒级）与宿主机资源上限。K8s 场景用
  namespace=PR 号同构实现，资源配额是新增的管理面。
- **Q：PR 合并后环境谁销毁？**
  生命周期钩子：CI 的 post-merge 步骤调 down；CI 保险 + 定时巡检
  （每天清扫存活超过 24h 的 env-pr-*）。本实验的「无残留验收」脚本就是
  巡检器原型——环境工厂必须配「环境墓园清理工」，否则又是数据越跑越多的
  环境版。
- **Q：和测试平台什么关系？**
  环境工厂是平台的底座模块：用例管理/调度/报告都假设「环境随叫随到」。

  用它——基础设施三段论：发现痛点、供给能力、机制推广。

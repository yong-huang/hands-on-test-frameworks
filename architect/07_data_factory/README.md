# 07 · 测试数据工厂与自清理：让「数据越跑越多」有解

> 每个团队都被问过那句话：「测试库怎么又满了？」——造数随意、清理靠人、
> 孤儿数据没人认领。本实验给出三层药方：**工厂造数**（默认值 + 覆盖参数）、
> **用例级生命周期**（teardown 自动归还）、**命名空间 GC**（崩溃孤儿的兜底清扫）。
> 实测：3 轮套件连跑行数纹丝不动，100 条孤儿一键清光、1 条手工真实数据安然无恙。

## Background

「数据越跑越多」的根源是自动化没有生命周期设计：每条用例造数据、没人清理，
跑一个月后测试库变成垃圾场——断言变慢（全表扫描）、唯一索引冲突
（随机数据撞历史数据）、环境重建越来越频繁。

第二个坑是用例相互污染：`assert list() 里第一个是我造的` 这类写法，
依赖「全库只有我的数据」这个不成立的前提，并行必炸。

第三个坑是清理不敢跑：一个没有明确安全边界的 `DELETE` 脚本，
没人敢在真实库上执行——于是垃圾永远堆着。

解法是三层药方互相配合：工厂统一造数口径，用例级清理覆盖正常路径，
命名空间 GC 兜底异常路径——**安全边界一致**：命名空间外的行永远不出现在
删除语句里。

## What

测试数据工厂是一套带生命周期的造数机制：

- **工厂造数**：`create()` 不传参数就生成一条合理订单（随机仓库名/商品/
  1-5 件/1-99 元），传参即覆盖——造数效率 = 默认值质量 × 覆盖成本，
  和 fixture 的默认+覆盖设计同构。
- **用例级生命周期**：`lifecycle` 上下文管理器/fixture（pytest 的夹具机制）
  按造的 id 在 teardown（测试结束后的清理阶段）精确归还，
  覆盖 99% 的正常路径。
- **命名空间 GC**：只清 `QA-` 前缀的孤儿数据，兜底进程崩溃留下的泄漏。

可以把这套机制想成图书馆的借阅制度：借书登记（工厂造数带标记）、还书（用例级清理按 id 归还）、期末清库（GC 只回收"馆藏编号 QA- 开头"的书，读者的私人藏书绝不碰）。

但和图书馆不同的是，这里的"前缀约定"把「哪些数据可以删」从人工判断变成了机器可判定的前缀匹配——GC 的可信度来自它永远不会删不该删的东西。


## When to Use

典型场景：

- CI 反复连跑的套件：数据自造自清，环境永不满仓。
- 并行用例：工厂给每条数据唯一标记，断言只认自己的增量窗口。
- 长期无人管的测试库：先巡检（QA- 占比）、再一次性 GC 清算历史欠账。

何时不用：只读测试（不造数据就不用清）；一次性手工探索
（造一条测完手动删也行）——机制的价值在规模与重复，不在单次。

关键设计（这段在做什么：安全边界与精确性的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| QA- 前缀进 customer 字段 | 不能改 SUT（被测系统）schema 时的最小侵入方案 | 前缀约定要写进团队规范，否则两个工厂两个命名空间 |
| cleanup 按 id 逐条删 | 比「删 QA- 全部」精确，误删面最小 | 中途断电仍会泄漏——所以需要 GC 兜底 |
| GC 先巡检后清扫 | 破坏性操作前先让人看见范围 | `--sweep` 永远不该是默认行为 |
| 断言只看增量窗口 | 并行友好，不依赖全库静止 | 全表行数断言只在清理验证时用（本实验用途） |

## Quick Start

前置条件：labs/00 体检通过；种子建库后基线 10 行。

```bash
cd architect/07_data_factory
./data_factory.sh apply     # 种子建库（基线 10 行）+ 巡检
./data_factory.sh observe   # 生命周期 → 3 轮套件 → 孤儿清扫（真数据受保护）
./data_factory.sh clean
```

实测输出（节选）：

```
① 工厂生命周期：基线 10 → 造数后 15 → 自动清理后 10 ✅
② 连跑 3 轮演示套件：
   3 passed / 巡检：全表 10 行（QA- 0 行）×3 轮全部如此
③ 插入 100 条 QA- 崩溃孤儿 + 1 条手工真实数据：
   巡检：全表 111 行，QA- 命名空间 100 行，命名空间外（受保护）11 行
④ gc.py --sweep：已清扫 100 行孤儿；剩余全表 11 行
   手工真实数据仍在 ✅（GC 只动 QA- 命名空间）
```

诚实预期：三个数字是本实验的验收锚点——3 轮连跑后全表仍是 10 行
（零泄漏）、100 条孤儿被清光、命名空间外的 11 行（含手工真实数据）原封不动。

## How It Works

**命名空间纪律**。工厂造的每条订单 customer 一律 `QA-` 前缀。
这个约定把「哪些数据可以删」从**人工判断**变成**机器可判定的前缀匹配**
——巡检报告按前缀分桶（QA- 100 行 / 受保护 11 行），清扫范围一目了然。

**双层清理的分工**。用例级（`lifecycle` 上下文管理器/fixture）按 id 精确
归还，覆盖 99% 的正常路径；命名空间 GC 兜底进程崩溃留下的孤儿。
只靠前者，一次 CI 中断就泄漏一批数据；只有后者，删除粒度太粗。
两层缺一不可。

**巡检先行**。GC 分两步：巡检（只读，报告各命名空间行数）与
`--sweep`（清扫，只动 QA- 前缀）。破坏性操作前先让人看见范围——
`--sweep` 永远不该是默认行为，它应该是一个显式的、被人确认过的动作。

## Pitfalls & Q&A

踩坑清单：

- **两个工厂两套前缀**。现象：GC 漏清另一个团队造的数据。
  解法：前缀约定写进团队规范，一个命名空间一个仓库。
- **断言依赖全库静止**。现象：并行跑时 `len(list()) == 1` 偶发失败。
  解法：断言只看自己造的增量窗口。
- **`--sweep` 进定时任务**。现象：误删无处追责。解法：兜底清扫保持显式
  （巡检 → 人工确认 → 清扫），该自动化的是用例级清理。
- **造数撞唯一索引**。现象：跑久了随机数据与历史数据冲突。
  解法：唯一字段用 uuid/时间戳，不用随机字典词。

深入问答：

- **Q：生产数据拉到测试库，脱敏怎么做？**
  命名空间同源思路：脱敏要保证**引用完整性**（同一手机号脱敏后仍是同一
  假号，否则关联断）+ **格式保真**（能过校验逻辑）+ **不可逆**（假手机号
  反查不出真号）。脱敏本身应是流水线里的自动环节，人工导库 = 泄漏事故预定。
- **Q：造数在 API 层还是 DB 层？**
  API 层走真实业务流（顺带测了创建逻辑，但慢且依赖服务）；DB 层快且无
  依赖，但绕过校验可能造出「业务上不可能存在的脏数据」。本实验用 store 层
  （数据访问层）折中。原则：给「读路径」造数可下沉，给「写路径」造数必须
  走 API。
- **Q：测试数据管理平台（数据银行）什么时候才值得建？**
  当三类成本 crossing：造数代码重复率、数据准备时长占用例执行时长的比例、
  因数据问题失败的用例占比——三者之和超过平台建设成本时立项。
  小团队用 factory + 约定就够了，这是「平台不是从 0 建的」的又一例。
- **Q：并发用例共享数据集怎么不互相污染？**
  三选一：唯一标记 + 窗口断言（本实验）、数据租户隔离（每人/每并行槽
  一套数据）、copy-on-write（读共享 + 写时复制）。labs/09 的 xdist 翻车
  就是缺第一层的活教材。
- **Q：为什么 GC 不用定时任务自动跑？**
  兜底清扫应该是显式动作（巡检→人工确认→清扫），自动化它等于给了删库
  一个 cron。真正该自动化的是用例级清理——清理的最高境界是根本不需要 GC。

# 07 · 测试数据工厂与自清理：让「数据越跑越多」有解

> 每个团队都被问过那句话：「测试库怎么又满了？」——造数随意、清理靠人、孤儿数据没人认领。
> 本实验给出三层药方：**工厂造数**（默认值+覆盖参数）、**用例级生命周期**（teardown 自动
> 归还）、**命名空间 GC**（崩溃孤儿的兜底清扫）。实测：3 轮套件连跑行数纹丝不动，
> 100 条孤儿一键清光、1 条手工真实数据安然无恙。清单第 7/28 项。

## 1. 为什么需要它

- **数据越跑越多**：没有生命周期的自动化，跑一个月后测试库=垃圾场，断言越来越慢；
- **用例相互污染**：`assert list() 里第一个是我造的` 这种用例，并行必炸——
  工厂给每条数据唯一标记，断言只认自己的窗口；
- **清理不敢跑**：一个 `DELETE` 脚本若没有明确的安全边界，没人敢在真实库上执行。

（只清 QA- 前缀），两者的安全边界一致——命名空间外的行永不在删除语句里出现**。

## 3. 快速开始

```bash
cd architect/07_data_factory
./data_factory.sh apply     # 种子建库（基线 10 行）+ 巡检
./data_factory.sh observe   # 生命周期 → 3 轮套件 → 孤儿清扫（真数据受保护）
./data_factory.sh clean
```

实测输出（节选）：

```
① 工厂生命周期：基线 10 → 造数后 15 → 自动清理后 10 ✅
② 连跑 3 轮演示套件：
   3 passed / 巡检：全表 10 行（QA- 0 行）×3 轮全部如此
③ 插入 100 条 QA- 崩溃孤儿 + 1 条手工真实数据：
   巡检：全表 111 行，QA- 命名空间 100 行，命名空间外（受保护）11 行
④ gc.py --sweep：已清扫 100 行孤儿；剩余全表 11 行
   手工真实数据仍在 ✅（GC 只动 QA- 命名空间）
```

## 4. 核心概念

### 4.1 命名空间纪律
工厂造的每条订单 customer 一律 `QA-` 前缀。这个约定把「哪些数据可以删」从**人工判断**
变成**机器可判定的前缀匹配**——GC 的可信度来自它永远不会删不该删的东西。

### 4.2 双层清理
用例级（`lifecycle` 上下文管理器/fixture）按 id 精确归还，覆盖 99% 的正常路径；
命名空间 GC 兜底进程崩溃留下的孤儿。只靠前者，一次 CI 中断就泄漏一批数据；
只有后者，删除粒度太粗。两层缺一不可。

### 4.3 工厂默认值
`create()` 不传参数就生成一条合理订单（随机仓库名/商品/1-5 件/1-99 元），
传参即覆盖——**造数效率 = 默认值质量 × 覆盖成本**，和 fixture 的默认+覆盖设计同构。

## 5. 关键设计

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| QA- 前缀进 customer 字段 | 不能改 SUT schema 时的最小侵入方案 | 前缀约定要写进团队规范，否则两个工厂两个命名空间 |
| cleanup 按 id 逐条删 | 比「删 QA- 全部」精确，误删面最小 | 中途断电仍会泄漏——所以需要 GC 兜底 |
| GC 先巡检后清扫 | 破坏性操作前先让人看见范围 | `--sweep` 永远不该是默认行为 |
| 断言只看增量窗口 | 并行友好，不依赖全库静止 | 全表行数断言只在清理验证时用（本实验用途） |

## 7. 深入要点

**Q1：生产数据拉到测试库，脱敏怎么做？** 命名空间同源思路：脱敏要保证**引用完整性**
（同一手机号脱敏后仍是同一假号，否则关联断）+ **格式保真**（能过校验逻辑）+ **不可逆**
（假手机号反查不出真号）。脱敏本身应是流水线里的自动环节，人工导库=泄漏事故预定。

**Q2：造数在 API 层还是 DB 层？** API 层走真实业务流（顺带测了创建逻辑，但慢且依赖服务）；
DB 层快且无依赖，但绕过校验可能造出「业务上不可能存在的脏数据」。本实验用 store 层
（数据访问层）折中。原则：给「读路径」造数可下沉，给「写路径」造数必须走 API。

**Q3：测试数据管理平台（数据银行）什么时候才值得建？** 当三类成本 crossing：造数代码
重复率、数据准备时长占用例执行时长的比例、因数据问题失败的用例占比——三者之和超过
平台建设成本时立项。小团队用 factory + 约定就够了，这是「平台不是从 0 建的」的又一例。

**Q4：并发用例共享数据集怎么不互相污染？** 三选一：唯一标记+窗口断言（本实验）、
数据租户隔离（每人/每并行槽一套数据）、copy-on-write（读共享+写时复制）。本仓库
labs/09 的 xdist 翻车就是缺第一层的活教材。

**Q5：为什么 GC 不用定时任务自动跑？** 兜底清扫应该是显式动作（巡检→人工确认→清扫），
自动化它等于给了删库一个 cron。真正该自动化的是用例级清理——清理的最高境界是
根本不需要 GC。

## 8. 总结

3 轮连跑行数纹丝不动、100 条孤儿一键清扫、真数据永受保护——测试数据的「越跑越多」
从此是一个可验证的命题而不是玄学。命名空间纪律 + 双层清理这两招，迁移到任何仓库都成立。

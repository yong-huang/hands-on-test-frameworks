# 23 · 质量度量体系与看板：「你们质量怎么度量」的一页纸答案

> 「你们团队质量怎么度量？」是架构师的高频开放题，大多数人答「看缺陷数和
> 覆盖率」就停了。本实验给出带三要素的答案：每个指标有**公式**（防口径之争）、
> **来源**（可抽查核对）、**反 gaming 说明**（防指标造假）。实测：6 个指标从
> 兄弟项目产物采集，抽查 3 项全部与原始产物一致；数据缺失时看板明示缺失
> 而不是编数。非功能篇收官。

## Background

没有度量体系的质量改进是玄学：不知道基线，就证明不了「变好了」——
所有优化争论都退回各说各话。

坏指标比没指标更糟：单一缺陷数考核催生「不报缺陷」，单一覆盖率考核催生
「删断言凑行覆盖」——指标一旦被考核，就会朝着指标本身优化。
每个指标必须配 anti-gaming 说明：预判它会被怎么钻空子，并提前拆解。

看板的信任来自可核对：每个数值都标数据来源（文件路径+字段路径），
抽查对得上才有公信力。「相信我」撑不过第二次汇报。

## What

质量度量看板是**指标字典的渲染**：字典（configs/metrics.yaml）定义每个
指标的三要素——公式、来源、anti-gaming；采集器只读兄弟项目产物，
渲染成静态 HTML。

数据源对应关系：01 审计产生分层比例、03 门禁产生覆盖率、13 flaky 平台产生
flaky 率（flaky 指时好时坏、重跑才过的不稳定用例，flaky 率即不稳定用例占比）。

可以把看板想成体检报告的汇总页：每一项都有参考区间（公式定口径）、
化验单出处（来源可核对）、以及"这个指标怎么被钻空子"的医生备注
（anti-gaming）。但和体检报告不同的是，数据生产和展示是分离的——
看板是只读聚合器，挂了不影响生产；各项目的数据契约即看板的接口。

**缺失明示是底线**：数据源不存在时看板写「数据缺失（先跑 apply 生成）」
而不是填 0——**0 和缺失是两种完全不同的事实**，混用它们是数据造假的
第一步。

## When to Use

典型场景：

- 质量周报/发版前检查：六个指标的静态页，数字全部可抽查。
- 指标体系评审：字典 yaml 就是评审对象——新增指标=加一行配置。
- 跨团队口径对齐：公式进字典，flaky 率的分母之争在字典里终结。

何时不用：指标没人消费时别上（看板不是垃圾场，指标没人看就该删）；
数据源尚未自动化产出的指标先进字典标注「规划中」，不上看板凑数。

实测输出（6 个指标，节选）：

```
- 自动化分层比例: unit:74.4% / integration:11.5% / e2e:12.2%
- 用例总规模: 418
- 金字塔形状判定: 过渡形态 ⚠️（偏 E2E，端到端测试占比过高）
- flaky 用例率: 40.0        ← 本实验撰写时（2026-09-19）3 轮轻量检测的实测快照
- SUT 数据层行覆盖率: 98
- 发布门禁状态: PASS
抽查 3 项全部与原始产物一致 ✅（验收线 ≥2）
```

## Quick Start

前置条件：兄弟项目（01 审计 / 03 门禁 / 13 flaky）可被 apply 重新生成数据源；
纯离线。

```bash
cd architect/23_metrics_dashboard
./metrics_dashboard.sh apply     # 生成数据源：01 审计 + 03 门禁 + 13 flaky 检测
./metrics_dashboard.sh observe   # 渲染看板 → 抽查核对 3 项 → 诚实缺失演示
./metrics_dashboard.sh clean
```

诚实预期：抽查断言进脚本（「看板可信」要可验证，人工看一眼的核对撑不过
第二次汇报）；诚实缺失演示里删掉某数据源后，看板对应指标应显示
「数据缺失」而不是 0。

关键设计（这段在做什么：度量公信力的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 字典 yaml 而非硬编码 | 新增指标=加一行配置 | 指标没人消费就该删，字典不是垃圾场 |
| 来源路径相对仓库根 | 兄弟项目产物即接口 | 产物结构变更要同步字典——接口变更纪律 |
| 抽查断言进脚本 | 「看板可信」要可验证 | 人工看一眼的核对撑不过第二次汇报 |
| apply 生成数据源 | 前置项目的产物被 clean 后可再生成 | 轻量模式（13 用 3 轮）控制数据源成本 |

## How It Works

**指标字典三要素**。

**公式**统一口径之争（flaky 率的分母是用例数还是失败次数？字典说了算）。

**来源**是数据契约：文件路径+字段路径，兄弟项目改结构要同步字典。

**anti-gaming** 是对指标被钻空子方式的预判与拆解（自动化覆盖率用
collect-only——pytest 只收集用例清单不执行的精确计数，不用可刷的
「文件数比值」口径）。


**看板是只读聚合器**。采集器不产数据只读产物——数据生产与展示分离：
01 审计产生分层比例、03 门禁产生覆盖率、13 产生 flaky 率。
各项目的数据契约即看板的接口。

**缺失明示**。数据源不存在 → 「数据缺失（先跑 apply 生成）」，
绝不填 0。

## Pitfalls & Q&A

踩坑清单：

- **指标直接考核个人**。现象：为指标而指标（删断言凑覆盖率）。
  解法：组织约定写进字典头部——度量用于定位系统性问题，不用于个人绩效。
- **0 当缺失用**。现象：数据源挂了指标归零，趋势图断崖。
  解法：缺失明示，0 与缺失是两种事实。
- **产物结构变更不通知字典**。现象：看板静默变空。
  解法：来源路径是接口，变更走同步纪律。
- **指标只增不减**。现象：字典变垃圾场，没人记得每个指标是干嘛的。
  解法：没有 owner、三周不变、不引发行动的指标下架。

深入问答：

- **Q：DORA 四指标怎么接进来？**
  部署频率/变更前置时长/变更失败率/MTTR（平均恢复时间）——数据源是流水线与工单系统（部署事件、PR 时间戳、事故工单）。
  接入方式与本实验同构：字典加四行、采集器加数据源适配器。

DORA 答「交付效能」，本实验 6 指标答「质量健康」，  两板合一面板才是完整的效能看板（项目 27 就是干这个的）。

- **Q：逃逸率怎么统计？**
  逃逸缺陷 = 生产发现的、本可在测试阶段拦截的缺陷。分母用
  「发布缺陷总数 = 测试发现 + 逃逸」，逃逸率 = 逃逸/总发布缺陷——分母
  不含「没发现的缺陷」（没人知道它存在），口径必须写进字典。
  项目 26 的逃逸分析是它的定性版。
- **Q：自动化覆盖率怎么算才不造假？**
  本实验用 collect-only（只收集不执行的精确计数，字典里的 anti-gaming）：不是
  「自动化用例文件数/手工用例数」这种可刷指标，也标明统计时点。
  更严格的口径是「需求覆盖」（每条需求至少一条自动化用例）——需要用例
  与需求的映射表，成本高一档但抗 gaming 强一档。
- **Q：看板没人看怎么办？**
  三个信号：指标没有 owner、数值三周没变化、没有因看板引发的行动。
  看板的正确用法是**挂进例行机制**（周会第一页、发版前必查）——没人
  消费的指标应该下架。
- **Q：度量会伤害团队吗？**
  会，如果指标直接考核个人。反 gaming 的最后防线是组织约定：度量用于
  定位系统性问题，不用于个人绩效——这条要写进字典的头部声明，
  不是口头默契。

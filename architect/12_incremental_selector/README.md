# 12 · 静态增量测试选择器：不跑一个测试，0.22 秒圈出影响面

> 精准测试有两条腿：[项目 4](../04_precise_testing/README.md) 的**运行时路线**
> （覆盖率上下文，精确到行）和本实验的**静态路线**（AST import 依赖图，
> 零执行成本）。实测：88 个模块、42 个测试文件的仓库里，对 store.py 的一行
> 变更，0.22 秒选出 4 条测试并给出理由链——同一变更运行时路线推荐 2 条，
> 报告并列对比两条路线的选择差。

## Background

没有覆盖档案的仓库（新接手、历史包袱）也需要增量能力——运行时路线
（项目 4）的档案要靠全量跑一次才建立，冷启动期它无能为力。

静态路线的原料免费：每个 Python 文件的 import 语句。AST（抽象语法树，
源码的结构化解析结果）提取 import → 建立「谁用了谁」的反向索引 →
从变更文件反向可达的测试文件即选中集——全程零执行，秒级完成。

「变更影响分析」也是 AI 测试热题的地基：没有依赖图，AI 也是空谈——
依赖图是事实层，模型是解释层。

两条路线的分工由此确立：静态是「可能受影响」的超集（宁多选不漏选），
运行时是「真实碰过」的精确子集——本实验的报告把两者并列对比，
差异一目了然。

## What

静态增量测试选择器是一套零执行的变更影响分析：扫全仓 `*.py` 建模块注册表，
变更文件反向 BFS（广度优先搜索）引用图，可达的测试文件即选中集，
每条选中项带理由链（store.py → 谁引了它 → 哪个测试）。

可以把静态选择器想成城市的供水管网图：不拧开水龙头实测水流（不跑测试），只看管道连接图（import 图）判断"上游改动会影响哪些用户"——凡是管网连得上的都算受影响。

但和管网图不同的是，代码还有「不沿管道走」的依赖（HTTP 调用、动态 import）——这些是静态路线的天然盲区，正是运行时路线补刀的地方。


**过近似是静态分析的本分**：import 解析刻意只取顶层名、同名模块全部保留
——宁多选不漏选，精确性交给运行时路线。

## When to Use

典型场景：

- 新接手仓库的冷启动：没有覆盖档案，静态路线立刻可用。
- PR 流水线第一道筛选：0.22 秒的静态圈选先裁剪，再让运行时推荐做精修。
- 变更影响沟通：理由链让 reviewer 一眼看懂"为什么选这些测试"。

何时不用：仓库里大量用例是 HTTP 层/API 层（不 import 被测模块）时，
静态路线的盲区太大，应以运行时/契约路线为主；动态 import 泛滥且无法
治理的代码库，漏报会失控。

关键设计（这段在做什么：保守近似与可信度的四个决定）：

| 设计 | 为什么 | 坑 |
|:---|:---|:---|
| 只保留仓内注册的 import | 排除 stdlib/三方包的噪音 | 同名模块（conftest/main）会过近似——可接受 |
| conftest.py 也算测试资产 | 它的 import 变了同样影响用例（labs/14 经它命中） | 只统计不选中，选中集仍以 test_*.py 为准 |
| 理由链取末 3 跳 | 链太长没人看 | 截断处要标「…」，别伪装成直接依赖 |
| 变更文件 .py 过滤 | 非代码变更（README）不触发 | yaml 配置变更应走配置感知路线（项目 17） |

## Quick Start

前置条件：仓库本体即可（零执行、零依赖、无需 Docker）。

```bash
cd architect/12_incremental_selector
./incremental_selector.sh apply     # 扫全仓建 AST 注册表（零执行）
./incremental_selector.sh observe   # 造真实变更 → 静态选择 → 断言 → 与项目 4 对比 → 还原
./incremental_selector.sh clean
```

实测输出（同一变更，两条路线对比）：

```
② 静态选择：选中 4 条（0.22s，零测试执行）
   - labs/13_db_tests/tests/test_concurrent.py   理由链：store.py → test_concurrent.py
   - labs/13_db_tests/tests/test_isolation.py    理由链：store.py → test_isolation.py
   - labs/13_db_tests/tests/test_migration.py    理由链：store.py → test_migration.py
   - labs/14_testcontainers/tests/test_postgres.py（经 conftest import 链间接命中）
③ 验收断言：labs/13（直接 import store）在列 ✅；无关 labs（02/05/06）未误选 ✅
④ 双路线对比：静态选中 4 / 运行时推荐 2
   结论：静态是「可能受影响」的超集（宁多选不漏选），运行时是「真实碰过」的精确子集
```

诚实预期：静态路线对 labs/12 的 API 测试**完全不可见**（httpx 直接打 SUT——
被测系统——的 HTTP 接口，不 import store）——HTTP 层依赖只有运行时/契约路线看得见。
这不是缺陷是边界，也是两条路线互补的根源。

## How It Works

**模块注册表与过近似**。扫描全仓 `*.py`，按文件名（stem）注册模块名 →
定义文件列表（同名模块多个定义全部保留）。import 解析刻意只取顶层名——
保守过近似，宁多选不漏选。

**反向 BFS 与理由链**。变更文件入队 → 每个引用它的文件入队并记录来源 →测试文件（test_*.py）即选中。理由链是选择器的可信度来源：「为什么选我」必须能一路指回变更点，否则就是黑盒。

全链存 JSON 供机器审计，MD 报告给人看（取末 3 跳）——双表示是报告设计的通用模式。


**与运行时路线的组合投产**。标准两级流水：PR 上静态秒级圈选（保底集合）
→ 若覆盖档案存在，运行时推荐做精修（交集跑、并集报）。
没有档案时静态独挑——这正是新项目冷启动的答案。

## Pitfalls & Q&A

踩坑清单：

- **动态 import 骗过解析器**。现象：`importlib`/字符串拼接的 import 对
  AST 不可见，漏报。解法：规范禁止魔法 import + 运行时路线兜底，
  而不是把解析器写成解释器。
- **理由链伪装成直接依赖**。现象：截断的链看起来像一跳。
  解法：截断处显式标「…」。
- **非代码变更触发选择**。现象：改 README 也圈出一堆测试。
  解法：变更文件按 `.py` 过滤；yaml 配置走配置感知路线（项目 17）。
- **把「不选」当漏报**。labs/03 不 import store，变更 store.py 不选它
  恰是正确行为——增量选择只对变更负责，不对「测试可能挂」负责
  （那是 flaky 治理的事）。

深入问答：

- **Q：静态和运行时路线怎么组合投产？**
  标准两级流水：PR 上静态秒级圈选（保底集合）→ 若覆盖档案存在，
  运行时推荐做精修（交集跑、并集报）。没有档案时静态独挑。
- **Q：为什么 import config_parser 的 labs/03 测试没被选中？**
  变更是 store.py，labs/03 不 import store——「不选」恰是正确行为。
- **Q：理由链为什么取末 3 跳？**
  人的工作记忆容不下 6 跳引用链；末 3 跳足够回答「它和变更的关联是什么」。
  全链存 JSON 供机器审计，MD 报告给人看。
- **Q：和 AI 变更影响分析什么关系？**
  依赖图是「事实层」，LLM 是「解释层」：把图+diff 喂给模型让它生成影响
  说明与补测建议，比裸问模型可靠一个量级——「先建图再谈智能」是分水岭。

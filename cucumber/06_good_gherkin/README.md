# 06 · 好坏 Gherkin：从"怎么点"到"什么规则"

> 同一个业务（同名订单允许重复下单）可以写出两种 Gherkin：命令式版本 9 步
> （点这、输那、等 1 秒），声明式版本 5 步（连续创建 2 笔订单，列表应有 2 笔）。
> 两版同跑同绿——语义等价；但可读性、维护成本与执行耗时相差一个档次。
> 本实验用 grep 门禁把"声明式"变成可持续的约束。

## Background

BDD 团队最常见的退化路径：一开始场景写得很业务（"顾客下单后应收到确认"），
三个月后场景变成"点击 id 为 btn-order 的按钮"——Gherkin 退化成了
用自然语言语法写的选择器脚本，业务侧彻底失去阅读能力。

根因是把 Gherkin 当成了 UI 自动化脚本格式，而不是需求表达格式。
区别在于步骤的抽象层级：声明式场景的每一步说**业务动作**
（连续创建 2 笔订单），命令式场景的每一步说 **UI 操作**（点击按钮、填输入框）。

## What

本实验保留同一业务的两份 Gherkin：`checkout_bad.feature`（命令式，反面教材）
与 `checkout_good.feature`（声明式，推荐形态）。两版绑定到同一页面对象、
跑同一个 SUT，业务结果完全一致——差异只在表达层级与维护成本。

可以把两版想成菜谱的两种写法：命令式是"开火、倒油 10 毫升、拿起锅铲"，
声明式是"热锅冷油、翻炒至断生"。新手照命令式能做出来，
但换一口锅就废；声明式描述的是烹饪意图，设备换了依然成立。
但和菜谱不同，Gherkin 的门禁可以自动化——grep 就能抓住命令式泄漏。

## When to Use

| 信号 | 用声明式重构 | 保持现状 |
|:---|:---|:---|
| 场景里出现按钮名/输入框字样 | ✅ 立即重构 | ❌ 业务侧已读不懂 |
| 同一操作在多处复制定义 | ✅ 参数化收敛 | ❌ 改一处漏三处 |
| 场景需要裸等待（waitForTimeout） | ✅ 等待内聚进页面对象 | 脆弱且慢 |
| 一次性探索性验证 | 可直接写 | ✅ 不必强上 Gherkin |

判断口径：**feature 文件是给"不看代码的人"读的**——只要这个定位成立，
命令式泄漏就该被门禁拦截。

## Quick Start

```bash
cd cucumber/06_good_gherkin
./good_gherkin.sh          # apply 起靶场 → observe 语义等价 + 门禁 + 耗时对照 → clean
```

observe ① 两版同跑同绿——步骤数 9 对 5，业务结果相同：

```
--- 坏版本（命令式）：---
1 scenario (1 passed)
9 steps (9 passed)
--- 好版本（声明式）：---
1 scenario (1 passed)
5 steps (5 passed)
```

observe ② 跑 Gherkin 门禁，声明式文件零 UI 操作词：

```
>>> checkout_good.feature 零 UI 操作词 ✓
```

验收方式：两版同绿（语义等价）+ 门禁通过。变异实验：往
`checkout_good.feature` 里加一行 `当 点击订单添加按钮` 重跑——
`scripts/check_gherkin.sh` 当场报行号并返回非零。

## How It Works

**命令式场景的三个症状。** 对照两份 feature 可见：步骤名是 UI 操作
（输入框、点击按钮）；同一操作复制定义（"再次点击"是"点击"的复制品，
为了凑场景顺序）；出现裸等待（`等待1秒`——把不确定的异步固化成定时）。
三个症状互为因果：步骤太碎导致复制，复制导致定义翻倍，翻倍放大等待成本。

**声明式把"怎么点"下沉到页面对象。** `连续创建 {int} 笔 {string} 订单`
一条步骤绑定里循环调用 `checkout.createOrder()`——等待 POST 的细节
内聚在页面对象（lab 05 的动作边界等待）。场景只剩业务语义，
步骤定义只剩一处循环。

**grep 门禁把纪律固化。** `scripts/check_gherkin.sh` 用词表
（点击、输入框、按钮、等待1秒…）扫描声明式 feature，命中即报行号
并返回非零。词表是活的：团队评审中新出现的命令式措辞应该加进词表，
门禁的记忆就替代了人的记忆。

**耗时对照暴露裸等待的税。** 坏版本里两个裸等待固定吃掉 2 秒；
好版本用 web-first 断言（自动等待）零定时等待。除速度外更重要的是
稳定性：裸等待在慢环境会"等不够"而红，在快环境白等——两头不讨好。

## Pitfalls & Q&A

**Q：命令式版本真的"错"吗？它也跑绿了。**
它此刻绿，但每个 UI 微调（改按钮文案、换控件、加载变慢）都会让它红，
每次红都需要懂实现的人来修——维护成本随 UI 变更次数陡增。

声明式版本在同样的变更下大概率不红（业务规则没变）——
这就是"测的是规则还是界面"的分野。

**Q："连续创建 2 笔"里为什么可以出现数字 2？这不算实现细节吗？**
2 是业务语义（订单允许重复，两笔可见即可验证），不是实现细节。
判断标准：把这个数字换成业务语言重读——"连续创建若干笔同类订单"依然通顺。
反例是"点击 2 次按钮"——次数与业务无关，纯属操作机械重复。

**Q：门禁词表会误伤吗？比如业务就叫"一键下单按钮"？**
可能误伤，处理方式与 lint 规则相同：确属业务词汇的用行内标记豁免
（如改写措辞避开），或把词表细化为更精确的 UI 操作短语。
豁免要有注释、要过评审——否则词表会逐渐失效。

**Q：裸等待 2 秒对执行时间影响大吗？**
单场景 2 秒看着不大，乘以场景数就是套件的真实税负。更糟的是它不稳定：
慢环境下 2 秒不够就 flaky。

web-first 断言的自动等待既快又稳——
本实验实测：好版本 5 步无任何定时等待，与坏版本同绿。

**Q：旧套件已经命令式了，怎么迁移？**
按"命令式步骤的使用频次"排序：被引用最多的步骤先重构进页面对象，
场景改写为声明式并挂门禁，一个 feature 一个 feature 推进。
lab 02 的 grep 门禁就是迁移的验收器——每迁一个文件，门禁覆盖一个文件。

# 15 · WebSocket 实时推送：帧级断言与通道可控性

> 实时功能的可怕之处在于"看不见"——帧来了没有、什么时候来的、UI 有没有跟上。
> 本实验用四条用例把 WS 通道变成可控靶场：真实推送驱动状态演进并验证时延、
> `routeWebSocket` 注入伪造帧、主动制造闪断验证自动重连、伪帧对账证明服务端权威。

## Background

轮询时代的实时性靠"多问几次"，WebSocket（WS，浏览器与服务器的全双工长连接）
让服务器可以主动推。但它给测试出了三道新题：连接有生命周期（建立、断开、重连）、
帧是异步到达的（时机不确定）、内容是应用自定义协议（没有标准 schema 可依）。

Playwright 的应对分三层：`page.on('websocket')` 监听连接与每一帧（观测）；
`routeWebSocket` 拦截通道——透传、伪造、闪断随测试定义（控制）；
web-first 断言照常覆盖 UI 结果（验证）。三层合起来，实时行为从"玄学"变成"靶场"。

## What

pw-store 的订单状态由服务端定时器驱动：新单 created，2 秒后广播 paid，再 2 秒 shipped。
每一步都经 WS 广播，前端收到帧后 refetch 列表——服务器权威、UI 只做展示。

可以把 WS 通道想成一条专线电话：routeWebSocket 是在那条线上装的分接器，
测试既能旁听每一句（framereceived），也能冒充总机喊话（伪造帧），
甚至剪线再接（闪断与重连）。但和电话不同，前端听到消息后并不直接相信——
它会重新拉一遍列表，以服务端数据为准。

## When to Use

| 场景 | 工具 | 本实验靶点 |
|:---|:---|:---|
| 验证推送驱动的状态更新 | `page.on('websocket')` + web-first 断言 | 状态演进与 1.5s 时延 |
| 注入"服务端永远不会发"的帧 | `routeWebSocket` 伪造 | 伪 deleted 帧的对账 |
| 断线重连逻辑 | 闪断注入（close + 重连放行） | 徽标红→绿 |
| 推送内容本身的协议正确性 | 服务端单测 / 契约测试 | 不在本层 |

判断口径：**UI 层测"对帧的反应"，协议层测"帧本身对不对"**。
两者混在 E2E 里会让失败定位变模糊。

```bash
cd playwright/15_pw_realtime
./realtime.sh          # apply 体检 → observe 四条用例 → clean
```

observe ① 四条用例全绿：

```
  ✓  1 真实推送：WS 帧驱动订单状态演进，UI 同步更新 (2.6s)
  ✓  2 mock WS：注入伪造帧驱动 UI（routeWebSocket） (69ms)
  ✓  3 断连重连：连接闪断 → 徽标变红 → 自动重连恢复 (2.1s)
  ✓  4 服务端权威：伪删除帧后 UI 与服务端对账一致
  4 passed (5.4s)
```

用例 ① 是时延验收的核心：帧监听记录服务端广播 paid 的时刻，
UI 属性断言通过后检查差值——本机 refetch 在百毫秒级，1.5s 阈值留足余量：

```
expect(Date.now() - paidAt, 'UI 更新距广播帧应 < 1.5s').toBeLessThan(1_500);
```

验收方式：四条全绿；用例 ① 的 `paidAt` 断言证明"真的收到过广播帧"；
用例 ③ 的 `connections` 计数证明"观测到 2 次连接"（首次 + 重连）。

## How It Works

**监听必须挂在连接建立之前。** 本实验实测踩过：把 `waitForEvent('websocket')`
写在 `login()` 之后——而 WS 连接在页面加载时就建立了，监听永远等不到事件，
用例 20 秒超时。"先等后动"在 WS 场景的第一步是：**先挂监听，再打开页面**。

**routeWebSocket 是通道级的中间人。** 处理器里的 `ws` 是页面侧路由，
`ws.connectToServer()` 同步建立到真实服务端的连接——两者之间的每条消息
都可以透传、改写或吞掉。

本实验的 mock 用例 = 透传 + 从"服务端侧"伪造 deleted 帧；
闪断用例 = 首连 800ms 后 `ws.close()`，重连放行。

**闪断为什么不用 `setOffline`。** 实测 `context.setOffline(true)` 掐不断
已建立的空闲 WS：没有流量就没有感知，连接静静活着。

主动 close 才是对"网络闪断"的忠实模拟——
应用侧看到的是同样的 onclose 事件与 1 秒重连。

**服务端权威是对账的锚点。** 伪造帧宣称"订单已删除"，前端 refetch 后
列表与之前一致——伪帧只触发了一次刷新，没有改变任何真实数据。

这个设计让前端逻辑极简（收到帧 → 重拉列表），也让"回滚"这类语义
天然由服务端保证：UI 从不发明状态。

## Pitfalls & Q&A

**Q：为什么时延断言是 1.5s 而不是 1s？**
链路是"广播帧 → 前端 refetch → 渲染"，本机实测百毫秒级，但并行负载、
GC 停顿都可能加倍。断言给 1.5s 是留出可复现余量——性能类阈值
（lab 14 同理）按实测分布留 5-10 倍余量，而不是拍一个好看的数字。

**Q：闪断注入为什么恰好选 800ms？**
要晚于"连接建立 + 首帧 welcome"（否则断的是半成品连接），
也要早于测试断言的超时。800ms 在两者之间；重连是客户端固定的 1 秒后，
所以徽标"红→绿"的全程约 2 秒。数字都不神秘，都是被断言约束出来的。

**Q：`connectToServer` 是同步的，会不会丢前置帧？**
连接在 handler 里同步建立，之后的帧才会经过路由——
建连瞬间的帧不存在丢失窗口（握手完成前路由尚未生效）。

若需要观测首帧 welcome，在 handler 的透传路径上挂监听即可
（本实验的透传就是这条线）。

**Q：伪帧测试算不算"测了不存在的行为"？**
算——而且这正是它的价值：验证应用面对**恶意或异常帧**的行为。
生产环境里恶意帧（伪造删除、越权推送）真实存在；应用"收到帧只 refetch、
不信任帧内容"的形态天然免疫。这条用例把该性质钉进了套件。

**Q：时序查看器页面偏长，交互版要滚屏正常吗？**
正常。sequence 类型的查看器画布固定 920×760，加上工具栏后页面高度
超过 900 视口（程序化检查会如实报 overflow）——这是查看器对时序类型的
固定形态，不是内容缺陷；本实验的四视口证据图已保留在 images/ 供查验。

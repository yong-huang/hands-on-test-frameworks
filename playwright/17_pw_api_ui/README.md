# 17 · API+UI 混合：API 管事实，UI 管呈现

> "UI 全程造 100 条数据"是 E2E 反模式——慢、脆、还把被测行为和测试脚手架搅在一起。
> 本实验立分层纪律：API 负责"让世界进入目标状态"（造数、清场），
> UI 只负责"验证世界被正确呈现"（分页、目标行）。实测：API 造 100 条 182ms，
> UI 造 10 条 432ms——单位成本差一个数量级。

## Background

只用 UI 操作的套件有个隐含假设：一切前置状态都要靠点出来。要验证"第 3 页有我的订单"，
就得先点 47 次创建——每一步都是执行成本与失败风险，而这些步骤本身不是被测行为。

分层是标准解：API 层操作事实（直接调接口造数、改状态、清场），
UI 层只验证呈现（页面显示与事实一致）。

这样 UI 用例的数量与被测页面行为挂钩，而与数据规模解耦——
验证第 3 页分页不需要"点出"43 条数据，只要它们存在即可，从哪来不重要。

## What

本实验给 pw-store 的订单区加了客户端分页（每页 20 条），混合用例的形态是三明治：
`/api/reset` 回到种子 → API 预置 n 条（41-50）→ **UI 只验证**第 3 页的内容
（页码指示、余数页行数、目标行存在）→ teardown `/api/reset` 清零。

可以把分层想成剧组拍戏：API 是置景组（把场景布置到位），UI 测试是摄影组
（只管画面里对不对）。置景组不用表演，摄影组不搬道具——
但两边共享同一份剧本（服务端真相）。

成本差异是实测量级的：置景走 API 毫秒级，
靠演员走位（UI 操作）布置同样的场景要贵一个数量级。

## When to Use

| 操作 | 走 API | 走 UI |
|:---|:---|:---|
| 造前置数据（批量、无关被测点） | ✅ 毫秒级 | 成本随数量线性涨 |
| 验证数据被正确展示 | ❌ 那是 API 测试 | ✅ 断言真实渲染 |
| 清场/重置 | ✅ /api/reset | ❌ |
| 被测交互本身（分页点击、表单） | ❌ 绕过了被测点 | ✅ 唯一正解 |

判断口径：**被测行为走 UI，其余全走 API**。一条用例里 UI 操作越少，
它对"页面行为"的断言越纯。

## Quick Start

```bash
cd playwright/17_pw_api_ui
./api_ui.sh          # apply 体检 → observe 12 条混合用例 → clean
```

observe ① 的输出里有两类关键数据——造数计时与 12 个执行：

```
    [timing] API 造 100 条: 182 ms
  ✓  1 API 造 100 条 ≤5s（UI 造同量级约需数分钟，对比见 README）
  ✓  2 混合 01: API 预置 41 条，UI 第 3 页验证目标行
  ✓ 11 混合 10: API 预置 50 条，UI 第 3 页验证目标行
    [timing] UI 造 10 条: 432 ms（约 43 ms/条）
  12 passed (2.9s)
```

验收三条：API 造 100 条 ≤5s（实测 182ms）；10 条混合用例全绿
（每条验证"第 3 页的余数行数与目标行"，行数随预置量 41→50 递变）；
afterAll 的 teardown 断言数据回到 3 条种子——**清零是被断言的**，不是口头承诺。

## How It Works

**分页是被测能力，混合用例是它的靶场。** pw-store 的订单列表带客户端分页
（每页 20 条）。混合用例的算术是确定性的：reset 后 3 条种子 + 预置 n 条
= 共 3+n 条；n 取 41-50 使总数恰为 3 页，第 3 页行数 = 3+n-40（随 n 递变）。

目标行固定在第 3 页末尾。

断言因此能精确到行数，而不是"多于 0 条"这种模糊检查。

**beforeEach/afterAll 是清场的机械保证。** 每条混合用例前 `/api/reset`，
全部用例后再 reset 并断言 `orders.length === 3`——teardown 的效果也进断言，
"清零"从口头约定变成可红的检查。

共享内存态 SUT 的套件（lab 10 的教训）靠这一手保住可复现性。

**UI 造数对照是分层收益的实测证据。** 专门留一条用例走表单创建 10 条
（43ms/条），与 API 造数（约 2ms/条）同轮计时——18 倍的差距写进报告。

对照数据会随机器浮动，结论（一个数量级）稳定。

**API 直打用的是 Node 全局 fetch 而非 Playwright 的 request。**
两者都能带 authorization 头；全局 fetch 的优势是不依赖浏览器上下文——
beforeEach 的造数发生在 page 创建之前也能跑。

需要"与页面共享 cookie"的场景（lab 04 的权限矩阵）才用 `page.request`。

## Pitfalls & Q&A

**Q：混合用例为什么每条都 reset？重置不是有成本吗？**
reset 是毫秒级内存操作，成本可忽略；它买到的确定性是算术级的——
"reset 后恰好 3 条种子 + 本批 n 条"让分页断言能写精确等式。

不 reset 的话，前序用例的数据残留会让"第 3 页行数"变成动态谜题
（lab 02 的跨用例累积坑在百条规模会被放大成必然）。

**Q：API 预置的数据在 UI 里一定能看到吗？**
本实验能：SPA 挂载时拉全量列表、客户端分页切片——API 写入内存后
任何后续加载都看得见。

若列表是服务端分页，API 预置后同样成立，
只是 UI 断言入口从"切片"变成"带页码的请求"。分层的成立条件是
"API 与 UI 共享同一数据源"，本靶场天然满足。

**Q：为什么 worker 固定 1？并行跑混合用例行不行？**
`/api/reset` 是全局重置——两个 worker 并行时，A 的 reset 会清掉 B 刚造的数据。

要么给 reset 加命名空间（按 worker 隔离数据域），要么像本实验一样串行。
lab 10 的唯一前缀协议适用于"只增不改"的用例；涉及全局重置时，
串行是更诚实的档位。

**Q：分层之后，纯 UI 的端到端用例还要吗？**
要，但角色变了：混合用例覆盖"每个页面行为 × 各种数据规模"，
纯 E2E 只留 1-2 条关键路径全流程作冒烟。

两者是覆盖矩阵的两种粒度，不是新旧替代关系。

**Q：分页为什么做在客户端？**
靶场规模（百条内）客户端切片足够，还让"分页"的断言入口完全在 UI 层。

服务端分页（page/pageSize 参数）是数据量上去后的必然演进，
届时混合用例的 API 预置部分不变，UI 断言入口改为带参请求——
分层的价值正在于这种演进不动另一层。

# 10 · 并行与隔离：4 个 worker 抢一个 SUT 的秩序

> 并行是把套件时间除以 N 的最直接手段，代价是所有"刚好没撞上"的隐患集中爆发。
> 本实验 23 条用例 4 workers 全并行（20 条订单用例 + serial 组），
> 用唯一前缀数据协议证明零串号，并给出 workers=1 vs 4 的同机实测耗时。

## Background

串行套件慢得理直气壮：一条接一条，任何数据改动都轮得到每条用例看见。
开并行后时间账好看了，但两个新问题随之而来：一是用例间通过共享 SUT 互相踩
（你删的订单正是我要断言的）；二是隐藏的顺序依赖暴露——
"恰好排在前面跑"的用例一旦被并行调度到后面，整个链条塌方。

解法是给并行立规矩：数据层面用唯一前缀隔离（每条用例只认自己创建的数据）；
顺序层面用 `describe.serial`（真有依赖链的用例显式声明串行）。

同时把"改造掉依赖"作为比加 serial 更优先的选项。

## What

Playwright 的并行模型：worker 进程（每个 worker 一个独立浏览器上下文）
按 workers 档位开 N 个，用例队列分发进去；`fullyParallel: true` 让同文件内的
用例也不再排队。

20 条订单用例各自经 API 创建带唯一前缀的订单，
浏览器里只断言"自己的那一行"——别人的增删与我无关。

可以把并行调度想成四条收银通道：排队的人（用例）随便去哪条队，
各扫各的购物车。但和超市不同，这里所有通道共用同一个仓库（SUT 内存态），
所以每件商品上架时都要贴上专属条码（唯一前缀）——找错货是纪律问题，
不是调度问题。

## When to Use

| 场景 | 全并行 | serial 组 | workers=1 |
|:---|:---|:---|:---|
| 无依赖的独立用例（默认形态） | ✅ | — | 慢但稳 |
| 多步流程（创建→改→删同一条数据） | ❌ 互相踩 | ✅ 显式按序 | 也可兜底 |
| 排查可疑的串号/flaky | ❌ 干扰判断 | ❌ | ✅ 先降维复现 |
| 视觉基线/严格时序断言 | ⚠️ 谨慎 | ⚠️ | ✅ 最稳 |

判断口径：**默认写"可并行"的用例**（自带数据、只断言自己），
serial 是给改造不掉的依赖链的例外通道，不是偷懒的默认档。

## Quick Start

```bash
cd playwright/10_pw_parallel
./parallel.sh          # apply 体检 → observe 并行 + serial + 耗时对比 → clean
```

observe ① 4 workers 跑全部 23 条用例（20 并行订单 + 3 条 serial 组）：

```
=====> [observe] ① 4 workers 全并行：20 条订单用例 + serial 组，零串号
  23 passed (1.7s)
```

observe ③ 是同机实测的档位对比（先各自验证全绿、再独立计时）：

```
>>> workers=1 : 3360 ms（已验证全绿）
>>> workers=4 : 1840 ms（已验证全绿）
>>> 加速比: 1.83x（浏览器/SUT 共享单机，非线性属正常）
```

验收方式：4 workers 全绿；把 serial 组里 ③ 删除用例的依赖断言
（`expect(orderId).toBeTruthy()`）删掉重跑多次，若调度顺序改变该组会红——
这就是 serial 存在的意义被程序化验证。

## How It Works

**唯一前缀是数据层的隔离协议。** 每条用例的订单标题形如
`W3-N15-mumvtq8g`（worker 序号 + 用例序号 + 随机串），
创建后只断言 `filter({ hasText: title })` 命中 1 行。

并行下其他用例创建/删除任何订单，都不影响"我的那一行"这个断言的真值——
隔离不靠运气，靠构造。

**造数走 API 而不是 UI。** 20 条用例的订单创建全部经 fetch 直打接口
（毫秒级），浏览器只承担"验证 UI 展示"这一件事。

UI 造数（填表单点按钮）单条要 1-2 秒且本身可能抖，
并行下把非被测行为塞进 API 是速度与稳定双赢的标准做法。

**serial 组的依赖断言是自检机制。** 组内 ② 验证存在、③ 删除都以
"① 创建成功产出 orderId"为前提，每条开头先 `expect(orderId).toBeTruthy()`。

若调度顺序被打乱，依赖断言先红，错误信息直接指向"依赖 ① 的产物"，
而不是深处某个莫名其妙的 404。

**expect.toPass 包住整个导航重试。** 4 并发高压下，单页首次加载可能抖动
（本实验实测踩过：订单列表偶发空载）。

把"goto + 断言"整体包进 `await expect(async () => {...}).toPass({ timeout })`，
失败就整段重来——比在局部缝补等待更可靠，也是 lab 13 flaky 治理的核心武器之一。

## Pitfalls & Q&A

**Q：加速比为什么不是 4x？**
瓶颈不在用例执行：SUT 是单进程（内存态共享），浏览器启动/上下文创建有固定成本，
本机 CPU 核数也有限。

并行的收益上限是"可并行部分的耗时占比"（Amdahl 定律），
1.83x 已经是共享单机 SUT 场景的合理数字。真想再快，沿两个方向：
减少串行段（lab 09 的 fixture 加速 setup），或分布式 sharding（lab 18）。

**Q：`fullyParallel: true` 会不会影响 lab 04 那种 storageState project？**
不影响——project 之间本来就独立。

它改变的是同一文件内用例的执行顺序：不再按声明顺序排队。
依赖"文件内先后"的用例必须迁移到 `describe.serial` 或拆成 API 前置——
本实验的 serial 组就是示范。

**Q：并行下所有用例共享一个 SUT，数据无限膨胀怎么办？**
pw-store 的订单状态会自动演进且 `/api/reset` 可重置（lab 02 的可测性设计）。

更普遍的做法：每个用例只造自己用的数据、断言完自己清理
（lab 09 Q&A 讲过的夹子形状）。共享内存态 + 唯一前缀 + 用后清理，
三件套足以支撑百级并行。

**Q：serial 组挂了，后面的用例还跑吗？**
默认跑（serial 只保证"按声明顺序开始"）。加
`test.describe.configure({ mode: 'serial' })` 后，组内一条失败，
剩余用例标记为 skipped——适合"第一步失败、后面必连环失败"的强依赖链。

本实验保留默认模式：三步各自独立红绿，排障信息更完整。

**Q：为什么并行套件要关 trace？**
trace 全量录制是磁盘 IO 大户，4 个 worker 同时写会吃掉并行收益
（本实验实测：开着 trace 的跑批明显更慢）。

并行跑批配 `trace: 'off'`，失败复现时单独开——
排障是低频动作，别让它给高频执行上税。

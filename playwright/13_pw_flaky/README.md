# 13 · flaky 治理：给"偶发"立案底，给"最终一致"配武器

> flaky（时好时坏的不稳定用例）是 E2E 套件信用的头号杀手：红一次信用归零，绿回来也没人信。
> 本实验注入两条真实形态的 flaky（预热型、偶发 500 型），用 retries 让它们全绿但留下案底，
> 再用 toPass / retry 分支两件武器展示收敛与根治，最后以"连续 5 轮 0 unexpected"收口。

## Background

处理 flaky 有两个极端，都是错的：一是"红了就重跑，绿了就当没发生"——
套件的信号价值随每次放水衰减；二是一次红就删用例——覆盖流失，缺陷从缺口漏回生产。

治理的正形介于两者之间：retries（失败自动重试的机制）让偶发不再阻断流水线，
但重试通过的用例在报告里标 flaky 而不是 passed——**偶发被记录成案底**。
案底驱动分诊：能根治的根治（修等待、修环境），暂不能根治的显式注解并持续监控。

## What

本实验的两条注入用例对应真实世界的两类偶发：预热型（首跑必红——缓存未热、
编译未完成）与抖动型（后端偶发 500）。retries=2 让它们最终全绿，list 输出
如实显示 `2 flaky`；HTML 报告里有独立徽标。

可以把 flaky 治理想成医院的分诊台：重试机制是分诊前的稳定措施（先让病人不闹），
flaky 案底是病历（这次什么症状、第几次了），分诊决定去根治科室还是留院观察。
但和医院不同，"留院观察"（接受偶发）必须写明病因——无案底的接受等于放水。

## When to Use

| 手段 | 适用场景 | 本实验靶点 |
|:---|:---|:---|
| retries 档案 | 一切偶发的兜底缓冲 | 两条注入用例 |
| `toPass` 整体重试 | "导航 + 断言"整段抖动 | API 造单最终一致 |
| `expect.poll` 轮询 | 异步数据逐渐收敛 | 订单出现时机抖动 |
| retry 分支 | 重试时裁剪慢路径 | 首次全量、重试关键路径 |
| 删除用例 | 覆盖重复且无法治 | 本实验不演示（慎用） |

判断口径：**先归因再选武器**。时序类偶发用 poll/toPass 收敛；环境类偶发修环境
（预热、种子、资源隔离）；真正不可控的外部依赖才考虑接受注解或移除。

## Quick Start

```bash
cd playwright/13_pw_flaky
./flaky.sh          # apply 体检 → observe 单轮案底 + 五轮稳定性 → clean
```

observe ① 单轮跑批——两条注入用例首跑红、重试绿，报告如实记账：

```
✘  1 [chromium] › 注入① 预热型：首次必红，重试绿（已标 flaky）
✓  2 [chromium] › 注入① 预热型：首次必红，重试绿（已标 flaky） (retry #1)
✘  3 [chromium] › 注入② 偶发 500：重试后恢复（治理对照）
✓  4 [chromium] › 注入② 偶发 500：重试后恢复（治理对照） (retry #1)
>>> flaky 案底 2 条 ✓（重试通过被如实记录）
```

observe ② 是套件级稳定性验收：同一套件连跑 5 轮，每轮 0 unexpected：

```
>>> 第 1/5 轮：2 flaky 2 passed ，unexpected=0
>>> ……（第 2-4 轮省略）
>>> 第 5/5 轮：2 flaky 2 passed ，unexpected=0
>>> 5 轮 0 unexpected ✓
```

验收方式：flaky 案底 ≥2 且 5 轮 0 unexpected。变异实验：把 config 的
`retries: 2` 改成 `retries: 0` 重跑——注入① 必红，套件整体变红，
这就是"没有重试缓冲时偶发的代价"。

## How It Works

**retries 的档案语义。** `retries: 2` 下失败的用例最多执行 3 次；任何一次通过
即不再重试，但首次失败已记录——list 输出与 HTML 报告都计入 flaky 而非 passed。

这解决了"重试放水"的信用问题：流水线能走通，账本上留着标记。
本版本没有 `test.flaky()` 修饰符，flaky 状态由"重试后通过"自动判定；
补充案由用 `testInfo.annotations.push({ type: 'flaky', description })`。

**toPass 是"整段重来"的收敛武器。** `await expect(async () => {...}).toPass({ timeout })`
把一个闭包整体反复执行直到通过——闭包内部可以是"刷新页面 + 断言"这样的复合动作。

与 poll 的分工：poll 轮询一个取值函数（返回值成为断言对象），
toPass 重跑一个动作块（导航、刷新都可以包进去）。
lab 10 的并行重试也是 toPass。

**retry 分支裁剪暴露面。** `test.info().retry` 在用例内可读：首次尝试走全量回归
（含 1.2s 慢接口），重试时只验关键路径。

价值在偶发高发的套件里：重试不必重复全部成本，但核心断言一次不缺。
注意分支逻辑要简单——用例内两个版本的差异过大本身就是维护负担。

**5 轮 0 unexpected 是套件级承诺。** 单轮绿可能靠运气，连续 5 轮的
unexpected 计数为零才是稳定性的可执行定义。unexpected 与 flaky 是两个维度：
flaky 是"重试救回来的"，unexpected 是"救不回来的"——治理目标是
前者可见可控、后者为零。

## Pitfalls & Q&A

**Q：retries 开大了会怎样？**
真偶发被掩盖的概率随重试次数上升：retries 为 5 时，成功率 50% 的坏用例
全红的概率只剩 3%——它会以 flaky 的身份长期潜伏。

工程口径：本地 0-1、CI 2 是常见档位；flaky 案底持续增长说明重试在掩护债务，
应回到分诊环节消化。

**Q：注入② 为什么不用上次演示的 `textContent()` 立即查询？**
本实验迭代过一版：注入① 用了 `textContent()`，结果用例不红——
这类查询会**等元素出现**，表格渲染后拿到正确文本，"偶发"根本没发生。

（lab 08 的病例二同源教训。）注入类演示必须真红一次，否则治理流程无从谈起。

**Q：`test.flaky()` 修饰符去哪了？**
本系列锁定的 1.62 版本线没有这个修饰符，flaky 状态由"重试后通过"自动判定。

需要补充案由时用注解：`testInfo.annotations.push({ type: 'flaky', description })`。
版本 API 面有差异时，以 `index.d.ts` 的实际类型为准，不背旧文档。

**Q：flaky 用例在并行（lab 10）下会更糟吗？**
会。并行放大了共享资源的竞争，偶发概率上升。

治理顺序应当是：先在 workers=1 下让单线程行为稳定（本实验的形态），
再开并行（隔离协议兜底），最后才谈 CI 分发。
跳过前两步直接上 CI 并行，flaky 会以"只在 CI 红"的形态出现——最难排查的一种。

**Q：怎么度量套件的 flaky 水平？**
看两个数：flaky 计数 / 总用例数（HTML 报告直接给数），以及 unexpected 计数
（必须趋零）。

健康套件的形态是：flaky 少而都有案由、unexpected 长期为零。
本实验的 5 轮脚本可以直接当每周例行的健康检查跑。

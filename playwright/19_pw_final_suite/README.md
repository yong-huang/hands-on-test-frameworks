# 19 · 🏁 终极串联：一条命令、15 个套件、一道质量门禁

> 前面 17 个实验各自为战，本实验把它们串成一条回归流水线：`./run_suite.sh`
> 按序执行 15 个套件（163 条用例），采集结果总表，最后过三道门禁
> （0 失败、flaky ≤ 2、时长 ≤ 20 分钟）——本机实测 78 秒全绿通过。

## Background

分散的套件各有验收，但"整个系列现在是否健康"没有答案：某次共享靶场改动
（比如 lab 17 给订单区加分页）会让远处不知情的套件悄悄变红，只有把所有套件
按序跑一遍才知道。串联跑批的另一样产出是**漂移清单**——哪些套件在共享 SUT
演进后失配，一目了然。

本实验的 run_suite.sh 就是这条流水线：第一次真实串联跑出了 11 条失败
（locale 漂移 × 7 个 config、视觉基线过期、分页导致的找行失效），
修复后收敛到全绿——串联本身就是最好的集成测试。

## What

流水线形态：套件清单（名称 | 目录 | 命令）→ 逐个执行并采集日志 →
正则抽取 passed/failed/flaky 计数 → 汇总总表 → 门禁判定（失败 0、
flaky ≤ 2、时长 ≤ 20 分钟，任一超限返回非零退出码）。

可以把 run_suite.sh 想成巡检列车：15 节车厢（套件）依次过检，
每节出一份检验单（日志与计数），车尾的检核员（门禁）汇总签字。
但和巡检不同，列车是**串行**的——共享 SUT 的套件并行会互相污染
（lab 10/17 的结论），这条流水线刻意用秩序换确定性。

## When to Use

| 场景 | 用 run_suite.sh | 单套件脚本 |
|:---|:---|:---|
| 共享靶场（pw-store）改动后 | ✅ 全系列回归 | 会漏远处套件 |
| 系列"健康检查"（每周/交付前） | ✅ 门禁输出结论 | 逐个跑无总账 |
| 开发单个实验 | ❌ 太重 | ✅ 秒级反馈 |
| CI 定时全量回归 | ✅ 加上 lab 18 的分片 | — |

判断口径：**改共享物（SUT、fixtures、config 约定）必跑串联**；
单实验开发用单套件脚本，两者是包含关系而非竞争。

## Quick Start

```bash
cd playwright/19_pw_final_suite
./run_suite.sh
echo $?   # 0 = 门禁通过；非 0 = 有失败/超限
```

真实输出（本机实测）：

```
=====> [report] 套件结果总表
01 TS 原生栈             15 passed   0 failed   0 flaky  ✓
04 认证矩阵              16 passed   0 failed   0 flaky  ✓
11 设备与仿真矩阵        36 passed   0 failed   0 flaky  ✓
……（15 个套件全表）
合计: 163 passed, 0 failed, 2 flaky
总时长: 78 s（约 1 分钟，阈值 20 分钟）
=====> [gate] 质量门禁
✅ 门禁通过：0 failed、flaky 2/2、时长达标 —— 全系列回归 GREEN 🏁
```

验收方式：`./run_suite.sh; echo $?` 输出 0；总表 15 行无 ✗；
变异实验：临时改坏 lab 03 的一条断言重跑——总表 03 行变 ✗、合计 failed=1、
门禁返回非零。三条门禁（失败/flaky/时长）都由脚本真实判定。

## How It Works

**套件清单是数据，不是代码。** 15 个套件以"名称 | 目录 | 命令"三元组列在
数组里，新增套件加一行即可。

清单刻意排除三个成员：lab 08（内置人为失败病例）、lab 12（失败标本）、
lab 18（依赖容器）——放进回归会让门禁恒红。排除是显式决策，清单里留了注释。

**计数抽取信任 reporter 的输出契约。** 脚本用正则从日志抽
`N passed / N failed / N flaky`——依赖 list reporter 的固定格式
（lab 12 的 reporter 体系）。

多段计数用 `paste -sd+ | bc` 累加。不做逐用例解析，
是因为门禁只需要三个总量。

**门禁的三个阈值都有出处。** failed=0 是底线；flaky ≤ 2 对应 lab 13 两条
注入用例的已知案底（治理目标是可见可控，不是清零幻象）。

时长 ≤ 20 分钟对应清单文档的承诺（实测 78 秒，余量 15 倍）。
阈值写在脚本头部常量区，改起来一处生效。

## Pitfalls & Q&A

**Q：第一次串联跑出 11 条失败，说明了什么？**
说明串联跑批本身就是集成测试。11 条失败的根因有三类：7 个实验的 config
没钉 locale（lab 11 给靶场加了语言跟随，Playwright 默认 en-US 让应用切成英文）。

另外两类：SUT 改版后视觉基线过期（lab 06 重新生成）、
分页改版后找行逻辑失配（lab 10 翻页查找）。
全部修复后收敛全绿——这正是"改共享物必跑串联"的实证。

**Q：为什么用 `bc` 累加计数？macOS 自带吗？**
是，macOS/Linux 都自带 bc。多段计数累加（如三浏览器各 5 passed）先
`grep -oE '[0-9]+ passed'` 再拼加法。awk 也能做，但 bc 的表达式错误更直观；
本实验实测两个方案都可行，取了报错更友好的。

**Q：门禁失败时怎么快速定位？**
总表里 ✗ 的行对应日志文件（`logs/<首词>.log`），失败详情 grep Error 即得。
本实验修复 11 条失败时全部依赖这套日志，没有重放任何一次全量跑批——
日志的一次性采集 + 离线分析，是串联跑批的效率来源。

**Q：这套流水线能直接搬去 CI 吗？**
能，配上 lab 18 的分片就是完整形态：串联脚本保证"顺序正确性"，
分片保证"横向吞吐"。

共享内存态 SUT 的约束（lab 10/17 已述）意味着 CI 上要么按套件分片
（SUT 每片独享），要么给 reset 加数据域——本系列选择前者，
与 run_suite.sh 的清单结构天然对齐。

# 06 · 数据库性能：EXPLAIN 会说真话，瓶颈会转移

> 双语言剖析把代码层清干净了，但数据库是另一个世界：这里的行为由
> **数据量、统计信息和计划器（查询优化器：为每条 SQL 挑选执行步骤的组件）**决定。本实验让靶场的 Postgres 开口说话
> ——pg_stat_statements 排行揪出头号查询，EXPLAIN ANALYZE 拍下
> Seq Scan → Index Scan 的 **144 倍**，再亲手复现连接池打满。
> 最大的收获却是一条方法论：**解决一个瓶颈，下一个瓶颈才现形。**

## Background

应用侧剖析永远照不到数据库内部：慢在扫表、慢在锁、慢在死元组（UPDATE/DELETE 留下的过期行版本，高频更新的表会越积越多），
各有各的证据链——必须让数据库自己开口。

让数据库说真话有个前提：**数据量要真实**。"数据量太小计划器永远选
Seq Scan"——200 行的表全扫就是最优解，性能实验必须先把数据量做到
十万行级，计划器的行为才有代表性。

连接池是应用与 DB 之间的隐形成本中心：打满时 P95 的形状
（排队到超时的阶梯）与慢查询的形状（连接个个在干活）完全不同——
学会分辨这两种形状，是 DB 性能工程的第一课。

## What

数据库性能诊断的三层证据链：**放大数据 → pg_stat_statements 排行定
嫌疑 → EXPLAIN ANALYZE 拍执行计划 → 建索引看数字跳水 → 100 VU 复现
连接池打满 → 调参验证钳制解除**。

可以把这三层想成刑侦流程：pg_stat_statements 是报案记录（哪些语句
花掉的时间最多），EXPLAIN ANALYZE 是现场勘查（这条语句实际怎么执行、
扫了多少行），池实验是模拟演练（压力下排队行为长什么样）。
但和刑侦不同的是，证据全部可复算——每条 SQL 都能当场再跑一遍。

EXPLAIN 的两个数字要一起看：**扫描行数**（决定成本）与**实际耗时**
（决定体验）。实测（本机，stock 15 万行）：

| 阶段 | 扫描方式 | 扫描行数 | 该节点耗时 |
|:---|:---|---:|---:|
| 建索引前 | Seq Scan | 116,504 | 7.792 ms |
| 建索引后 | Index Scan | 50 | **0.054 ms** |
| **变化** | 计划器改主意 | 2330x | **144x** |

配套排行证据：列表 JOIN 的 mean 从 11.16ms → 0.03ms（**370x**）。

## When to Use

典型场景：

- 慢查询治理：pg_stat_statements 排行 → EXPLAIN 定罪 → 索引/改写修复
  → 排行复查（瓶颈转移了吗）。
- 容量前体检：数据量放大到真实量级后，计划器行为才可信。
- 连接池调参：复现打满 → 调上限 → 确认钳制解除（P95 形状辨认可用）。

何时不用：ORM 层能解决的 N+1 问题（一次列表查询引发每行各一次子查询，labs/04 的 D1 类缺陷）不必下潜到
DB 层；纯应用侧的瓶颈（项目 04/05 已归因）别来数据库找。

**瓶颈转移实录（本实验最有价值的一课）**：索引修好后再看排行——**UPDATE stock 以 21ms 均值顶成了头号查询**：15 万行高频更新表死元组膨胀 + 同商品热点行锁竞争。

它一直都在（建索引前 23.62ms），只是当时被更慢的 JOIN 挡着。连接池调参后 P95 没降反而横住，正是因为瓶颈已经转移到它身上。治理方向（本系列不展开）：降低更新频率、表分区、autovacuum 调优。


## Quick Start

前置条件：项目 01 靶场栈运行中；psql 客户端（脚本走 docker exec）。

```bash
cd performance/06_db_performance
./db_perf.sh all      # 全证据链：排行→EXPLAIN→索引→池实验→报告
./db_perf.sh drop-index   # 撤索引恢复 D7 现场（复跑教学用）
open docs/db_analysis.md
```

**连接池打满的形状辨认**。

100 VU 压 45s，池上限 10 时：`pg_stat_activity` 的活跃连接被钉死在 **10**，请求在应用侧排队直到池超时（psycopg_pool 默认 30s）——P95 呈 30s 阶梯状、错误率 13%。

把上限调到 40 后峰值钉在 40，**钳制确认解除**；P95 没降是瓶颈转移，不是池的锅。判别口诀：**连接池打满 = 活跃连接贴着上限 + PG 自己很闲；慢查询 = 活跃连接个个都在干活。**


上限不是越大越好：每个连接是一个 PG 进程（~10MB），
max_connections=100 的默认额度要先留给运维、监控和备份连接。

关键参数（这段在做什么：排行榜与执行计划拍摄的两条 SQL）：

```sql
-- 排行榜（总耗时视角；mean_ms 看单条，total_ms 看总量）
SELECT round(total_exec_time::numeric,1) total_ms, calls,
       round(mean_exec_time::numeric,2) mean_ms, left(query,60)
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;
-- 拍计划（BUFFERS 告诉你缓存命中）
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) SELECT ...;
```

## How It Works

**排行定嫌疑**。pg_stat_statements 按 total（总量）与 mean（单条）
两个视角各看一遍：总量高的是优化收益（修一条省一片），
单条高的是用户体验（一个请求等多久）。

**EXPLAIN 定罪**。`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` 拍下真实执行：扫描方式（Seq/Index）、扫描行数、每节点耗时、缓存命中。

为什么有了索引计划器还可能不用：

- 统计信息过期（没跑 ANALYZE，计划器按旧数据估算）。
- 选择率估算偏差（计划器猜错 WHERE 条件会过滤掉多少行，猜错就弃用索引）。
- 小表全扫更便宜（读全表比走索引再回表更快）。
- 索引列上的函数/类型转换导致索引不可用。


**池实验辨认形状**。活跃连接贴着上限 + PG 空闲 = 池打满（扩池）；
活跃连接个个在干活 + pg_stat_statements 有对应慢语句 = 慢查询
（修 SQL）——两种形状两种药，吃错药会更糟。

## Pitfalls & Q&A

踩坑清单（本实验真踩）：

- **psql 的 `-f`/`-o` 路径在容器里解析失败**。解法：宿主机路径用 stdin
  管道和 shell 重定向。
- **EXPLAIN FORMAT JSON 被表头包裹**。解法：psql 加 `-tA` 拿纯 JSON。
- **数据量不够，计划器不说真话**。200 行的表 Seq Scan 就是 optimal。
  解法：先放大到十万行级再做计划实验。
- **bash 的 `$VAR` 后面紧跟全角字符**。多字节字节会被并进变量名，
  "unbound variable" 报在根本不存在的名字上。解法：变量一律加 `${}`。
- **改了代码 `up -d` 不重建镜像**。POOL_MAX_SIZE 旋钮上线必须 `--build`
  （项目 05 同款坑）。

深入问答：

- **Q：怎么找到最该优化的 SQL？**
  pg_stat_statements 按 total 与 mean 两个视角各看一遍：总量高的是
  优化收益，单条高的是用户体验。
- **Q：为什么有了索引计划器还可能不用？**
  四大成因已在 How It Works 逐条展开——核心是计划器按估算成本选路，估算错了路就错。
- **Q：连接池打满和慢查询怎么区分？**
  打满：活跃连接=池上限且 PG 空闲，P95 呈超时阶梯；慢查询：连接个个
  在干活，pg_stat_statements 有对应慢语句。
- **Q：高频 UPDATE 表会出什么问题？**
  死元组膨胀（表/索引变大变慢）、autovacuum 追不上、热点行锁竞争
  ——本实验的 UPDATE stock 21ms 就是活标本。

# 07 · 缓存三大问题：穿透、击穿、雪崩，逐一复现逐一设防

> 靶场里的 Redis 弹药上膛了。给 shop 的详情接口装上 Cache-Aside
> （三档开关：`off` / `on` 裸缓存 / `hardened` 全防护），然后把三大问题
> **当实验做**——每个问题都先在裸缓存上复现出数字，再切 hardened 档看
> 防护生效。最终成绩：命中率 97.6%、穿透 DB 调用 11968→305、击穿回源
> 554→109、雪崩 DB 峰值 402→20/s（**20 倍削峰**）。

## Background

缓存是性能工程里唯一"不加硬件就能数量级提速"的手段，但它自带三种
崩溃模式——不了解模式的团队会在第一次大促时集体认识它们。

三种模式的区别全在**失效的拓扑**：穿透是"查的东西不存在"，击穿是
"一个热 key 失效"，雪崩是"一批 key 同时失效"——拓扑不同，
复现方法与防护手段完全不同。把它们当实验做，比背名词有效得多。

本实验的三大问题防护全部实测验证：每个问题先在裸缓存（on 档）上复现出
数字，再切 hardened 档看防护生效——防护代码没有经过实验验证之前，
都不能算写完。

## What

Cache-Aside 是缓存的基本读模式：先查缓存，miss 则回源 DB 并回填缓存。
本实验给它装三档开关做对照实验：`off`（纯 DB）/ `on`（裸缓存）/
`hardened`（空值缓存 + singleflight + TTL——Time To Live，缓存条目的存活时长——抖动全防护）。

**三大问题的失效拓扑**（一张表分清）：

| | 失效的是什么 | 典型场景 | 防护 |
|:---|:---|:---|:---|
| 穿透 | 数据在缓存**和** DB 里都不存在 | 恶意扫描不存在的 id | 空值缓存 / 布隆过滤器（注） |
| 击穿 | **一个热 key** 到期 | 秒杀商品详情过期 | singleflight / 逻辑过期 |
| 雪崩 | **一大批 key** 同时到期 | 同批预置、同一时刻写入 | TTL 抖动 / 多级缓存 |

布隆过滤器：一种省内存的快速判断结构，只能回答"一定不存在/可能存在"，放在缓存前直接拦掉不存在的 id。

可以把三大问题想成餐厅前台的三种事故：客人点了一道菜单上根本没有的菜（穿透——每次都得进后厨问）；招牌菜刚好卖完一瞬之间五十桌同时催单（击穿——后厨被同一道菜挤爆）；打烊前全部菜品同时撤单、第二天的菜单又同时上新（雪崩——后厨一瞬间全负荷）。

但和餐厅不同的是，这里的每一次"进后厨"都有计数——防护有没有用，数字说话。


**singleflight**（单飞）是击穿的核心防护：同一个 key 的并发回源合并成
一次——第一个拿锁的回源，其余等锁者 double-check 后直接用缓存。

## When to Use

典型场景：

- 读多写少的热点数据（商品详情、配置、榜单）：Cache-Aside 基础款。
- 防护代码验收：穿透/击穿/雪崩三组实验分别验证三道防线。
- 容量规划前置：命中率与回源率决定 DB 的真实压力水位。

何时不用：强一致要求的数据（余额、库存扣减的权威值）不宜缓存
——要缓存必须接受 TTL 窗口内的旧读或上失效管道；
命中率天然低的长尾数据，缓存只有成本没有收益。

实测结果（本机数据，全部可复算）：

| 实验 | on（裸缓存） | hardened（全防护） | 防护手段 |
|:---|:---|:---|:---|
| 命中率（热点只读 20VU×30s） | **97.6%** PASS | — | Cache-Aside 本身 |
| 穿透（20VU 打不存在 id） | 11,968 次 DB 调用全穿 | **305 次**，BLOCKED | 空值缓存（短 TTL） |
| 击穿（50VU 集火 + 5 次 DEL） | 554 次回源（惊群：50 并发同一时刻回源同一 key） | **109 次**，合并回源 | per-key singleflight |
| 雪崩（100 key 同批过期） | DB 峰值 **402/s** | **20/s**（20x 削峰） | TTL ±20% 抖动 |

## Quick Start

前置条件：项目 01 靶场栈运行中（Redis 已在栈内空载待命）；
k6 就绪。

```bash
cd performance/07_caching
./caching.sh all     # 七轮实验（on/hardened 交叉）→ docs/caching.md
./caching.sh clean   # 恢复 off 对照态
```

k6 按实验切换打靶姿势（热点只读 / 不存在 id / 单 key 集火 / 预热后等
过期），shop 的 `CACHE_MODE` 在 on/hardened 间重建切换，DB 回源次数用
pg_stat_statements 差值逐秒取证。

**singleflight 的锁内回填（本实验真踩）**。第一版防护：等锁 →double-check → 回源 → 释放锁 → **回填**。

结果 hardened 反而更糟（DB 峰值 202/s > 裸缓存的 90/s）：等锁者在锁释放后 double-check，但此刻前一个请求还没来得及回填，照样打 DB——锁只带来了串行化，没带来合并。

修复：**回源与回填都放进临界区**，等锁者 double-check 时必然命中。


关键参数（这段在做什么：hardened 档读路径的锁序）：

```python
# Cache-Aside 读路径（hardened 档）
cached, found = cache_get(key)          # miss 计数
with key_lock(key):                     # singleflight：同 key 并发合并
    cached, found = cache_get(key)      # double-check
    if not found:
        row = _load_product(pid)        # 回源
        cache_put(key, ..., CACHE_TTL)  # 回填（锁内！TTL ±20% 抖动）
```

## How It Works

**取证方式**。DB 回源次数用 pg_stat_statements 差值逐秒取证——
雪崩实验测的是**瞬时峰值**不是总量：总量上 on/hardened 差不多
（都会回源一遍），逐秒采样才能看出 402 vs 20 的削峰。

**三道防线的机制**。空值缓存把"不存在的 id"也缓存（短 TTL），
恶意扫描的重复查询不再打 DB；per-key singleflight 把同 key 并发回源
合并成一次；TTL ±20% 抖动让同批 key 的过期时间错开，
雪崩的同步回源被摊平。

**一致性取舍**。本实验用 Cache-Aside + 写路径删缓存：先更 DB 再删缓存，
容忍短暂不一致；强一致要上订阅 binlog（数据库把每次写操作记下的流水）的失效管道，或干脆接受 TTL
窗口内的旧读。

## Pitfalls & Q&A

踩坑清单（本实验真踩）：

- **`redis.setex` 的单位是秒**。传成 `ttl*1000` 就是缓存 18 小时、
  永不过期，雪崩实验直接哑火（三轮没信号才抓到）。
- **读写混合拉低命中率**。下单写路径主动 DEL 缓存（Cache-Aside 的正确
  行为）——命中率实验必须用只读场景，否则 97.6% 会变成 58%。
- **singleflight 回填在锁外**。现象：hardened 比 on 更糟（见 Quick Start 的"锁内回填"实录）。
  解法：回源与回填都放进临界区，并发防护代码用击穿实验验收。
- **雪崩只看总量**。现象：on/hardened 总量差不多，误判防护无效。
  解法：逐秒采样看峰值。

深入问答：

- **Q：穿透/击穿/雪崩的区别与对策？**
  记住三者的区别在"失效的东西是什么"（都不存在 / 一个热 key /
  一批 key），对策自然推出（空值缓存 / singleflight / TTL 抖动）。
- **Q：singleflight 为什么要 double-check？**
  等锁期间前一个请求可能已完成回填；不 double-check 会重复回源。
  且回填必须在锁内，否则 double-check 形同虚设。
- **Q：缓存与 DB 的一致性怎么保证？**
  Cache-Aside + 写路径删缓存：先更 DB 再删缓存，容忍短暂不一致；
  强一致要上订阅数据库变更日志（binlog——数据库把每次写操作记下的流水）的失效管道，或接受 TTL 窗口内的旧读。
- **Q：热点 key 还有别的防击穿手段吗？**
  逻辑过期（不删、异步刷新）、永不过期 + 主动更新、多副本 key 打散
  ——都是"把合并做进读路径"的变体。

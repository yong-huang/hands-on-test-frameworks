# 10 · 性能回归门禁 + 容量评估报告：系列的终点，守护的起点

> 调优是一次性的，守护是长期的。本实验把前 9 个实验的结论变成两件资产：
> 一道**会咬人的门禁**（性能预算 + 基线对比，回归注入即红），一份**容量
> 评估报告**（拐点、饱和点、扩容建议、全程 before/after）。实测三连：
> 🟢 14.1ms → 注入回归 🔴 132.1ms（+836%）→ 修复 🟢 12.6ms。

## Background

没有门禁的性能优化是"逆水行舟"：今天修好的 P95，下个月的合并悄悄退
回去——没有人故意劣化性能，但每一次"先这样，回头再优化"的合并都在
悄悄还回去。性能要"守住"，必须像功能一样进 CI（持续集成，提交后自动跑检查的服务）。

性能预算（budget）是把 SLO 翻译成机器可读的判定规则——CI 的 exit
code 就是它的牙齿。没有预算的性能门禁只是"跑一遍压测看感觉"。

容量评估报告是性能工程的交付物：老板不关心你的火焰图，
关心"能扛多少、什么时候扩、扩什么"——性能工作的最后一步是
把技术结论翻译成决策依据。

## What

性能回归门禁是一套自动判定系统：**健康版采基线并固化 → 门禁绿 →
故意换回缺陷版（项目 04 的三缺陷）→ 门禁自动红并指出退化指标 →
恢复修复版 → 门禁回绿**。`regression_gate.py` 的退出码就是 CI 语义：
0 绿、1 红。

可以把门禁想成体重管理计划：先称一次记录基线（固化），之后每次
"体检"（CI 压测）对比基线，超预算（P95 退化 ≤25%）即红——
体重反弹立刻知道。但和体重不同的是，门禁第一道检查是**样本量**：
<100 个请求直接拒绝判定——样本太少时数字没有判定资格，这是门禁可信度的一半。

**预算的数字来源**（`budget.toml` 三条：P95 退化 ≤25%、错误率 ≤2%、
吞吐下降 ≤15%）：

- P95 的 25% = 高于日常抖动（健康复测自身的波动 <20%）、
  低于用户可感阈值；
- 预算要跟着 SLO 走：SLO 500ms 时 25% 的余量还有 375ms 的绝对空间；
- 预算宁可先松后紧：太紧的门禁天天红，很快就会被人为禁用。

## When to Use

典型场景：

- CI 合并门禁：合并到主干之前跑短场景（smoke 级预算判定）——
  门禁要快，否则没人等它。
- 性能预算的周期维护：定期（如每周）用健康主干重采基线，
  基线漂移要审计（对比新旧基线的差异是否来自合法变更）。
- 系列收官交付：容量评估报告汇总全系列数字
  （拐点、饱和点、扩容建议），每个数字可复算。

何时不用：无持续迭代的一次性系统（门禁没有守护对象）；
负载天然剧烈波动且无稳定基线可采的服务——先做负载建模归一
（项目 02）再谈门禁。

实测：门禁三连（本机数据）：

| 阶段 | shop P95 | 判定 |
|:---|---:|:---|
| 健康基线 | 14.1ms | 🟢 通过 |
| 注入回归（还原三缺陷） | **132.1ms（+836%）** | 🔴 不通过 |
| 修复恢复 | 12.6ms | 🟢 通过 |

诚实预期：注入阶段的 shorturl 也红了（+87%）——共享机器上的邻居退化
会连累无辜服务，CI 资源隔离是门禁的工程前提（本机实验里作为现象记录）。

## Quick Start

前置条件：项目 01 靶场栈运行中；全流程约 10 分钟。

```bash
cd performance/10_regression_gate
./gate_run.sh all      # 基线 → 绿 → 注入回归 → 红 → 修复 → 绿 → 容量报告（约 10 分钟）
./gate_run.sh gate     # 只跑判定（CI 里就这一条）
open docs/capacity.md
```

关键参数（这段在做什么：CI 入口与机器可读的 SLO）：

```bash
# 门禁判定（CI 里就这一条，退出码即语义）
python3 regression_gate.py shop && python3 regression_gate.py shorturl
# 预算（机器可读的 SLO）
[budget.toml] p95_regression_max = 0.25 ...
```

**容量报告必备四节**：当前容量与饱和点、瓶颈归因、扩容建议（扩什么、
扩多少、预期收益）、历史调优的证据链——数字都要能复算。
`docs/capacity.md` 是本系列的终交付物。

## How It Works

**门禁的判定链**。样本量守门（<100 拒判）→ 基线对比（本次 P95 vs
固化基线）→ 预算裁决（三条预算全过才绿）→ 退出码输出。
失败报告会点名退化指标（哪个指标、退化多少、预算多少）——
红灯必须可解释，否则没人信。

**基线的纪律**。门禁基线是"当前健康版"的快照，与项目 01 的
"缺陷时代"基线分开放——基线混用会让退化判定失真。
基线随健康主干定期重采，漂移要审计。

**预算与 SLO 的关系**。SLO 是对用户的承诺，预算是各服务分到的退化
额度之和要能保住 SLO——预算是 SLO 的逐层分解，改 SLO 必须重审预算。

## Pitfalls & Q&A

踩坑清单（本实验真踩）：

- **手写 YAML 解析器把缩进 strip 掉**。现象：所有键都进了错误层级，
  预算全读不到。解法：直接用 stdlib `tomllib`，预算文件写成 TOML。
- **门禁基线污染别人历史**。现象：项目 01 的"缺陷时代"基线被门禁
  拿来对比，判定错乱。解法：基线分开放、命名带语境。
- **`TAG=xx func` 的前缀赋值当函数参数用**。`$1` 是另一回事
  （本脚本踩了两回）。解法：两种传参机制分开用。
- **预算一次定太紧**。现象：门禁天天红被禁用。解法：先松后紧，
  随治理棘轮收紧。

深入问答：

- **Q：性能回归门禁放在 CI 哪个阶段？**
  合并到主干之前跑短场景（smoke 级预算判定）；全量容量评估放 nightly。
  门禁要快，否则没人等它。
- **Q：基线怎么防止过期？**
  定期（如每周）用健康主干重采；基线漂移要审计
  （对比新旧基线的差异是否来自合法变更）。
- **Q：容量报告必备哪几节？**
  当前容量与饱和点、瓶颈归因、扩容建议（扩什么、扩多少、预期收益）、
  以及历史调优的证据链——数字都要能复算。
- **Q：预算和 SLO 的关系？**
  SLO 是对用户的承诺，预算是各服务分到的退化额度之和要能保住 SLO
  ——预算是 SLO 的逐层分解。

**系列收官**：🟢 → 🔴 → 🟢 的三连证明了门禁真的会咬人。至此十个项目
闭环：**定 SLO → 基线压测 → 负载建模 → 观测 → 双语言剖析 → 数据库诊断 →
缓存 → 并发调参 → 泄漏定位 → 回归门禁与容量结论**。每个数字可复算，
每个结论有出处，每个防护都被攻击验证过——这就是性能工程的完整方法论。

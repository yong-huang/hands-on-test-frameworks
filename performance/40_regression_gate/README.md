# 🏁 40 · 性能回归门禁 + 容量评估报告：系列的终点，守护的起点

> 调优是一次性的，守护是长期的。本项目把前 9 个实验的结论变成两件资产：
> 一道**会咬人的门禁**（性能预算 + 基线对比，回归注入即红），一份**容量
> 评估报告**（拐点、饱和点、扩容建议、全程 before/after）。实测三连：
> 🟢 14.1ms → 注入回归 🔴 132.1ms（+836%）→ 修复 🟢 12.6ms。

## 1. 为什么需要它

- 没有门禁的性能优化是"逆水行舟"：今天修好的 P95，下个月的合并悄悄退回去；
- 性能预算（budget）是把 SLO 翻译成机器可读的判定规则——CI 的 exit code
  就是它的牙齿；
- 容量评估报告是性能工程的交付物：老板不关心你的火焰图，关心"能扛多少、
  什么时候扩、扩什么"。

## 4. 核心概念

### 4.1 实测：门禁三连（本机数据）

| 阶段 | shop P95 | 判定 |
|:---|---:|:---|
| 健康基线 | 14.1ms | 🟢 通过 |
| 注入回归（还原三缺陷） | **132.1ms（+836%）** | 🔴 不通过 |
| 修复恢复 | 12.6ms | 🟢 通过 |

注意注入阶段的 shorturl 也红了（+87%）：共享机器上的邻居退化会连累无辜
服务——CI 资源隔离是门禁的工程前提（本机实验里作为现象记录）。

### 4.2 性能预算怎么定

`budget.toml` 三条：P95 退化 ≤25%、错误率 ≤2%、吞吐下降 ≤15%。数字来源：
- P95 的 25% = 高于日常抖动（健康复测自身的波动 <20%）、低于用户可感阈值；
- 预算要跟着 SLO 走：SLO 500ms 时 25% 的余量还有 375ms 的绝对空间；
- 预算宁可先松后紧：太紧的门禁天天红，很快就会被人为禁用。

### 4.3 样本量守门

门禁第一道检查是**样本量**（<100 个请求直接拒绝判定）——5 VU × 30s 有
上千请求，够；但如果有人偷偷把时长改成 5s，门禁拒绝用 30 个样本下结论。
统计显著性是门禁可信度的一半。

### 4.4 易错点（本实验真踩）

- **手写 YAML 解析器把缩进 strip 掉**，所有键都进了错误层级——直接用
  stdlib `tomllib`，预算文件写成 TOML；
- **门禁基线不要污染别人的历史**：31 号实验的基线是"缺陷时代"的文物，
  门禁基线是"当前健康版"的快照，两者必须分开放；
- `TAG=xx func` 的前缀赋值和函数参数 `$1` 是两回事（本脚本踩了两回）。

## 7. 面试要点

- **Q: 性能回归门禁放在 CI 哪个阶段？** 合并到主干之前跑短场景（smoke 级
  预算判定）；全量容量评估放 nightly。门禁要快，否则没人等它。
- **Q: 基线怎么防止过期？** 定期（如每周）用健康主干重采；基线漂移要审计
  （对比新旧基线的差异是否来自合法变更）。
- **Q: 容量报告必备哪几节？** 当前容量与饱和点、瓶颈归因、扩容建议（扩什么、
  扩多少、预期收益）、以及历史调优的证据链——数字都要能复算。
- **Q: 预算和 SLO 的关系？** SLO 是对用户的承诺，预算是各服务分到的退化
  额度之和要能保住 SLO——预算是 SLO 的逐层分解。

## 8. 总结与系列收官

🟢 → 🔴 → 🟢 的三连证明了门禁真的会咬人。至此十个项目闭环：**定 SLO →
负载建模 → 观测 → 双语言剖析 → 数据库诊断 → 缓存 → 并发调参 → 泄漏定位
→ 回归门禁与容量结论**。每个数字可复算，每个结论有出处，每个防护都被
攻击验证过——这就是性能工程的完整方法论。

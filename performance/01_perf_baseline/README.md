# 01 · 双 SUT 靶场 + 基线压测：性能工程闭环的起点

> 功能测试回答"对不对"，性能工程回答"快不快、能扛多少、慢在哪"。
> 本系列用两个**故意带病上线**的被测系统当靶场：FastAPI 商店 + Go 短链服务，
> 各埋了若干性能缺陷（答案锁在 `SECRET_DEFS.md`，破案前别看）。本篇先把靶场
> 立起来，跑出**优化前基线**——后面每个实验的"提升了多少"，都拿它做对照。

## Background

没有基线的优化是玄学：改了一行代码，P95（95 分位延迟）从 130ms 变 128ms，算提升吗？
可能是抖动，可能是缓存预热，也可能什么都没变——没有"优化前"的固定
参照系，任何"变快了"都不可证明。

性能调优的另一个误区是只在单一语言栈上练手：Python 与 Go 的剖析器
（py-spy vs pprof）、并发模型（GIL vs goroutine）完全不同——
只会一种，性能问题的半个世界对你永远不可见。

本系列的双靶场因此刻意设计：两个 SUT 各埋若干性能缺陷，
用"破案"的方式练「压 → 观 → 剖 → 调」的完整闭环。
本篇先立靶场、出基线；定位手段分别在项目 4-9 揭晓。

## What

性能基线是优化工作的对照原点：固定场景、固定指标、固定环境跑出的
一组数字——后续每次变更重跑同一场景，差异即效果。

基线报告（`docs/baseline.md`）固定五指标：RPS（每秒请求数）、P50/P95/P99（把全部请求耗时排序后取 50%/95%/99% 位置的值，P95 即"95% 的请求都比它快"）与错误率。

场景锁定 5 VU（Virtual User，压测器里一个循环发请求的虚拟用户）× 30s——**基线要的是稳定可复现，不是压垮**。

可以把基线想成体检报告的"入院记录"：后续每次治疗（优化）前后都量同一组体征，疗效才有据可查。但和体检不同的是，基线必须锁定场景（负载形状不变），否则两次数字根本不可比。


靶场拓扑：k6 从左右两路施压，shop（读写 ≈2:1）与 shorturl
（跳转:创建 ≈9:1）；两个 SUT 共享一套 Postgres（各自独立库），
Redis 本篇空载入库（项目 7 的弹药）；压测产物经 summary-export
汇成五指标基线报告。

## When to Use

典型场景：

- 调优实验的对照组：每次修复跑 `observe` 重出基线报告，P95 变化登记进
  报告的"后续项目登记表"。
- 容量认知的起点：知道"带病状态下的正常表现"，异常才有定义。
- 双栈学习方法论：同一套流程在 Python/Go 各走一遍，剖析方法论成对掌握。

何时不用：一次性脚本没有"后续优化"就无需基线；生产系统的基线采集
要另做容量规划（本篇是教学靶场，5 VU 是刻意的小负载）。

## Quick Start

前置条件：Docker 运行中（labs/00 体检项）；k6（命令行压测工具）CLI 就绪。

```bash
cd performance/01_perf_baseline
./perf_baseline.sh all      # 起栈+等健康+抽查 → 压测两轮 → 生成基线报告
./perf_baseline.sh observe  # 只重跑压测与报告（对比修复效果时用）
./perf_baseline.sh clean    # 停栈删卷，回到实验前状态
```

首跑实测（2026-09 本机验证）：

```
=====> [wait] 等两个 SUT 健康
✅ perf-shop 就绪: http://localhost:19331/health
✅ shorturl 就绪: http://localhost:19332/healthz
=====> [verify] 抽查种子数据与核心端点
{"items":[{"id":1,"name":"product-1","price":211.93,"stock":1000},...],"total":2}
301 -> https://example.com/long/target/1
```

实测基线（本机数据，Apple Silicon / Docker Desktop）：

| 服务 | RPS | P50(ms) | P95(ms) | P99(ms) | 错误率 |
|:---|---:|---:|---:|---:|---:|
| perf-shop (FastAPI) | 43.0 | 12.8 | **130.7** | 133.5 | 0% |
| shorturl (Go) | 19.0 | 1.2 | 3.6 | 4.5 | 0% |

诚实预期：先自己读数据再往下看——shop 的 P50 才 12.8ms，P95 却跳到130.7ms，**分位数断裂**说明少数请求被某个固定开销拖住（下单路径里有一段120ms 的串行调用，每两次迭代触发一次，恰好锚在 P50~P95 之间）。

shorturl 各分位平滑，量级也小一个数量级——但别被表象骗了，它肚子里另有货。破案线索到此为止，答案在 `SECRET_DEFS.md`。


关键参数（这段在做什么：compose 连接串与 k6 导出开关）：

## How It Works

**基线的复现性设计**。固定 5 VU × 30s 的封闭场景（后续项目 2 会讲开放
模型），固定五指标导出（`summaryTrendStats`），固定种子数据——三次变量
全锁死，跑出的数字才有"对照"资格。压满负载会撞拐点、抖动放大，
修复效果淹没在噪声里——找拐点是另一场景（项目 2）。

**健康检查用业务信号**。postgres 健康检查不能只用 `pg_isready`：
TCP 就绪时 init 脚本可能还没跑完，下游会 load 到空表。本实验用
"种子 count 查询"当健康信号——「等数据库真的能答业务问题」
而不是「端口通了」（labs/11 的健康检查原则在 compose 里的落地）。

**缺陷纪律（本系列的学习方法）**。靶场代码里的缺陷位都有
`【缺陷位之一】` 注释占位，但**是什么、为什么慢、怎么确认**，
要靠后续实验的剖析器自己找；`SECRET_DEFS.md` 是答案册：破案前不看，
破案后对照归因是否成立。

## Pitfalls & Q&A

踩坑清单（本实验踩过的真坑）：

- **postgres 健康检查误报就绪**。现象：下游 load 到空表。
  解法：种子 count 查询当健康信号，不依赖 `pg_isready`。
- **init 脚本权限伪装成空数据**。现象：第二个服务的库表 owner 是
  `POSTGRES_USER` 角色，查询静默返回 0 行。解法：
  `ALTER TABLE ... OWNER TO`，且别吞 `rows.Err()`——
  否则权限错误会伪装成"0 行数据"。
- **端口冲突**。现象：893x 端口起不来。原因：本机被 OrbStack 的端口
  转发占用。解法：宿主侧改用 1933x；装了多套 Docker 运行时
  （OrbStack/Docker Desktop）时先 `lsof -iTCP` 查占位。

深入问答：

- **Q：基线为什么固定 5 VU 而不是压满？**
  基线的职责是提供可复现的对照系；压满会撞拐点，抖动放大，修复效果
  淹没在噪声里。找拐点是另一场景（项目 2）。
- **Q：P50 正常但 P95 断崖，说明什么？**
  少数请求吃到了固定开销或排队：慢下游调用、锁等待、GC 停顿。
  分位数形态本身就是第一层归因。
- **Q：压测机与 SUT 同机会怎样？**
  相互抢 CPU，绝对值失真但趋势可用；严肃结论要分机或至少记录资源曲线
  （项目 3 的监控栈就是为此）。
- **Q：为什么一个靶场要两种语言？**
  性能问题与运行时模型强相关：GIL 下的 CPU 热点、goroutine 泄漏、
  锁竞争的表现与排查工具完全不同，双语言逼你掌握两套剖析方法论。

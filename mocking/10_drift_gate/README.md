# 10 · Mock 漂移巡检门禁：真服务是基准，mock 对表

> mock（替身：代替真实依赖应答的假服务）最大的谎言是「我一直是对的」。本篇实现漂移巡检器：以真服务应答为
> 基准，对 mock 应答做双向结构 diff，按三类归类——mock_missing（真有
> mock 无）、mock_extra（mock 声明了不存在的东西）、type_changed（类型
> 漂移）。实测：对齐契约基线巡检 0 漂移退出码 0；注入一次字段删减
> （created_at 被删），报告定位到该字段且退出码 1；类型漂移
> （amount number→string）同样拦截；恢复对齐契约后门禁归零放行。

## Background

08 的 [Prism](../08_prism/README.md)（从契约生成应答的 mock 工具）应答
从契约生成，09 的 [stub](../09_pact_stub/README.md)（按既定规则应答的
替身服务器）应答来自 pact——共同前提是「契约与现实一致」。

这里的契约（声明接口请求/响应结构的规格文件）与 pact（记录接口使用方
期望的契约文件）是两种真源——替身应答各自从真源生成。

事后的发现方式都很贵：联调时对不上账、上线后前端拿不到字段。把发现
提前的手段是巡检：定期把真服务应答与 mock 应答做结构对比，任何类别
的漂移在门禁里当场报红——漂移从「上线事故」降级为「一次红灯」。

## What

漂移巡检门禁是三件套：真服务（结构基准）、被检 mock（本篇用 08 的
Prism，吃契约应答）、巡检器（对两者逐探测点做递归结构 diff）。漂移
按相对真服务的方向分三类：

| 类别 | 含义 | 例子 |
|:---|:---|:---|
| `mock_missing` | 真服务有、mock 没有 | created_at 被从契约删除 |
| `mock_extra` | mock 多出、真服务没有 | mock 里声明了废弃字段 |
| `type_changed` | 两边都有但类型不同 | amount 真服务是 number，mock 是 string |

可以把巡检器想成替身的**年检站**：真服务是厂检标准，mock 每次过检都要
对表，任何一项不合格就扣下（退出码 1）。但和车辆年检不同的是：这里的
「不合格」被精确归类到字段与类别——报告直接告诉你改哪里。

## When to Use

典型场景：

- mock 长期服役的团队：08/09 的替身跑了几个月，定期巡检防「契约与现实
  悄悄分家」。
- 契约变更流程的最后一环：契约合并后自动巡检，确认替身已同步。
- 事故复盘：接口变更没人通知消费方时，巡检报告就是时间线证据。

何时不用：mock 与真服务本来就允许不同（降级语义、脱敏字段）→ 把豁免
（已知且接受的差异白名单）写进巡检配置——本篇最小巡检器未实现豁免，
属生产化方向——而不是让门禁永远红着；真服务本身不稳定 → 先稳住基准
（固定应答的假上游，如本篇 real_service）再谈巡检。

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| [契约测试](../../labs/15_pact/README.md) | 验证真 provider（接口的实现方）守约 | 契约与「实现」的一致性 |
| 契约驱动 mock（08） | 契约变了 mock 立刻变 | 漂移的源头治理 |
| 漂移巡检（本篇） | 真响应 vs mock 应答对表 | 存量替身的常态化体检 |

## Quick Start

前置条件：node/npx（Prism 5.16.0，同 08）；仓库根 venv（labs/00 体检
通过，含 httpx 与 PyYAML）；另用 curl 与 lsof（macOS 自带）；npx 首次运行会先把 Prism 包拉进缓存
（约几十秒、无输出），属正常而非卡死。

```bash
cd mocking/10_drift_gate && ./drift_gate.sh all
```

实测输出（节选）：

```
=====> [observe] ② 基线巡检：契约与真服务对齐，0 漂移，退出码 0
  ✅ [GET /orders/{id}] status 200/200，漂移 0 处
    ……

=====> [observe] ③ 注入字段删减（created_at 从契约移除）→ 巡检定位该字段 + 退出码 1
  ❌ [GET /orders/{id}] status 200/200，漂移 1 处
     · mock_missing: $.created_at（真服务有、mock 没有）
  ❌ [POST /orders] status 201/201，漂移 1 处
     · mock_missing: $.created_at（真服务有、mock 没有）
    ……
>>> 退出码 1（符合预期 1）
>>> 巡检报告定位到被删字段 created_at ✅

=====> [observe] ⑤ 恢复对齐契约 → 门禁归零放行
  ✅ [GET /orders/{id}] status 200/200，漂移 0 处
    ……
>>> 退出码 0（符合预期 0）

>>> 验收：结构 diff 报告 ✅ 字段删减定位+退出码 1 ✅ 类型漂移拦截 ✅ 归零放行 ✅
```

诚实预期：③ 的注入方式是「改契约再重启 Prism」——漂移是被刻意制造的，
巡检器的工作是抓住它而不是防止它；④ 的类型格只报 GET 一处，因为
amount 只在 GET 应答里。基线 0 漂移的前提是 real_service 与对齐契约
逐一对照写过——基准本身也需要被认真维护，这是巡检的隐性成本。

## How It Works

**diff 以真服务为基准、按方向归类**。递归走真应答的每个键：mock 没有
→ `mock_missing`；mock 多出的键 → `mock_extra`；两边都有则比类型——
int 与 float 同算 number（123 与 123.5 是同一语义），其余类型不同即
`type_changed`：

```python
for k in real:
    if k not in mock:
        out.append({"path": f"{path}.{k}", "kind": "mock_missing", …})
    else:
        diff(real[k], mock[k], f"{path}.{k}", out)
```

**探测点是结构化对表的最小单位**。本篇两个探测点（GET/POST）各自带
期望状态码；巡检器同时核对状态码与应答结构——你在输出里看到的
`status 200/200` 就是两边各自的状态码，先于结构参与判定。

**退出码是门禁的全部接口**。无漂移 exit 0，有漂移 exit 1 且报告落盘
`reports/drift.md`（逐处定位到字段路径与类别）——CI 里一行
`python drift_gate.py … || exit 1` 就是完整的拦截逻辑，门禁不需要
理解漂移内容，只需要尊重那个数字。

**契约注入演示了「被检物可替换」**。三份契约（对齐/缺字段/类型漂移）
由 yaml 库从对齐版程序化生成（生成脚本未随库提交，派生逻辑见各文件
title 与 diff）——漂移注入改的是 mock 的真源，不是巡检器的输入。

巡检器对「mock 怎么来的」全然无知，这是它能看住任何替身
（Prism/pact stub/自研）的原因。

## Pitfalls & Q&A

踩坑清单：

- **基准不稳，巡检全废**。现象：每次巡检漂移点都不一样。原因：真服务
  应答带随机值或时间戳。解法：基准侧用固定应答（本篇 real_service 全
  确定性）；真服务无法固定时，把易变字段列入豁免清单（本篇未实现，
  属生产化方向）。
- **豁免清单会变成漂移的藏身处**。现象：豁免越加越多，门禁常绿但
  mock 早就不像真服务了。原因：豁免是「已知且接受」的白名单，不是「不想看」的垃圾场。
  解法：豁免必须带理由与复审日期、进 diff 报告（本篇未实现豁免，
  此为生产化方向的要求）。
- **int 与 float 判成类型漂移**。现象：真服务 123、mock 123.5 被报红。
  原因：按 Python 类型名比较，int≠float。解法：数字族归并为同一
  `kind`（见 `kind()` 的 NUMBER 集合），语义同为一个数字。

深入问答：

- **Q：巡检、契约测试、漂移门禁是一件事吗？**
  方向不同：labs/15 验「真 provider（接口的实现方）守不守契约」，08 验
  「mock 守不守契约」，本篇验「mock 像不像真服务」——基准分别是契约
  与真服务应答。理想顺序：契约先行（08 起替身）→ verify（labs/15 的 provider 校验）
  → 常态巡检（本篇）兜底。
- **Q：为什么不用现成 jsondiff？**
  门禁需要按类别（missing/extra/type）分类报告并定位路径，通用 diff
  库给的是统一格式的补丁视图（patch 格式的差异文本），还要二次解析归类。自研递归 60 行，
  输出即报告——清单原计划用库，选型时依此改判，依据写在代码注释里。
- **Q：巡检多久跑一次？**
  频率与真服务的变更速度成正比：接口稳定期每周足以，快速迭代期挂在
  每次契约/服务合并后。门禁的价值在「必跑」，不在「跑得多勤」——
  一周一次但从不跳过的巡检，好过每天跑但随手豁免的巡检。

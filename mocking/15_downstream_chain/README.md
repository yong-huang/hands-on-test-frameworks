# 15 · ⛓️ 下游依赖链虚拟化：BFF 三下游，断网也全绿

> 订单聚合 BFF 依赖 支付/风控/短信 三个下游——真依赖模式要 3 个服务全部
> 存活才能测。本篇用 01 的声明式替身顶上：杀光全部真下游后，同一套集成
> 测试在虚拟化模式下照样全绿（真下游存活数 3/3 → 0/3）；替身里把支付
> 注入 500，BFF 走 PENDING_RETRY 降级而不崩。

## Background

聚合层（BFF，Backend For Frontend：为前端聚合多个下游数据的后端服务）
的测试成本随下游数量线性增长：N 个下游 N 套环境、N 份数据、N 个故障源。
更糟的是「要测聚合逻辑，就得每个下游都像样地活着」——任何一家休假，
聚合测试全体变红。

虚拟化的答案：下游地址做成配置，BFF 代码不改，真下游与替身可切换。
替身按真下游的形状应答，聚合逻辑的测试从此只依赖「替身的规则表」，
不依赖任何一家外部服务。

## What

下游依赖链替身 = 同一份 BFF 代码 + 可切换的下游地址表。两种模式：

| 模式 | 下游 | 用途 |
|:---|:---|:---|
| 真依赖（real） | 支付/风控/短信 各自独立服务（:9801-9803） | 对照组：聚合逻辑与真实形状对齐 |
| 虚拟化（mock） | 01 声明式替身单实例（:9810，/pay /risk /sms 三路径） | 断网演练 + 故障注入 |

可以把 BFF 想成只认地址不认人的项目经理：下游是谁、活不活，他只看
通讯录（环境变量）。通讯录从真服务换成替身，他的工作方式一行不变——
这正是「地址表驱动」的替身切换与 07 矩阵（对同一下游穷举故障）的
互补：矩阵管单下游的坏，本篇管整条链的切换。

## When to Use

典型场景：

- 聚合/BFF 层的 CI 环境：虚拟化模式下不需要任何真下游存活，测试
  又快又稳。
- 下游故障演练：替身里改一条规则就是一次下游宕机，验证降级分支。
- 新下游接入评审：先在替身里定义形状，聚合逻辑先行开发。

何时不用：下游有状态且交互复杂（多轮握手）→ 替身表达不了，用
testcontainers 真依赖（labs/14 的路线）；只测单个下游自身 → 那是
下游自己的单测。

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 真依赖测试 | 环境重、形状真 | 集成验收、发布前 |
| 声明式替身链（本篇） | 单替身多路径、地址表切换 | 聚合逻辑、故障演练 |
| 故障矩阵（07） | 单下游穷举故障格 | 降级分支的系统性覆盖 |

## Quick Start

前置条件：仓库根 venv（labs/00 体检通过，含 httpx）；同目录
../01_declarative_mock 的 mockserver.py 与本篇 stubs/；另用 curl 与
lsof（macOS 自带）。

```bash
cd mocking/15_downstream_chain && ./downstream_chain.sh all
```

实测输出（节选）：

```
=====> [observe] ② 真模式：3 个真下游全部在场，BFF 集成测试全绿
真下游存活数：3/3
  聚合应答：{"payment": "TXN-REAL-001", "risk": "approve", "sms": "MSG-REAL-001", …}
  ✅ 无降级标记 — []

=====> [observe] ③ 断网：杀光全部 3 个真下游，切换虚拟化模式（01 声明式替身 :9810）
真下游存活数：0/3（全部阵亡）
  ✅ payment 正常落账 — TXN-MOCK-001

=====> [observe] ④ 故障注入：替身里的支付改 500 → BFF 走 PENDING_RETRY 降级
  ✅ 支付失败 → PENDING_RETRY（不崩） — PENDING_RETRY
  ✅ 降级标记恰好 1 项 — ['pay']

>>> 环境对比：真依赖模式需 3 个下游存活，虚拟化模式 0 个（数据见上）
>>> 验收：真模式全绿 ✅ 断网后虚拟化模式全绿 ✅ 支付故障降级 PENDING_RETRY ✅
```

诚实预期：虚拟化模式应答里的值（TXN-MOCK-001 等）来自替身规则表——
与真下游值不同是替身的本质；断言看的是 BFF 的分支行为（落账/降级/
标记），不是具体值。故障注入通过切换 stubs 目录实现（替身重启即生效）。

## How It Works

**地址表驱动，代码零改动**。BFF 的下游地址从环境变量读取，两种模式
只差通讯录：

```python
MODE = os.environ.get("DOWNSTREAM_MODE", "mock")
if MODE == "real":
    BASES = {"pay": "http://127.0.0.1:9801", …}
```

**逐依赖独立降级**。checkout 对三个下游各自 try，各自有降级分支
（支付 PENDING_RETRY / 风控 DEFAULT_PASS / 短信 skipped），并在
degraded 数组里留下痕迹——聚合层的价值就是「部分下游死掉时整体仍可
用」，这个价值必须被断言而不是被假设。

**故障注入是换一份规则表**。stubs_fault/ 里支付返回 500，替身重启
即生效；④ 步断言「降级标记恰好 1 项」——多一项说明无辜下游被牵连，
少一项说明注入没生效。

## Pitfalls & Q&A

踩坑清单：

- **BFF 默认模式与启动脚本不一致**。现象：真模式跑出 mock 的值
  （PENDING_RETRY）。原因：代码里 DOWNSTREAM_MODE 默认 mock，启动命令
  忘了传 real。解法：模式写进启动日志（本篇 BFF 启动即打印模式与
  下游表），断言失败时先看日志。
- **同一替身目录混放正常与故障规则**。现象：故障注入永远不生效。
  原因：01 替身「特异度平分先定义胜出」，正常规则先加载就永远赢。
  解法：正常/故障拆两个 stubs 目录，注入时整体切换。
- **替身端口被残留进程占用**。现象：新替身起不来或 BFF 连到旧实例。
  原因：上一轮脚本中断残留。解法：apply 先对全部端口清场（含上次
  中断残留），clean 后逐一确认空闲。

深入问答：

- **Q：为什么不把三个下游做成三个替身实例？**
  01 替身按路径匹配，单实例三路径即可承载三个下游——端口数量从 3
  降到 1，环境矩阵更小。真依赖模式才需要真端口分离（那是现实约束）。
- **Q：聚合层的「部分成功」怎么表达？**
  degraded 数组就是答案：BFF 不隐瞒任何降级，把每个降级依赖列为
  标记。消费方可以据此决定「有降级就提示用户」或「静默接受」——
  隐瞒降级的聚合层是最难排障的那种。
- **Q：真实环境里下游地址会变吗？**
  会（域名、端口、网关前缀）。地址表就该是配置而非代码——本篇用
  环境变量演示最小形态，生产里由服务发现/网关承担，BFF 的原则不变：
  只认地址不认人。

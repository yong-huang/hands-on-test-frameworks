# 07 · 故障注入矩阵：把「想到哪测到哪」变成逐格穷举

> 替身（代替真实依赖应答的假服务）能注入的异常此前只有应答层的——状态码
> 与延迟（见 [02](../02_wiremock/README.md)、[04](../04_dynamic_response/README.md)），
> 断连这类传输层故障由 WireMock（业界标准的 HTTP 替身服务器）的原生 fault
> 字段在本篇补齐。异常验证通常是想到哪测到哪，本篇改成穷举：给贯穿场景的
> 结账客户端写上 7 个分支（1 条正常路径 + 6 条降级路径），再用 WireMock 的
> admin API（它的管理端点 HTTP 接口，路径前缀 /__admin，可动态增删应答规则）
> 逐格注入 7 类场景（无故障基线 + 6 类故障），逐格断言「客户端进入的分支」：
> 7 格全部命中专属分支、错格即红、覆盖率报告落盘（格子 7/7、分支 7/7）。

## Background

结账客户端要面对的故障其实是有清单的：上游慢、上游挂、拒绝服务、限流、
应答破损、线路断裂——但测试这些的方法一直是「想到哪测到哪」：某次事故
后补一个超时测试，某次评审提到 429（限流状态码：请求过多被拒绝）再补一个。没被想到的故障分支，
代码里写了降级逻辑，测试里却从未执行过。

覆盖率的盲区在此：分支覆盖率会说「这些 if 都覆盖了」，但不会告诉你
「503 进的分支断言的是不是 503 该有的行为」。穷举要求两张表对齐：
故障怎么注入、客户端该进哪个分支——一格一行，逐格断言。

WireMock 的注入能力（[02](../02_wiremock/README.md) 的状态码、
[04](../04_dynamic_response/README.md) 的延迟）加上它的原生 fault 字段
（连接重置这类传输层故障），足够拼出全部格子。

缺的只是一个驱动器，把「注入→执行→断言」循环起来并出报告。

## What

故障注入矩阵是一张两列表：每行声明「注入什么故障」与「客户端必须进入
哪个分支」。本实验的矩阵 7 行，每行对应客户端一个专属分支——一格一分支，
错格即红：

| 格子 | 注入方式 | 客户端分支 | 客户端的态度 |
|:---|:---|:---|:---|
| 无故障基线 | 200 正常应答 | `DIRECT_SUCCESS` | 直达 |
| 延迟 200ms | `fixedDelayMilliseconds: 200` | `SUCCESS_SLOW` | 成功但记慢调用 |
| 超时 3s | `fixedDelayMilliseconds: 3000`（> 客户端 500ms 超时） | `PENDING_RETRY` | 重试后落离线队列 |
| HTTP 503 | `status: 503` | `CIRCUIT_OPEN` | 重试耗尽即熔断（连续失败后主动停止调用该依赖） |
| HTTP 429 | `status: 429` | `RATE_LIMITED` | 立即排队，不重试 |
| 畸形 JSON | 200 + 残缺 body | `FALLBACK_DEFAULT` | 默认值兜底 |
| 断连 | `fault: CONNECTION_RESET_BY_PEER` | `FAIL_FAST` | 快速失败不重试 |

可以把客户端想成一个遇事有章程的接线员：慢了记一笔、断了立刻挂、
对方说忙就排队、对方语无伦次就按标准话术兜底。矩阵就是**查岗表**——
逐个场景拨过去，验证接线员每次都按章程办事。但和抽查不同的是：
查岗表穷举了全部章程，抽查漏掉的正是没被拨过的那一条。

## When to Use

典型场景：

- 客户端有明确降级设计（重试/熔断/兜底/限流）：矩阵把设计文档变成
  可执行断言。
- 事故复盘后的回归补强：把事故对应的故障格加进矩阵，永远回归。
- 新依赖接入评审：矩阵覆盖率报告就是「异常路径测试是否齐」的证据。

何时不用：客户端没有降级逻辑（失败就崩）→ 先写降级再写矩阵，否则
矩阵只会证明「它崩了」；故障在传输层之下（DNS、TLS 握手）→ 需要
更底层的网络仿真，WireMock 的 fault 字段够不到。

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 手写异常用例 | 一条测试一个场景，易漏 | 只有一两种明确要防的故障 |
| 故障矩阵（本篇） | 表驱动穷举 + 覆盖率报告 | 降级分支多、要求逐格可对账 |
| 混沌工程平台 | 随机注入真实基础设施 | 生产级韧性验证，非替身层面 |

诚实预期：矩阵里「慢」与「超时」是两格不是一格——200ms 在客户端
500ms 超时之内（慢但成功），3s 超出（触发重试直至兜底），分界线由
`SLOW_THRESHOLD_S` 与 `TIMEOUT_S` 两个阈值决定；改阈值就会改判格，
这正是阈值该被测试钉住的证据。

## How It Works

**每格一行声明，驱动器循环三件事**。矩阵是 Python 里的一张表——
每行 `(格子名, WireMock 响应定义, 预期分支, 语义)`。驱动器逐格执行：
清空 WireMock 全部映射、注入当前格的单条 stub、跑一次客户端结账、
把实际分支与预期对表：

```python
inject(resp)                    # DELETE /__admin/mappings + POST 单条 stub（存根：一条「请求长什么样 → 应答什么」的规则）
branch = checkout(base)         # 被测对象：返回「进入了哪个分支」
ok = branch == expected         # 错格即红
```

`checkout` 返回分支名而不是业务结果——把「进入了什么状态」做成显式
返回值，矩阵才断言得动。这是被测对象为可测性做的唯一让步。

**六类故障对应 WireMock 的三种注入面**。状态码类（503/429）改 `status`；
内容类（畸形 JSON）改 `body`；时空类（延迟/超时）用
`fixedDelayMilliseconds` 与客户端超时的差值。

传输层（断连）用原生 `fault: CONNECTION_RESET_BY_PEER`——
[02](../02_wiremock/README.md) 的状态码、[04](../04_dynamic_response/README.md)
的延迟、加上原生 fault，前两个阶段的注入能力在此合流。

**覆盖率报告是矩阵的出厂证明**。逐格执行完输出两行对账：格子 7/7
（每格都执行且符合预期）、分支 7/7（每个分支都被恰好一格触发）。
报告落盘 `reports/matrix.md`，可直接贴进 PR 与评审。

## Pitfalls & Q&A

踩坑清单：

- **「慢」和「超时」共享一个阈值边界**。现象：调小客户端超时后，
  慢格开始判成超时格。原因：两格的分界就是 `TIMEOUT_S` 与
  `SLOW_THRESHOLD_S` 的相对关系。解法：阈值进配置并写进矩阵语义，
  改阈值必须连带核对矩阵两行。
- **重试让故障格变慢**。现象：超时格执行明显长于其他格（3 次尝试各等满
  500ms 约 1.5s；503 格同样连打 3 次但应答即时，只多两次往返）。原因：
  客户端超时后重试 2 次，共 3 次尝试。解法：调小 `TIMEOUT_S` 可线性
  缩短；如需观察每格耗时，可在驱动器里计时写进报告（当前报告不含耗时）。
- **断连格必须用原生 fault 而不是「关掉靶场」**。现象：模拟断连时
  直接停掉 WireMock，所有格全变连接错误。原因：断连是「这一格的
  应答形态」，不是「靶场消失」。解法：用
  `fault: CONNECTION_RESET_BY_PEER`，靶场始终在线。

深入问答：

- **Q：矩阵怎么扩？**
  加一行：想清楚新故障的注入方式与客户端该有的态度，表里添格、
  客户端添分支（若无）。矩阵行数 = 客户端降级章程的条数，多一格
  就多一条章程，少一格就是章程没写全。
- **Q：为什么不混沌工程（随机注入生产故障）？**
  层次不同：矩阵在替身层穷举已知故障、可重复、进 CI；混沌在真实
  基础设施探未知脆弱点。矩阵是回归资产，混沌是探索手段，前者便宜
  到可以每次提交都跑。
- **Q：一格触发多个分支（先重试后熔断）怎么断言？**
  本实验让 `checkout` 只返回**最终**分支——重试是路径不是终点。
  若要断言路径，让客户端返回分支序列（如 `["RETRY", "CIRCUIT_OPEN"]`），
  矩阵的预期列跟着改成序列即可，驱动器一行不用改。

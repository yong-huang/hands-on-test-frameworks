# 16 · 压测中的下游虚拟化：100 并发零错答、双档延迟见敏感性

> 压测最怕「测的是下游而不是被测物」：真下游先被打垮，报告里全是别人的
> 错误。本篇给 15 的 BFF 配上虚拟化下游，k6 100 VUs 压两档（替身延迟
> 50ms/500ms）：全程零错答、P95 随下游延迟相应上涨（207→1563ms）、
> 替身命中计数与 k6 迭代精确对账（零泄漏）。

## Background

压测聚合服务时，真下游是最大的噪声源：它有自己的容量上限，先被压垮，
错误混进报告，你分不清是 BFF 撑不住还是下游撑不住。更根本的问题：
「下游慢 10 倍时 BFF 会怎样」这类容量敏感性实验，真下游根本不配合
（它不会按你的要求变慢）。

虚拟化给出第三个选择：下游用替身（延迟精确可控），压测的变量只剩
BFF 自己。

对表替身命中计数还能证明「压测期间真下游零请求」——零泄漏是被
计数器断言的，不是被假设的。

## What

压测虚拟化 = 稳定延迟的替身下游 + k6 负载 + 对账三件套：

| 断言 | 数据源 | 含义 |
|:---|:---|:---|
| 零错答 | k6 http_req_failed | 两档全程错误率 0 |
| 延迟敏感性 | 两档 P95 对比 | 下游 50→500ms，BFF P95 相应上涨 |
| 零泄漏 | 替身命中计数 vs k6 迭代 | 全部流量落在替身，真下游零请求 |

可以把整套想成给 BFF 装上**跑步机**：替身是履带（速度可控），k6 是
配速员，对账是跑步机上里程表与校服上传感器的核对。但和真跑步不同的是：
履带速度可编程——同一台 BFF，两档下游延迟就是两次容量实验。

## When to Use

典型场景：

- 容量敏感性实验：下游延迟 ×2/×10 时被测物吞吐如何衰减——替身的
  延迟旋钮精确可控。
- 压测隔离：CI 里压测不惊扰共享下游。
- 零泄漏回归：压测期间真下游必须零请求（安全/合规场景的硬要求）。

何时不用：要测「真下游 + 被测物」整体容量 → 全真链路压测（15 真模式
+k6）；下游行为不可替（有状态协议、复杂交互）→ 退回 testcontainers。

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 全真链路压测 | 数据真实、变量多 | 发布前整体容量验收 |
| 虚拟化压测（本篇） | 变量只剩被测物 | 容量敏感性实验、CI 压测 |
| 故障矩阵（07） | 单请求级异常注入 | 降级分支正确性（非容量） |

## How It Works

**延迟旋钮就是替身的一个参数**。mock_downstream 启动时带 --delay-ms，
每个应答前精确睡眠——500ms 档只是换一个参数重启替身。第二档前重启
替身意味着命中计数归零，所以零泄漏对账按「当前档迭代×3」核。

**零泄漏的账本**。每次 checkout 调三个下游，第二档 1000 次迭代应产生
恰好 3000 次替身命中（±1% 线程计数松弛）；同时 apply 阶段就断言真
下游端口 9801-9803 全部不在场——构造性 + 对账双重证明。

**BFF 需要压测加固**。首跑 100 VUs 错答率 1.27%：stdlib BFF 每请求
新建 httpx 连接 + 监听队列太浅。加固（共享连接池 + request_queue_size
=256）后零错答——这两个点本身就是容量实验的产出。

## Pitfalls & Q&A

踩坑清单：

- **k6 summary 字段名与直觉不符**。现象：读 `iterations_count` /
  `percentile(95)` 拿到 undefined。原因：--summary-export 的迭代数在
  `metrics.iterations.count`，P95 在 `http_req_duration["p(95)"]`。
  解法：先 `python -m json.tool` 看真实结构再写解析。
- **档位切换必须重启替身**。现象：改 --delay-ms 不重启，P95 纹丝不动。
  原因：延迟是启动参数，进程不重启不生效。解法：脚本逐档重启替身，
  计数器归零恰好用于分档对账。
- **真下游未清场 = 泄漏假阴性**。现象：泄漏断言通过但有流量打到真
  下游。原因：9801-9803 有残留进程抢答。解法：apply 阶段断言三个
  端口全部死亡（构造性前提），不靠事后发现。

深入问答：

- **Q：为什么 500ms 档吞吐恰是 50ms 档的约 1/8？**
  BFF 串行调三个下游，单请求耗时 ≈ 3×下游延迟 + BFF 自身开销。
  50ms 档单请求约 170ms（吞吐 8117/15s≈540/s），500ms 档约 1.5s+
  （1000/15s≈67/s）——比值 8 ≈ 耗时比，串行聚合的容量被下游延迟
  1:1 放大，这正是实验要暴露的容量形状。
- **Q：P95 比「平均延迟 + 下游延迟」还大，正常吗？**
  正常：P95 是分布的 95 分位，长尾（GC、线程调度、连接池等待）全被
  它吃进。看容量问题要看分布（P50/P95/P99），不要只看均值。
- **Q：100 VUs 是「100 并发用户」吗？**
  是 100 个并发迭代执行器，每个迭代完成后立即开下一轮——它是请求级
  并发压力，不是思考时间建模的真实用户。要模拟真实用户节奏，给
  iterations 加 sleep 或改用 constant-arrival-rate 场景。

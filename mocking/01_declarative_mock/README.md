# 01 · 声明式 mock server：把外部依赖换成一张规则表

> 被测代码总要去调别人的 HTTP 接口——对方没开发完、超时、返回什么都不可控。
> 声明式 mock（把「什么请求答什么」写成配置文件，而不是写在测试代码里的做法）
> 让同一个服务按规则表自动应答。本实验用纯标准库实现一个，实测：同一 URL
> 四条规则按特异度各答各的、未命中带逐条原因的 404、1000 并发零错答。

## Background

没有替身时，测试直接调真实依赖，替身靠手写：在测试代码里 monkeypatch
（运行时把模块或对象的函数临时替换成假实现的手法）掉网络调用（labs/04 做法），
或者写一个只会背固定台词的假类。

手写替身有两个具体代价：场景一变——「大额订单要进风控」「POS 渠道免审」
——就得改替身代码、重跑测试；假实现还只读死数据，请求特征一变它还是答
原来的话，等于没测到这个分支。

把规则从代码挪进配置文件是自然的下一步：一个场景就是规则表里的一条记录，
服务只留一套通用匹配引擎。规则怎么选、没匹配上怎么办，本实验就造这两件事。

## What

声明式 mock server 是一种按预写规则自动应答的独立 HTTP 服务，用来把被测
代码的外部 HTTP 依赖换成可控替身。规则表里的每条记录叫 stub（存根：一条
「请求长什么样 → 应答什么」的规则），存在 `stubs/*.json` 里，改规则不改代码。

可以把服务想成前台接线员，规则表是他手边的应答手册。但和按顺序翻手册
不同的是：他会自动挑**约束最细**的那条规则来回答——来电说「POS 渠道的
大额订单」，他不会拿「任何订单」的话术应付。

特异度分（一条规则约束了多少请求特征）度量约束的细度：method+path 得 0 分，
每多管一个 header 加 10 分、每多管一条 body 条件加 20 分。同一 `POST /orders`
上就能排出四级阶梯：

| 请求特征 | 胜出规则 | 分数 |
|:---|:---|---:|
| 只对上了路径 | `order-any` | 0 |
| + header `X-Channel: pos` | `order-pos-channel` | 10 |
| + body 金额 > 1000 | `order-big-amount` | 20 |
| + 两者都有 | `order-pos-big` | 30 |

## When to Use

典型场景：

- 依赖还没开发完：契约已定，消费方拿规则表先测起来，不等对方排期。
- 异常分支要可控：超时、拒绝、进风控真实世界等不来，改一条规则就能稳定复现。
- 并行测试要确定性：1000 个请求谁的应答都必须一样，真实依赖做不到。

何时不用：

- 依赖是「我方的」且容器化成熟（数据库、队列）→ testcontainers，用容器拉起真实依赖（[labs/14](../../labs/14_testcontainers/README.md)）。
- 要验证双方对接口的预期是否一致 → 契约测试（[labs/15](../../labs/15_pact/README.md)）。
- 依赖真实存在且稳定、只想离线复现 → 录制回放式挡板，数据后向（[architect/08](../../architect/08_mock_server/README.md)；本实验规则前向）。

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 手写替身（monkeypatch） | 逻辑在测试代码里，改场景要改代码 | 单测里替掉一两个函数级依赖 |
| 录制回放挡板 | 应答来自真实流量的录制 | 依赖已存在、响应复杂难手写 |
| 声明式 mock（本篇） | 应答来自规则文件，按请求特征选择 | 依赖未就绪/场景需要精确控制 |
| 契约测试 | 验证双方预期，不替你应答业务分支 | 前后端各自发版的集成对齐 |

## Quick Start

前置条件：仓库根已建 venv（labs/00 体检通过）或任意 Python 3.11+；服务端纯标准库；脚本另用 curl 与 lsof（macOS 自带）。

```bash
cd mocking/01_declarative_mock && ./declarative_mock.sh all
```

实测输出（节选）：

```
=====> [apply] ① 清场（含上次中断的残留端口）+ 加载 stubs/ 规则起 mock(:9100)
    ……
① 特异度阶梯：同一个 POST /orders，四份请求四种应答
  ✅ 无附加条件 → order-any（0 分） — state=created review=False
    ……
  ✅ POS 头 + 大额体 → order-pos-big（30 分） — state=created review=True
    ……
② 支付规则：Visa 直通、其他卡复核、缺幂等键响亮未命中
  ✅ 缺幂等键 → 404 响亮未命中 — 2 条候选规则各自说明了失败原因
    ……

③ 并发正确性：50 线程 × 20 轮，1000 个请求零错答
  ✅ 1000 并发请求全部命中预期规则 — 0 个错答/失败

④ 命中统计：每条规则的应答次数与未命中数
  {"hits": 1006, "misses": 1, "by_stub": {"order-any": 168, …}, "loaded": 6}
  ✅ hits = 4+2+1000 = 1006 — 实际 1006
```

诚实预期：①②③④ 全部 ✅ 是验收线；② 的 404 是设计好的教学点，不是环境
坏了——幂等键（Idempotency-Key，防同一笔支付重复扣款的请求标识）缺失时，
两条规则必须都拒绝并各自说出原因。`hits = 1006` 的对账还证明服务是刚起的
干净实例：有残留服务接答时，这个数字必错。

## How It Works

**规则是数据，引擎是代码**。`stubs/*.json` 启动时一次性加载，运行期只读
（`"Idempotency-Key": "*"` 表示只要求该 header 存在）。

每个应答都带 `X-Mocked-By`（哪条规则答的）和 `X-Match-Score`（特异度分）——
Quick Start 输出里的 `order-pos-big（30 分）` 就是服务端自己报的。

**匹配分两步：先入围，再评分**。method+path 对得上的规则进候选；约束全部
满足的候选按特异度分取最高者，平分则先定义的胜出——What 节的四级阶梯
就是分数排出来的：

```python
score = HEADER_SCORE * len(m.get("headers", {})) + BODY_SCORE * len(m.get("body", []))
if score > best_score:      # 平分不覆盖：先定义的规则保住应答权
    best, best_score = stub, score
```

**未命中必须响亮**。没有规则全约束满足时，404 的 body 逐条列出失败原因：

```json
{"error": "no_stub_matched",
 "candidates": [{"id": "pay-visa-fast", "reason": "缺少 header Idempotency-Key"},
                "……"]}
```

静默兜底会让「规则表过期了」变成最难查的灵异失败。响亮的 404 加上
`__stats__` 端点的逐规则计数（GET `/__stats__` 即返回 JSON 统计），
规则表一腐化就能被发现。

**并发下「谁应答」也是确定的**。ThreadingHTTPServer（标准库多线程 HTTP
服务器）承载只读规则表，1000 个并发请求逐一核对 `X-Mocked-By` 仍全部正确
——并发只改变谁来处理，不改变匹配结果。

## Pitfalls & Q&A

踩坑清单：

- **后台服务杀不掉，清理静默失效**。现象：clean 打印「已清理」，端口仍被占。
  原因：包装壳 `trap "" TERM` 吸信号噪声，SIG_IGN 处置（操作系统层面
  「忽略信号」的设定）被子进程继承，python 从此无视 SIGTERM。解法：子壳
  恢复默认处置再 `exec` python；TERM 无效时清理函数升级 `kill -9`。
- **残留旧进程接答健康检查**。现象：新实例绑定失败已崩，apply 却显示就绪。
  原因：健康检查只问「端口有没有人答」，答话的是残留进程。解法：起服后
  留暴露窗口再验活，靠统计对账兜底。
- **body 不是合法 JSON 时，body 条件全部不满足**。这不是 bug：文本 body 无从
  求值 `$.amount`，失败原因会写进 404 诊断；生产级会把迷你求值器换成
  JSONPath 库（用路径表达式在 JSON 里定位数据的规范）。

深入问答：

- **Q：声明式和录制回放（architect/08）怎么分工？** 依赖真实存在、响应复杂
  难手写 → 录制回放，数据是后向拿来的；依赖还没存在、或要精确控制每个
  分支 → 声明式，规则是前向写出来的。两者可叠加：先录一版再整理成规则。
- **Q：为什么不用现成的 WireMock？** 用 WireMock 重做本实验场景是本系列的
  独立一课（见 [docs/mocking.md](../../docs/mocking.md) 清单项目 2）。先造最小
  匹配器，才知道 mappings、匹配优先级这些配置项各自在解决什么。
- **Q：mock 应答是死的，测试会不会「假绿」？** 会，这是替身的共同风险。
  防线三层：未命中诊断与统计（替身层面）；契约测试验证规则表与真实接口
  一致（labs/15，双方层面）；真实联调抽查（环境层面）。

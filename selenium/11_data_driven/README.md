# 11 · 数据驱动下单

## Background

一条用例只测一组数据的写法，让「多地区多形态」的输入验证变成复制粘贴地狱。
数据驱动把**数据从用例里拆出来**：用例是流水线，数据是流水线上的货。

## What

- `orders.json`：5 组国际地址（中/英/日/德/特殊字符韩文混排）+ 1 组非法（纯空白地址）
- 5 条参数化用例：填表 → 提交 → 回读断言 `customer`/`address` 逐字段一致；
  收件人带**唯一毫秒后缀**——回读匹配上后缀即证明读的是本轮数据而非缓存
- 1 条负向用例：空地址提交被客户端拦截，`#form-error` 出现「地址必填」且回读区不出现

## When to Use

- 同一流程 × 多组输入（地区/币种/边界值/非法值）
- 需要证明「数据真实生效」而非「页面刷新过了」的场景——毫秒后缀是通用技巧

## Quick Start

```bash
cd selenium/11_data_driven
./11_data_driven.sh            # 6 passed
```

实测输出（2026-10-26）：`6 passed in 4.20s`

## How It Works

- `pytest.mark.parametrize(ids=标签)` 让报告里每组数据可读（中国地址/英文地址/…）
- 数据文件与测试解耦：改数据不动代码，加一组地址就是加一行 JSON
- 负向组与正向组分开写——断言语义不同（正向比对内容，负向比对拦截）

## Pitfalls & Q&A

- **坑：多组数据复用同一浏览器会话时残留上轮输入**——每条用例 `clear()` 后再填，
  并用毫秒后缀自证数据生效
- **坑：非法数据的预期写「不崩溃」**——太弱；要断言到具体错误提示文案与「回读区未出现」
- **Q：为什么不用 CSV？** JSON 天然支持结构化（地址里的逗号/换行）；CSV 留给纯表格数据

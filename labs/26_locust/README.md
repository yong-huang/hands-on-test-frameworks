# 26 · 性能测试（Locust）：10→100 并发阶梯加压，找到 SUT 的拐点

> 功能全绿不代表上线能活。Locust 用 Python 写压测场景：虚拟用户群爬坡加压，
> RPS/P95 曲线会告诉你 SUT 能扛多少、瓶颈在哪。读完本篇你能写出带权重与
> 思考时间的压测场景、跑一次 10→100 的阶梯加压，并把拐点与 lab 13/14 的
> 数据库结论对上——性能问题从来不是孤立的。

## Background

功能测试回答"对不对"，压测回答两个完全不同的问题：**当前容量是多少？**
加压时先死在哪里？这两个问题功能测试永远答不了——一条用例的通过不产生
任何并发信息，而线上事故几乎都发生在"功能全对但并发上来"之后。

压测工具的老一代（JMeter 等）用 GUI 拼场景，场景文件难进版本库、
难做断言逻辑。Locust 的路线是场景即代码：压测场景就是 Python 类，
任务权重、思考时间、断言全部可编程——压测脚本因此可以走代码评审、
进版本库、跟业务一起演进。

本实验对 SUT 做阶梯加压：100 虚拟用户以每秒 10 个的速率爬坡，
逐档对比 RPS/延迟/失败率，找出性能拐点并与前面实验的数据库结论互相印证。

## What

Locust 是一个用 Python 写压测场景的开源负载测试工具：`HttpUser` 子类
声明虚拟用户行为，`@task` 权重控制各行为的比例，`between()` 定义思考时间
（模拟真人操作间隔的随机等待），headless 模式输出 CSV/HTML 统计。

可以把压测想成餐厅的客流演练：虚拟用户是虚拟的顾客，爬坡是客流
从 10 桌渐涨到 100 桌，RPS 是每秒接单数，P95 是 95% 订单的上菜时限。
但和餐厅不同的是，压测要**主动设计顾客行为**——只点便宜菜（读多写少）
还是全点硬菜（写密集）由权重决定，行为设计错了结论就错了。

阶梯加压（stair load）找拐点的原理：并发逐档抬升，RPS 先随并发线性涨、
趋平、再回落——趋平点就是拐点（系统饱和的位置）。

## When to Use

典型场景：

- 上线前容量评估：给"能扛多少并发"一个有数据的答案。
- 瓶颈定位：P95 恶化先分清是全端点还是单端点（单端点查实现，
  全端点查资源——CPU/锁/连接池）。
- 治理方案验证：换库/异步化改造前后各压一轮，改善有数字。

何时不用：功能验证阶段不需要压测（先对再快）；一次性活动页且流量
可预估很小时，粗略冒烟即可——压测环境搭建与数据治理有成本。

由于爬坡速率是每秒 10 个用户、总时长 2 分钟，100 并发桶占了绝大部分采样时长，30~90 各桶只是爬坡途中的短瞬态——所以本机曲线没有呈现教科书式的"涨→趋平→回落"，拐点并未出现（SUT 未被打饱和，P95 全程被 1.5s 慢接口锚死）。


```python
class MinistoreUser(HttpUser):
    wait_time = between(0.5, 1.5)     # 思考时间
    @task(3)                           # 浏览:下单 = 3:1
    def browse(self): ...
    @task(1)
    def create_order(self): ...        # 下单用唯一客户名——数据也要隔离
```

## How It Works

**场景建模**：`@task(3)/@task(1)` 权重控制读写比例（3:1 的浏览:下单），
`between(0.5, 1.5)` 思考时间让施压节奏像真人。下单用唯一客户名——
**压测数据也要讲隔离**，别让唯一索引打架导致失败率虚高。

**拐点的数学形态**：RPS ≈ 并发 × 1/(响应时间+思考时间)——响应时间劣化时
RPS 增长放缓甚至回落。这是判读饱和的通用标尺。实测表的读接口 RPS 随并发从 17 涨到 70，
而 P95 全程被慢接口锚死在 1500ms：`time.sleep(1.5)` 占住线程池名额，
并发下排队效应被放大。

**瓶颈归因的对照链**：下单写接口高档位延迟增长更快，根因是**SQLite 单写者锁**（lab 13 实测过 `database is locked`，lab 14 实测Postgres MVCC 无此问题）——写请求串行排队，并发越高队越长。

这份报告给出的两条治理路径：换库（解写锁）+ 慢接口异步化（解线程池占用），全部有前面实验的实测背书。


**数据治理**：压测造了上万行订单，`clean` 会删库重置——
百万行测试数据会让下一次压测的基线失真（查询计划器——数据库决定一条查询
怎么执行的组件——面对的数据量变了）。

## Pitfalls & Q&A

踩坑清单：

- **压测机与 SUT 同机抢 CPU**。现象：数字比独立部署低。
  解法：本机数据看趋势可以，绝对值要在部署形态一致时才可比。
- **拿生产数据形态压测试库**。现象：结论不可迁移。
  原因：数据量差几个量级，查询计划器行为完全不同。
- **压测数据不清理**。现象：下一轮基线漂移。解法：clean 删库，
  每轮从同样空库起跑。
- **场景权重随手写**。现象：压出来的曲线与真实流量形态无关。
  解法：权重与思考时间按线上流量分布定，并写进场景注释。

深入问答：

- **Q：RPS 和并发用户什么关系？** RPS ≈ 并发 × 1/(响应时间+思考时间)——
  响应时间劣化时 RPS 增长放缓甚至回落，这就是拐点的数学形态。
- **Q：P95 恶化先查什么？** 先看是全端点恶化还是单端点：单端点查实现
  （本实验是 sleep），全端点查资源（CPU/锁/连接池）。
- **Q：压测数据要清理吗？** 要——百万行测试数据会让下一次压测的基线失真。

# 12 · API 测试套件：httpx + pytest 给 SUT 来 30 条真 HTTP 用例

> 单测没法告诉你"HTTP 层接起来对不对"。API 测试在真端口上对 SUT 发真请求：
> 状态码、响应头、schema、负向分支一次测全。读完本篇你能写出 30 条互相独立的
> API 用例——乱序跑、并行跑都绿，因为数据"自造自清"。

## Background

单元测试把网络 mock 掉（lab 04），换来速度与确定性，但也留下盲区：路由对不对、序列化丢没丢字段、校验层拦不拦负数、状态码语义对不对——这些只有把 HTTP 请求真的发出去才知道。

一条 `422` 响应背后是 pydantic（Python 的数据校验库）、FastAPI、数据层三层的合奏，任何一层走音，单测全绿也发现不了。


API 测试（对运行中的服务发真实 HTTP 请求的测试）补上这一层。
它对环境的要求也更高：服务要起、数据要干净、用例之间不能互相踩——
"共享魔法数据"（依赖谁先跑谁写死的 ID）和"拍屁股走人"
（造的数据不清理，垃圾堆积）是两种常见反模式。

本实验对 lab 11 的 SUT 写 30 条互相独立的用例，独立实例（8901 端口 + 独立空库）
运行，不污染演示数据。

## What

API 测试是在真端口上对服务发真实 HTTP 请求、断言响应（状态码、头、体、schema）
的测试层。它测的是**接口契约**（服务对外的承诺：什么输入给什么输出），
不含 UI。

可以把 API 测试想成验收新家电：单测是拆开机器测每个零件，API 测试是插上电
按说明书操作面板——说明书写的每个按钮（接口）都得按说明书反应（契约）。
但和验收家电不同的是，测试用的"电和水"（数据）要自己带自己收：
每条用例经工厂现造数据，teardown 现场清理。

本实验的技术栈：`httpx`（支持连接池复用的 HTTP 客户端）做请求端，
pytest fixture 做生命周期管理，pydantic 做响应 schema 校验。

## When to Use

典型场景：

- 服务端接口的契约回归：重构后 30 条用例跑一遍，契约漂移当场被抓。
- 负向分支验证：缺字段 422、负数量 422、非法状态 400、不存在 404——
  API 的健壮性藏在 4xx 里。
- CI（持续集成，提交后自动跑检查的服务）里的服务级冒烟：起 SUT → 全量 → 并行，2 秒量级跑完。

何时不用：纯函数逻辑单测更合适（快一个数量级）；用户在浏览器里的完整路径
（点按钮、看渲染）是 E2E 的领地——API 测试只管接口，不管页面。

同类方式对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 单元测试 + mock | 快，但测不到 HTTP 层 | 业务逻辑 |
| API 测试 | 真请求真端口，测契约 | 服务端回归的主战场 |
| E2E（浏览器） | 覆盖 UI 路径，最慢 | 关键用户路径 |

```python
r.headers["location"]                        # 201 创建后能按图索骥

OrderOut.model_validate(r.json())            # schema 锁
```

## How It Works

**session 级 client + function 级工厂**的分工：`httpx.Client(base_url=...)`
在 session 级 fixture 里创建，整个运行复用 TCP 连接池。

`order_factory` 是 function 级 fixture，每条用例现造带唯一标记的数据，
并在 teardown 里循环 DELETE 清理。

fixture 的清理保证与用例成败解耦（lab 02 的 try/finally 语义）——任何一步崩了，teardown 都会跑，测试库不留尸体。


**schema 校验锁**：`OrderOut.model_validate(response_json)` 一行把字段名与类型
锁死。服务端改字段名或类型时，用例当场红——这是 lab 15 消费者驱动契约测试的
轻量前置体验：先在消费者侧立 schema，再谈跨团队契约。

**负向用例的断言细节**：404 用例还校验 `detail` 里带回不存在的 id——
错误信息本身也是契约的一部分；user 角色打 admin 接口必须 403，
权限矩阵这样才闭环。

**数据窗口**：断言总数时用 `>=` 或限定自己造的数据窗口，绝不假设
"最后一个订单是我造的"——并行与乱序下，别人的用例随时在插数据。

## Pitfalls & Q&A

踩坑清单：

- **conftest.py 放错层级，fixture 不生效**（本实验踩过）。现象：`-c configs/`
  方式运行时根目录 conftest 找不到。解法：conftest 放 `tests/` 目录，层级稳定。
- **httpx 响应头小写化**。现象：`r.headers["X-Total-Count"]` 取不到。
  原因：httpx 把响应头统一转小写。解法：`r.headers["x-total-count"]`。
- **依赖"最后一个订单是我造的"**。现象：偶发总数断言失败。
  解法：总数断言用 `>=` 或限定自己的数据窗口。
- **服务没起就跑用例**。现象：全套 `ConnectTimeout`。
  解法：把"起服务 + 轮询健康检查"放进脚本 apply 步骤（lab 11 的经验）。

深入问答：

- **Q：API 测试和 E2E 的边界？** API 测试只管接口契约（无 UI）；E2E 管用户路径
  （有浏览器）。同一 SUT，两层互补不重叠。
- **Q：怎么保证用例可乱序？** 不依赖执行顺序、不依赖他例数据、清理挂 teardown。
  判定法：`-k` 随机圈子集都应全绿——本实验 observe ③ 就是这个判定法的实操。
- **Q：测试环境的数据从哪来？** 自造最优（不依赖种子漂移）；造不了的用 fixture
  预置；绝不共享可变数据。

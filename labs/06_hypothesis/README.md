# 06 · property-based 测试（Hypothesis）：让机器替你发明用例

> 手写用例是"编剧"——你只能想到自己想得到的输入。Hypothesis 是"轰炸机"：
> 你声明性质（无论输入是什么都该成立的规律），它随机生成成百上千组输入去炸，
> 炸出问题还会自动收缩成最小复现。读完本篇你能写出三种经典性质、读懂 Falsifying
> 报告、用 `@example` 把战果钉成永久回归。本实验有真实战果：它当场挖出两个
> 实验代码作者自己都没料到的 bug（见 Pitfalls）。

## Background

手写用例的覆盖边界是作者的想象力。边界值（0、负数、空表）、组合（大数配小数）、
序列（push 之后 pop 再 push）——能想到的都写了，想不到的永远测不到。
浮点均值函数就是个典型：谁会手写 `[1e300, 1.0, -1e300]` 这种输入？
但它恰好在普通求和实现上触发精度灾难（大数先把小数"吞"掉）。

property-based 测试（基于性质的测试，也叫 PBT）换了一个思路：与其枚举输入，
不如声明**性质**——无论输入是什么都必须成立的规律。框架随机生成大量输入去验证
性质，发现反例后把输入逐位简化到最小复现。随机性保证了每次运行都在探索新的输入角落，
这正是手写用例做不到的。

Hypothesis 是 Python 生态的 PBT 框架：`@given` 声明输入策略，失败自动收缩
（shrink），反例存进本地数据库（`.hypothesis/` 目录）下次必重放。

## What

性质（property）是一条"对所有合法输入都成立"的断言。PBT 用例的形态是：
`@given(策略)` 生成输入 → 执行断言 → 失败则收缩输入 → 报告最小复现。

可以把 Hypothesis 想成一台轰炸机：你只画靶心（性质），它负责投弹（随机输入），
炸到目标还会把弹着点标注清楚（收缩出最小样例）。但和轰炸机不同的是，
它炸出的战果需要你亲手固化——随机发现是惊喜，`@example(...)` 标注才是契约：
修复后无论策略怎么改，这个输入每次必跑。

三种经典性质形态：

- **往返（roundtrip）**：`decode(encode(x)) == x`——编解码器的天条。
- **不变量**：排序结果"有序 + 是原列表的重新排列（置换）+ 再排序幂等（排一遍和排两遍结果一样）"，三条断言锁死一个 sort。
- **等价对拍**：新实现对照一个简单参照实现（本实验 buggy_mean 对照 fsum 版）。

## When to Use

典型场景：

- 编解码、序列化、格式转换：往返性质一行顶几十条手写用例。
- 数据结构操作：用 RuleBasedStateMachine 随机执行操作序列并随时校验不变量。
- 数值算法：对拍一个简单但慢的参照实现，精度差异立刻现形。

何时不用：输入域没有清晰性质可声明时（比如大量业务分支逻辑），
手写用例更直接；策略设计不出来就别硬上——**策略设计决定挖雷概率**，
随机的价值在于探索你没想到的区域，而不是替代你思考边界在哪。

同类方式对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 手写示例用例 | 锁定已知关键样本 | 回归保护、关键样本 |
| property-based | 覆盖全输入域的规律 | 算法、解析、数据结构 |
| 两者组合 | @example 固化 PBT 战果 | 生产级测试的标配 |

它展示的是朴素求和 `buggy_mean` 的精度缺陷：`[1e300, 1.0, -1e300]` 三个数朴素相加会因浮点溢出配对抵消得到 0.0，而精确均值是 0.333...。

修复版性质全绿。


关键字段（这段在做什么：控制生成次数、超时与固定回归）：

```python
@settings(max_examples=200, deadline=None)   # 次数与超时（CI 友好）
@given(st.lists(...))                        # 随机生成
@example([1e300, 1.0, -1e300])               # 固定回归：无论策略怎么改必跑
```

## How It Works

**生成与偏向**：`st.text()`、`st.integers()`、`st.lists(...)` 是基础策略；`st.one_of` 混抽多种形态。

本实验埋雷用例的策略特意让大数（±1e150~1e300）与小数（±1e3）混抽——"大数吞小数"的精度 bug 需要特定组合才触发，策略里放进去，挖雷概率才高。这就是"策略设计决定挖雷概率"的落地。


**收缩（shrink）**：失败输入被逐位简化——更短的列表、更小的数、更简单的结构——
直到再简化一步性质就通过了为止。你看到的 `[1e+300, 1.0, -1e+300]`
就是收缩的终点：三个数一眼看懂，而不是一屏乱数。调试时间从"两小时"压缩成"看一行"。

**反例数据库**：发现的失败样例存进 `.hypothesis/` 目录，下次运行（哪怕换了策略）
会先重放历史反例。修复后，`@example` 标注再把最小复现钉进代码成为永久回归锚点。

**有状态轰炸**：对队列类这样的有状态组件，`RuleBasedStateMachine` 用 `@rule`
声明操作（push/pop）、用 `@invariant` 声明随时校验的不变量（长度与模型一致），
框架随机执行几百步规则序列——比手写操作序列便宜一个数量级。

## Pitfalls & Q&A

踩坑清单：

- **`deadline` 默认 200ms 误报 Flaky**。现象：I/O 或慢机器上报告"执行时间不稳定"。
  解法：慢数据上 `deadline=None`，或调大阈值。
- **`.hypothesis/` 数据库该不该进版本库**。团队项目进库（共享回归战果）；
  教学仓库 clean 掉。本实验脚本 clean 会清掉它。
- **`suppress_health_check=[HealthCheck.too_slow]` 滥用**。它静默"策略太慢"警告，
  但慢策略真正的解法是重新设计策略，不是关警告。
- **实验撰写时的真实战果（诚实记录）**：
  1. `decode(encode([]))` 返回 `['']` 而非 `[]`——空输入边界 bug，已修复。

  2. `encode([''])` 与 `encode([])` 同为 `""`——该格式天生无法区分空串元素，     已把策略约束为非空字符串并作为格式限制写进 `props.py`。

     这两个 case 手写用例都很难想到，正是 PBT 价值的实证。


深入问答：

- **Q：PBT 能替代手写用例吗？** 不能替代，是互补：手写锁"已知关键样本"，
  性质锁"全输入域规律"，`@example` 负责把战果固化。
- **Q：怎么测有状态组件？** RuleBasedStateMachine：规则=操作、不变量=随时断言、
  模型=简单参照实现（model-based testing 思想）。

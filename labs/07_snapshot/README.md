# 07 · 快照测试（syrupy）：一行断言守住整个大对象

> 断言一个 30 个字段的 API 响应要写 30 行 assert？改一个字段就维护到崩溃。
> 快照测试换个问法："输出和上次认可的版本一模一样吗？"——一行断言守全场，
> 变更必须经人审 diff 后有意更新。读完本篇你能走完 破坏→红→更新→绿 的完整闭环，
> 并知道快照适合什么、不适合什么。

## Background

大而稳定的输出无处不在：API 返回的 JSON 载荷、渲染出的整段 HTML、编译产物。
逐字段断言它们，成本随字段数线性增长，而且总有漏网字段——没人给第 30 个字段写 assert。
更麻烦的是维护：任何一个小改动都要同步改一串断言，改漏一个就误报。

问题的本质是缺少一个**回归基线**（上次被认可的正确输出的存档）：
没有基线，"输出变没变"只能靠人眼比对；有了基线，"任何变化都红"才可能自动化。
快照测试就是基线的工程化：首跑把当前输出拍成快照存档，之后每次运行做精确比对，
不一致就红并给出双向 diff，确认合法后显式更新基线。

syrupy 是 pytest 生态的快照标准件：单文件存储（`.ambr`）、可读的 diff 报告、
参数化自动分名。

## What

快照测试（snapshot testing）是一种"与上次认可版本全量比对"的断言方式：
测试体只写一行 `assert snapshot == 输出`，基线本体存放在
`tests/__snapshots__/*.ambr` 文件里——这个文件要提交进版本库，它就是基线。

可以把快照想成装修前的房屋验收照片：入住（首跑）拍下每个房间的样子，
之后的定期检查（后续运行）逐张对比照片，任何挪动都会被发现。
但和照片不同的是，快照的更新是显式动作——发现"合法的重新装修"（预期内的变更）后，
要人审 diff 并执行 `--snapshot-update` 换基线，而不是默默换照片。

首跑生成、此后比对：`--snapshot-update` 生成基线；日常运行永远是"现输出 vs 基线"。

## When to Use

典型场景：

- 结构稳定的大对象：API JSON 载荷、订单明细这类几十个字段的输出。
- 整段渲染产物：HTML 片段、报表文本、终端输出。
- 序列化格式回归：配置文件、消息格式的形态一旦意外漂移要立刻知道。

何时不用：输出含时间戳、UUID、随机数等不稳定源时——要么先冻结/mock 掉
（lab 04 的 freezegun），要么用 syrupy 的 matcher 钩子归一化，否则快照天天红；
高频变化的探索期原型也不适合，基线维护成本会吞掉收益。

同类方式对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 逐字段断言 | 表达业务规则，精确但冗长 | 关键字段的业务断言 |
| 快照断言 | 一行守全场，任何变化都红 | 整体形态的意外漂移 |
| 人眼 diff | 无基线依赖，但靠不住 | 只适合一次性检查 |

## Quick Start

前置条件：labs/00 体检通过（syrupy 已装）。被测对象 `renderer.py`：
订单 API 载荷构造 + HTML 行渲染。

```bash
cd labs/07_snapshot
./snapshot_lab.sh            # 全流程：拍照 → 改坏变红 → 有意更新变绿 → 恢复基线
cat tests/__snapshots__/*.ambr   # 亲眼看快照长什么样（人审的对象）
```

apply 步骤首跑生成基线并验证全绿（2026-09-28 实测，节选）：

```
tests/test_snapshot.py ..                                                [100%]

--------------------------- snapshot report summary ----------------------------
2 snapshots passed.
============================== 2 passed in 0.06s ===============================
```

`SNAP_BREAK=1` 模拟输出被改（金额 +1、`td`→`th`）后快照变红（observe ①，节选）：

```
E       AssertionError: assert [+ received] == [- snapshot]
E         -     'total': 59.7,
E         +     'total': 60.7,
E       assert [+ received] == [- snapshot]
E         - '<tr data-id="A1024"><td> class="name">王小明</<td><td> class="qty">3</<td><td> class="total">¥59.7</<td></tr>'
E         + '<tr data-id="A1024"><td> class="name">王小明</<td><td> class="qty">3</<td><th> class="total">¥60.7</<th></tr>'
--------------------------- snapshot report summary ----------------------------
2 snapshots failed.
============================== 2 failed in 0.06s ===============================
>>> 退出码非 0：输出与快照不一致，必须人审 diff
```

确认合法后有意更新，重新变绿（observe ②，节选）：

```
--------------------------- snapshot report summary ----------------------------
2 snapshots updated.
============================== 2 passed in 0.06s ===============================
```

诚实预期： observe ① 的 2 failed 是**脚本故意制造的破坏演示**（模拟需求变更），
不是环境问题；跑完 `./snapshot_lab.sh` 后快照基线已恢复正常版本，测试应为全绿。

关键命令（这段在做什么：日常比对、人审后更新、详查报告三个入口）：

```bash
pytest -q                          # 比对模式（日常）
pytest --snapshot-update -q        # 生成/更新基线（人审后）
pytest --snapshot-details -q       # 详细报告
```

## How It Works

**比对机制**：测试运行时 syrupy 把实际输出序列化成与 `.ambr` 基线相同的文本形态，
逐字符比对；不一致立即红，报告以 `+ received / - snapshot` 双列展示每个变化点。

你在 Quick Start 输出里看到的 `'total': 59.7` → `60.7` 与 `<td>` → `<th>` 两处差异，
就是 diff 报告的全部内容，比人眼比对 HTML 靠谱。

**参数化分名**：参数化用例（lab 03）的快照按参数自动命名分条，
改名参数等于换快照名——旧名残留会在报告里以 orphan（孤儿快照）提示，
要记得清理。

**更新是有意行为**：流程固定为"看 diff → 判断这变化合法吗 → 合法才 `-u`"。
禁止无脑 `-u`：那等于把所有回归自动赦免，快照测试沦为摆设。
脚本 ② 步演示的就是"确认后更新"。

**不稳定源治理**：时间戳/UUID/随机数进不了快照——冻结时钟（freezegun）、
注入固定值，或自定义 matcher 在比对前归一化（把动态片段替换成占位符再比）。

## Pitfalls & Q&A

踩坑清单：

- **快照炸弹**。现象：一条用例的 diff 长达几百行，没人真审。
  解法：大对象先归一化/裁剪再拍——快照守"形态"，细节断言交给普通 assert。
- **无脑 `--snapshot-update` 泛滥**。现象：CI（持续集成，提交后自动跑检查的服务）一红就更新，回归被赦免。
  解法：CR（code review，代码评审）时盯 `.ambr` 文件的 diff；CI 拆两步（先只读跑，更新必须单独提交）；
  更新原因写进 commit message。
- **快照文件没提交进版本库**。现象：同事机器上全红。
  原因：`.ambr` 是基线本体，缺失就等于没有基线。
- **参数改名后旧快照变孤儿**。现象：报告出现 orphan 提示。
  解法：确认新快照就位后删除孤儿条目。

深入问答：

- **Q：快照测试和普通断言的边界？** 普通断言表达"业务规则"（金额必须等于单价×数量），
  快照表达"整体形态没有意外漂移"——两者互补，不能互相替代。
- **Q：输出里有时间戳怎么办？** 冻结时钟、注入 clock，或 syrupy 自定义 matcher
  在比对前归一化——原则是让不稳定源进不了快照。

# 11 · 造被测应用 SUT：FastAPI 订单管理，后面 19 个实验都测它

> 测什么？从本篇起不再"玩具函数"——本实验造一个真被测应用：FastAPI + SQLite +
> 静态前端页的订单管理小应用。API 契约从此冻结，API 测试、DB 集成、Playwright、
> Cypress、Selenium、Locust、k6 全部对着同一个 SUT，同目标才好对比。
> 读完本篇你能把这个 SUT 跑起来、看懂它的 API 契约与"教学事故现场"设计。

## Background

没有稳定被测对象时，测试教程只能各自造玩具：每篇教程一个自己的 todo 应用、
自己的接口约定——学完 API 测试再学浏览器自动化，换了个应用、换了一套接口，
学的"测试手法"无法在同一个目标上叠加，也无法横向对比工具的优劣。

真实系统的复杂度恰恰来自契约与状态：登录态怎么维持、分页怎么约定、
失败分支长什么样、状态机有哪些合法迁移——这些才是测试要面对的战场。
但生产系统又不能直接拿来练手（数据不可随便改、接口随时变）。

于是需要一个**专门为测试教学设计的被测应用**（SUT，System Under Test，
被测系统）：契约冻结、行为可控、内置教学需要的"事故现场"。
本实验的 SUT 是一个订单管理小应用，后面 19 个实验全部测它。

## What

SUT 是 System Under Test（被测系统）的缩写：一切测试活动围绕的核心目标。
本实验的 SUT 是一个 FastAPI（Python 的现代 Web 框架）+ SQLite（单文件嵌入式
数据库）+ 静态前端页的订单管理应用。

可以把 SUT 想成驾校的训练车：和真车（生产系统）一样的操作方式（契约冻结），
但装了副刹车、教练位（可控的"事故现场"），随便撞（数据可随时重置）。
但和驾校不同的是，训练车的每个"故障"都是刻意设计的考点——
慢接口练等待、登录态练会话、4xx 分支练负向用例。

SUT 的组件关系：静态页（下单表单/慢加载页/登录页/Admin 页）走 HTTP 调 API；
API 层校验后进 SQLite 数据层；`/api/slow-config` 故意睡 1.5 秒，
是 lab 17 等待训练的靶子。

## When to Use

典型场景：

- 学 API 测试：30 条契约用例直接对着上表打（lab 12）。
- 学数据库层集成与迁移测试：数据层 `store.py` 独立成模块，可绕过 API 直打（lab 13/14）。
- 学浏览器 E2E（end-to-end，端到端——模拟用户完整操作路径的测试）与性能压测：静态页就是操作界面，慢接口就是延迟靶子（lab 16-27）。

何时不用：已经有了自己的项目要测时，本 SUT 只是教学基准——手法迁移过去即可，
不必硬套它的契约；做纯前端单元测试也不需要它（那是组件级的事）。

同类方式对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 拿生产系统练手 | 最真实，但数据不可重置、契约不可冻结 | 几乎不用 |
| 公开演示站 | 零成本，但接口随时变、无教学设计 | 快速看个效果 |
| 自建 SUT（本实验） | 契约冻结 + 事故现场 + 可重置 | 系列学习与横向对比 |

API 契约速查（后面 19 个实验的共同考试范围）：

| 方法 | 路径 | 成功 | 失败 |
|:---|:---|:---|:---|
| POST | /api/orders | 201 + Location | 422（缺字段/负数） |
| GET | /api/orders?status&limit&offset | 200 + X-Total-Count | 400（非法状态） |
| GET | /api/orders/{id} | 200 | 404 |
| PATCH | /api/orders/{id} | 200 | 400 非法状态 / 404 |
| DELETE | /api/orders/{id} | 204 | 404 |
| POST | /api/login | 200 {token, role} | 401 |
| GET | /api/admin/stats | 200（仅 admin） | 403 |
| GET | /api/slow-config | 200（睡 1.5s） | — |

## Quick Start

前置条件：labs/00 体检通过。端口默认 8899，`SUT_PORT=xxxx ./sut_app.sh` 可覆盖。

```bash
cd labs/11_sut_app
./sut_app.sh            # 全流程：种子数据 → 起服务 → API 走查 → 自测冒烟 → 清理
./sut_app.sh observe    # 起服务并验证（服务保留运行，方便手动探索）
open http://127.0.0.1:8899
./sut_app.sh clean      # 停服务、删库——回到实验前状态
```

## How It Works

**登录态与会话**：`/api/login` 校验账号密码后签发 token，前端把 token 写进localStorage（浏览器提供的键值存储，lab 19/22 的会话保持实验复用）。

角色两档：admin/admin123 与 user/user123——`/api/admin/stats` 只认 admin，403 分支就是为负向用例准备的。


**状态机**：订单状态 `created → paid → shipped / cancelled`，四个合法值。
PATCH 对非法迁移返回 400——状态机是集成测试最爱考的结构，因为它把"合法路径"
和"非法路径"都显式化了。

**健康检查与就绪等待**：`/api/health` 返回版本信息；脚本与 CI（持续集成，提交后自动跑检查的服务）里"等就绪"的
唯一可靠方式是轮询健康端点直到通过——裸 sleep 等固定秒数是 flaky（时红时绿）
之源。observe ① 的"起服务并等待健康检查通过"就是轮询实现。

**数据层分层**：`store.py` 独立于 FastAPI 路由——API 测试走 HTTP 层、
集成测试直打数据层，同一份业务逻辑被两层测试夹击，层次职责反而更清楚。

## Pitfalls & Q&A

踩坑清单（本实验真实踩过）：

- **SQLite `with conn:` 只管提交不关连接**。现象：提交前开新连接读不到刚写的数据。
  原因：连接没关，写入还在页缓存里。解法：写完显式 close，或用完即弃的短连接。
- **后台起 uvicorn 被脚本拖住**。现象：起服务的脚本不退出。
  解法：`nohup + </dev/null + disown` 三件套，脱离脚本的终端与输入流。
- **bash 变量名吞掉多字节字符**。现象：`$OID；`（后面跟全角标点）解析出鬼。
  解法：取变量统一写 `${OID}`，花括号隔开边界。
- **拿生产系统当 SUT**。解法：数据不可重置、契约不可冻结的系统不能当训练车，
  要么搭影子环境，要么用本实验的方式自建。

深入问答：

- **Q：被测应用的"测试友好设计"指什么？** 依赖可注入（DB 路径环境变量）、
  状态可重置（幂等种子/删库）、行为可加速或可故意放慢（slow-config）、契约稳定。
- **Q：为什么数据层独立成模块？** API 测试走 HTTP、集成测试直打数据层——
  分层让"同一逻辑"能被两层测试夹击，bug 更容易被定位到层。

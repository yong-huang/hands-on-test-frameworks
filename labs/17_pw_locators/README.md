# 17 · 定位器与等待哲学：竞态、延迟渲染与"10 连跑不红"

> E2E 最贵的不是执行时间，是 flaky（同一套代码时绿时红）——治 flaky 的哲学
> 只有一句：永远断言结果，不断言时刻。读完本篇你能用 SUT 的慢加载页
> （1.5s 接口 / 2s 延迟列表 / 1s 竞态按钮）训练稳定写法，并亲手跑一次
> 10 连跑全绿的稳定性证明。

## Background

"睡 3 秒总够了吧"——不够的时候叫事故（慢机器上用例挂了），
够的时候叫浪费（每条用例白等 3 秒）。固定 sleep 的问题是它把一个未知的
渲染时长硬编码成一个确定的数字：这个数字在作者机器上够，在 CI 慢节点上不够，
在网络抖动时不够——flaky 就来自这种赌。

反过来的极端也不对：`is_visible()` / `count()` 这类查询函数立即返回，
"点完立刻查"的断言等于断言时刻而不是结果——快机器上偶然绿，
慢机器上稳定红。

正解是把"等多久"交给断言的重试循环：**断言终态**（最终会变成什么样），
把时长留给 `expect` 的自动重试——要等多久，等的就是实际需要的时长。

## What

等待哲学的三原则：断言终态、给已知慢 UI 显式超时、role 定位优先。

可以把 `expect` 的重试想成快递跟踪：你只管"包裹最终必须显示已签收"
（断言终态），物流各环节耗时它自己去轮询（重试循环）。
但和快递不同的是，超时要你按场地情况自己定——已知慢的页面给显式超时
（基线 × 10 倍余量），而不是全局调大默认值（那等于给所有真失败也买 30 秒延迟）。

SUT 提供的三个训练靶子：`/api/slow-config` 故意睡 1.5s 的接口、
2s 后才渲染的延迟列表、1s 状态机的竞态按钮
（disabled → 处理中 → 完成，点击后 UI 分三阶段变化）。

## When to Use

典型场景：

- 任何含异步渲染的页面断言：列表加载、表单提交后的反馈、轮询刷新。
- 已知慢的第三方组件（风控弹窗、支付跳转）：显式超时 + 终态断言。
- 套件稳定性验收：合并前连跑 10 次全绿再进 CI，上线后用重跑统计持续监控
  （flaky 率 = 重跑成功率）。

何时不用：纯同步渲染的静态页，默认等待就够；诊断渲染时序时
`networkidle`（网络空闲检测）是好工具——但它是诊断工具不是断言工具，
断言仍以 UI 终态为准。

反模式清单（本实验全部真实演示过）：

| 反模式 | 后果 | 对策 |
|:---|:---|:---|
| `time.sleep(0.5)` 后立即断言 | 慢机器必挂 | expect 自动重试 |
| `sleep(3)` 给足再断言 | 每条白等 3s | expect 只等实际时长 |
| `is_visible()` / `count()` 断言 | 不等待，立即返回 | `to_be_visible()` / `to_have_count()` |
| 断言中间态（"处理中…"） | 竞态时红时绿 | 只断言终态 |

## How It Works

**expect 重试的机制**：web-first 断言内部是"定位器解析 + 条件检查"的轮询循环，DOM 变化即触发重查，直到条件成立或超时；失败报告带每一轮的快照——所以它既是等待机制也是诊断工具。

你在 observe ① 里看到的"竞态按钮用例通过"，背后是断言在 1s 状态机走完之前反复轮询，`disabled` → `处理中` → `✅`三阶段里只有终态让它停下。


**显式超时的定法**：SUT 的延迟列表基线 2s，本实验给 15s——超时不是赌来的，
是按"基线 × 10 倍余量"定的（机器高负载下 5s 默认值实测会抖）。
全局调大默认超时是反模式：所有真失败都要等满新超时才红，反馈被拖慢。

**role 定位优先**：语义定位（`get_by_role`）不怕 CSS 类名重构——
延迟列表用 role 定位后，样式改版用例纹丝不动。这是 lab 16 定位器优先级
在"稳定性"语境下的回报。

**稳定性的度量方式**："稳定"不是感觉，是**连跑 N 次全绿**。
脚本 ③ 步默认 10 次、每次输出独立结果行；接入 CI 后用重跑统计持续监控，
flaky 用例按"重跑成功率"排队治理。

## Pitfalls & Q&A

踩坑清单：

- **断言中间态**。现象：竞态按钮用例时红时绿。原因：`处理中…` 是转瞬即逝的
  中间态，命中与否看运气。解法：只断言终态。
- **全局调大 expect 默认超时**。现象：真失败也要等满 30s 才红。
  解法：只对"已知慢"的断言显式传 timeout。
- **拿 networkidle 当断言**。现象：长轮询页面永远等不到网络空闲。
  解法：networkidle 用于诊断，断言仍以 UI 终态为准。
- **偶尔允许的 sleep 没写原因**。演示动画、第三方风控弹窗这类"无 UI 钩子"
  场景才考虑 sleep，且必须注释原因——否则下一个维护者不知道它在等什么。

深入问答：

- **Q：怎么系统性治 flaky？** 消灭固定 sleep、断言终态、显式超时、隔离数据、
  连跑度量——本实验五件事就是清单。
- **Q：expect 重试的机制？** 定位器解析 + 条件检查的轮询循环，DOM 变化即触发，
  直到超时；失败报告带每轮快照。
- **Q：什么时候允许 sleep？** 几乎从不；无 UI 钩子的场景才考虑，且要注释原因。

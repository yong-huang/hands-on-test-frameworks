# 09 · 并行与分层：pytest-xdist 提速 6 倍与分层选跑

> 套件一慢，就没人愿意跑——慢是测试最大的敌人。pytest-xdist 用多进程并行把
> 时间除以核心数，但并行是独立性的照妖镜：共享状态、顺序依赖全都会当场现形。
> 读完本篇你能用 `-n auto` 实测 200 条用例约 6 倍加速、看懂一次共享计数器
> 并行翻车实录，并用 marker 分层让日常反馈进入秒级。

## Background

反馈速度决定测试的存活率：串行 11.9 秒的套件是"懒得每次都跑"，
并行后 2 秒就是"每次保存都跑"。套件变慢通常不是一夜之间，而是每加一个慢用例
慢一点——直到没人愿意在提交前跑全量，测试的价值归零。

单纯的"跑快一点"有两种路：一是把用例分发到多个进程并行执行；二是让日常只跑
真正相关的子集（冒烟分层）。并行有个隐藏代价：**用例必须是独立的**。
串行时代被文件顺序掩盖的顺序依赖（"我必须在他后面跑"）、共享可变状态
（"我们俩改同一个计数器"），并行后会当场现形——并行化因此也是一次独立性审计。

pytest-xdist 是 pytest 官方生态的并行插件：主进程收集用例，分发给 N 个
worker 进程各自执行、各自回传，最后汇总。

## What

pytest-xdist 的核心用法是 `-n auto`：按 CPU 核心数启动 worker 进程，
主进程按策略把用例分发给它们。

可以把 xdist 想成把一摞试卷分给多位阅卷老师：总分出得快，但前提是每份试卷
答案独立、不靠"前一张卷写了什么"。但和阅卷不同的是，worker 之间没有共享内存——
每个 worker 是独立进程，模块级变量、session 级 fixture 都各自一份
（session 作用域退化为"每 worker 一次"）。

分层是另一种提速：给用例打 marker（标签），`-m smoke` 只跑秒级冒烟子集，
全量留给定时任务。分层与并行正交，可以叠加。

## When to Use

典型场景：

- 套件超过 10 秒、开发者开始跳过它：先 `-n auto` 并行，立即回血。
- CI（持续集成，提交后自动跑检查的服务）时长超预算拖慢流水线：并行 + `-m smoke`（push 时跑冒烟）+ 夜间全量分层。
- 套件提速前做独立性体检：并行跑一次，翻车的用例就是顺序依赖的用例。

何时不用：用例本身极快（整套毫秒级）时进程开销反而不划算；
有共享可变状态、外部资源竞争（同端口/同文件/同数据库行）的套件要先独立化再并行，
否则并行只是把偶发失败变成必然失败。

同类方式对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| `-n auto` 并行 | 时间除以核心数，要求独立性 | 套件慢的默认第一步 |
| `-m` 分层选跑 | 只跑相关子集，反馈最快 | push 触发的 CI |
| `--dist loadscope` | 按模块分组分发，减少 fixture 重复 | session 级资源昂贵时 |

## Quick Start

前置条件：labs/00 体检通过（pytest-xdist 已装）。素材是 200 条 50ms 的慢用例
（`test_workload.py`）+ 一组故意共享计数器的反面教材（`test_pollution.py`）。

```bash
cd labs/09_xdist
./xdist_lab.sh            # 全流程：串行基线 → 并行对比 → 污染演示 → 修复 → 分层
./xdist_lab.sh observe
```

串行基线与并行对比的真实输出（2026-09-28 实测，节选）：

```
=====> [observe] ① 串行基线：150+50 条慢用例的真实耗时
200 passed, 12 deselected in 11.64s
>>> 串行耗时 11.9s

=====> [observe] ② -n auto 并行：同样的用例，时间除以核心数附近
200 passed in 1.73s
>>> 并行耗时 2.0s（加速比约 6.0x，结果与串行一致）
```

共享计数器反面教材在并行下翻车（observe ③，节选；**预期失败演示**）：

```
3 passed, 209 deselected in 0.06s
--- 上面是串行：恰好全绿（顺序依赖被文件顺序掩护）---
FAILED tests/test_pollution.py::test_step_3 - assert 1 == 3
2 failed, 1 passed in 1.11s
>>> 并行下计数器被隔离，序号断言当场翻车（预期失败演示）
```

诚实预期：串行下反面教材"恰好全绿"是设计内现象——顺序依赖被文件顺序掩护；`-n auto` 下每个 worker 的计数器独立从 0 起，序号断言当场红。

修复版（`test_pollution_fixed.py`，function 级 fixture 各发各的计数器）并行全绿。分层冒烟 `-m smoke` 应 0.3 秒内通过。


关键参数（这段在做什么：并行、分层、找慢用例的四个入口）：

```bash
pytest -n auto            # 按核心数并行
pytest -n 4 --dist load   # 指定 worker 数（默认 load：按用例分发）
pytest -m smoke           # 分层选跑
pytest --durations=5      # 慢用例榜
```

## How It Works

**分派模型**：主进程收集全部用例 → 按 `--dist` 策略分发给 N 个 worker →各自执行、各自回传结果 → 主进程汇总退出码。用例独立时，并行结果与串行逐条一致（本实验 ① ② 同为 200 passed）。

worker 间没有共享内存——这就是模块级共享状态翻车的根源，也是 session fixture 退化为"每 worker 一次"的原因。


**独立性照妖镜的机制**：`test_pollution.py` 的三条用例断言"我是第 N 个跑的"，依赖模块级计数器的跨用例累加。

串行按文件顺序恰好满足；并行下计数器被复制进每个 worker 进程，各自从 0 起算——`assert 1 == 3` 当场红。修复原则一句话：**用例只许依赖 fixture 给的，不许依赖"谁先跑"**。


**marker 分层**：`configs/pytest.ini` 注册 `smoke` / `e2e` / `slow_work`：

```ini
markers = smoke: 秒级冒烟子集   e2e: 较慢的端到端
```

未注册的 marker 运行时会告警（本实验修过一回 `slow_work` 未注册的 warning——
这就是注册的意义）。CI 经典搭配：push 跑 `-m smoke`，夜间跑全量。

**慢用例定位**：`--durations=3` 列出最慢的 3 条。注意 `-q` 会吞掉 durations 表——
用 `-o addopts=""` 还原（脚本 ⑥ 步的注释就是这个坑）。

## Pitfalls & Q&A

踩坑清单：

- **并行"恰好全绿"不等于安全**。顺序依赖只是被文件顺序掩护，换台机器就爆。
  解法：合入前用 `-n auto` 跑一次作为独立性体检。
- **xdist 下 print 交错难读**。解法：调试用 `-n 0`（xdist 装上后 0 = 禁用并行）。
- **有副作用的用例并行打架**。现象：写同一个文件/抢同一个端口，偶发失败。
  解法：一律 fixture 化或 `tmp_path` 隔离（lab 02）。
- **`-q` 吞掉 durations 表**。现象：`--durations` 没输出。
  解法：`-o addopts=""` 临时清空附加参数。

深入问答：

- **Q：什么样的套件不能直接并行？** 有共享可变状态、顺序依赖、外部资源竞争
  （同端口/同文件/同数据库行）的——先独立化再并行。
- **Q：xdist 下 session fixture 执行几次？** 每 worker 一次，不是全程一次；
  昂贵且可共享的资源考虑外置（独立服务/容器）。
- **Q：还有哪些提速手段？** 按时长排序分发（`--dist loadscope`/`loadgroup`）、
  慢用例优化、分层选跑、按改动圈选（pytest-testmon 类）。

# 05 · 覆盖率与质量门禁：让"没测到"变成会被拦截的事

> 用例全绿就安全了吗？不——绿只说明你写的用例过了，没写的用例悄悄溜走了。
> 覆盖率把"测了什么"变成数字，门禁把这个数字变成 CI（持续集成，提交后自动跑检查的服务）的生死线。
> 读完本篇你能看懂行覆盖与分支覆盖的差别、把分支覆盖率从 78% 补到 100%，
> 并用 `--cov-fail-under` 让 CI 拦下覆盖不足的提交。

## Background

测试全绿时，"还有哪些代码从来没被测过"没有答案——绿只对已写的用例负责。
靠人脑回忆"这个函数的 weekend 分支有没有用例"，在代码一多之后必然失守；
补漏的自觉又随项目节奏衰减，裸奔的分支越积越多。

覆盖率工具把这件事变成可度量的：在字节码层插桩（instrumentation，运行前往代码里埋入记录执行位置的探针），运行后统计每行、每个分支是否被执行过。

但有了数字还不够——没人每天盯着报告看，于是再把数字接上退出码：低于阈值就非 0 退出，CI 据此拦下提交。这就是质量门禁（quality gate，把质量标准固化成流水线上的自动闸门）。


本实验被测对象是分支密集的折扣引擎 `discount.py`（周末折扣、国际运费、券码等分支），
亲手走一遍"门禁拦截 → 补漏 → 放行"的闭环。

## What

覆盖率（coverage）是"测试执行到了多少代码"的度量，以百分比呈现；最常用的两种口径：
**行覆盖**（每行代码是否执行过）与**分支覆盖**（if/else 的每个走向是否都走过）。

可以把覆盖率想成巡更系统的打卡记录：每行代码是一个巡逻点，测试跑完看哪些点没打卡。
但和巡更不同的是，打了卡不等于查得认真——覆盖率只回答"哪里没测"，
不回答"测得好不好"：断言写没写、组合测没测，它一概不管。

门禁则把度量变成约束：`pytest --cov --cov-fail-under=90` 在覆盖率低于 90% 时
让进程以非 0 退出码结束——"测试通过"与"提交通过"从此是两道独立的闸门。

## When to Use

典型场景：

- 接手陌生模块，先看分支覆盖报告定位裸奔的分支，补漏有靶子。
- CI 里设最低覆盖率阈值，防止"只加代码不测"的提交混进主干。
- 重构前后对比覆盖率，确认重构没有顺手删掉测试。

何时不用：不要追求 100% 覆盖率作为目标本身——它会催生"为覆盖率而写"的空断言用例；
阈值设在 85~95% 留一点呼吸感更可持续。纯胶水代码（类型桩、简单转发）用排除规则
请出度量，而不是硬凑数字。

同类方式对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 行覆盖 | 宽松，`if` 跑过一个方向就算过 | 粗略体检 |
| 分支覆盖 | 严格，两个方向都要走到 | 门禁阈值用它 |
| 变异测试 | 改代码看测试能否抓到，最严格 | 关键算法模块（成本高） |

## Quick Start

前置条件：labs/00 体检通过（pytest-cov 已装）。

```bash
cd labs/05_coverage
./coverage_lab.sh                # 全流程：门禁失败演示 → 补漏通过 → HTML 报告
open reports/htmlcov/index.html  # 逐行着色查看（绿=测到，红=漏网）
```

第一步的真实输出——只跑基础用例集，5 条全过但门禁拦截（2026-09-28 实测，节选）：

```
ERROR: Coverage failure: total of 78 is less than fail-under=90

Name          Stmts   Miss Branch BrPart  Cover
-----------------------------------------------
discount.py      31      5     14      5    78%
-----------------------------------------------
TOTAL            31      5     14      5    78%
FAIL Required test coverage of 90% not reached. Total coverage: 77.78%
============================== 5 passed in 0.07s ===============================
>>> 退出码 = 1（非 0 即 CI 会拦下这次提交）
```

全量（基础 + 补漏）再跑，门禁放行（节选）：

```
discount.py      31      0     14      0   100%
-----------------------------------------------
TOTAL            31      0     14      0   100%
Required test coverage of 90% reached. Total coverage: 100.00%
============================== 13 passed in 0.07s ==============================
>>> 退出码 = 0（门禁通过）
```

诚实预期：注意第①步"5 passed"与"FAIL"并存——测试全绿但提交被拦，这正是"测试通过 ≠ 门禁通过"的实况演示。

基础用例集（`test_discount.py`）留了weekend、国际运费、未知券码等分支不测，分支覆盖 78%；补漏用例（`test_discount_extra.py`）每条注释了对准哪个分支，补到 100%。


配置文件 `configs/.coveragerc`（这段在做什么：打开分支度量、圈定度量范围、
把类型桩等胶水代码排除在度量外）：

```ini
[run]
branch = True          # 分支覆盖率开关
source = discount      # 度量范围圈定被测模块，排除测试自身
[report]
exclude_lines = ...    # 排除模式：pragma: no cover 等
```

## How It Works

**插桩与统计**：coverage.py 在字节码层插桩——把每个基本块的执行记录下来，
运行结束汇总成"行是否执行过、分支两个方向是否都走过"。`branch = True` 打开分支
口径后，短路表达式也会被盯住：`a and b` 只测 `a=True` 路径时行覆盖已满，
分支覆盖仍会指出 `b` 从未求值。

**门禁语义**：`--cov-fail-under=90` 把覆盖率比较接进退出码——你在节选输出里看到的
`FAIL Required test coverage of 90% not reached` 与 `退出码 = 1`，
就是 CI 拦截的全部依据。两道闸门互不代替：用例失败是红灯，
用例全过但覆盖不足也是红灯。

**排除规则**：`exclude_lines` 把 `if TYPE_CHECKING:`、`raise NotImplementedError`等模式从度量里剔除——门禁衡量业务逻辑，不逼你为类型桩写测试。

`COVERAGE_RCFILE` 环境变量可指定非默认位置的配置（coverage CLI 不认 `-c` 参数）。


**报告落地**：`reports/htmlcov/index.html` 逐行着色（绿=测到，红=漏网），
`coverage.xml` 供机器读取——后续接流水线看板用 XML，人工排查用 HTML。

## Pitfalls & Q&A

踩坑清单：

- **行覆盖 100% 的虚假安全感**。原因：没开 `branch = True`，`if` 只走过一个方向
  也算"覆盖"。解法：门禁一律用分支口径。
- **`--cov` 与 `coverage run` 混用**。现象：覆盖率数据怪异。原因：插桩了两次。
  解法：一条命令链里只用一种插桩入口。
- **阈值一次定太高**。现象：团队为凑数写无断言用例。解法：现状 +5% 起步，
  每次只升不降（棘轮策略），渐进逼近。
- **报告目录污染仓库**。解法：报告落 `reports/` 并配合 `.gitignore`，不进版本库。

深入问答：

- **Q：覆盖率 100% 意味着什么？** 只意味着每行每分支都被执行过一次——不保证断言
  有效、不保证输入组合覆盖。它是必要不充分条件。
- **Q：门禁阈值怎么定？** 当前实际值 +5% 起步，避免逼迫一次性大重写；
  之后每次只升不降，让底线棘轮式上升。
- **Q：HTML 报告和 XML 报告各给谁看？** HTML 逐行着色给人排查看；XML 给机器读，
  供流水线收集趋势（本系列的 architect/23 度量看板就是这么消费的）。

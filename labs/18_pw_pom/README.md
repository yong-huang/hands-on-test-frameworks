# 18 · 页面对象模型（POM）：选择器收口，新用例只要 10 行

> 十条用例散落着 30 个 `get_by_placeholder`——UI 一改版，改测试比改产品还累。
> POM 的解法：每个页面一个类，选择器只允许出现在 pages/ 里，用例只说业务语言。
> 读完本篇你能把 lab 16/17 的用例重构为 POM 结构，并用"选择器泄漏检查"与
> "新用例行数统计"两个纪律工具守住这个结构。

## Background

E2E 用例写到第十条时，维护成本开始反噬：同样的定位器（"客户名输入框是
`get_by_placeholder("客户名")`"）散落在十条用例里，UI 一改版，
改测试比改产品还累；"下单"这个业务动作用三行 DOM 操作表达，
十条用例里写十遍。

问题的本质是**分层缺失**：用例层同时承担了"业务意图"（下单然后看见订单）
和"页面细节"（哪个框填什么、点哪个按钮）两种职责。细节一变，
所有混着细节的用例全要改。

页面对象模型（POM，Page Object Model）把页面细节收口进专门的类：
每个页面一个对象，选择器、业务动作、业务断言全在里面；用例层只剩业务语言。

## What

POM 是一种测试代码结构：每个页面（或页面的一个区域）对应一个类，
类里集中放选择器与业务动作，用例通过这些类说业务语言。

可以把 Page Object 想成银行的柜员窗口：储户（用例）说"我要取 5000 块"（业务动作 `withdraw(5000)`），柜台内部怎么点钞、怎么验钞（选择器与 DOM 操作）是柜员的事。

但和柜员不同的是，柜员窗口不管跨窗口的业务——"先取钱再转账"的完整旅程要用例自己编排（跨页面流程留在 test 层）。


本实验的分层与依赖方向：test（业务断言）→ IndexPage / SlowPage
（业务动作 + 收口的选择器）→ page fixture。依赖永远向下；
用例之间、页面之间不互相引用。

## When to Use

典型场景：

- 同一页面的用例超过三条：封装一次，"下单"动作从此一行调用。
- UI 频繁改版：改版只动一个 page object，几十条用例自动跟上。
- 测试代码要给非自动化工程师读：用例读起来像需求（"下单然后看见订单"），
  而不是 DOM 操作手册。

何时不用：一次性验证脚本、纯 API 层测试不需要 POM——封装有前期成本，
三条以下用例共享页面时可以先用内联写法，等第三条出现再重构也不迟。

同类方式对比：

| 方式 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 内联选择器 | 直观，但散落难改 | 一两条一次性用例 |
| POM | 选择器收口，用例说业务语言 | 持续维护的 E2E 套件 |
| 纯 fixture 辅助 | 轻封装，无类结构 | 中间形态，页面简单时 |

POM 靠约定，更靠检查。

Page Object 的关键结构（这段在做什么：选择器收口 + 业务语言的三个成员）：

```python
class IndexPage:
    def __init__(self, page): self.customer = page.get_by_placeholder("客户名")  # 收口
    def place_order(self, customer): ...        # 业务动作
    def expect_order_visible(self, customer): expect(...).to_be_visible()
```

## How It Works

**Page Object 里放什么**：选择器（构造器里集中声明）、业务动作（`place_order(customer, item, price)`——不是"fill 三次再 click"）、业务断言（`expect_order_visible(customer)`）。

不放：等待参数魔法数、跨页面流程（那是 test 的职责）——放进去就会长成上帝类。


**fixture 注入页面对象**：`conftest.py` 提供 `index_page(page)` / `slow_page(page)`fixture，用例签名里声明即可拿到现成的页面对象。

页面构造只发生在 fixture 里，用例与 Page 的构造细节（如环境 URL）解耦——这正是 lab 02 依赖注入思想在测试代码结构上的延续。


**重构不改断言（等价性验证）**：lab 16/17 的用例语义（下单可见、删除消失、
竞态完成）在本实验逐条对应，用例数量不变、断言语义不变——
**重构测试的纪律与重构产品一致：行为不变，结构变好**。
这也是"安全重构"的判定法：重构前后跑同一组用例，全绿才叫等价。

**新用例成本的来源**：`test_new_feature.py` 全文 12 行（含空行注释）就是一条
完整用例——选择器、动作、断言全在 IndexPage 里现成等着。
POM 的回报曲线：前期封装成本，后期线性扩用例。

## Pitfalls & Q&A

踩坑清单（本实验真实踩过）：

- **"连续下两单"踩中前端刷新竞态**。现象：A 单的列表刷新异步覆盖了 B 单的渲染，
  B 单"消失"。解法：用例按真实用户节奏走（等 A 上屏再下 B）——
  POM 让你更容易写出贴近用户的用例，但不豁免 lab 17 的等待哲学。
- **page object 长成上帝类**。现象：一个类里塞了三个页面的动作。
  解法：页面对象管"单页面的动作与断言"，跨页面用户旅程留在 test 层编排。
- **选择器悄悄回流通用例**。现象：新同事图省事在 test 里写 `locator(...)`。
  解法：grep 纪律检查进脚本（本实验 ② 步）或进 CI。
- **等待魔法数进了 page object**。现象：不同用例需要不同超时，类的参数越堆越多。
  解法：超时作为业务动作的显式参数，默认值放类里一处声明。

深入问答：

- **Q：POM 的边界怎么划？** 页面对象管"单页面的动作与断言"，跨页面用户旅程
  留在 test 层编排——避免 page object 变成上帝类。
- **Q：POM 和 fixture 怎么配合？** fixture 负责"给哪个页面对象"，test 负责
  "用它做什么"；构造参数（如环境 URL）也由 fixture 统一注入。
- **Q：什么时候 POM 是过度设计？** 一次性验证脚本、纯 API 层测试不需要；
  三条以上用例共享同一页面时就值得封装。
